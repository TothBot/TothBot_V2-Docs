NAMESPACE SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document defines the complete namespace model for
TothBot V2. It governs how Document Control Numbers (DCNs)
are assigned, interpreted, and validated across all
controlled documents in the TothBot V2 document control
system.

This is a clean-slate specification. It shares no legacy
constraints with any prior TothBot namespace. All decisions
in this document are derived from first principles using
FP/DP analysis. Where this document conflicts with any
prior TothBot namespace document, this document governs.

============================================================
2. SCOPE
============================================================

This specification applies to ALL controlled documents and
code files in the TothBot V2 system, across BOTH repositories:

  TothBot_V2-Docs (github.com/TothBot/TothBot_V2-Docs)
    Scope: All specification and governance documents.
    File format: .txt (Claude project compatible).
    DC header format: Standalone 7-field header block.

  TothBot_V2-Code (github.com/TothBot/TothBot_V2-Code)
    Scope: All trading system code, operational support
    scripts, configuration files, and deployment files in
    the trading system repository.
    File format: .py, .sh, .txt, .ini, .service, and others.
    DC header format: 7-field header embedded as a comment
    block at the top of each file, using the file's native
    comment syntax (# for Python and bash, etc.).

HR-DC-001  ALL files in TothBot_V2-Code are controlled
           documents. There are no uncontrolled files
           in TothBot_V2-Code.

HR-DC-002  Every file in TothBot_V2-Code MUST have a
           7-field DC header. This is not optional.
           Missing or malformed headers are document
           control violations.

HR-DC-003  Every file in TothBot_V2-Code MUST be
           registered in 1010000 Section 5 Code File
           Registry. Unregistered files are violations.

HR-DC-004  Every file in TothBot_V2-Code MUST have a
           Revision History section in comment format.

Corrective action: This scope expansion corrects the
governance gap documented in TB00079 where the scope
limitation to TothBot_V2-Docs only was found to be
incorrect and was causing document control violations.

Any document outside both repositories is an uncontrolled
working copy and has no governing authority.

This specification does not apply to TothBot-Docs or
TothBot-Code (the original TothBot system). Those
repositories are permanent read-only archives governed
by their own namespace.

4. DCN STRUCTURE
============================================================

All DCNs follow the format: AABCDDD

  AA  = Domain (2 digits, 00–11)
  B   = Sub-Domain level (1 digit, 0–9)
  C   = Instance level (1 digit, 0–1)
  DDD = Sequential instance number within sub-domain

------------------------------------------------------------
4.1 DOCUMENT TIER DEFINITIONS
------------------------------------------------------------

  Tier 1 — Domain Document (B=0, C=0, DDD=000)
    IS the domain. One per domain. Anchors all sub-domains.
    Example: 0300000 Governance

  Tier 2 — Sub-Domain Anchor (B=1-9, C=0, DDD=000)
    Anchors a governance family to its Domain Document.
    Example: 0310000 Governance_Procedures_Anchor

  Tier 3 — Instance Document (B=1-9, C=1, DDD=001+)
    Elaborates one specific component within the sub-domain.
    Example: 0311001 Namespace_Specification

------------------------------------------------------------
4.2 PARENT CHAIN RULE
------------------------------------------------------------

Every document must have an unbroken parent chain:

  Instance → Sub-Domain Anchor → Domain Document

The parent chain must be explicitly declared in every
document's Section 2 (Parent Chain). No document may be
committed to GitHub without its complete parent chain
already committed.

5. CODE FILE DOCUMENT CONTROL HEADER FORMAT
============================================================

Code files and operational scripts in TothBot_V2-Code are
controlled documents. They use the same 7-field header as
TothBot_V2-Docs documents, embedded as a comment block at
the top of the file.

------------------------------------------------------------
5.1 MANDATORY CODE FILE HEADER FORMAT
------------------------------------------------------------

For Python files (.py) and bash scripts (.sh):

  # DocDCN:     [DCN of governing AA=10 coding spec]
  # DocTitle:   [Descriptive_File_Title_Underscores]
  # DocVersion: [dv/rv/v + major_minor, e.g., dv1_0]
  # DocOwner:   [Bill]
  # DocPath:    [github.com/TothBot/TothBot_V2-Code/path]
  # DocDate:    [MM-DD-YYYY]
  # DocTime:    [HH:MM:SS UTC, 24-hour]

For non-Python files (.ini, .txt, .service, etc.):
  Use the file's native comment syntax.
  If no comment syntax exists, place the header as the
  first 7 lines of the file in the same key: value format.

The header MUST appear on the first lines of every file.
For bash scripts, the header follows the shebang line
(#!/usr/bin/env bash) — the shebang MUST be line 1.
No code, imports, or content may precede the header block
(beyond the shebang for bash scripts).

------------------------------------------------------------
5.2 CODE FILE HEADER FIELD RULES
------------------------------------------------------------

DocDCN:
  References the governing AA=10 coding specification DCN.
  For files governed by Engineering_Best_Practices: 1011001.
  For component .py files: the DCN of their governing spec
  (e.g., ws_manager.py → 1011002 WS_Manager_Coding_Spec).
  For operational scripts: the DCN of their governing
  operational-scripts coding spec (TBD in AA=10
  Sub-Domain 1 Operations).

DocTitle:
  Descriptive title of the file or configuration.
  Underscores only. No spaces.
  Example: Git_Ignore_Configuration, WS_Manager,
  TothBot_Sweep_Script.

DocPath:
  Full path in the repository:
  github.com/TothBot/TothBot_V2-Code/[relative/path/file]
  NOT the VPS deploy path. NOT the local Windows path.

DocVersion:
  Follows the same rules as all controlled documents.
  Starts at dv1_0. Increments on every change.

------------------------------------------------------------
5.3 CODE FILE REVISION HISTORY REQUIREMENT
------------------------------------------------------------

Every code file MUST include a Revision History section
in comment format. Format:

  # ============================================================
  # REVISION HISTORY
  # ============================================================
  #
  #   dv1_0  MM-DD-YYYY  Initial. [brief summary]
  #   dv1_1  MM-DD-YYYY  [what changed]

The Revision History grows with the file. No entry is
ever removed. The complete change history is retained.

============================================================
9. LIFECYCLE STATES
============================================================

Every document exists in exactly one lifecycle state.
The state is encoded in DocVersion.

  dv  — Draft Version
        Active development. Under constant review. Bill may
        approve directly (dv → v). Not yet authoritative.
        Example: dv1_0, dv1_1, dv2_0

  rv  — Revision Version
        An approved document requiring changes returns to
        rv state. Not used for initial document development.
        Bill re-approves after revision is complete.
        Example: rv1_0

  v   — Approved Version
        Bill-approved. Authoritative. Governs the system.
        Changes require v → rv before returning to v.
        Example: v1_0, v2_0

  rt  — Retired
        No longer authoritative. Retirement removes the
        document from HEAD via `git rm` + commit + push.
        Git history preserves all prior versions; use
        `git log --follow <path>` to inspect a retired
        document's full version history. No rt-prefix
        successor file at HEAD; no tombstone document
        body; no _Archive folder. See TB00000 v2_32 §11
        and 0311003 v1_2 VP-010(c) for the authoritative
        standing practice.
        DCN permanently reserved. Never reused.
        Example: rt1_0 (DocVersion at moment of
        retirement; recorded in git history only).

State transitions:
  dv → v   (Bill approves working draft directly)
  v  → rv  (approved document requires changes)
  rv → v   (Bill re-approves after revision)
  v  → rt  (document retired)

============================================================
10. VERSIONING
============================================================

Version numbers follow the pattern: state + major_minor

  dv1_0   First draft, first minor version
  dv1_1   First draft, second minor version
  rv1_0   Review of first major version
  v1_0    First approved version
  v2_0    Second approved version (major revision)

Minor version: corrections, clarifications, additions
that do not change scope or governing decisions.

Major version: changes to scope, governing decisions,
structural changes, or any change requiring full
re-approval.

Every change increments the version. No exceptions.

15. EMBEDDED ASSET ARCHITECTURE
============================================================

------------------------------------------------------------
15.1 Purpose and Scope
------------------------------------------------------------

Section 15 governs every embedded asset in every
controlled document in TothBot V2. An embedded asset is
any non-prose information element that the controlled
document presents as a unit: diagrams, images, charts,
tables rendered as images, embedded data files, audio
samples, video samples, or any other functionally-binary
content.

Section 15 defines:

  (a) The architecture by which embedded assets are
      stored, named, and referenced.
  (b) The reference syntax controlled documents use to
      cite assets.
  (c) The validation rules that detect missing or
      misnamed assets.
  (d) The rendering contract that derived formats
      (.docx, .pdf, .xlsx, .pptx) MUST honor when
      transforming the .txt source plus assets into a
      deliverable binary.
  (e) The migration rule for any existing document that
      contains inline embedded assets in violation of
      the external-file architecture.

Section 15 is the AUTHORING-LAYER governance for
embedded assets. The DELIVERY-LAYER governance lives in
TB00000 §4.1 (DR-007 Binary Artifact Content-
Completeness Validation, CI-002 External Asset
Architecture, CI-003 No Inline Binary Embeds, CI-004
Reference Syntax Binding, CI-009 Asset Presence
Verification). Sections 15 and TB00000 §4.1 work
together: Section 15 defines the asset model, TB00000
§4.1 enforces it at delivery.

Section 15 closes ERROR-TB00149-02 SVG-DROP-IN-BINARY-
GENERATION at the authoring-architecture layer.

------------------------------------------------------------
15.1.1 SCOPE — APPLIES TO NON-HTML CONTROLLED DOCUMENTS
------------------------------------------------------------

Sections 15.1 through 15.12 apply to NON-HTML controlled
documents — primarily .txt source-of-truth files with
external embedded asset files (.svg, .png, .jpg, .jpeg,
.csv, .wav, .mp3, .mp4) per §15.3 taxonomy.

For HTML controlled documents (filename suffix
"_Claude_Source.html" per KPL-005 in 0311006 dv1_2):
SECTION 15.13 GOVERNS. HTML controlled documents are a
SPECIAL CASE in which the structural contract of the
HTML format requires inline embedded content (inline
<svg>, inline <style>, inline <script>) and the
external-asset architecture defined in §15.2 through
§15.10 is OVERRIDDEN within HTML scope only. The
override is bounded — it applies only to the HTML
documents themselves, not to any non-HTML documents
referenced by them or referencing them.

Validation rules V-020 through V-036 in §15.7 remain in
force for non-HTML controlled documents. New V-037 in
§15.7 covers HTML controlled documents. The TB00000
v2_20 §4.1 CI-002 EXTERNAL ASSET ARCHITECTURE and
CI-003 NO INLINE BINARY EMBEDS are amended in v2_20
to carry the same HTML scope exception.

------------------------------------------------------------
15.2 Foundational Principle — External Asset Files
------------------------------------------------------------

Every embedded asset is an EXTERNAL FILE stored
separately from the .txt controlled document that
references it. Inline embeds of any kind are PROHIBITED
in .txt source. This prohibition applies regardless of
whether the embedded content is structurally text (e.g.,
SVG XML) or structurally binary (e.g., base64 PNG).

The four reasons:

  (1) The .txt controlled document is the
      source-of-truth for prose, structure, and
      references. Mixing prose with binary-functioning
      content makes the .txt file harder to read,
      review, edit, and audit.

  (2) The rendering pipeline (which produces .docx and
      .pdf from .txt) operates deterministically when
      assets are external. Rendering pipelines that
      attempt to interpret inline embeds silently fail
      (the TB00149 ERROR-TB00149-02 origin pattern):
      the pipeline strips the inline embed and
      substitutes a stub note rather than rendering
      the asset.

  (3) Asset reuse across documents requires assets to
      be addressable. Inline embeds are not
      addressable.

  (4) Version control of assets requires assets to be
      first-class files. Inline embeds inherit the
      version of their host document and cannot be
      independently versioned.

15.3 Asset Type Taxonomy
------------------------------------------------------------

Section 15 covers the following asset types. Each type
has a designated file extension and a role in the
rendering pipeline.

  TYPE      EXTENSION   ROLE
  ----      ---------   ----
  Diagram   .svg        Vector graphics for
                        architectural diagrams,
                        flowcharts, state machines,
                        timing diagrams. Source-of-
                        truth is the SVG XML; the
                        rendering pipeline rasterizes
                        to PNG for .docx embed and
                        embeds vector or raster in
                        .pdf.
  Image     .png        Raster graphics for
                        screenshots, photographs,
                        captured data plots. .png is
                        the lossless raster format;
                        rendering pipeline embeds
                        directly with no
                        transformation.
  Image     .jpg/.jpeg  Raster graphics for
                        photographs where lossy
                        compression is acceptable.
                        Rendering pipeline embeds
                        directly.
  Data      .csv        Structured data referenced by
                        the controlled document.
                        Rendering pipeline either
                        embeds as a typographic table
                        or includes the .csv as an
                        attachment.
  Audio     .wav/.mp3   Audio samples. Rendering
                        pipeline includes as
                        attachment in .docx and .pdf.
  Video     .mp4        Video samples. Rendering
                        pipeline includes as
                        attachment in .docx and .pdf.

New asset types may be added to this taxonomy only by
amendment to Section 15 with a new revision history
entry. Use of any asset type not enumerated above is
PROHIBITED.

15.5 Asset Filename Convention
------------------------------------------------------------

The canonical asset filename pattern is:

  [ParentDCN]_[Type][N]_T[Tier]_R[R]_[ShortTitle].[ext]

Where:

  ParentDCN    The 7-digit DCN of the parent
               controlled document (e.g., 0500000).
  Type         The asset type word, capitalized:
                 Diagram   for .svg vector graphics
                 Image     for .png / .jpg / .jpeg
                 Data      for .csv
                 Audio     for .wav / .mp3
                 Video     for .mp4
                 Context   for the unique Tier 1
                           Context diagram of a
                           parent (special case;
                           see TIER 1 RULE below).
  N            The sequence number within the parent
               document for this Type, starting at
               1, incrementing by 1 for each next
               asset of the same Type. REQUIRED for
               all Types except Context.
  Tier         An integer in {1, 2, 3, 4} per the
               §15.11 Architecture Blueprint
               Framework:
                 1 = Context (system-level overview,
                              one per parent DCN)
                 2 = Container (subsystem grouping)
                 3 = Component (single contract,
                                state machine, or
                                decision tree)
                 4 = Sequence (time-ordered scenario)
               The literal "T" prefix precedes the
               integer (e.g., T1, T2, T3, T4).
  R            An integer in {0, 1, 2, ...} denoting
               the asset revision within the parent
               document version. R0 is the initial
               authoring of the asset. R1, R2, ...
               denote successive revisions to the
               same asset (content updates, defect
               fixes, refresh against current parent
               document content). R increments
               independently of the parent
               document's version. The literal "R"
               prefix precedes the integer (e.g.,
               R0, R1, R2).
  ShortTitle   A short descriptive title in
               PascalCase or Snake_Case. Spaces
               PROHIBITED. Special characters
               PROHIBITED. Maximum 60 characters.
  ext          The file extension (lowercase) per
               §15.3 taxonomy.

TIER 1 RULE — N OMISSION:
A parent controlled document has at most ONE Tier 1
Context diagram. For Tier 1 Context diagrams ONLY,
the N component is OMITTED from the filename. The
Type word "Context" is itself unique within the
parent. Any tier other than Tier 1 REQUIRES an
explicit N. A second Tier 1 Context diagram for a
parent is PROHIBITED — the parent's Tier 1 view is
unique by definition.

Examples (canonical):

  0500000_Context_T1_R0_System_Context.png
    (Tier 1 Context — N omitted per Tier 1 rule)
  0500000_Image1_T2_R0_Kraken_API_Connection_Architecture.png
    (Tier 2 Container — refresh of dv1_23 Image1)
  0500000_Image2_T2_R0_Trading_Pipeline.png
  0500000_Image3_T2_R0_Exit_Architecture.png
  0500000_Diagram1_T2_R0_Kraken_API_Connection_Architecture.svg
    (Tier 2 SVG source — same diagram as Image1)
  1011002_Image1_T3_R0_WS_Manager_State_Machine.png
    (Tier 3 Component — state machine)
  1011002_Image2_T3_R1_Reconnect_Decision_Tree.png
    (Tier 3 Component — first revision after R0)
  0211001_Data1_T3_R0_CIATS_Trade_Outcome_Schema.csv

Examples (PROHIBITED — V-021 / V-025 / V-031 / V-036
violations):

  diagram1.svg
    (no parent DCN prefix)
  0500000_diagram1.svg
    (Type word not capitalized)
  0500000_Diagram_1.svg
    (sequence number separated by underscore)
  0500000_Diagram1.svg
    (T[Tier] and R[R] missing — V-031 violation)
  0500000_Image1_T5_R0_Foo.png
    (Tier value out of {1,2,3,4} — V-031 violation)
  0500000_Context1_T1_R0_System_Context.png
    (Tier 1 with explicit N — violates Tier 1 Rule;
     Context type is unique per parent)
  0500000_Context_T2_R0_Foo.png
    (Context type used at Tier other than 1 —
     PROHIBITED)
  0500000_Image1_R0_Foo.png
    (T[Tier] missing)
  0500000_Image1_T2_Foo.png
    (R[R] missing)
  0500000_Image1_t2_R0_Foo.png
    (lowercase t prefix — PROHIBITED; T must be
     uppercase)
  0500000_Image1_T2_R0_Kraken_API connection.png
    (spaces in ShortTitle)
  0500000_Image1_T2_R0_Kraken-API.png
    (hyphens in ShortTitle)

R-COMPONENT SEMANTICS.
The R component encodes asset-level revision INSIDE
a parent document version. Two scenarios drive R
increments:

  (1) Asset content refresh while parent unchanged.
      Diagram refreshed to reflect current parent
      content without parent version increment.
      R0 -> R1. Reference syntax in parent .txt
      MUST update to the new R value (V-023 binding
      requires exact filename match). Parent version
      increment is REQUIRED if the parent .txt
      reference syntax changes.

  (2) Asset defect fix while parent unchanged.
      Asset has a labeling defect, overlap, color
      error, or other rendering defect that does
      not affect parent prose. Fix produces R+1.

R does NOT reset on parent version increment. R is
monotonic per asset over the asset's lifetime. R
resets only when the asset is RETIRED and a NEW
asset of the same Type-N is authored from scratch
(rare; documented per §15.9).

A controlled document that references an asset that
does not exist as a file in the parent folder is
incomplete (V-023 violation).

LEGACY COMPATIBILITY.
Asset filenames authored under the v1_4 §15.5 pattern
(without T[Tier]_R[R]) MAY exist in the corpus at
the time v1_5 enacts. Such filenames are LEGACY and
MUST be migrated to the new pattern at the next
normal version increment of the parent controlled
document, per §15.9 migration procedure as
extended for the [_T][_R] additions.

------------------------------------------------------------
15.6 Reference Syntax in Controlled Documents
------------------------------------------------------------

Within a .txt controlled document, every embedded asset
is referenced using the canonical syntax:

  [Asset file: <filename>]

Where <filename> is the EXACT canonical filename of the
asset per §15.5. The reference is positioned at the
insertion point where the rendered asset should appear
in derived formats.

Examples (canonical):

  [Asset file: 0500000_Diagram1_Kraken_API_Connection_Architecture.svg]
  [Asset file: 1011002_Image1_WS_Manager_State_Machine.png]
  [Asset file: 0211001_Data1_CIATS_Trade_Outcome_Schema.csv]

LEGACY COMPATIBILITY: The pre-v1_4 reference syntax
"[Diagram file: <filename>]" is recognized by the
rendering pipeline as an alias for "[Asset file:
<filename>]" but is DEPRECATED. New references MUST use
"[Asset file: ...]". Existing "[Diagram file: ...]"
references in the corpus migrate to "[Asset file: ...]"
on the next normal version increment of each affected
document.

PROHIBITED VARIANT FORMS:

  [Image: filename.png]         (missing "file:" word)
  [File: filename.svg]          (missing asset type)
  [Diagram1]                    (missing filename)
  [See diagram 0500000_...svg]  (prose; not a formal
                                 reference)
  inline `<svg>...</svg>` XML   (CI-003 violation;
                                 see §15.10)
  base64-encoded image data     (CI-003 violation)

The rendering pipeline recognizes ONLY the canonical
syntax (and the deprecated [Diagram file: ...] alias
during migration). It does NOT scan prose for asset
mentions. A document that intends to render an asset
MUST use the formal reference syntax.

15.7 Validation Rules for Embedded Assets
------------------------------------------------------------

  V-020  Asset filename begins with parent DCN
         (7 digits, no separator before underscore).

  V-021  Asset filename uses an extension enumerated
         in §15.3 (.svg, .png, .jpg, .jpeg, .csv,
         .wav, .mp3, .mp4). Other extensions
         PROHIBITED.

  V-022  Asset file lives in the SAME folder as
         parent .txt controlled document. Subfolders
         for assets PROHIBITED.

  V-023  Every "[Asset file: filename]" reference
         (or deprecated "[Diagram file: filename]"
         alias) in a .txt controlled document has a
         corresponding asset file in the parent
         folder with the EXACT canonical filename
         specified.

  V-024  Asset N+1 of a given Type does not exist
         without Asset N of the same Type for the
         same parent DCN. Sequence numbers within a
         Type are dense (no gaps).

  V-025  Asset filename matches the canonical
         §15.5 pattern. Filenames not matching are
         a V-025 defect requiring rename.

  V-026  No asset file exists in a parent folder
         without a corresponding "[Asset file: ...]"
         reference in the parent .txt controlled
         document. Orphan asset files (asset present,
         no reference) are a V-026 defect requiring
         either reference addition or asset removal.

  V-027  No "[Asset file: ...]" reference exists in
         a parent .txt controlled document without a
         corresponding asset file in the parent
         folder. Orphan references (reference
         present, no asset) are a V-027 defect — the
         inverse of V-023; both phrasings MUST hold.

  V-028  No INLINE embedded assets in any .txt
         controlled document. Inline `<svg>` XML,
         inline base64 data, inline Office Open XML
         fragments, inline PDF byte sequences — all
         PROHIBITED. Per CI-003 in TB00000 §4.1.

  V-029  Asset filename ShortTitle component
         contains only [A-Z][a-z][0-9_] characters.
         No spaces, no hyphens, no special
         characters, no Unicode outside ASCII.

  V-030  Maximum asset filename length 200
         characters (cross-platform filesystem
         portability).

  V-031  Tier value validation. The T[Tier]
         component of every asset filename MUST
         contain an integer in {1, 2, 3, 4}.
         Other values are PROHIBITED. The literal
         "T" prefix MUST be uppercase. The literal
         "R" prefix on the R[R] component MUST
         also be uppercase. Asset filenames
         missing T[Tier] OR R[R] are V-031
         violations requiring rename per §15.9
         migration procedure.

  V-032  Structured-tag resolution. Every
         structured tag (prefix:CANONICAL_NAME)
         appearing in any in-SVG <title> or
         <desc> element of a Tier 1, Tier 2, or
         Tier 3 diagram MUST resolve to a
         registry entry in §15.12 Asset-Tag
         Canonical Registry. The prefix MUST
         match one of the 14 type prefixes
         enumerated in §15.11. The
         CANONICAL_NAME MUST exactly match an
         entry registered under that prefix
         (case-sensitive). Unresolved tags are
         V-032 violations.

  V-033  Orphan-tag detection (bidirectional).
         Every constraint, hard rule, AR, gate,
         module, container, contract, layer,
         regime, event, parameter, decision,
         channel, indicator, or PT_MODE marker
         enumerated in any in-scope spec
         document MUST be referenced by at
         least one diagram tag in the
         architecture blueprint set, AND every
         diagram tag MUST resolve to a real
         spec entity. Unreferenced spec
         entities are forward-orphan V-033
         violations; tags pointing to absent
         spec entities are reverse-orphan
         V-033 violations. Both directions
         MUST hold.

  V-034  Type-relation validation. Tags MUST
         compose only via the type-relation
         rules enumerated in §15.11. For
         example: a Module MAY enforce a
         HardRule but MAY NOT enforce an
         Event; a Gate MAY emit an Event but
         MAY NOT contain a Container. Type-
         relation violations are V-034
         defects. Full rule list maintained
         in §15.11.

  V-035  Tier cardinality. Every Tier-N
         element with N >= 2 in any diagram
         MUST have at least one Tier-(N-1)
         parent reference (drill_target up)
         AND at most one Tier-(N+1) child
         reference per Tier-N element
         (drill_target down). Orphan-leaf
         (Tier-N with no parent for N >= 2)
         and orphan-root (Tier 1 element
         with parent reference) are V-035
         violations.

  V-036  Naming consistency. CANONICAL_NAME
         tokens used in diagram tags
         (case-sensitive) MUST exactly match
         the entry name in §15.12. Diagram
         filenames (per §15.5 ShortTitle)
         SHOULD align with the diagram's
         primary CANONICAL_NAME but are not
         strictly bound. Hyphenation,
         underscore vs camelCase, and
         pluralization differences in tags
         vs registry are V-036 violations.

  V-037  HTML controlled document figure-
         structure validation. APPLIES ONLY
         to controlled documents with .html
         extension and "_Claude_Source.html"
         filename suffix per §15.13 and
         KPL-005 in 0311006 dv1_2.

         Every <figure class="diagram"> in an
         HTML controlled document MUST contain
         exactly one of the following:
           (a) Exactly one inline <svg>
               element (the rendered diagram).
               The figure's class attribute is
               literally "diagram" (single
               class), OR
           (b) Exactly one
               <div class="placeholder-box">
               element (a pending-authoring
               placeholder). The figure's
               class attribute is literally
               "diagram diagram-placeholder"
               (two classes).

         Identity parity: the count of
         <figure class="diagram"> elements
         (rendered + placeholder combined)
         MUST equal the document's diagram
         budget per its DC header DocVersion
         and revision history. The count of
         <figure class="diagram"> elements
         containing inline <svg> MUST equal
         the count of authored diagrams as
         declared in the §15.13 inline-asset
         inventory at the top of the
         document body.

         Violations:
           V-037.1 <figure class="diagram">
                   contains zero <svg> AND zero
                   <div class="placeholder-box">.
                   Empty figure = defect.
           V-037.2 <figure class="diagram">
                   contains both an inline <svg>
                   AND a <div class="placeholder-
                   box">. Mixed figure = defect.
           V-037.3 <figure class="diagram">
                   contains more than one inline
                   <svg> OR more than one
                   <div class="placeholder-box">.
                   Multi-asset figure = defect
                   (each asset gets its own
                   figure).
           V-037.4 Inventory mismatch between
                   declared diagram count and
                   actual <figure> count. Drift
                   = defect.

         Enforcement: Pre-delivery validation
         per TB00000 v2_20 §4.1 DR-007 HTML
         scope amendment plus session-open
         pre-flight per 0311002 v1_10 §8.2.5
         DC-PREFLIGHT-007 sub-check (f) HTML
         SCOPE.

  V-038  Diagram-prose authority parity. APPLIES
         to every diagram-bearing controlled
         document at every authoring/amendment
         cycle. Per §15.14 (NEW v1_10) and
         TB00000 §4.5 DD-001..DD-010, diagrams
         are the canonical Design Documents and
         govern over prose. V-038 enforces that
         every architectural rule, contract,
         decision, gate, layer, regime, param,
         container, mod, indicator, evt, channel,
         ar, or pt_mode identifier asserted in
         document prose has a corresponding
         diagram element — either a T-2+
         namespace-token labeled group with
         matching CANONICAL_NAME OR a root <desc>
         governs: list entry — somewhere in the
         document's diagram set.

         Violations:
           V-038.1 Prose asserts a rule /
                   contract / decision / gate /
                   layer / regime / param /
                   container / mod / indicator /
                   evt / channel / ar / pt_mode
                   identifier with no
                   corresponding diagram
                   labeled-group tag and no
                   corresponding root <desc>
                   governs: entry. Prose-only
                   architecture = defect.
           V-038.2 Prose and diagram both
                   reference the same identifier
                   but with conflicting
                   semantics (different
                   parent_diagram, different
                   constraints, different
                   consumes/produces, etc.).
                   Conflict = defect; resolution
                   per §15.14.3 (diagram
                   governs; prose updated to
                   match).
           V-038.3 Diagram contains a labeled
                   group or root <desc> entry
                   not referenced anywhere in
                   document prose, AND the
                   identifier is not recorded
                   as a known diagram-only
                   architectural element. Stale
                   diagram tag candidate; flag
                   for §15.14.5 cross-check
                   resolution.

         Enforcement: Pre-amendment cross-check
         per §15.14.5; session-open pre-flight
         per 0311002 DC-PREFLIGHT (future
         amendment); pre-delivery DR-007 HTML
         scope sweep extended to include V-038
         scan.

         Closure of TB00163 §7.4 DIAGRAMS-AS-
         CANONICAL governance gap is at the
         §4.5 / §15.14 standing-rule layer;
         V-038 is the validation-layer companion.

  V-039  Parent-chain-completeness. APPLIES to
         every controlled document with multiple
         parent documents at every authoring /
         amendment cycle. Per §15.15 (NEW v1_17)
         and TB00000 §1.2 PRIMARY MISSION loss-
         prevention dependency-visibility
         requirement: every coding specification
         (AA=10), every architectural artifact,
         and every instance specification MUST
         cite every parent specification whose
         rules it implements OR whose module it
         depicts in its parent chain section
         (§2 PARENT CHAIN, §11 RELATED DOCUMENTS,
         or equivalent parent-citation section).
         The canonical form is 4-parent canonical
         (or N-parent canonical for an N-parent
         document set): all N parent specifications
         must be cited; no omissions.

         Violations:
           V-039.1 Coding spec parent chain
                   incomplete. The AA=10 spec
                   §2 PARENT CHAIN omits one or

                   implements. Defect requires
                   amendment to add the missing

           V-039.2 Architectural-artifact parent

                   0500000 diagram-bearing prose

                   Defect requires amendment to
                   add the missing parent
                   reference in the diagram-
                   bearing prose.
           V-039.3 Instance-spec parent citation
                   incomplete. The instance-spec
                   §11 RELATED DOCUMENTS (or
                   equivalent) omits a parent

                   requires amendment to add the
                   missing parent citation.

         per 0311002 DC-PREFLIGHT (future

         retirement campaign.

         Closure of TB00255 §3.1 universal
         parent-chain-completeness rule
         ratification is at the §15.15 standing-
         rule layer; V-039 is the validation-
         layer companion.

15.8 Rendering Contract for Derived Formats
------------------------------------------------------------

Every derived format (.docx, .pdf, .xlsx, .pptx) is
produced by a deterministic rendering pipeline that
reads the .txt Claude Source and the asset files it
references, then produces the derived format. The
pipeline MUST honor the following contract:

  RC-1 EVERY ASSET REFERENCE PRODUCES A RENDERED
       ASSET.
       For every "[Asset file: filename]" reference
       in the .txt source, the rendering pipeline
       produces a rendered asset embedded in the
       derived format at the corresponding position.
       The rendering pipeline MUST NOT silently
       drop, skip, or stub-substitute any asset
       reference.

  RC-2 RENDERING PER ASSET TYPE.
       The rendering pipeline applies the following
       per-Type transformations:

         .svg → .docx: rasterize to PNG at 2x
                       display resolution (minimum
                       150 DPI), embed PNG in body
                       at reference position.
         .svg → .pdf:  embed vector SVG directly
                       where possible; fall back to
                       PNG raster (300 DPI) where
                       vector embed unsupported.
         .png/.jpg/.jpeg → .docx, .pdf: embed
                       directly.
         .csv → .docx: render as typographic table
                       OR embed as attachment.
         .csv → .pdf:  render as typographic table
                       OR embed as attachment.
         .wav/.mp3/.mp4 → .docx, .pdf: embed as
                       file attachment.

  RC-3 PIPELINE FAILURE IS A DEFECT.
       If the rendering pipeline cannot render any
       asset reference, the pipeline MUST FAIL and
       the derived format MUST NOT be produced. A
       failed render is reported to Claude (and
       through Claude to Bill) as a defect requiring
       remediation. Stub-note substitution is
       PROHIBITED per CI-008.

  RC-4 NO PIPELINE-INTRODUCED CONTENT.
       The rendering pipeline produces ONLY content
       derived from the source-of-truth set. It MUST
       NOT add prose, captions, watermarks,
       footers, or any other content not present in
       the source-of-truth. Header / footer / page
       numbers may be added per a documented
       rendering profile, but no body content.

  RC-5 NO PIPELINE-INTRODUCED LOSS.
       The rendering pipeline preserves ALL prose,
       structure, references, and asset embeds from
       the source-of-truth set, with only the
       transformations enumerated in TB00000 §4.1
       CI-007 (T-1 through T-5) permitted. Any
       deviation is a defect.

  RC-6 DETERMINISTIC OUTPUT.
       Two invocations of the rendering pipeline on
       the same source-of-truth set produce
       semantically equivalent output. Byte-level
       differences are permitted only in non-content
       metadata (e.g., creation timestamps in PDF
       metadata).

------------------------------------------------------------
15.9 Migration Rule for Existing Inline Embeds and Legacy Filenames
------------------------------------------------------------

Two migration scopes apply under §15:

  SCOPE A — Inline embeds.
    Any existing controlled document that contains
    inline embedded assets (in violation of V-028 /
    CI-003) MUST be migrated to the external-file
    architecture on the next normal version
    increment of that document.

  SCOPE B — Legacy filenames (NEW v1_5).
    Any asset filename authored under the v1_4
    §15.5 pattern (without T[Tier]_R[R]) MUST be
    migrated to the v1_5 pattern at the next
    normal version increment of the parent
    controlled document. The migration step is a
    pure rename operation; asset content is
    preserved byte-for-byte unless an R increment
    is independently warranted per §15.5
    R-COMPONENT SEMANTICS.

The migration procedure for SCOPE A is:

  STEP 1 EXTRACTION.
         Each inline `<svg>` XML embed is extracted
         from the .txt source and saved as a
         separate file in the parent folder, named
         per §15.5 canonical convention with
         T[Tier] and R[R] assigned per
         §15.11/§15.12. The extraction preserves
         the SVG XML byte-for-byte; no editing is
         performed.

  STEP 2 REFERENCE SUBSTITUTION.
         Each inline embed in the .txt source is
         replaced by the canonical "[Asset file:
         filename]" reference at the same position.

  STEP 3 RENDERING REGENERATION.
         The .docx and .pdf are regenerated from the
         migrated .txt source plus the extracted
         asset files via the §15.8 rendering
         pipeline. The regenerated binaries pass
         TB00000 §4.1 DR-007 content-completeness
         validation.

  STEP 4 REVISION HISTORY ENTRY.
         The version increment's revision history
         entry explicitly enumerates the migration:
           - Asset extraction count and filenames.
           - Reference substitution count.
           - Binary regeneration confirmation.
           - Tier and R assignments per
             §15.11/§15.12.

  STEP 5 VALIDATION.
         Run V-020 through V-036 against the
         migrated document and asset files. All
         MUST pass.

The migration procedure for SCOPE B is:

  STEP 1 RENAME.
         Each legacy asset file is renamed to the
         v1_5 pattern. T[Tier] is assigned per
         §15.11 tier discipline (Tier 2 for
         existing Container-class diagrams in the
         current corpus). R[R] is set to R0 if the
         asset content is unchanged from its
         legacy form, OR R1+ if a content refresh
         is bundled with the rename.

  STEP 2 REFERENCE UPDATE.
         Every "[Asset file: ...]" reference in
         the parent .txt source is updated to the
         new filename. V-023 binding requires
         exact filename match; stale references
         FAIL validation.

  STEP 3 RENDERING REGENERATION.
         Per SCOPE A STEP 3.

  STEP 4 REVISION HISTORY ENTRY.
         The version increment's revision history
         entry enumerates the rename mapping
         (legacy -> v1_5) for each asset file.

  STEP 5 VALIDATION.
         Run V-020 through V-036 against the
         renamed document and asset files. All
         MUST pass.

Migration is NOT a content change in the
information-content sense (the same diagrams are
present after migration, just stored or named
differently). However, the structural change
(.txt source layout, asset file presence,
reference syntax, filename pattern) is significant
and MUST be documented in the revision history.

15.10 Prohibited Patterns
------------------------------------------------------------

The following patterns are PROHIBITED in any
controlled document. Detection of any pattern is a
V-028 / CI-003 violation requiring immediate
remediation per §15.9.

  PP-1  Inline `<svg>...</svg>` XML embed in .txt
        source. (THE TB00149 ERROR-TB00149-02
        ORIGIN PATTERN.)

  PP-2  Inline base64-encoded image data in .txt
        source.

  PP-3  Inline Office Open XML fragments
        (`<w:p>`, `<w:tbl>`, etc.) in .txt source.

  PP-4  Inline PDF byte sequences in .txt source.

  PP-5  Embedded binary content via any encoding
        scheme (uuencode, hex, ASCII85) in .txt
        source.

  PP-6  Asset files stored in subfolders below the
        parent .txt source location.

  PP-7  Asset filenames not conforming to §15.5
        canonical pattern.

  PP-8  Reference syntax variant forms not
        recognized in §15.6.

  PP-9  Asset files present without corresponding
        references (orphan assets, V-026
        violation).

  PP-10 References present without corresponding
        asset files (orphan references, V-027
        violation).

  PP-11 Untagged labeled element in any Tier 1,
        Tier 2, or Tier 3 diagram. Every <g>
        group wrapping a labeled element in a
        tagged diagram MUST carry <title> and
        <desc> per §15.11 encoding rules, OR be
        explicitly marked <g class="decoration">
        for visual-only elements (legend boxes,
        zone backgrounds, ornamental rules).
        Untagged labeled elements are V-032
        violations.

  PP-12 Tag prefix outside the §15.11 14-type
        scheme. Use of any prefix other than
        mod:, container:, contract:, gate:,
        layer:, regime:, evt:, param:, rule:,
        decision:, channel:, indicator:, ar:,
        pt_mode: is PROHIBITED. New prefixes
        require §15 amendment.

  PP-13 Cross-tier reference without
        drill_target attribute. A Tier-N
        element MAY reference Tier-(N+1) or
        Tier-(N-1) elements ONLY via the
        drill_target structured-tag attribute
        per §15.11. Direct same-diagram
        cross-tier reference (e.g., a Tier 2
        Container diagram visually mixing a
        Tier 3 Component element without a
        drill_target boundary) is PROHIBITED.

  PP-14 Schema-version drift. Tagged diagrams
        MUST declare schema version in the
        diagram-level <desc> element
        (e.g., schema_version: 1.0). Diagrams
        omitting schema_version are PROHIBITED.
        Schema upgrades follow §15 amendment
        procedure.

15.11 Architecture Blueprint Framework (NEW v1_5)
------------------------------------------------------------

Section 15.11 establishes the four-tier architecture
blueprint structure and the T-2+ tag taxonomy schema
v1.0 governing every diagram in the controlled
document corpus. The framework is a governance layer
ABOVE the file-storage and rendering rules in
§15.1-§15.10. It governs the SEMANTIC content of
diagrams, not their physical encoding.

Section 15.11 closes the architectural drift defect
class (Diagram 1-6 currency miss, A-10/A-7/A-9/I-6
tag absence, AR-070 silent narrowing, D-08
Chesterton's fence) at the diagram-corpus governance
layer. The complementary asset-tag canonical registry
in §15.12 holds the data; §15.11 defines the schema.

Schema Version: 1.0
First-issue date: 05-05-2026
Revision window: planned after TB00151b completion
  (matches existing project pattern of "rule added
  after defect class proves necessity").

------------------------------------------------------------
15.11.1 Four-Tier Structure
------------------------------------------------------------

Every diagram in the controlled corpus is assigned to
exactly ONE tier:

  Tier 1 — CONTEXT.
    System-level overview. Shows the controlled
    system as a single unit and its primary
    external actors / boundaries. Exactly ONE
    Tier 1 diagram per parent DCN. Filename Type
    = "Context"; N is omitted per §15.5 Tier 1
    Rule.
    Example: 0500000_Context_T1_R0_System_Context

  Tier 2 — CONTAINER.
    Subsystem grouping. Shows the controlled
    system decomposed into major containers
    (modules, subsystems, regime taxonomies,
    architectural layers). Multiple Tier 2
    diagrams per parent DCN are permitted; each
    addresses a distinct subsystem facet.
    Example: 0500000_Image1_T2_R0_Kraken_API_Connection_Architecture

  Tier 3 — COMPONENT.
    Single contract, state machine, or decision
    tree. One Tier 3 diagram per significant
    contract surface. Authored on-demand per
    spec module, not exhaustively. Tier 3
    accrues approximately one diagram per
    significant module across the project life.
    Example: 1011002_Image1_T3_R0_WS_Manager_State_Machine

  Tier 4 — SEQUENCE.
    Time-ordered scenario. Authored on-demand
    when a defect class or contract negotiation
    requires temporal ordering for clarity.
    Examples include AR-070 silent-narrowing
    sequence, A-10 sequence-gap recovery, D-08
    constraint-removal trace.
    Example: 0500000_Sequence1_T4_R0_AR_070_Narrowing_Trace

------------------------------------------------------------
15.11.2 Tier Discipline (E2)
------------------------------------------------------------

Tier discipline is enforced via the following rules:

  E2-A REFERENCE SCOPE.
       A Tier-N element references Tier-(N+1)
       and Tier-(N-1) elements ONLY. Direct
       reference across two or more tiers
       (e.g., Tier 1 directly to Tier 3) is
       PROHIBITED. Cross-tier traversal occurs
       through an intermediate Tier-(N) element.

  E2-B DRILL_TARGET ATTRIBUTE.
       Tier-N to Tier-(N+1) references are
       encoded as drill_target structured-tag
       attributes. Visually, this typically
       renders as a dashed boundary, an explicit
       drill arrow, or a "see Tier 3 component"
       annotation. The drill_target attribute is
       MANDATORY for every Tier-N element that
       has a corresponding Tier-(N+1) elaboration.

  E2-C ORPHAN PROHIBITION.
       Every Tier-N element with N >= 2 MUST
       have at least one Tier-(N-1) parent
       reference (drill_target up). Tier 1
       elements MUST NOT carry drill_target up
       attributes. Per V-035.

  E2-D CARDINALITY.
       Each parent DCN has exactly one Tier 1
       Context. Tier 2 cardinality is bounded
       only by the natural decomposition of the
       parent system. Tier 3 cardinality is
       bounded by significant contract count.
       Tier 4 cardinality is on-demand only.

15.11.3 T-2+ Tag Taxonomy v1.0
------------------------------------------------------------

Every Tier 1, Tier 2, and Tier 3 diagram carries
in-SVG structured tags encoded as <title> and
<desc> elements per tagged <g> group. Tier 4
diagrams MAY carry tags (recommended for sequence
participants) but are not strictly required to.

  ENCODING.
    <g id="..." class="...">
      <title>prefix:CANONICAL_NAME</title>
      <desc>
        canonical: prefix:CANONICAL_NAME
        tier: <1|2|3|4>
        parent_diagram: <parent diagram filename
                         or "none" for Tier 1>
        drill_targets: <comma-separated list of
                        prefix:NAME tokens, or
                        "none">
        constraints: <comma-separated list of
                      ar: / rule: / decision:
                      tokens this element
                      enforces or witnesses>
        consumes: <comma-separated list of
                   evt: / channel: / param:
                   tokens this element reads>
        produces: <comma-separated list of
                   evt: / channel: / param:
                   tokens this element emits>
        schema_version: 1.0
      </desc>
      ... visual content ...
    </g>

  Decorative-only elements (legend boxes, zone
  backgrounds, ornamental rules) are exempt from
  tagging via <g class="decoration"> marker. No
  <title>/<desc> required for decorations.

  TYPE PREFIXES (14, MANDATORY SET).
    mod:        Module (TothBot Python module or
                logical processing unit)
    container:  Container (subsystem, repo,
                pathway, runtime environment)
    contract:   Contract (cross-module interface,
                callback signature, ABI surface)
    gate:       Gate (pipeline gate, validation
                gate, dispatch gate)
    layer:      Layer (exit layer, architectural
                layer)
    regime:     Regime (six-regime taxonomy
                bucket or regime-state element)
    evt:        Event (logged event, emitted
                signal, async notification)
    param:      Parameter (CIATS-owned starting
                value or system parameter)
    rule:       HardRule (HR-* identifier from a
                spec document)
    decision:   Decision (D-* locked decision
                from 0500000 or AR-* element)
    channel:    Channel (Kraken WS channel, REST
                endpoint, internal queue)
    indicator:  Indicator (technical indicator
                or computed signal)
    ar:         AR (architectural reasoning
                identifier from 0500000 or
                downstream specs)
    pt_mode:    PT_MODE (paper-trading mode
                operational marker per
                0211005)

  CANONICAL_NAME tokens are case-sensitive and
  MUST exactly match an entry in §15.12.

  ANCHORED ID SCHEME.
    Every tag uses prefix:CANONICAL_NAME form.
    The CANONICAL_NAME is registry-bound: a
    diagram MUST NOT introduce a new
    CANONICAL_NAME absent from §15.12. Adding
    a new entity requires §15.12 amendment
    BEFORE the diagram referencing it is
    finalized.

15.11.6 Diagram-Level Root <desc> Contract (NEW v1_7)
------------------------------------------------------------

§15.11.3 codifies the LABELED-GROUP <g><desc>
schema (one <desc> per tagged <g> element). This
section codifies the separate DIAGRAM-LEVEL root
<desc> schema (exactly one <desc> immediately
following the root <svg>'s <title>). Both schemas
co-exist within a single SVG: the root <desc>
governs the diagram as a whole; labeled-group
<desc> elements govern individual tagged <g>
groups.

The diagram-level root <desc> is MANDATORY for
every Tier 1, Tier 2, and Tier 3 diagram. Tier 4
diagrams MAY carry a root <desc> but are not
strictly required to.

  ENCODING.
    <svg ...>
      <title>diagram_canonical_name</title>
      <desc>
        diagram_canonical: [DCN]_[Type][N]_T[Tier]_R[R]_[ShortTitle]
        tier: <1|2|3|4>
        parent_dcn: <four-or-more-digit DCN of
                     governing parent document>
        schema_version: 1.0
        R-increment: R<integer>
        governs: <comma-separated list of rule: /
                  ar: / decision: / container: /
                  param: tokens this diagram
                  enforces or witnesses at the
                  whole-diagram level>
        drill_targets: <enumerated drill targets
                        per tier rules below>
        parent_diagram: <parent diagram filename
                         OR field OMITTED for
                         Tier 1>
        sacred_constraints: <comma-separated list
                             of hardcoded values
                             outside CIATS scope,
                             e.g., "Net 1:1.5 R:R">
      </desc>
      ... <g> labeled groups and decoration ...
    </svg>

  TIER 1 RULES (DIAGRAM-LEVEL).
    T1-A parent_diagram FIELD OMITTED.
         The root <desc> of a Tier 1 diagram
         MUST NOT include the parent_diagram
         field. A Tier 1 diagram is the
         system-context root and has no parent
         diagram by definition. Per §15.5
         filename rule (N omitted) and §15.11.1
         tier rule (Tier 1 is the top tier).

    T1-B drill_targets FIELD MANDATORY AND
         EXHAUSTIVE.
         The drill_targets field of a Tier 1
         root <desc> MUST enumerate exactly one
         entry per Tier 2 child of the same
         parent DCN. Each entry MUST be a BARE
         CANONICAL-NAME of the form
         [DCN]_Image[N]_T2_[ShortTitle], without
         R-state suffix (AMENDED v1_11 per
         DEC-009 ratified at TB00170; pre-v1_11
         form [DCN]_Image[N]_T2_R[R]_[ShortTitle]
         RETIRED).

         Adding a new Tier 2 diagram under the
         same parent DCN REQUIRES a corresponding
         R-increment of the Tier 1 diagram and a
         drill_targets entry addition.

         R-INCREMENTS OF EXISTING TIER 2 FIGURES
         do NOT trigger Tier 1 R-increments.
         drill_targets are decoupled from Tier 2
         R-state; the bare canonical-name resolves
         the figure regardless of current R-state.

         RATIONALE (NEW v1_11).
         Under DD-001 (diagrams canonical) the
         drill_targets field is a navigation
         pointer from Tier 1 to Tier 2 figures.
         R-states are mutable versioning
         attributes (advance R-1 -> R-2 -> R-3
         across sessions). Canonical-name identity
         (DCN + Image[N] + Tier + ShortTitle) is
         immutable. Pointers must reference stable
         identifiers; binding them to mutable
         R-state forces Tier 1 churn on every
         Tier 2 R-increment, propagating drift.
         The current R-state of any Tier 2 figure
         is discoverable from the figure's own
         <title>diagram_canonical</title> field.

         RESOLUTION SEMANTICS.
         A bare canonical-name drill_target
         entry resolves to the CURRENT R-state
         instance of the named Tier 2 diagram.
         Implementation: the bare-name
         [DCN]_Image[N]_T2_[ShortTitle] matches
         the canonical-name prefix of the current
         diagram_canonical
         [DCN]_Image[N]_T2_R[R]_[ShortTitle];
         the [R] component is resolved at lookup
         time from the target figure's own root
         <desc>.

         TIER 2 ELEMENT-LEVEL drill_targets
         (drill_targets fields on individual
         <g> elements within Tier 2 figures
         pointing to other Tier 2 figures, per
         §15.11.3): same bare-canonical-name
         convention applies. Migration of
         element-level drill_targets to bare
         form is sequenced for next R-increment
         of each Tier 2 figure (no retroactive
         multi-figure amendment per DEC-003
         Path A one-diagram-per-session).
         Pre-v1_11 element-level drill_targets
         in _R[R] form are tolerated until
         per-figure migration completes.

    T1-C tier FIELD VALUE FIXED.
         The tier field MUST be the literal value
         "1". No other value is permitted in a
         Tier 1 diagram root <desc>.

    T1-D LABELED-GROUP parent_diagram VALUE
         WITHIN A TIER 1 DIAGRAM.
         Labeled groups <g> inside a Tier 1
         diagram (governed by §15.11.3) MUST
         declare parent_diagram = "none" in their
         per-group <desc>. The "none" literal is
         the §15.11.3 form for tagged groups in
         Tier 1; the diagram-level field T1-A
         remains OMITTED. The two are distinct:
         T1-A removes the field at diagram root;
         T1-D sets the field to "none" at every
         tagged <g> within the diagram.

  TIER 2/3/4 RULES (DIAGRAM-LEVEL).
    T2P-A parent_diagram FIELD MANDATORY.
         Tier 2, 3, and 4 diagram root <desc>
         elements MUST include the parent_diagram
         field, populated with the filename of
         the parent diagram in the tier above.
         For Tier 2: parent_diagram = the Tier 1
         diagram of the same parent DCN. For
         Tier 3: parent_diagram = the Tier 2
         diagram that drills to this Tier 3
         component. For Tier 4: parent_diagram =
         the Tier 2 or Tier 3 diagram that
         scopes this sequence.

    T2P-B drill_targets FIELD CONDITIONAL.
         Tier 2 diagrams MAY include a
         drill_targets field enumerating Tier 3
         components reached from elements within
         the diagram. Tier 3 diagrams MAY include
         a drill_targets field enumerating Tier 4
         sequences. When present, every entry
         MUST be a BARE CANONICAL-NAME of the
         form [DCN]_Image[N]_T[Tier]_[ShortTitle]
         per the same convention as T1-B
         (AMENDED v1_11 per DEC-009). Bare-name
         entries resolve to the current R-state
         of the named target diagram at lookup
         time. Pre-v1_11 _R[R] form is tolerated
         until per-figure migration completes.

  CO-EXISTENCE WITH §15.11.3.
    The diagram-level root <desc> (this section)
    and the labeled-group <g><desc> (§15.11.3)
    co-exist in the same SVG file. The root
    <desc> applies to the diagram as a whole.
    Each tagged <g> MUST carry its own <desc>
    per §15.11.3. The two schemas share the
    schema_version field; both MUST declare
    schema_version: 1.0 under v1.0 of the tag
    taxonomy.

  VALIDATION COVERAGE.
    The validation classes V1-V6 enumerated in
    §15.11.4 apply to root <desc> as follows:
      V1 (drill traversal): Tier 1 T1-B
        completeness — every Tier 2 child of
        the parent DCN is enumerated.
      V2 (cross-tier reference scope): root
        parent_diagram and drill_targets MUST
        cross exactly one tier boundary
        (Tier-N references Tier-(N+1) or
        Tier-(N-1) only, per E2-A in §15.11.2).
      V4 (type-relation): governs and
        sacred_constraints fields use the same
        prefix taxonomy enumerated in §15.11.3
        (rule:, ar:, decision:, etc.).

  RECURRENCE PREVENTION RATIONALE.
    Pre-v1_7, the diagram-level root <desc>
    schema was de-facto pattern only — present
    in 0500000 dv1_24 D1 through D7 root
    descriptions but not codified. This created
    a documentation gap (DR-008 partial) and a
    Tier 1 authoring gap (DR-001) where no
    written contract specified what fields a
    root <desc> must contain or how Tier 1
    differs from Tier 2+. v1_7 closes both gaps:
    the root <desc> contract is now explicit,
    Tier 1 deviations from the Tier 2+ rule are
    enumerated as T1-A through T1-D, and the
    schema is anchored to schema_version 1.0
    alongside §15.11.3.

------------------------------------------------------------
15.13 HTML CANONICAL FORMAT FOR DIAGRAM-BEARING DOCUMENTS
      (NEW v1_6)
------------------------------------------------------------

15.13.1 PURPOSE

Section 15.13 governs the SPECIAL CASE of TothBot V2
controlled documents whose authoring-and-delivery
architecture is HTML rather than the .txt-plus-external-
assets architecture defined in §15.2 through §15.12. HTML
is the CANONICAL FORMAT for diagram-bearing controlled
documents in TothBot V2 starting with the 0500000 dv1_24
supersession.

The HTML format is selected as canonical because the
Claude.ai project knowledge stack uniquely supports the
combination of three properties that no other format Bill
has access to combines:

  (1) BROWSER-NATIVE RENDERING. Bill opens .html files by
      double-click and views prose, structure, and
      diagrams in a single rendered view without any
      external tool.
  (2) TEXT-EXTRACTING INDEXER. project_knowledge_search
      extracts plain text from .html cleanly, including
      SVG-internal <title> and <desc> elements,
      supporting full-text search and cross-reference
      verification.
  (3) INLINE SVG VISUAL RENDERING. The Claude.ai search-
      result preprocessor rasterizes inline <svg>
      elements visually for Claude, making diagrams
      visible to Claude in addition to readable as XML.

KPL-005 in 0311006 dv1_2 records the platform-shaped
authoring contract that follows from these three
properties.

15.13.2 SCOPE OF HTML CANONICAL FORMAT

HTML is the canonical format for controlled documents
that:
  (a) Contain at least one diagram (a figure rendered
      as a graphical asset, not pure prose), AND
  (b) Are authored as a SINGLE source-of-truth file
      under the §15 architecture, AND
  (c) Have a DocPath that identifies the document as
      a controlled instance under one of the AA
      domains.

Examples in scope: 0500000 System_Architecture_Overview
(dv1_24 onward); future Tier-2-and-below diagram-bearing
specs.

Examples NOT in scope: pure-prose controlled documents
(governance procedures, coding specs without diagrams,
session logs, NSIs). These remain .txt under the §15.2
through §15.12 architecture.

15.13.3 HTML CONTROLLED DOCUMENT FILENAME CONVENTION

The canonical HTML filename pattern is:

  [DCN]_[DocTitle]_[DocVersion]_Claude_Source.html

Where [DCN] is the 7-digit DCN, [DocTitle] is the
underscored title (no spaces), and [DocVersion] is the
lifecycle-prefixed version (dvN_M / rvN_M / vN_M /
rtN_M).

Example:
  0500000_System_Architecture_Overview_dv1_24_Claude_Source.html

The literal "_Claude_Source.html" suffix is REQUIRED.
This distinguishes the canonical source file from any
browser-saved or auto-renamed copies, and is the
filename signal used by 0311002 v1_10 §8.2.5
DC-PREFLIGHT-007 sub-check (f) HTML SCOPE.

No companion files are produced. There is no .docx
counterpart. There is no .pdf counterpart. There are no
external _svg.txt files. There are no external .png
files. The single .html file IS the document, the
diagrams, and the deliverable.

15.13.4 DC HEADER FOR HTML CONTROLLED DOCUMENTS

The 7-field DC header per §8 is rendered as an HTML
table near the top of the <body>:

  <header class="dc-header">
    <h1>[DocTitle]</h1>
    <table class="dc-meta">
      <tr><td>DocDCN</td><td>[7-digit DCN]</td></tr>
      <tr><td>DocTitle</td><td>[underscored title]</td></tr>
      <tr><td>DocVersion</td><td>[lifecycle+version]</td></tr>
      <tr><td>DocOwner</td><td>Bill</td></tr>
      <tr><td>DocPath</td><td>[GitHub.com/...]</td></tr>
      <tr><td>DocDate</td><td>[MM-DD-YYYY]</td></tr>
      <tr><td>DocTime</td><td>[HH:MM:SS UTC]</td></tr>
    </table>
  </header>

The DocPath field MUST end with "_Claude_Source.html".
The seven fields MUST appear in this exact order. Field
labels MUST match the §8.5 mandatory header field names
exactly.

15.13.5 INLINE DIAGRAM EMBEDDING

Diagrams in HTML controlled documents are inline <svg>
elements wrapped in a <figure class="diagram"> structure:

  <figure class="diagram">
    <div class="diagram-svg">
      <svg viewBox="0 0 W H" xmlns="http://www.w3.org/2000/svg">
        ...inline SVG content...
      </svg>
    </div>
    <figcaption>[caption text]</figcaption>
  </figure>

Pending-authoring diagrams use placeholder figures:

  <figure class="diagram diagram-placeholder">
    <div class="placeholder-box">
      <p class="placeholder-title">[Diagram N — Title]</p>
      <p class="placeholder-note">[pending-authoring note]</p>
    </div>
    <figcaption>[caption text]</figcaption>
  </figure>

V-037 in §15.7 governs figure-structure validation.

The structured-tag taxonomy defined in §15.11 and the
Asset-Tag Canonical Registry defined in §15.12 apply
unchanged to inline <svg> elements in HTML controlled
documents. Tags appearing in <title> and <desc>
elements inside the inline <svg> are subject to the
same V-032 / V-033 / V-034 / V-035 / V-036 validation
rules.

15.13.6 OVERRIDE OF EXTERNAL-ASSET ARCHITECTURE WITHIN
        HTML SCOPE

Within HTML controlled documents:

  - §15.2 FOUNDATIONAL PRINCIPLE — EXTERNAL ASSET FILES.
    Overridden. Inline <svg> IS the canonical embedding.
    The four reasons enumerated in §15.2 are addressed
    differently in HTML scope:
      (a) Source-of-truth. The single .html file IS the
          source-of-truth — no separate .txt to "mix"
          with binary content.
      (b) Rendering pipeline. The browser is the
          rendering pipeline. Inline <svg> is rendered
          natively by the DOM. No silent stripping
          failure mode (the ERROR-TB00149-02 root
          cause is structurally absent).
      (c) Asset reuse. Cross-document SVG reuse, when
          needed, is achieved by copying the inline
          <svg> element verbatim between documents.
          Both copies are first-class versioned content
          inside their host documents.
      (d) Asset versioning. The inline <svg> inherits
          the version of its host HTML document.
          Diagram-only revisions to a controlled
          document increment the host document's
          version per 0311003 versioning rules.

  - §15.3 ASSET TYPE TAXONOMY. Not applicable in HTML
    scope (no external asset files).

  - §15.4 ASSET STORAGE LOCATION. Not applicable.

  - §15.5 ASSET FILENAME CONVENTION. Not applicable.
    HTML controlled documents have only the host
    .html filename per §15.13.3.

  - §15.6 REFERENCE SYNTAX IN CONTROLLED DOCUMENTS.
    Not applicable. Inline <svg> is the embedding,
    not a reference.

  - §15.7 VALIDATION RULES. V-020 through V-036 do
    NOT apply (no external asset files to validate).
    V-037 DOES apply.

  - §15.8 RENDERING CONTRACT FOR DERIVED FORMATS. Not
    applicable. There are no derived formats.

  - §15.9 MIGRATION RULE. Reframed for HTML scope: any
    pre-HTML-adoption diagram-bearing document migrates
    to HTML by authoring a new .html source-of-truth
    file with inline <svg> diagrams, retiring the prior
    .txt + sidecar files via 0311002 cascade plan, and
    incrementing the parent document's DocVersion. The
    0500000 dv1_23 -> dv1_24 supersession is the
    reference migration.

  - §15.10 PROHIBITED PATTERNS. PP-1 (NO INLINE BINARY
    EMBEDS in .txt) is unaffected — it is a .txt-scope
    rule and HTML scope is outside its scope. CI-003 in
    TB00000 v2_20 carries the same HTML scope exception.

  - §15.11 ARCHITECTURE BLUEPRINT FRAMEWORK. Applies
    unchanged. Tier discipline, T-2+ tag taxonomy, and
    schema versioning all apply to inline <svg>
    elements in HTML controlled documents the same way
    they apply to standalone .svg files in non-HTML
    documents.

  - §15.12 ASSET-TAG CANONICAL REGISTRY. Applies
    unchanged. Registry entries are referenced by
    structured tags inside <title> and <desc> elements
    of inline <svg>, identical to the standalone .svg
    case.

15.13.7 DELIVERY VALIDATION

Per TB00000 v2_20 §4.1 DR-007 HTML scope amendment, an
HTML controlled document is delivered after passing the
six-step pre-delivery validation procedure with the HTML
scope substitutions:

  STEP 1 — DR-004 STRUCTURAL INTEGRITY.
    Skipped for HTML (text container, not binary).

  STEP 2 — DR-007 CONTENT COMPLETENESS — HTML SCOPE.
    DR-007.1 asset-reference parity: identity check
             (source <svg> count = rendered <svg>
             count = N, always 1:1).
    DR-007.2 section-heading parity: <h2> / <h3> tag
             count matches the document's section
             outline.
    DR-007.3 structural-marker parity: tags appearing
             inside the document text body are
             preserved (HTMLParser feed produces
             zero orphan closes).
    DR-007.4 word-count parity: extracted plain-text
             word count matches the source document
             body word count after subtracting
             enumerated transformations.
    DR-007.5 placeholder/stub scan: figures with class
             "diagram diagram-placeholder" are
             EXPECTED for not-yet-authored diagrams
             and are NOT a stub-substitution defect;
             other "stub" / "TODO" / "MISSING" tokens
             outside placeholder figures ARE flagged.
    DR-007.6 revision-history parity: <h2>REVISION
             HISTORY</h2> section contains every
             version entry from initial dv1_0 forward.

  STEP 3 — OP-003 PROHIBITED-STRING SCAN. Applies
           unchanged.

  STEP 4 — DR-005 CANONICAL NAMING — HTML SCOPE.
           Filename matches the §15.13.3 pattern with
           "_Claude_Source.html" suffix.

  STEP 5 — DR-003 BATCH ASSEMBLY. Applies unchanged.

  STEP 6 — DR-006 SINGLE-TURN DELIVERY. Applies
           unchanged.

15.13.8 SESSION-OPEN PRE-FLIGHT

Per 0311002 v1_10 §8.2.5:
  DC-PREFLIGHT-007 sub-check (f) HTML SCOPE applies
  the V-037 figure-structure identity-parity check.
  DC-PREFLIGHT-008 sub-check (d) HTML SCOPE skips
  binary-integrity checks (HTML is text container)
  and applies HTML well-formedness check (Python
  html.parser feed with zero orphan closes and
  zero unclosed elements at EOF) instead.

15.13.9 RECURRENCE PREVENTION

The HTML canonical format adoption is the architectural
fix for the underlying class of defects of which
ERROR-TB00149-02 SVG-DROP-IN-BINARY-GENERATION was one
instance. The defect class is "rendering-pipeline-
silently-loses-content-from-source." The HTML adoption
eliminates this class because:

  - There is no rendering pipeline (browser DOM is
    direct rendering, not transformation).
  - There is no source-vs-derived gap (single-format
    canonical).
  - There is no out-of-band asset reference to break
    (inline <svg> is the embedding, not a reference).

The OI-080 cumulative content-integrity violation
counter remains active for non-HTML controlled
documents (which retain the rendering-pipeline
exposure) but no further HTML-scope incidents are
expected.

15.14.1 PURPOSE

§15.14 establishes the namespace-level enforcement
of the diagrams-as-canonical-and-authoritative
principle codified at the project-instructions
level in TB00000 v2_23 §4.5 DD-001..DD-010. Where
§4.5 codifies the rule with absolute-standing-rule
treatment matching the §4.2 / §4.3 / §4.4
enforcement pattern (pre-emit scan + self-catch +
recurrence tracking), §15.14 binds the rule to the
0311001 namespace mechanics: diagram tag
taxonomy (§15.11.3), root <desc> contract
(§15.11.6), canonical registry (§15.12), and the
new V-038 validation rule (§15.7).

The principle: in any controlled document that
contains both diagram(s) and prose (currently the
single 0500000 System_Architecture_Overview HTML
controlled document; future Tier-2-and-below
diagram-bearing specs as authored), the
DIAGRAM(S) ARE THE AUTHORITATIVE source for all
architectural rules, contracts, decisions, gates,
layers, regimes, parameters, containers, modules,
indicators, events, channels, architectural
reasoning entries, and pt_mode identifiers. Prose
contextualizes the diagrams and explains them in
narrative form; prose does NOT govern. When prose
and diagram conflict, the diagram wins; prose is
updated to match the diagram, never the reverse.

15.14.3 DIAGRAM-OVER-PROSE AUTHORITY RULE

In every diagram-bearing controlled document
within the §15.14.2(a)-(b) scope, the following
authority hierarchy is in force:

  (1) The diagram(s) — the inline <svg> figures
      and their root <desc> elements, T-2+
      namespace-token labeled groups (per
      §15.11.3), structured key:value <desc>
      bodies (per §15.11.6), and visual content
      — are the AUTHORITATIVE source for every
      architectural rule, contract, decision,
      gate, layer, regime, parameter, container,
      mod, indicator, evt, channel, ar, and
      pt_mode element they encode.

  (2) Prose in the same document is NARRATIVE
      and EXPLANATORY. Prose contextualizes the
      diagram for the reader; prose does NOT
      establish architecture. Architectural
      content in prose is a derived restatement
      of what the diagram already encodes.

  (3) Where prose and diagram conflict, the
      DIAGRAM GOVERNS. Resolution is to update
      prose to match diagram. Updating diagram
      to match prose is PROHIBITED unless the
      prose-side change is itself driven by an
      antecedent diagram amendment (in which
      case the diagram-update rule per §15.11.6
      and §15.13 applies and the prose update
      is then consequential).

  (4) New architectural rules, contracts, etc.
      MUST first appear in the appropriate
      diagram element (root <desc> governs:
      list, labeled-group <desc>, or visual
      content as applicable). Prose introducing
      a new architectural rule WITHOUT a
      corresponding diagram element is a
      V-038.1 defect.

15.14.5 V-038 NEW VALIDATION RULE

V-038 (defined in §15.7 above) is the
diagram-prose authority parity validation rule.
At every controlled-document
authoring/amendment cycle, the document is

  (1) Enumerate every architectural identifier
      asserted in document prose
      (rule:/contract:/decision:/gate:/layer:/
      regime:/param:/container:/mod:/indicator:/
      evt:/channel:/ar:/pt_mode:).

      labeled group CANONICAL_NAME and every
      root <desc> governs: list entry across

  (3) Compute the symmetric difference. Each
      unmatched identifier surfaces as a V-038
      defect candidate per §15.7 V-038.1
      (prose-only) or V-038.3 (diagram-only).
      Each shared identifier with conflicting
      semantics surfaces as a V-038.2 defect
      candidate.

  (4) Defects are recorded in the Master
      Defect Register and resolved per §15.14.3
      (diagram governs).

(future 0311002 amendment) and at pre-delivery

DR-007.8 amendment-pending).

15.14.6 INTERACTION WITH §15.13 HTML CANONICAL
        FORMAT

§15.13 (HTML CANONICAL FORMAT FOR DIAGRAM-BEARING
DOCUMENTS) governs the FILE FORMAT of a diagram-
bearing controlled document — the document is a
single .html file with inline <svg> figures and
the "_Claude_Source.html" filename suffix. §15.14
governs the AUTHORITY HIERARCHY between diagram
and prose WITHIN that single .html file.

The two rules are complementary, not redundant:

  - §15.13 says: "the document is one .html
    file with inline diagrams" (the FORMAT).
  - §15.14 says: "within that one .html file,
    the diagrams govern over the prose" (the
    HIERARCHY).

A document can satisfy §15.13 (correct HTML
format) and still violate §15.14 (prose
asserting architecture not encoded in
diagrams). V-037 (§15.7) catches §15.13
violations; V-038 (§15.7) catches §15.14
violations. Both validation rules apply at
every diagram-bearing document amendment.

15.15.6 INTERACTION WITH §15.14 V-038

§15.14 V-038 covers diagram-vs-prose authority
parity (within-document and cross-document
relative to 0500000 canonical diagrams). §15.15
V-039 covers parent-citation completeness
(parent-specification references in the parent-
citation section vs body content). The two
rules are complementary:

  - V-038 catches: prose asserts architectural
    identifier not encoded in diagram.
  - V-039 catches: parent specification cited
    in body but absent from parent-citation
    section.

A document can pass V-038 (all architectural
identifiers encoded in diagrams) and still
fail V-039 (parent-citation section incomplete
relative to body content). Both rules apply at
every amendment cycle.

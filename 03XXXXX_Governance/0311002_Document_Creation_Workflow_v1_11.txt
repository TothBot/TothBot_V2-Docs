============================================================
1. PURPOSE
============================================================

This document defines the mandatory sequenced order in
which all TothBot V2 controlled documents must be created.
It is the authoritative work plan for building the complete
TothBot V2 document set from which the system will be coded.

Sequence is governed by four rules:

  RULE 1 — Domain dependency order.
  Lower AA domain documents must exist before higher AA
  domain documents can be written.

  RULE 2 — Tier dependency order within a domain.
  Domain Document before Sub-Domain Anchor. Anchor before
  Instance Documents in that sub-domain.

  RULE 3 — AA=10 coding spec timing is coupling-gated.
  No AA=10 Coding Specification may be written until its
  parent specification document (AA=04 through AA=08)
  is in approved (v) state, except for Working Draft (dv)
  coding specs created under the WD Exception below.

  WD EXCEPTION — Working Draft Coding Specs:
  Working Draft (dv) placeholder coding specifications may
  be created at any time to capture requirements from
  analysis, validation, or FP/DP sessions before their
  parent specification documents exist. WD coding specs
  carry a "Must be Included From Previous Analysis" section.
  They do not violate document control because they are
  working drafts that will be completed and approved only
  after their parent specifications are in approved (v)
  state. This exception prevents requirement loss.

  WD DOCUMENTS CREATED THIS SESSION (03-24-2026):

  Loosely coupled components (AA=10 concurrent with parent):

  All AA=03 Governance documents must reach approved (v)

  GATE 1 is passed. No exceptions.

STEP 8.2.1  CODE FILE REGISTRY — MANDATORY MAINTENANCE RULE
------------------------------------------------------------

1010000 Trading_System_Coding_Anchor Section 5 contains
the Code File Registry. This registry is the formal
controlled link between every Pathway 2 code file (.py)
and its governing AA=10 coding specification.

RULE — CODE FILE REGISTRY UPDATE IS MANDATORY:
After every session in which any Pathway 2 code file
in TothBot_V2-Code is created or modified, the Code
File Registry in 1010000 Section 5 MUST be updated
before the session closes. The registry must reflect:

  (1) The correct governing coding spec DCN and title
      for every code file.
  (2) The current version of the governing coding spec
      at the time of the code change.
  (3) The date of the registry update (UTC).

NOTE: Commit hashes are NOT tracked in the registry.
Git provides commit history natively via git log.
Requiring hash entries in 1010000 forced a second
TothBot_V2-Docs commit after every TothBot_V2-Code
commit — a circular maintenance defect with no
traceability benefit. Removed per TB00082.

Failure to update the Code File Registry before session
close is a document control violation — it breaks the
formal traceability chain between specifications and code.

This rule applies retroactively from Phase 8 start.
The Code File Registry was not created at Phase 8 start.
This is the corrective action establishing it formally.

STEP 8.2.5  STEP A — SESSION-OPEN PRE-FLIGHT VALIDATION
            MANDATORY RULE

Every session of Claude work on TothBot V2 begins with
STEP A pre-flight. STEP A is the formally-defined
session-open validation checkpoint. It runs before any
substantive work is performed in the session. Its
purpose is to detect and surface drift between the
session's authorized starting state (as defined by the
preceding session's NSI) and the actual observed state
of the work environment. Drift detected at STEP A
HALTS the session until resolved.

STEP A consists of three sequential checks. ALL three
MUST be executed before any substantive session work
begins. ANY check that fails halts the session.

------------------------------------------------------------
DC-PREFLIGHT-001  CHECK 1 — PROJECT-FOLDER EXPECTED-STATE
                  VALIDATION
------------------------------------------------------------

Claude executes a bash sweep of /mnt/project/ and
compares the observed file set to the KEPT and ABSENT
lists defined in the preceding NSI's project-folder
expected-state section (DC-CLEANUP-006 paragraph (a)
and (b)).

Required validation:

  (a) Every file in the NSI KEPT list MUST be present
      in /mnt/project/. Missing KEPT files indicate
      Bill's post-session upload step did not complete
      (DC-SYNC-002 violation) or files were
      inadvertently removed.

  (b) No file in the NSI ABSENT list MAY be present
      in /mnt/project/. Lingering ABSENT files
      indicate Bill's post-session removal step did
      not complete (cleanup workflow incomplete per
      DC-CLEANUP-005).

  (c) Files present in /mnt/project/ but neither in
      KEPT nor ABSENT lists are FLAGGED as unexpected
      drift. They do not necessarily halt the session,
      but Claude reports them and asks Bill to confirm
      whether they should be in the KEPT list.

  (d) The DC-CLEANUP-002 MUST-PRESERVE set (TB00001,
      TB00012, TB00013, TB00014, TB00020) is checked
      independently of the NSI lists. Any MUST-PRESERVE
      file missing from /mnt/project/ HALTS the
      session immediately and is recovered from GitHub
      archive before any other work proceeds.

TB00121) — three consecutive DC packages (TB00118,
TB00119, TB00120) had pending post-session Bill

DC-PREFLIGHT-003  CHECK 3 — NSI CODE-EDIT-LIST
                  VALIDATION AGAINST DEPLOYED CODE
------------------------------------------------------------

When the preceding NSI specifies code edits to be
performed in the upcoming session (per any STREAM,
work item, or task that names a target file and
specific line numbers, snippets, or edit
descriptions), Claude MUST validate the edit list
against the actual deployed code at session open
BEFORE applying any edit.

Required validation steps:

  (a) For each NSI-specified target file, read the
      file from the local working tree at the path
      identified in the NSI.

  (b) For each NSI-specified edit (line number,
      pre-edit snippet, or condition), verify the
      edit is still applicable as written. Common
      drift conditions:
        - Line numbers shifted due to upstream edits.
        - Pre-edit snippet text changed.
        - Edit already applied in a prior session.
        - Multiple instances of the pre-edit snippet
          exist where NSI assumes one.

  (c) For each NSI-specified edit, scan the WHOLE
      file for additional sites that match the
      same edit pattern. The NSI edit list is
      treated as a starting point, NOT an exhaustive
      enumeration. Pattern: NSI-author may have
      enumerated some sites and missed others;
      pattern-match across the full file before
      applying.

  (d) For NSI-specified validation gates (e.g., "grep
      X must return zero hits", "py_compile must
      pass"), verify the gate semantics are
      achievable given the actual file state. A gate
      that requires zero hits of a token cannot pass
      if the NSI edit list omits sites where the
      token appears.

DRIFT HANDLING:

  Case 1 — Edit list complete and accurate:
    Proceed with edits as NSI-specified.

  Case 2 — Edit list incomplete (additional sites
           found via pattern match):
    HALT before any edit applied. RR-SCOPE-007 self-
    catch fires. Report the additional sites to Bill
    and request explicit scope authorization (full
    enforcement OR NSI-literal partial enforcement OR
    halt for NSI amendment).

  Case 3 — Edit list inaccurate (line numbers wrong,
           snippet text drifted, edit already
           applied):
    HALT before any edit applied. Report the drift
    to Bill and request direction (resync to actual
    state OR halt for NSI amendment).

  Case 4 — Validation gate unachievable with NSI
           edit list:
    HALT before any edit applied. Report the gate
    impossibility to Bill. This is the same class as
    Case 2 — NSI under-enumerated edit sites.

ROOT CAUSE ADDRESSED:

three-edit list for ws_manager.py dv1_24 was carried
forward verbatim through TB00136 NSI §4 -> TB00137
NSI §1 -> TB00138 NSI §1 -> TB00139 NSI §1 without
re-validation against deployed code. Three additional
edit sites (L3098, L3165, L3168) were never
enumerated. Claude Code self-caught the gap at
STREAM 1 open, halted, and requested Bill direction
before applying any edit. Bill authorized the
six-site fix. Without DC-PREFLIGHT-003 as a formal
mandatory rule, the next NSI carry-forward of an

This check supplements TB00000 v2_15 §4.3.1
RR-SCOPE-007 (no silent narrowing of user-specified
scope) by establishing a procedural pre-flight

DC-PREFLIGHT-006  PRE-DEPLOY RATE-LIMIT AND RESOURCE-
                  ENVELOPE IMPACT ANALYSIS
------------------------------------------------------------

Rate-limit and resource-envelope impact analysis
required before deploy of any code change that
modifies the exchange-API traffic profile.

DC-PREFLIGHT-006 is distinct from DC-PREFLIGHT-001
through DC-PREFLIGHT-005 in trigger and timing.
DC-PREFLIGHT-001 through DC-PREFLIGHT-005 fire at
session open and gate session work. DC-PREFLIGHT-006
fires at pre-deploy of a specific code change and
gates deploy. Both families are pre-action checks;
they are not redundant and they do not substitute
for each other.

SCOPE TRIGGER. This pre-flight check fires when any
pending code change affects, directly or indirectly,
any of the following:

  (a) Number of WS connections opened or held.
  (b) Number of WS subscribes issued, or the
      rate at which subscribes are issued.
  (c) Number of REST requests issued, or their
      rate.
  (d) Number of channels subscribed per
      connection.
  (e) Universe size, symbol set, or pair filter
      passed to the WS manager.
  (f) Reconnect cadence, retry policy, or
      backoff strategy on either WS or REST.
  (g) Any timer, polling interval, or scheduling
      cadence affecting exchange-API traffic.

When the trigger fires, the change MUST NOT be
deployed to the VPS until the five-question
rate-limit and resource-envelope analysis below
is documented in the relevant session log,
Architectural Decision Record, or spec
amendment.

THE FIVE QUESTIONS.

  Q1  TRAFFIC PROFILE.
      What quantitative traffic profile does
      the change introduce? Required:
        - Connections held (count).
        - Subscribes per second peak (count/s).
        - Subscribes per session (count).
        - REST requests per minute (count/min).
        - Steady-state inbound message rate
          (msg/s aggregate; msg/s per
          connection).
      Numerical answers required. Adjectives
      ("low", "modest", "comparable to before")
      do not satisfy Q1.

  Q2  EXCHANGE LIMIT.
      What is the documented exchange-side limit
      for each traffic axis named in Q1?
      Citation to specification document
      required (0411001, 0411002, or upstream
      Kraken documentation with retrieval date).
      Adjectives do not satisfy Q2.

  Q3  UTILIZATION AND MARGIN.
      For each traffic axis, compute:
        utilization = (Q1 value) / (Q2 limit)
        margin      = 1 - utilization
      Margin must be at minimum 25% on every
      axis under steady-state, and at minimum
      50% on every axis under burst conditions
      (subscribe storm, reconnect storm,
      universe re-evaluation). If any axis
      fails margin, deploy is BLOCKED until
      the change is revised to meet margin or
      the change is FP/DP-justified to Bill
      with explicit margin-waiver.

  Q4  EMPIRICAL VALIDATION.
      What empirical evidence demonstrates the
      calculated traffic profile matches reality
      under the change? Required: citation to a
      probe run, long-window test, paper-trading
      observation, or other measurement that
      confirms Q1 numbers. If no such evidence
      exists, the change requires probe-run-
      before-deploy unless Bill explicitly
      waives the empirical-validation
      requirement.

  Q5  ROLLBACK PLAN.
      If the deploy produces a rate-limit storm
      or other traffic anomaly despite Q1-Q4
      clearing, what is the detection mechanism
      and what is the rollback procedure?
      Required:
        - Detection: which log, alert, or metric
          surfaces the anomaly within X minutes.
        - Rollback: exact command sequence
          (typically `git revert <hash> &&
          systemctl restart tothbot`) and
          elapsed time from detection to bot
          restored.

PRE-DEPLOY GATE. Pre-commit blocking is not
required. Authoring and review cycles in

friction. The gate fires before VPS `git pull`

DC-PREFLIGHT-009  PRE-AMENDMENT CASCADE-CURRENCY-CHECK
------------------------------------------------------------

Cascade-currency-check required before authoring any
amendment to a controlled specification that is cited
by version, by tagged element identifier, or by content
reference in any downstream specification.

DC-PREFLIGHT-009 is distinct from DC-PREFLIGHT-001
through DC-PREFLIGHT-008 in trigger and timing.
DC-PREFLIGHT-001 through DC-PREFLIGHT-005 fire at
session open and gate session work. DC-PREFLIGHT-006
fires at pre-deploy of a specific code change and
gates deploy. DC-PREFLIGHT-007 and DC-PREFLIGHT-008
fire at session open and gate asset-inventory and
binary-content state. DC-PREFLIGHT-009 fires at
pre-authoring of a specific specification amendment
and gates the authoring action. All families are
pre-action checks; they do not substitute for each
other.

SCOPE TRIGGER. This pre-flight check fires when any
pending amendment to a controlled specification
affects, directly or indirectly, any of the
following:

  (a) The parent specification's version is cited
      by version number in any downstream
      specification's Parent Chain, Governing
      Documents, Architectural Authority, or
      cross-reference section.

  (b) An architectural authority element (AR-XXX,
      D-XX Ratified Decision, HR-XX-NNN, contract
      identifier, gate identifier, parameter
      identifier, container/module/indicator/event/
      channel/regime/layer/pt_mode tag) introduced,
      modified, or retired by the amendment has
      consumers in downstream specifications.

  (c) A parameter value, hard rule, or behavioral
      contract defined in the parent specification
      is replicated or referenced in downstream
      specifications (replication-by-citation
      pattern).

When the trigger fires, the amendment MUST NOT be
authored to its target version until the four-
question cascade analysis below is documented in
the relevant session log, amendment cover note,
or Architectural Decision Record.

THE FOUR QUESTIONS.

  Q1  CONSUMER IDENTIFICATION.
      Which controlled specifications cite the
      about-to-be-amended specification? Required:
      enumeration of every consuming spec by DCN +
      current version + citation location
      (§-number or §-name). Sources to consult:
      0311001 §15.12 tagged-element registries
      (rule:, contract:, ar:, decision:, gate:,
      layer:, regime:, pt_mode:, param:,
      container:, mod:, indicator:, evt:, channel:);
      Parent Chain sections of downstream specs;
      Architectural Authority sections; cross-
      reference indexes. Adjectives ("a few",
      "several downstream") do not satisfy Q1.

  Q2  CASCADE SCOPE.
      For each consumer identified in Q1, classify
      the cascade requirement:
        (a) CASCADE — consumer requires a semantic
            amendment in the same authoring action
            or an immediately-sequenced follow-up.
            Example: parent amends a hard rule that
            the consumer cites and depends on.
        (b) VERSION-CITATION REFRESH — consumer
            requires only a version-number refresh
            in its citation; no semantic change.
            Example: parent version bump from
            dv1_N to dv1_N+1 with no consumer-
            visible change beyond the citation.
        (c) NO CASCADE — consumer's citation is
            robust to the amendment. Example:
            consumer cites a different aspect of
            the parent that the amendment does
            not touch.
      Classification per consumer required.
      Ambiguous classifications default to
      CASCADE pending Bill review.

  Q3  SEQUENCING DECISION.
      For each consumer classified CASCADE or
      VERSION-CITATION REFRESH in Q2, name the
      sequencing plan:
        (a) SAME-SESSION CASCADE — consumer
            amended in the same session as the
            parent under the one-document-per-turn
            rule (separate turn).
        (b) NEXT-SESSION CASCADE — consumer
            amended in the immediately-following
            session with explicit NSI carry-
            forward citing this rule.
        (c) DEFERRED CASCADE — consumer amendment
            deferred to a named future phase or
            session with NSI carry-forward AND
            Open Item tracking. Deferral requires
            Bill explicit authorization.

  Q4  RECORD KEEPING.
      Where will the cascade decisions from Q1-Q3
      be recorded? Required: citation to the
      session log section, amendment cover note,
      or NSI carry-forward block where the
      analysis is logged. The record MUST
      identify each consumer by DCN, classify it
      per Q2, and name its sequencing per Q3.
      Records purely in chat without persistence
      to a controlled document do not satisfy Q4.

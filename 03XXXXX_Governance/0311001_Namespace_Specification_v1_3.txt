NAMESPACE SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document defines the complete namespace model for
TothBot V2. It governs how Document Control Numbers (DCNs)
are assigned, interpreted, and validated across all
controlled documents in the TothBot V2 document control
system.

This is a clean-slate specification. It shares no legacy
constraints with any prior TothBot namespace. All decisions
in this document are derived from first principles using
FP/DP analysis. Where this document conflicts with any
prior TothBot namespace document, this document governs.

============================================================
2. SCOPE
============================================================

This specification applies to ALL controlled documents and
code files in the TothBot V2 system, across BOTH repositories:

  TothBot_V2-Docs (github.com/TothBot/TothBot_V2-Docs)
    Scope: All specification and governance documents.
    File format: .txt (Claude project compatible).
    DC header format: Standalone 7-field header block.

  TothBot_V2-Code (github.com/TothBot/TothBot_V2-Code)
    Scope: All trading system code, operational support
    scripts, configuration files, and deployment files in
    the trading system repository.
    File format: .py, .sh, .txt, .ini, .service, and others.
    DC header format: 7-field header embedded as a comment
    block at the top of each file, using the file's native
    comment syntax (# for Python and bash, etc.).

HR-DC-001  ALL files in TothBot_V2-Code are controlled
           documents. There are no uncontrolled files
           in TothBot_V2-Code.

HR-DC-002  Every file in TothBot_V2-Code MUST have a
           7-field DC header. This is not optional.
           Missing or malformed headers are document
           control violations.

HR-DC-003  Every file in TothBot_V2-Code MUST be
           registered in 1010000 Section 5 Code File
           Registry. Unregistered files are violations.

HR-DC-004  Every file in TothBot_V2-Code MUST have a
           Revision History section in comment format.

Corrective action: This scope expansion corrects the
governance gap documented in TB00079 where the scope
limitation to TothBot_V2-Docs only was found to be
incorrect and was causing document control violations.

Any document outside both repositories is an uncontrolled
working copy and has no governing authority.

This specification does not apply to TothBot-Docs or
TothBot-Code (the original TothBot system). Those
repositories are permanent read-only archives governed
by their own namespace.

4. DCN STRUCTURE
============================================================

All DCNs follow the format: AABCDDD

  AA  = Domain (2 digits, 00–11)
  B   = Sub-Domain level (1 digit, 0–9)
  C   = Instance level (1 digit, 0–1)
  DDD = Sequential instance number within sub-domain

------------------------------------------------------------
4.1 DOCUMENT TIER DEFINITIONS
------------------------------------------------------------

  Tier 1 — Domain Document (B=0, C=0, DDD=000)
    IS the domain. One per domain. Anchors all sub-domains.
    Example: 0300000 Governance

  Tier 2 — Sub-Domain Anchor (B=1-9, C=0, DDD=000)
    Anchors a governance family to its Domain Document.
    Example: 0310000 Governance_Procedures_Anchor

  Tier 3 — Instance Document (B=1-9, C=1, DDD=001+)
    Elaborates one specific component within the sub-domain.
    Example: 0311001 Namespace_Specification

------------------------------------------------------------
4.2 PARENT CHAIN RULE
------------------------------------------------------------

Every document must have an unbroken parent chain:

  Instance → Sub-Domain Anchor → Domain Document

The parent chain must be explicitly declared in every
document's Section 2 (Parent Chain). No document may be
committed to GitHub without its complete parent chain
already committed.

5. CODE FILE DOCUMENT CONTROL HEADER FORMAT
============================================================

Code files and operational scripts in TothBot_V2-Code are
controlled documents. They use the same 7-field header as
TothBot_V2-Docs documents, embedded as a comment block at
the top of the file.

------------------------------------------------------------
5.1 MANDATORY CODE FILE HEADER FORMAT
------------------------------------------------------------

For Python files (.py) and bash scripts (.sh):

  # DocDCN:     [DCN of governing AA=10 coding spec]
  # DocTitle:   [Descriptive_File_Title_Underscores]
  # DocVersion: [dv/rv/v + major_minor, e.g., dv1_0]
  # DocOwner:   [Bill]
  # DocPath:    [github.com/TothBot/TothBot_V2-Code/path]
  # DocDate:    [MM-DD-YYYY]
  # DocTime:    [HH:MM:SS UTC, 24-hour]

For non-Python files (.ini, .txt, .service, etc.):
  Use the file's native comment syntax.
  If no comment syntax exists, place the header as the
  first 7 lines of the file in the same key: value format.

The header MUST appear on the first lines of every file.
For bash scripts, the header follows the shebang line
(#!/usr/bin/env bash) — the shebang MUST be line 1.
No code, imports, or content may precede the header block
(beyond the shebang for bash scripts).

------------------------------------------------------------
5.2 CODE FILE HEADER FIELD RULES
------------------------------------------------------------

DocDCN:
  References the governing AA=10 coding specification DCN.
  For files governed by Engineering_Best_Practices: 1011001.
  For component .py files: the DCN of their governing spec
  (e.g., ws_manager.py → 1011002 WS_Manager_Coding_Spec).
  For operational scripts: the DCN of their governing
  operational-scripts coding spec (TBD in AA=10
  Sub-Domain 1 Operations).

DocTitle:
  Descriptive title of the file or configuration.
  Underscores only. No spaces.
  Example: Git_Ignore_Configuration, WS_Manager,
  TothBot_Sweep_Script.

DocPath:
  Full path in the repository:
  github.com/TothBot/TothBot_V2-Code/[relative/path/file]
  NOT the VPS deploy path. NOT the local Windows path.

DocVersion:
  Follows the same rules as all controlled documents.
  Starts at dv1_0. Increments on every change.

------------------------------------------------------------
5.3 CODE FILE REVISION HISTORY REQUIREMENT
------------------------------------------------------------

Every code file MUST include a Revision History section
in comment format. Format:

  # ============================================================
  # REVISION HISTORY
  # ============================================================
  #
  #   dv1_0  MM-DD-YYYY  Initial. [brief summary]
  #   dv1_1  MM-DD-YYYY  [what changed]

The Revision History grows with the file. No entry is
ever removed. The complete change history is retained.

document defines the namespace-level rules. 1011001

============================================================
9. LIFECYCLE STATES
============================================================

Every document exists in exactly one lifecycle state.
The state is encoded in DocVersion.

  dv  — Draft Version
        Active development. Under constant review. Bill may
        approve directly (dv → v). Not yet authoritative.
        Example: dv1_0, dv1_1, dv2_0

  rv  — Revision Version
        An approved document requiring changes returns to
        rv state. Not used for initial document development.
        Bill re-approves after revision is complete.
        Example: rv1_0

  v   — Approved Version
        Bill-approved. Authoritative. Governs the system.
        Changes require v → rv before returning to v.
        Example: v1_0, v2_0

  rt  — Retired
        No longer authoritative. Moved to _Archive/.
        DCN permanently reserved. Never reused.
        Example: rt1_0

State transitions:
  dv → v   (Bill approves working draft directly)
  v  → rv  (approved document requires changes)
  rv → v   (Bill re-approves after revision)
  v  → rt  (document retired)

============================================================
10. VERSIONING
============================================================

Version numbers follow the pattern: state + major_minor

  dv1_0   First draft, first minor version
  dv1_1   First draft, second minor version
  rv1_0   Review of first major version
  v1_0    First approved version
  v2_0    Second approved version (major revision)

Minor version: corrections, clarifications, additions
that do not change scope or governing decisions.

Major version: changes to scope, governing decisions,
structural changes, or any change requiring full
re-approval.

Every change increments the version. No exceptions.

11. DCN ASSIGNMENT RULES
============================================================

11.1 Assignment Authority
Only Bill may assign DCNs. DCNs are registered in this
document (Section 12) at the time of assignment. A
document cannot exist without a registered DCN.

11.2 Assignment Sequence
Within any sub-domain, Instance Document DCNs are
assigned sequentially from DDD=001. The next available
DDD is the only valid choice. DCNs are not pre-reserved.

11.3 Permanent Reservation
Once assigned, a DCN is permanently associated with that
document title. Retired document DCNs are permanently
reserved and may never be reassigned.

15. DIAGRAM ASSET SPECIFICATION
============================================================

------------------------------------------------------------
15.1 Why Diagrams Are Separate Files
------------------------------------------------------------

Controlled documents are stored as .txt files (Claude
project folder compatible format). Binary image formats
cannot be embedded in .txt files. SVG files provide
structured vector graphics storable as text alongside
the parent document.

------------------------------------------------------------
15.2 Diagram Storage Location
------------------------------------------------------------

Each diagram asset is stored in the SAME folder as its
parent controlled document in TothBot_V2-Docs.

Example: 0500000 diagrams live in 05XXXXX_System_Architecture/.

------------------------------------------------------------
15.3 Diagram Filename Convention
------------------------------------------------------------

  [ParentDCN]_Diagram[N]_[ShortTitle].svg

Example:
  0500000_Diagram1_Kraken_API_Connection_Architecture.svg
  0500000_Diagram2_Trading_Pipeline.svg

A document that references a diagram that does not exist
as an SVG file is incomplete.

------------------------------------------------------------
15.4 Referencing Diagrams in Controlled Documents
------------------------------------------------------------

Within a .txt controlled document, each diagram is
referenced by its exact filename:

  [Diagram file: 0500000_Diagram1_Kraken_API_Connection_Architecture.svg]

------------------------------------------------------------
15.5 Validation Rules for Diagram Assets
------------------------------------------------------------

  V-020  Diagram asset filename begins with parent DCN
  V-021  Diagram asset uses .svg extension
  V-022  Diagram asset lives in same folder as parent doc
  V-023  Every diagram reference in a .txt document has
         a corresponding SVG file in the folder
  V-024  Diagram N+1 does not exist without Diagram N
         for the same parent DCN

NAMESPACE SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document defines the complete namespace model for
TothBot V2. It governs how Document Control Numbers (DCNs)
are assigned, interpreted, and validated across all
controlled documents in the TothBot V2 document control
system.

This is a clean-slate specification. It shares no legacy
constraints with any prior TothBot namespace. All decisions
in this document are derived from first principles using
FP/DP analysis. Where this document conflicts with any
prior TothBot namespace document, this document governs.

============================================================
2. SCOPE
============================================================

This specification applies to all controlled documents
stored in the TothBot V2 GitHub repository
github.com/TothBot/TothBot_V2-Docs.

Any document outside this repository is an uncontrolled
working copy and has no governing authority.

This specification does not apply to TothBot-Docs or
TothBot-Code (the original TothBot system). Those
repositories are permanent read-only archives governed
by their own namespace.

============================================================
4. DCN FORMAT
============================================================

All Document Control Numbers follow this deterministic
7-digit structure:

  AA B C DDD

  AA  = Major Domain (00-11, always two digits)
  B   = Tier designation (0-9)
  C   = Document category (0-1)
  DDD = Specific document number (000-999)

This format is fixed. No exceptions. All seven positions
are always present. Leading zeros are always included.

Examples:
  0500000 = AA=05, B=0, C=0, DDD=000
  0531001 = AA=05, B=3, C=1, DDD=001
  1101001 = AA=11, B=1, C=1, DDD=001

============================================================
5. THREE-TIER DOCUMENT HIERARCHY
============================================================

TothBot V2 uses a three-tier document hierarchy. Every
controlled document belongs to exactly one tier. Tier
membership is determined entirely by the B and DDD
positions of the DCN.

The traceability chain is mandatory and unbroken:

  Instance Document
    → Sub-Domain Anchor
      → Domain Document

No document may exist without a complete unbroken chain
to its Domain Document. This is quality built in.

------------------------------------------------------------
5.1 TIER 1 — Domain Document
------------------------------------------------------------

DCN pattern:  AA 0 0 000
              (B=0, C=0, DDD=000)

There is exactly one Domain Document per domain.
It is identified by B=0 and DDD=000.

B=0 is categorically distinct from B=1 through 9.
B=0 is not a sub-domain. It is the domain level itself.
A Domain Document at B=0 IS the domain expressed as a
controlled document. It does not introduce the domain.
It does not summarize the domain. It defines the domain
in its entirety at the framework level.

A Domain Document must be complete enough that a reader
fully understands the entire domain — its purpose, scope,
governing principles, and the structure of all documents
within it — without reading any Sub-Domain Anchor or
Instance Document.

Sub-Domain Anchors and Instance Documents elaborate
specific components that the Domain Document defines.
They do not define things the Domain Document left
undefined. If a Sub-Domain Anchor defines something not
traceable to the Domain Document, the Domain Document
is incomplete and must be updated first.

Test: Can every Instance Document in the domain trace
its existence to something already defined in the Domain
Document? If yes, the Domain Document is complete.
If no, it is not.

Domain Documents are the most stable documents in the
system. They change only when the domain itself changes
in fundamental scope or purpose.

------------------------------------------------------------
5.2 TIER 2 — Sub-Domain Anchor
------------------------------------------------------------

DCN pattern:  AA B 0 000
              (B=1 through 9, C=0, DDD=000)

There is exactly one Sub-Domain Anchor per sub-domain.
It is identified by B=1 through 9, C=0, and DDD=000.

A Sub-Domain Anchor defines a specific governance family
within the domain. It must trace explicitly back to the
Domain Document — stating which section or principle of
the Domain Document it elaborates.

A Sub-Domain Anchor governs all Instance Documents
within its sub-domain. No Instance Document may exist
in a sub-domain without a Sub-Domain Anchor.

A new sub-domain is created only when a new governance
family requires its own Anchor. Sub-domains are not
created for organizational convenience.

Sub-domains within a domain are numbered sequentially
B=1, B=2, B=3 as they are created. Numbers are not
pre-reserved. B=0 is permanently reserved for the
Domain Document.

------------------------------------------------------------
5.3 TIER 3 — Instance Document
------------------------------------------------------------

DCN pattern:  AA B 1 DDD
              (B=1 through 9, C=1, DDD=001 through 999)

Instance Documents elaborate a specific component
defined by the Sub-Domain Anchor of their sub-domain.
They must trace explicitly back to their Sub-Domain
Anchor.

DDD=000 is permanently reserved for Anchor Documents
at all tiers. Instance Documents use DDD=001 through
999 assigned sequentially as documents are created.
Numbers are not pre-reserved.

------------------------------------------------------------
5.4 TIER DETERMINATION QUICK REFERENCE
------------------------------------------------------------

  B=0, C=0, DDD=000    → Domain Document (Tier 1)
  B=1-9, C=0, DDD=000  → Sub-Domain Anchor (Tier 2)
  B=1-9, C=1, DDD=001+ → Instance Document (Tier 3)

  B=0 with DDD=001+ is invalid.
  B=0 with C=1 is invalid.
  DDD=000 with C=1 is invalid.

6. DOMAIN DEFINITIONS
============================================================

TothBot V2 uses 11 domains, AA=00 through AA=11.

Domains are ordered by dependency. A domain with a lower
AA number must be defined before a domain with a higher
AA number can function. This ordering is not arbitrary.
It reflects the logical dependency chain of the system.

------------------------------------------------------------
AA=00  Ethics_and_Safety
------------------------------------------------------------

Constrains the entire system including operator authority.
No domain, no document, no decision, no code can override
an ethics or safety principle. Exists before everything.
Has no dependencies.

Domain Document: 0000000_Ethics_and_Safety

------------------------------------------------------------
AA=01  Management
------------------------------------------------------------

Defines who governs, who decides, who approves, and who
is accountable for what. In a Deming system, authority
and responsibility are inseparable — whoever has the
authority owns the responsibility. Management is the
domain that defines these assignments.

Must exist before any governance procedure can function.

Depends on: AA=00

Domain Document: 0100000_Management

------------------------------------------------------------
AA=02  Operations
------------------------------------------------------------

In TothBot V2, Operations is not a procedural domain
describing how to run the system. Operations IS the
system's quality mechanism, continuous improvement
engine, and CIATS implementation — unified into one
domain.

This reflects Deming's core principle: quality is not
inspected in. It is not audited in. It is built into
the operating system itself. The way TothBot V2 operates
and the way it continuously improves are not two separate
things. They are one thing.

AA=02 Operations contains:
  - The quality standard the system must meet
  - The PDCA cycle that continuously improves it
  - CIATS — its data streams, statistical engine,
    parameter ownership model, and improvement workflows
  - Operational procedures for startup, shutdown,
    monitoring, and incident response
  - The Deming principles as operationalized in TothBot V2

There is no separate Quality domain. There is no
separate CIATS domain. Operations = Quality = CIATS.
They are one domain because they are one thing.

Depends on: AA=00, AA=01

Domain Document: 0200000_Operations

------------------------------------------------------------
AA=03  Governance
------------------------------------------------------------

Document control, namespace, versioning, change control,
records management. The procedural machinery that manages
the document system itself. Governance operates within
the quality standard defined by AA=02 Operations.

Depends on: AA=00, AA=01, AA=02

Domain Document: 0300000_Governance

------------------------------------------------------------
AA=04  Exchange_Interface
------------------------------------------------------------

The verified, controlled interface contract between
TothBot V2 and the exchange it operates on. In V2
this is Kraken Spot.

AA=04 is a V2 structural innovation. In prior versions,
exchange interface knowledge was scattered across system
and coding documents with no authoritative controlled
source. AA=04 creates a first-class domain for the
verified exchange interface.

AA=04 must be defined before system design (AA=05)
because TothBot V2 is designed to the interface — not
the other way around. If the exchange changes, AA=04
updates first and all downstream documents follow.

AA=04 also makes TothBot V2 exchange-portable in
principle: replacing AA=04 with a different exchange
interface does not require touching AA=05 through AA=11.

Depends on: AA=00 through AA=03

Domain Document: 0400000_Exchange_Interface

------------------------------------------------------------
AA=05  System_Architecture
------------------------------------------------------------

The complete technical architecture of TothBot V2 as
a three-system organism: Kraken (event source), TothBot
(event processor), and CIATS (improvement engine).

AA=05 defines every component, every data flow, every
connection point, and every design decision. It is
designed to the exchange interface contract in AA=04.

The Domain Document 0500000 is the TothBot V2 System
Architecture Overview produced in the March 2026
architecture sessions. It defines the organism in full
at the framework level.

Depends on: AA=00 through AA=04

Domain Document: 0500000_System_Architecture_Overview

------------------------------------------------------------
AA=06  Risk
------------------------------------------------------------

Risk rules, risk framework, parameter definitions,
drawdown rules, concentration limits, exposure limits,
circuit breakers, and position sizing rules.

AA=06 defines what parameters exist and what they
govern. CIATS (in AA=02) owns the parameter values.
AA=06 owns the risk framework within which those values
operate.

The only value not owned by CIATS is the net 1:1.5 R:R
constraint. This is hardcoded in AA=06. It is the only
permanent risk constraint in TothBot V2.

Depends on: AA=00 through AA=05

Domain Document: 0600000_Risk

------------------------------------------------------------
AA=07  Strategy
------------------------------------------------------------

Trading strategy: SSS signal generation model, regime
taxonomy and classification, asset selection criteria,
and the signal quality framework. Strategy operates
within the risk constraints defined in AA=06.

Depends on: AA=00 through AA=06

Domain Document: 0700000_Strategy

------------------------------------------------------------
AA=08  Trading_System
------------------------------------------------------------

The trading system implementation: Long Module, Exit
Controller (three-layer Kraken-native design), Selection
Controller, and Execution Engine. Implements AA=07
strategy within AA=06 risk constraints using the AA=04
exchange interface.

Renamed from Trading_Modules (prior system) because the
components are an integrated system with defined
interactions, not independent modules.

Depends on: AA=00 through AA=07

Domain Document: 0800000_Trading_System

------------------------------------------------------------
AA=09  Plans
------------------------------------------------------------

The Master Plan and Business Plan are the two synthesizing
documents for TothBot V2. They share one domain because
both are synthesizing documents — not operational or
technical — and neither will ever spawn a governance
family requiring its own sub-domain hierarchy.

Merging them into one Plans domain eliminates two sparse
single-document domains and keeps the namespace tight.

Sub-Domain 1 contains the Master Plan — the complete
integrated synthesis of all domains AA=00 through AA=08.
Written after all substantive domains are defined.

Sub-Domain 2 contains the Business Plan — the commercial
and financial context of TothBot V2. Built on the
Master Plan.

Depends on: AA=00 through AA=08

Domain Document: 0900000_Plans

------------------------------------------------------------
AA=10  Coding_Specification
------------------------------------------------------------

Translates all substantive domains into explicit,
unambiguous coding contracts. AA=10 is the direct input
to code. Every component defined in AA=04 through AA=08
has a corresponding AA=10 coding specification.

AA=10 has two completely independent pathways:

  Pathway 1 — GitHub Document Control Automation
    Runs in GitHub Actions on TothBot_V2-Docs.
    Never runs on the VPS.

  Pathway 2 — TothBot Trading System
    Runs on the VPS.
    Never runs in GitHub Actions.

Pathway separation is validated at every coding session.
Cross-pathway contamination is a defect requiring
immediate correction before coding continues.

Depends on: AA=00 through AA=09

Domain Document: 1000000_Coding_Specification

------------------------------------------------------------
AA=11  Compliance
------------------------------------------------------------

Audits and validates everything. Compliance can only
audit what already exists. Defined last because it
audits the complete system.

Depends on: AA=00 through AA=10

Domain Document: 1100000_Compliance

7. FOLDER STRUCTURE
============================================================

AA determines the top-level folder in TothBot_V2-Docs.
Folder names always use the two-digit AA prefix followed
by XXXXX representing the remaining 5 DCN digit positions.
This makes folder-to-DCN mapping visually unambiguous:
any 7-digit DCN beginning with AA belongs in the
corresponding AA folder.

  00XXXXX_Ethics_and_Safety/
  01XXXXX_Management/
  02XXXXX_Operations/
  03XXXXX_Governance/
  04XXXXX_Exchange_Interface/
  05XXXXX_System_Architecture/
  06XXXXX_Risk/
  07XXXXX_Strategy/
  08XXXXX_Trading_System/
  09XXXXX_Plans/
  10XXXXX_Coding_Specification/
  11XXXXX_Compliance/
  _Archive/

Structure within each domain folder is flat. No
sub-folders. The DCN encodes all hierarchy — sub-domain
information is in position B of the DCN. Adding sub-
folders would redundantly duplicate information already
present in the filename.

_Archive/ contains all retired documents regardless of
original domain. Underscore prefix ensures it sorts
last in all directory listings.

8. DOCUMENT HEADER
============================================================

Every controlled document must begin with the exact
seven-field header in this exact order:

  DocDCN:     [7-digit DCN, format AABCDDD]
  DocTitle:   [Underscores only, no spaces]
  DocVersion: [lifecycle state + version, e.g. dv1_0]
  DocOwner:   [Bill]
  DocPath:    [GitHub.com/TothBot/TothBot_V2-Docs/folder/file]
  DocDate:    [MM-DD-YYYY]
  DocTime:    [HH:MM:SS UTC, 24-hour]

All seven fields are mandatory. Order is mandatory.
No field may be omitted or reordered.

DocDate and DocTime are auto-filled at every version
update in UTC. They reflect the moment of version
creation, not the moment of GitHub commit.

============================================================
9. LIFECYCLE STATES
============================================================

Every document exists in exactly one lifecycle state.
The state is encoded in DocVersion.

  dv  — Draft Version
        Active development. Under constant review. Bill may
        approve directly (dv → v). Not yet authoritative.
        Example: dv1_0, dv1_1, dv2_0

  rv  — Revision Version
        An approved document requiring changes returns to
        rv state. Not used for initial document development.
        Bill re-approves after revision is complete.
        Example: rv1_0

  v   — Approved Version
        Bill-approved. Authoritative. Governs the system.
        Changes require v → rv before returning to v.
        Example: v1_0, v2_0

  rt  — Retired
        No longer authoritative. Moved to _Archive/.
        DCN permanently reserved. Never reused.
        Example: rt1_0

State transitions:
  dv → v   (Bill approves working draft directly)
  v  → rv  (approved document requires changes)
  rv → v   (Bill re-approves after revision)
  v  → rt  (document retired)

============================================================
10. VERSIONING
============================================================

Version numbers follow the pattern: state + major_minor

  dv1_0   First draft, first minor version
  dv1_1   First draft, second minor version
  dv2_0   Second major draft, minor resets to 0
  rv1_0   Review of first major version
  v1_0    First approved version
  v2_0    Second approved version (major revision)

Minor version: corrections, clarifications, additions
that do not change scope or governing decisions.

Major version: changes to scope, governing decisions,
structural changes, or any change requiring full
re-approval.

Every change increments the version. No exceptions.

11. DCN ASSIGNMENT RULES
============================================================

11.1 Assignment Authority
Only Bill may assign DCNs. DCNs are registered in this
document (Section 12) at the time of assignment. A
document cannot exist without a registered DCN.

11.2 Assignment Sequence
Within any sub-domain, Instance Document DCNs are
assigned sequentially from DDD=001. The next available
DDD is the only valid choice. DCNs are not pre-reserved.

11.3 Permanent Reservation
Once assigned, a DCN is permanently associated with that
document title. Retired document DCNs are permanently
reserved and may never be reassigned.

11.4 One DCN Per Document
One document gets one DCN. One DCN identifies one
document. No sharing, combining, or splitting.

11.5 Domain Document Rule
Every domain must have its Domain Document created
before any Sub-Domain Anchor or Instance Document
in that domain may be created.

11.6 Sub-Domain Anchor Rule
Every sub-domain must have its Sub-Domain Anchor created
before any Instance Document in that sub-domain may be
created.

15. DIAGRAM ASSET SPECIFICATION
============================================================

Controlled documents may include embedded diagrams. Because
.txt controlled documents cannot embed binary images, all
diagrams associated with a controlled document are stored
as separate controlled SVG asset files in the same folder
as the parent document.

------------------------------------------------------------
15.1 When Diagram Assets Are Required
------------------------------------------------------------

A diagram asset is required whenever a specification
document references a diagram that is essential to
understanding the system. Diagrams are not optional
decoration — if a diagram is referenced in a controlled
document, it must exist as a controlled asset.

------------------------------------------------------------
15.2 Diagram Asset File Naming
------------------------------------------------------------

Diagram assets follow this exact naming pattern:

  [DCN]_Diagram[N]_[Title].svg

  DCN   = 7-digit DCN of the parent document
  N     = Sequential diagram number (1, 2, 3...)
  Title = Underscore-separated title (no spaces)
  .svg  = File extension — SVG format required

Examples:
  0500000_Diagram1_Kraken_API_Connection_Architecture.svg
  0500000_Diagram2_Trading_Pipeline.svg
  0500000_Diagram6_Complete_System.svg

------------------------------------------------------------
15.3 Diagram Asset Storage
------------------------------------------------------------

DA-001  Diagram assets live in the same folder as their
        parent document. No sub-folders. No separate
        assets folder.

DA-002  Diagram asset filenames must begin with the DCN
        of their parent document. This makes the
        parent-child relationship unambiguous from the
        filename alone.

DA-003  SVG format is required. SVG is text-based,
        renders without external tools, diffs cleanly
        in Git, and is not lossy.

DA-004  Diagram assets are versioned with their parent
        document. When a diagram is updated, the parent
        document version increments to reflect the change.
        Diagram assets do not carry their own version
        numbers — the parent DCN and diagram number
        together uniquely identify the asset.

DA-005  Every diagram referenced in a controlled document
        must exist as a corresponding SVG file. A
        document that references a diagram that does not
        exist as an SVG file is incomplete.

------------------------------------------------------------
15.4 Referencing Diagrams in Controlled Documents
------------------------------------------------------------

Within a .txt controlled document, each diagram is
referenced by its exact filename:

  [Diagram file: 0500000_Diagram1_Kraken_API_Connection_Architecture.svg]

This format is unambiguous and links directly to the
file that must exist in the same folder.

------------------------------------------------------------
15.5 Validation Rules for Diagram Assets
------------------------------------------------------------

  V-020  Diagram asset filename begins with parent DCN
  V-021  Diagram asset uses .svg extension
  V-022  Diagram asset lives in same folder as parent doc
  V-023  Every diagram reference in a .txt document has
         a corresponding SVG file in the folder
  V-024  Diagram N+1 does not exist without Diagram N
         for the same parent DCN

TOTHBOT V2 0500000 CONSOLIDATION CAMPAIGN PLAN
============================================================

============================================================
1. PURPOSE
============================================================

This document defines the 0500000 Consolidation Campaign:
a multi-session program to consolidate all architectural
content of the TothBot V2 document set into the 0500000
System Architecture Overview diagram set, retire the
documents made redundant by that consolidation, and reduce
the controlled-document count to the minimum consistent
with governance.

The campaign exists to make the 0500000 diagrams the single
canonical, authoritative design source for TothBot. Prose
follows the diagrams; the diagrams do not follow prose.
The campaign eliminates the prose-driven error class in
which scattered specification prose drifts from, or
contradicts, the canonical diagrams.

This is a living plan. It is updated when a phase completes
or a Bill-ratified amendment materially changes the
campaign. Every update increments the version.

============================================================
3. CAMPAIGN OBJECTIVE
============================================================

3.1  Consolidate all architectural content into 0500000.
     Architectural content (parameters, contracts, gates,
     flows, events, and the values/notes that accompany
     them) is migrated into the 0500000 diagram set — into
     the relevant diagram, its governs/<desc> descriptors,
     its figcaption attestation, and the §9 mirror.

3.2  Retire redundant documents. Once a source document's
     architectural content is canonically present in
     0500000, the source document is retired through the
     established retirement gate (§7).

3.3  Minimize separate-document count. The end state is the
     fewest controlled documents consistent with governance:
     0500000 as the architectural canon, plus the
     non-consolidatable governance, code, and narrative
     documents that must remain separate (§4).

============================================================
4. RATIFIED SCOPE BOUNDARY (BILL, TB00393 — VERBATIM
   INTENT; DO NOT RE-LITIGATE)
============================================================

(a) 0500000 diagrams are canonical for ARCHITECTURE.
    Content is consolidatable into 0500000 if it is
    architectural - parameters, contracts, gates, flows,
    events, and the values/notes that go with them.

(b) STAY-OUT (not consolidatable):
    - Governance/process (AA=03): namespace rules,
      versioning, document workflow. 0500000 is governed
      by these; cannot absorb its own rulebook. Token
      registry §15.12 stays (it is the de-dup engine).
    - Code (AA=10 pure code-authoring coding specs):
      code is not architecture diagrams.
    - Business/plans/ethics (AA=00/01/09): mission,
      business plan, master plan - narrative.

(c) Everything else (AA=04/05/06/07/08 specs + TB00000
    §9.17 parameter values) is a consolidation candidate.

(d) §9.17 parameter values + CIATS-ownership MOVE into
    0500000 diagram notes; §9.17 then retires (new
    standard).

(e) Campaign plan lives in AA=09 as a NEW plan instance
    (not in 0500000, not a 0500000 amendment).

(f) Audit-first sequencing: read-only master register
    before any migration.

(g) Eat the elephant one bite at a time - manageable
    one-mission sessions per RR-SCOPE-011.

(h) Consolidate as much as possible; minimize separate-
    document count.

NOTE ON AA=02 (OPERATIONS): The ratified statements above
enumerate consolidation candidates (AA=04/05/06/07/08) and
STAY-OUT classes (AA=03/10/00/01/09) but do not place AA=02
Operations. AA=02 is therefore NOT pre-classified by this
plan. The master register (Mission 1.2 output) flags each
AA=02 document for Bill ratification before any AA=02

5. PHASE STRUCTURE
============================================================

The campaign executes in five phases. Phases run in order;
within a phase, work decomposes into one-mission sessions
per §6 (RR-SCOPE-011). No phase begins migration until the
master register (Mission 1.2) is ratified.

PHASE 0 — D8 THREAD CLOSURE (folded).
  The D8 blocker (param:concentration_cap_per_module and
  param:exposure_cap_pct unregistered in 0311001 §15.12,
  absent from TB00000 §9.17, and falsely attested at
  0500000 D8 figcaption L3004) is the campaign's first
  concrete unit of work. It is NOT executed as a standalone
  mission. It is the seed case for the Phase-1 migration
  pattern (§8): the two CIATS-owned params are registered
  in §15.12, their values migrate into D8 notes, and the
  false attestation is corrected in the same controlled
  pass. Full diagnosis: TB00393 SL §2/§3.

PHASE 1 — §9.17 PARAMETER-VALUE MIGRATION.
  Migrate TB00000 §9.17 parameter values plus CIATS-
  ownership metadata into the 0500000 diagram notes per the
  migration pattern (§8), one parameter-group per session.
  As each parameter-group's values land canonically in
  0500000, the corresponding §9.17 entry retires. The
  §15.12 token registry stays as the cross-diagram de-dup
  engine; only the VALUES move.

PHASE 2 — AA=05 COMPONENT SPECIFICATIONS.
  Migrate the architectural content of the AA=05 component
  specifications (0511001 WS_Manager, 0511002 Signal_
  Pipeline, 0511003 Execution_Engine, 0511004 Exit_
  Controller, 0511005 Position_Mirror, 0511006 Logger)
  into their canonical 0500000 diagrams and §9 mirror, one
  component per session, retiring each spec via §7 once its
  content is canonical.

PHASE 3 — AA=04/06/07/08 SPECIFICATIONS.
  Migrate the architectural content of the AA=04 exchange-
  interface specs (0411001/0411002/0411003), AA=06 risk
  specs (0610000), AA=07 strategy specs (0711001/0711002/
  0711003), and AA=08 trading-system specs (0811005) into
  their canonical 0500000 diagrams and §9 mirror, one spec
  per session, retiring each via §7.

PHASE 4 — ANCHOR / DOMAIN-DOC COLLAPSE + GOVERNANCE
  RECONCILIATION.
  Resolve the structural-anchor and domain-document
  question for the consolidated domains (0400000/0410000,
  0510000, 0600000/0610000, 0700000/0710000, 0800000/
  0810000). Collapse anchors and domain docs whose only
  remaining role was to point at now-retired instance
  specs. Reconcile 0311001 namespace, parent chains, and
  the governance registers (TB00153 Decision/Defect) to the
  post-campaign document set. This phase is governance-
  heavy and is sequenced last because it depends on every
  prior migration being complete.

============================================================
6. ONE-MISSION-PER-SESSION DECOMPOSITION (RR-SCOPE-011)
============================================================

Each session executes exactly one bite of the campaign:
one parameter-group, one component spec, or one anchor/
domain reconciliation. A session that completes its single
mission and closes cleanly is preferred over a session that
attempts multiple migrations and produces an inconsistent
intermediate state.

Rationale (loss-prevention prime directive, TB00000 §1.2):
an over-scoped session that leaves 0500000 in a half-
migrated state is the highest-loss failure mode in this
campaign, because every downstream coding decision reads
from 0500000. Two smaller productive sessions are superior
to one over-scoped session that then requires multiple
recovery sessions.

Each migration session uses the retirement gate (§7) end to
end for its single source document or parameter-group.

============================================================
7. RETIREMENT GATE (REUSE OF DD-012 SIX-STEP GATE)
============================================================

Every document retirement in this campaign uses the
existing DD-012 six-step retirement gate. No new retirement
mechanism is created.

  S-1  AUDIT. Confirm every architectural item in the
       source document is either already canonical in
       0500000 or is migrated in this same session. No
       orphaned architectural content.
  S-2  DIAGRAM AMEND. Migrate the architectural content
       into the canonical 0500000 diagram(s): diagram body,
       governs/<desc> descriptors, figcaption attestation,
       and §9 mirror.
  S-3  PARENT GAP-FILL. Fill any reference gap created in
       the parent chain so no surviving document points at
       a retired document without resolution.
  S-4  RETIREMENT. Retire the source document per the
       controlled retirement procedure.
  S-5  ANCHOR REVISION. Revise the anchor/domain document
       to drop the retired instance and reflect the new
       canonical location.
  S-6  GOVERNANCE. Update the governance registers (TB00153
       Decision Register, Master Defect Register, namespace
       0311001 as applicable) to record the retirement.

============================================================
8. MIGRATION PATTERN — §9.17 PARAMETER VALUE -> 0500000
   DIAGRAM NOTES (NEW STANDARD)
============================================================

This is the standard pattern for Phase 0 and Phase 1, and
the model for value-bearing migrations in later phases.

  P-1  IDENTIFY. Take one parameter-group from TB00000
       §9.17 (e.g. the two D8 CIATS-owned caps in Phase 0).
  P-2  TOKEN REGISTER. Register each parameter token in the
       0500000 §15.12 token registry if not already
       present. The token registry STAYS (§4(b)); it is the
       cross-diagram de-dup engine. Only the VALUES move.
  P-3  MIGRATE VALUE + OWNERSHIP. Write the parameter value
       and its CIATS-ownership metadata into the canonical
       0500000 diagram notes in three coordinated places:
         - the governs/<desc> descriptor of the owning
           diagram element;
         - the figcaption attestation of that diagram;
         - the §9 mirror.
  P-4  ATTESTATION TRUTH. Correct any figcaption attestation
       that previously claimed registration/presence that
       did not exist (the D8 L3004 false-attestation case).
       Attestation must match live grep-verified state.
  P-5  RETIRE §9.17 ENTRY. Once the value is canonical in
       0500000, retire that parameter-group's §9.17 entry.
  P-6  GOVERNANCE. Record per §7 S-6.

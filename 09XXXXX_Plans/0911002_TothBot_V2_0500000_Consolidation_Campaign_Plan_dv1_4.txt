TOTHBOT V2 0500000 CONSOLIDATION CAMPAIGN PLAN
============================================================

============================================================
1. PURPOSE
============================================================

This document defines the 0500000 Consolidation Campaign:
a multi-session program to consolidate all ARCHITECTURAL
content of the TothBot V2 document set into the 0500000
System Architecture Overview diagram set, retire the
documents made redundant by that consolidation, and reduce
the controlled-document count to the minimum consistent
with governance.

The campaign exists to make the 0500000 diagrams the single
canonical, authoritative design source for TothBot. Prose
follows the diagrams; the diagrams do not follow prose.
The campaign eliminates the prose-driven error class in
which scattered specification prose drifts from, or
contradicts, the canonical diagrams.

ARCHITECTURE vs TESTING SEPARATION (Option A, ratified at
TB00396; recorded as DEC-039). The campaign consolidates
ARCHITECTURE only. Parameter STARTING VALUES are transient
testing seeds and are NOT consolidated. They remain in
TB00000 §9.17, which is the permanent canonical parameter
registry and is NOT retired by this campaign. The detailed
rule is §3.1. This separation is the controlling scope
correction in dv1_1 and supersedes the dv1_0 "migrate
values then retire §9.17" scope wherever it appeared.

This is a living plan. It is updated when a phase completes
or a Bill-ratified amendment materially changes the
campaign. Every update increments the version.

3. CAMPAIGN OBJECTIVE
============================================================

3.1  ARCHITECTURE vs TESTING SEPARATION (OPTION A —
     CONTROLLING SCOPE RULE).

     This is the controlling scope rule of the campaign.
     All migration, retirement, and de-dup decisions defer
     to it.

     (a) ARCHITECTURAL content migrates into 0500000.
         Architectural content is system structure and
         contracts: component existence, component
         ownership, inter-component contracts, information
         flows, gates, regimes, channels, events, and
         module structure. It is permanent — it changes
         only on a design decision. It is migrated into the
         relevant 0500000 diagram, its governs/<desc>
         descriptors, its figcaption attestation, and the
         §9 mirror.

     (b) Parameter STARTING VALUES do NOT migrate.
         The numeric starting value of any parameter (paper
         wallet balances, per_trade_size_usd, drawdown
         thresholds, and every other value in TB00000
         §9.17) is a transient testing seed, not
         architecture. Per TB00000 §9.16 and §6.8, every
         starting value except the sacred 1:1.5 R:R floor
         is explicitly temporary: CIATS owns it, and paper
         trading replaces it with a data-derived value.
         Transient values are NOT consolidated into 0500000.

     (c) 0500000 records the architectural FACT, never the
         transient value. For any parameter, 0500000 records
         that the parameter EXISTS and WHO OWNS IT (CIATS,
         OPERATOR, or SACRED), as an architectural fact in
         the owning diagram element, its governs/<desc>
         descriptor, and its figcaption attestation. 0500000
         does NOT record the numeric starting value.

     (d) TB00000 §9.17 is the permanent canonical parameter
         registry. It holds every parameter starting value
         and its classification (SACRED / OPERATOR /
         CIATS-OWNED / RETIRED). It is NEVER retired by this
         campaign. It is the single home for transient
         testing values.

     RATIONALE (loss-prevention prime directive, TB00000
     §1.2). Migrating transient starting values into the
     canonical 0500000 diagrams would (i) pollute the
     canonical architecture source with non-canonical,
     frequently-changing content; (ii) make 0500000 — the
     highest-cost, highest-risk document to edit — stale the
     instant CIATS changes a value, reintroducing the very
     prose-driven-error class this campaign exists to
     eliminate, merely relocated into the diagrams; and
     (iii) violate the established testing-vs-architecture
     separation. The "complete and comprehensive" mandate
     for 0500000 is about ARCHITECTURAL completeness, not
     absorption of transient operational state.

3.2  Consolidate all ARCHITECTURAL content into 0500000.
     Per §3.1(a), the architectural content of every
     consolidation-candidate source document is migrated
     into the 0500000 diagram set. Where a source document
     also carries a parameter, only the architectural fact
     of that parameter (existence + ownership) migrates;
     the value stays in §9.17 per §3.1(b)-(d).

3.3  Retire redundant documents. Once a source document's
     ARCHITECTURAL content is canonically present in
     0500000 AND all its non-architectural content has a
     retained canonical home, the source document is retired
     through the established retirement gate (§7). See the
     de-dup rule (§9).

3.4  Minimize separate-document count. The end state is the
     fewest controlled documents consistent with governance:
     0500000 as the architectural canon, TB00000 §9.17 as
     the permanent parameter registry, plus the
     non-consolidatable governance, code, and narrative
     documents that must remain separate (§4).

5. PHASE STRUCTURE
============================================================

The campaign executes in FOUR phases — the UNIFIED OCS
4-PHASE MODEL (adopted at dv1_4; consistent with the
TB00394 v1_1 §PHASE-MODEL ratified roadmap). Phases run in
order. Within a phase, work decomposes into one-mission
sessions per §6 (RR-SCOPE-011): each session executes
EXACTLY ONE primary mission. No phase begins element-level
work until the master register (TB00394) is ratified
(Phase 0 complete).

Alongside the Phase 3 execution work, §5A defines two
reconciliation/new-architecture tracks (exit_reason
de-conflict and the SIGNAL_DECAY cancel trigger) that run
interleaved under the same §6 one-mission ceiling but are
NOT migration sub-stages. See §5A.

A "primary mission" is exactly one of: one source-document
ARCHITECTURAL audit; OR one architectural-content migration
of one source document (or one diagram / one sub-domain of
a large source document) into 0500000; OR one document
retirement; OR one governance/anchor reconciliation. No
phase, and no session, bundles more than one primary
mission. See §6.

  level) at TB00394 v1_1 (TB00469).
  The document-level MOVE / STAY / SPLIT classification of
  all 54 controlled documents plus the TB00000 §9.17
  parameter source against the ratified scope boundary
  (§4). The deliverable is the TB00394 Master Consolidation
  Register, which names the target 0500000 location for
  each MOVE/SPLIT source. Phase 0 is document-level scoping
  only; element-level scoping is Phase 1. The AA=02
  verdicts are FINAL per Bill ratification (TB00468
  Decision 1; TB00394 v1_1). The register MUST stay
  Bill-ratified as the audit-first basis (§4(f)) for every
  Phase-1+ session (§10).

  Per-document, element-level architectural audit. For each

  channel / ar / pt_mode). Read-only: produces an

PHASE 2 — DD-012 THREE-BUCKET CLASSIFICATION + SEQUENCING.

============================================================
6. ONE-MISSION-PER-SESSION DECOMPOSITION (RR-SCOPE-011)
============================================================

Each session executes EXACTLY ONE primary mission, in
strict compliance with TB00000 §4.3.1 RR-SCOPE-011
(SESSION-SCOPE-DECOMPOSITION DISCIPLINE). A primary mission
is one of:

  (a) ONE source-document ARCHITECTURAL audit (read-only;
      produces a gap finding, no migration).
  (b) ONE architectural-content migration of ONE source
      document — or, if the source is large, ONE diagram or
      ONE sub-domain of it — into 0500000.
  (c) ONE document retirement (via §7), in its own session,
      separate from the migration that made it redundant
      (§6.2).
  (d) ONE governance / anchor / domain-document
      reconciliation.

6.1  PER-SESSION CEILING. Per RR-SCOPE-011, a session
     produces no more than the one primary deliverable plus
     the mandatory companions (Session Log + Next Session
     Instructions + OCS + GitHub upload) and at most one
     paired TB00153 MDR closure entry and one paired
     TB00153 Decision Register entry that DIRECTLY close the
     primary mission. No session bundles two migrations, two
     retirements, or a migration plus an unrelated
     governance amendment.

6.2  MIGRATION AND RETIREMENT ARE SEPARATE SESSIONS.
     Migrating a source document's architectural content
     into 0500000 (mission type (b)) and retiring that
     now-redundant source document (mission type (c)) are
     TWO different primary missions and therefore TWO
     different sessions. The migration session lands the
     architecture in 0500000 and verifies de-dup (§9). The
     retirement session, run only after the migration
     session has closed cleanly, executes the §7 gate. This
     prevents an over-scoped session that both migrates and
     retires in one pass and leaves 0500000 half-migrated if
     it runs out of budget.

6.3  MIGRATION UNIT DEFINITION. The migration unit is ONE
     source document's ARCHITECTURAL content per session. If
     a source document is large, it is split across sessions
     by diagram or by sub-domain — one diagram / one
     sub-domain per session — and each split session is its
     own primary mission. The unit never spans two source
     documents.

RATIONALE (loss-prevention prime directive, TB00000 §1.2).
An over-scoped session that leaves 0500000 in a
half-migrated state is the highest-loss failure mode in
this campaign, because every downstream coding decision
reads from 0500000. Two smaller productive sessions are
superior to one over-scoped session that then requires
multiple recovery sessions. This is also why migration and
retirement are separated (§6.2): a retirement that runs
before its migration session has fully closed could remove
a source document while its architectural content is only
partially in 0500000.

7. RETIREMENT GATE (REUSE OF DD-012 SIX-STEP GATE)
============================================================

Every document retirement in this campaign uses the
existing DD-012 six-step retirement gate. No new retirement
mechanism is created. A retirement is its own session per
§6.2.

  S-1  AUDIT. Confirm every ARCHITECTURAL item in the source
       document is already canonical in 0500000 (landed by a
       prior migration session) AND that every
       non-architectural item has a retained canonical home
       (e.g. a parameter value in §9.17). No orphaned
       content. See the de-dup rule (§9).
  S-2  DIAGRAM AMEND. If S-1 finds any architectural item
       not yet canonical, this is NOT a retirement session —
       stop and schedule a migration session (§6.2). A
       retirement session performs no new architectural
       migration.
  S-3  PARENT GAP-FILL. Fill any reference gap created in
       the parent chain so no surviving document points at
       a retired document without resolution.
  S-4  RETIREMENT. Retire the source document per the
       controlled retirement procedure.
  S-5  ANCHOR REVISION. Revise the anchor/domain document
       to drop the retired instance and reflect the new
       canonical location.
  S-6  GOVERNANCE. Update the governance registers (TB00153
       Decision Register, Master Defect Register, namespace
       0311001 as applicable) to record the retirement.

8. MIGRATION PATTERN — ARCHITECTURAL FACT -> 0500000
   (OPTION A STANDARD; VALUES STAY IN §9.17)
============================================================

This is the standard pattern for the CIATS-ownership
architectural attestation of §9.17 parameters (a Phase 3
EXECUTION work-stream; formerly the old Phase 1) and the
model for the architectural-fact portion of value-bearing
migrations in Phase 3 execution. It is the pattern
demonstrated by the old Phase 0 D8 seed case (TB00395),
retained as closed history in §5.

  P-1  IDENTIFY. Take one parameter-group from TB00000
       §9.17 (e.g. the two D8 CIATS-owned caps in the Phase
       0 seed case).
  P-2  TOKEN REGISTER. Register each parameter token in the
       0500000 §15.12 token registry if not already present.
       The token registry STAYS (§4(b)); it is the
       cross-diagram de-dup engine.
  P-3  MIGRATE THE ARCHITECTURAL FACT (NOT THE VALUE). Write
       the parameter's EXISTENCE and OWNERSHIP (CIATS /
       OPERATOR / SACRED) into the canonical 0500000 diagram
       in three coordinated places:
         - the governs/<desc> descriptor of the owning
           diagram element;
         - the figcaption attestation of that diagram;
         - the §9 mirror.
       Record that the parameter's current starting value
       lives in TB00000 §9.17 (pointer, not value). DO NOT
       write the numeric starting value into 0500000.
  P-4  ATTESTATION TRUTH. Correct any figcaption attestation
       that previously claimed registration/presence that
       did not exist (the D8 L3004 false-attestation case).
       Attestation must match live grep-verified state. An
       attestation states the architectural fact and the
       §9.17 pointer; it never asserts a value 0500000 does
       not hold.
  P-5  §9.17 UNCHANGED. The parameter-group's §9.17 entry is
       NOT retired and NOT moved. §9.17 remains the
       permanent canonical home of the starting value
       (Option A; §3.1). This step replaces the dv1_0
       "retire §9.17 entry" step, which is SUPERSEDED.
  P-6  GOVERNANCE. Record per §7 S-6.

SUPERSESSION NOTE. The dv1_0 version of this pattern
included a step "P-5 RETIRE §9.17 ENTRY — once the value is
canonical in 0500000, retire that parameter-group's §9.17
entry." That step is REMOVED under Option A (DEC-039).
Values are never made canonical in 0500000; they stay in
§9.17; the §9.17 entry is never retired by this campaign.

9. DE-DUP RULE (RETIREMENT PRECONDITION)
============================================================

A specification is ARCHITECTURALLY redundant only when its
ARCHITECTURAL content is fully present in 0500000.

A source document is RETIRED only when BOTH hold:
  (a) all of its ARCHITECTURAL content is canonical in
      0500000 (architecture), AND
  (b) all of its NON-architectural content is in another
      retained canonical home — parameter starting values
      in TB00000 §9.17, governance in AA=03, code in AA=10,
      narrative in AA=00/01/09.

Residual non-architectural content that has NO retained
canonical home BLOCKS retirement. In particular, a
parameter starting value present only in a source document
must be reconciled into §9.17 (not into 0500000) before
that source document can be retired. A source document is
NEVER retired by moving its values into 0500000.

11. OUT OF SCOPE FOR ANY MIGRATION SESSION
============================================================

No migration or retirement session:
  - writes a parameter starting value into 0500000 (Option
    A; §3.1);

  - invents a parameter value (§10 open finding);
  - bundles more than one primary mission (§6,
    RR-SCOPE-011);
  - both migrates a source document and retires it in the
    same session (§6.2).

3.2 SYSTEMD SERVICE UNIT [IMP-08]
------------------------------------------------------------

VD-SYS-001  TothBot MUST run as a systemd service.

VD-SYS-002  Required unit file configuration:
            [Unit]
            Description=TothBot V2 Trading System
            After=network-online.target
            Wants=network-online.target

            [Service]
            Type=notify
            User=root
            WorkingDirectory=/root/TothBot_V2-Code
            EnvironmentFile=/root/.tothbot.env
            ExecStart=/usr/bin/python3 -m tothbot
            Restart=on-failure
            RestartSec=5
            WatchdogSec=120
            LimitNOFILE=65535

            [Install]
            WantedBy=multi-user.target

VD-SYS-003  WatchdogSec=120: if event loop hangs and watchdog
            ping stops, systemd detects after 120s and
            restarts. Prevents undetected frozen process.
VD-SYS-004  Type=notify: TothBot sends sd_notify READY=1
            after startup validation. Systemd knows when
            TothBot is actually ready.
VD-SYS-005  LimitNOFILE=65535: prevents EMFILE errors under
            high WS subscription load.

------------------------------------------------------------
3.3 SYSTEMD WATCHDOG LOOP [IMP-08]
------------------------------------------------------------

VD-WD-001   Separate asyncio.Task (watchdog_loop) runs 24/7.
VD-WD-002   Watchdog loop sends systemd WatchdogSec ping
            every 30 seconds:
              import sdnotify
              notifier = sdnotify.SystemdNotifier()
              notifier.notify("WATCHDOG=1")
VD-WD-003   If event loop hangs, watchdog Task stops.
            No ping within 120s = systemd restarts TothBot.
VD-WD-004   On startup completion: notifier.notify("READY=1")
VD-WD-005   Watchdog Task is long-running per WM-TASK-003.
            Stored as named instance variable.
VD-WD-006   Use systemd-python or sdnotify library.

3.4 LOGROTATE CONFIGURATION [IMP-09]
------------------------------------------------------------

VD-LOG-001  logrotate MUST be configured before first live run.
VD-LOG-002  Configuration: /etc/logrotate.d/tothbot
            /root/TothBot_V2-Code/logs/tothbot.log {
                daily
                rotate 90
                compress
                delaycompress
                missingok
                notifempty
                copytruncate
            }
VD-LOG-003  copytruncate: allows Logger async writer to
            continue writing to the same file descriptor
            while logrotate copies and truncates.
VD-LOG-004  90-day retention: sufficient for CIATS analysis.

3.7 API KEY IP WHITELISTING [dv1_1 AR-037]
------------------------------------------------------------

VD-KEY-006  Both DATA and TRADE API keys MUST be IP-whitelisted
            to the VPS IP address in Kraken account settings.
            Current VPS IP: 87.99.141.44 (Ashburn VA)
            Update on migration to Hillsboro OR.

VD-KEY-007  IP whitelisting procedure (Kraken UI):
            (1) Log in to Kraken account
            (2) Go to Settings → Security → API Keys
            (3) For each API key (DATA and TRADE separately):
                Click "Edit" or "Manage"
                Add VPS IP address to whitelist
            (4) Verify both keys show VPS IP as whitelisted
            (5) Test authentication from VPS before going live

VD-KEY-008  IP whitelisting prevents unauthorized use of
            API keys if accidentally exposed.

VD-KEY-009  CRITICAL: On any VPS migration:
            (1) Note the new VPS IP BEFORE decommissioning
                old VPS
            (2) Add new IP to both key whitelists
            (3) Verify authentication from new VPS
            (4) THEN decommission old VPS
            (5) Remove old IP from whitelists
            Failure to update whitelists = total trading halt
            on VPS migration.

3.8 KRAKEN STATUS API STARTUP CHECK [NEW dv1_2 AR-038]
------------------------------------------------------------

VD-STAT-001  ★ NEW dv1_2: TothBot MUST query the Kraken
             Status API during startup validation, before
             entering the main event loop.

             Endpoint: GET https://status.kraken.com/api/v2/
                           scheduled-maintenances/upcoming.json

             This is a PUBLIC endpoint. No authentication.
             No API key required. Returns upcoming scheduled
             maintenances in JSON format.

             Implementation in startup sequence:
               import aiohttp
               from datetime import datetime, timezone, timedelta

               async def check_upcoming_maintenance(session):
                   url = ("https://status.kraken.com/api/v2/"
                          "scheduled-maintenances/upcoming.json")
                   try:
                       async with session.get(url,
                                   timeout=aiohttp.ClientTimeout(total=10)
                       ) as resp:
                           data = await resp.json()
                       maintenances = data.get(
                           "scheduled_maintenances", [])
                       now = datetime.now(timezone.utc)
                       warn_threshold = now + timedelta(hours=2)
                       for m in maintenances:
                           start_str = m.get("scheduled_for", "")
                           if not start_str:
                               continue
                           start_time = datetime.fromisoformat(
                               start_str.replace("Z", "+00:00"))
                           if start_time <= warn_threshold:
                               logger.log(
                                   "KRAKEN_MAINTENANCE_SCHEDULED",
                                   level="CRITICAL",
                                   start_time=str(start_time),
                                   description=m.get("name", ""),
                               )
                               alert("CRITICAL",
                                     f"Kraken maintenance at "
                                     f"{start_time} UTC: "
                                     f"{m.get('name','')}")
                   except Exception as e:
                       logger.log("KRAKEN_STATUS_CHECK_FAILED",
                                  error=str(e),
                                  level="INFO")
                   # Always continue startup regardless

VD-STAT-002  BEHAVIOR RULES:
             (a) If maintenance scheduled within 2 hours:
                 Log KRAKEN_MAINTENANCE_SCHEDULED (CRITICAL).
                 Alert Bill via alert@tothbot.com.
             (b) If no maintenance within 2 hours:
                 Log KRAKEN_STATUS_CLEAN (INFO).
             (c) If Status API is unreachable:
                 Log KRAKEN_STATUS_CHECK_FAILED (INFO).
             In ALL cases: startup continues. This check
             is NEVER a blocking condition. TothBot may
             be starting in response to a VPS restart
             during or after maintenance — it must be
             able to come up and self-correct.

VD-STAT-003  WHY THIS MATTERS:
             At 5-minute candle frequency, entering positions
             30 minutes before a scheduled 60-minute
             maintenance window means TothBot will manage
             those positions through maintenance with reduced
             monitoring capability. Knowing in advance lets
             Bill:
             (a) Delay startup until after maintenance
             (b) Confirm resting TP/emergSL are protecting
                 any open positions
             (c) Avoid entering positions before maintenance
             The cost is a single REST call at startup
             (~1ms at Hillsboro, ~5ms at Ashburn).
             The benefit is awareness of a known risk.

5. FIVE CODING-READINESS QUESTIONS (TBD IN FINAL SPEC)
============================================================

  (1) What does VPS Deployment DO?
      Specifies all infrastructure configuration and
      process management for 24/7 TothBot operation.
  (2) Interfaces: systemd ↔ TothBot, logrotate ↔ Logger,
      environment file ↔ TothBot startup,
      Kraken Status API ↔ startup validation.
  (3) Hard rules:
      LimitNOFILE=65535 mandatory.
      WatchdogSec=120 with 30s ping loop.
      API keys in EnvironmentFile only — never in code.
      Both API keys IP-whitelisted to VPS IP.
      logrotate configured before first live run.
      IP whitelist updated BEFORE VPS migration.
      Kraken Status API checked at startup (non-blocking).
  (4) Triggered by: system boot, crash (Restart=on-failure),
      watchdog timeout.
  (5) Logs: all startup/shutdown events to journal and file,
      maintenance alerts at CRITICAL, status clean at INFO.

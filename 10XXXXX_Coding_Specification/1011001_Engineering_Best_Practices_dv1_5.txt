3.11 DECIMAL PRECISION FOR PRICE/QUANTITY ROUNDING [NEW dv1_4]
------------------------------------------------------------

BACKGROUND (AR-047 amendment, TB00016 NEW-12):
The original AR-047 specified math.floor(x / incr) * incr
for rounding. This operates on Python float arithmetic.
Float binary representation causes precision errors:

  price_increment = 0.1  (float)
  raw_price = 42350.15   (float from Kraken ticker)
  math.floor(42350.15 / 0.1) * 0.1
    = 42350.099999999985  ← WRONG (float arithmetic error)

  Correct approach:
  Decimal(str(42350.15)).quantize(
      Decimal(str(0.1)), rounding=ROUND_DOWN
  ) = 42350.1  ← CORRECT

For exchange orders, any rounding error = REJECTED ORDER =
failed trade entry. This directly violates loss minimization.

BP-DEC-001  ★ NEW dv1_4 CRITICAL: ALL price and quantity
            values received from Kraken (via WS or REST)
            MUST be converted to Decimal immediately on
            receipt using ONLY the string constructor:

              price = Decimal(str(msg["price"]))
              qty   = Decimal(str(msg["qty"]))

            NEVER use the float constructor:
              WRONG: Decimal(msg["price"])   ← float precision
              WRONG: Decimal(0.1)            ← wrong
              CORRECT: Decimal(str(0.1))     ← exact

            RATIONALE: orjson decodes JSON numbers as Python
            float by default. Decimal(float) inherits the
            binary representation error. Decimal(str(float))
            goes through the string representation first,
            which preserves the correct decimal digits.

            Applies to ALL values sourced from Kraken:
            - ticker bid, ask prices
            - executions avg_price, last_price, cum_cost
            - instrument price_increment, qty_increment,
              qty_min, cost_min
            - balances channel balance, amount
            - GetOHLCData OHLC candle values

BP-DEC-002  ★ ROUNDING FOR ORDER QUANTITY (Gate 8):
            Round DOWN (toward zero) to preserve R:R.
            Sending MORE quantity than sized = taker fee
            violation; sending LESS = conservative, OK.

              from decimal import Decimal, ROUND_DOWN

              def round_qty(raw_qty: Decimal,
                            qty_increment: Decimal) -> Decimal:
                  return raw_qty.quantize(
                      qty_increment,
                      rounding=ROUND_DOWN
                  )

              # Example:
              raw_qty = Decimal("0.12345")
              qty_incr = Decimal("0.001")
              result = round_qty(raw_qty, qty_incr)
              # result = Decimal("0.123")

BP-DEC-003  ★ ROUNDING FOR ENTRY LIMIT PRICE (Gate 8):
            Round DOWN (toward zero for buy = bid below ask).
            Ensures limit buy rests on book as maker order.

              def round_entry_price(raw_price: Decimal,
                                    price_increment: Decimal
                                    ) -> Decimal:
                  return raw_price.quantize(
                      price_increment,
                      rounding=ROUND_DOWN
                  )

BP-DEC-004  ★ ROUNDING FOR TP LIMIT PRICE:
            Round UP (toward positive infinity).
            TP is a SELL limit — higher sell price is
            better. Rounding UP maintains R:R constraint.

              from decimal import Decimal, ROUND_UP

              def round_tp_price(raw_tp: Decimal,
                                 price_increment: Decimal
                                 ) -> Decimal:
                  return raw_tp.quantize(
                      price_increment,
                      rounding=ROUND_UP
                  )

BP-DEC-005  ★ ROUNDING FOR EMERGSL TRIGGER PRICE:
            Round DOWN (toward zero).
            emergSL is a stop-loss SELL trigger — lower
            trigger price is more conservative (fires
            earlier, limits loss more). Rounding DOWN
            maintains loss-minimization mission.

              def round_emergsl_price(raw_sl: Decimal,
                                      price_increment: Decimal
                                      ) -> Decimal:
                  return raw_sl.quantize(
                      price_increment,
                      rounding=ROUND_DOWN
                  )

BP-DEC-006  ★ ROUNDING DIRECTION SUMMARY TABLE:

            Value                  Round   Why
            ─────────────────────  ──────  ──────────────────
            order_qty (entry buy)  DOWN    Conservative size
            entry limit_price      DOWN    Rest on book (maker)
            tp_price (sell limit)  UP      Better exit, R:R
            emergSL trigger price  DOWN    Earlier fire, safer
            qty (partial fill TP)  DOWN    Conservative exit

BP-DEC-007  ★ INSTRUMENT INCREMENT CONVERSION:
            All values from instrument channel snapshot
            MUST be converted to Decimal at parse time:

              for pair in instrument_snapshot["pairs"]:
                  pair_cache[pair["symbol"]] = {
                      "price_increment": Decimal(
                          str(pair["price_increment"])),
                      "qty_increment": Decimal(
                          str(pair["qty_increment"])),
                      "qty_min": Decimal(
                          str(pair["qty_min"])),
                      "cost_min": Decimal(
                          str(pair["cost_min"])),
                      "status": pair["status"],
                  }

            These Decimal values are then passed directly
            to all quantize() calls. No str() needed at
            quantize time since they're already Decimal.

BP-DEC-008  ★ MATH.FLOOR / MATH.CEIL PROHIBITION:
            math.floor() and math.ceil() MUST NOT be used
            for any price or quantity rounding in TothBot V2.
            They operate on Python floats and produce
            binary precision errors. Code review MUST reject
            any PR that uses math.floor or math.ceil for
            financial value rounding.

            ONLY permitted uses of math.floor/ceil:
            - Non-financial array indexing
            - Statistical computations (EWMA, CUSUM) where
              float precision is acceptable

DECISION RATIONALE (BP-DEC-001 through BP-DEC-008):
  TB00016 Search 4 confirmed from five independent sources
  (Python official decimal docs, Real Python rounding guide,
  GeeksforGeeks quantize, LabEx Decimal finance guide, 2026
  best practices article) that math.floor() on floats
  produces binary precision errors for decimal increments.
  The specific failure case: math.floor(42350.15 / 0.1) * 0.1
  gives 42350.09999... instead of 42350.1.

  On Kraken, order prices must be exact multiples of
  price_increment. A price of 42350.09999... would be
  rejected by the matching engine with EOrder:Invalid price.
  This would cause the entry to silently fail, leaving the
  pipeline believing a position was opened when it was not.

  For a 24/7 automated trading system, a silent order
  failure is a loss event. All rounding uses Decimal.quantize()
  which is the standard Python financial rounding method and
  is guaranteed to produce exact decimal representations.
  This directly serves TothBot's loss-minimization mission.

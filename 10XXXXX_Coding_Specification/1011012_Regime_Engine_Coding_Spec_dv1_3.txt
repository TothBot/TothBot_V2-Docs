============================================================
1. PURPOSE
============================================================

The Regime Engine classifies the current market regime
daily at 00:00 UTC for each pair in the trading universe.
The regime classification is the single most upstream
influence on all trade decisions: Gate 3 (pre-filter),
Gate 6 (sizing), and CIATS per-regime optimization all
depend on correct regime classification.

An incorrect regime classification has direct loss
consequences. It is the highest-priority correctness
requirement in the system.

3.9 ADX CONVERGENCE VALIDATION [NEW dv1_2]
------------------------------------------------------------

RE-FPD-004  ★ NEW dv1_2: CONVERGENCE DISTINCTION:
            There are two different data requirements for
            ADX(14):
            (1) FIRST VALID VALUE: 28 committed candles
                (already RE-FPD-001).
            (2) FULL CONVERGENCE ACCURACY: 2*N+100 candles
                = 2*14+100 = 128 candles.

            The "first valid value" requirement means the
            math can execute and produce a non-NaN result.
            The "convergence accuracy" requirement means the
            ADX value is stable and not subject to significant
            (~5%) precision errors from Wilder smoothing
            initialization.

            Source: Stock Indicators for Python library
            documentation (confirmed TB00013 Search 10):
            "You must have at least 2xN+100 periods of quotes
            to allow for smoothing convergence."

RE-FPD-005  ★ CONFIRMED ADEQUATE: With 719 committed daily
            candles available (response[:-1] of 720 returned):

              First valid ADX value: 28 candles needed.
              Full convergence:      128 candles needed.
              Available:             719 candles.

              Excess beyond convergence: 719 - 128 = 591
              Factor of safety: 719 / 128 = 5.6x

            TothBot V2 has 5.6x more data than required for
            full ADX convergence. The 28-candle minimum
            warm-up spec (RE-FPD-001) is correct in meaning
            "first valid value," but the actual computation
            is fully converged because we use all 719 candles
            in the Wilder smoothing recursion.

            NO SPEC CHANGE REQUIRED. RE-FPD-001 remains
            correct. This section documents the confirmation.

RE-FPD-006  ★ ADX WARM-UP IN CODE: When computing ADX
            incrementally (walk-forward), the warm-up
            applies to the initialization of the running
            smoothed values (TR_smooth, +DM_smooth, -DM_smooth,
            ADX itself). Because the Regime Engine always
            uses the full 719-candle history at 00:00 UTC
            (batch computation, not incremental), the
            warm-up is handled automatically. The Regime
            Engine does NOT compute ADX incrementally —
            it runs the full Wilder recursion on all 719
            committed candles once per day.

            Pipeline ATR(14) is computed INCREMENTALLY
            (RE-IND-004, AR-016). That incremental
            computation has its own 14-candle warm-up
            handled by the running ATR state.

            These are different ATR computations:
            (1) Regime Engine ATR: batch from 719 daily
                candles (fully converged).
            (2) Pipeline ATR: incremental from 5-min
                candles (warm-up on first 14 candles).
            They are different values for different purposes.
            Regime uses daily candle ATR for volatility
            regime classification. Pipeline uses 5-min
            candle ATR for MAE threshold and emergSL.
            Single source of truth means consistent data
            source per ATR type, not identical values.

DECISION RATIONALE (RE-FPD-004 through RE-FPD-006):
  TB00013 Search 10 sourced the convergence requirement
  from the Stock Indicators for Python library documentation
  and cross-referenced with multiple ADX implementation
  guides. The 2xN+100 convergence requirement was not in
  the prior spec. Adding it confirms our existing 719-candle
  data availability is more than adequate for fully converged
  ADX calculations. This validation is important because an
  insufficiently converged ADX could produce incorrect
  regime classifications, potentially blocking valid
  TRENDING_POS entries or allowing NON_DIR entries.
  With 5.6x excess data, this risk is definitively eliminated.
  The documentation also clarifies the difference between
  daily batch ADX (Regime Engine) and incremental 5-min ATR
  (pipeline), which are different computations with different
  warm-up states. This distinction must be explicit to prevent
  confusion during coding.

5. FIVE CODING-READINESS QUESTIONS (TBD IN FINAL SPEC)
============================================================

  (1) What does Regime Engine DO?
      Classifies current market regime for each pair
      daily at 00:00 UTC using committed daily OHLC.
      Staggered to avoid rate limits. Stale fallback on
      failure. Two-level tagging (asset + market).
  (2) Interfaces: REST API -> Regime Engine -> regime_cache
      -> Signal Pipeline (Gate 3, Gate 6), Position Mirror
      (market_regime tag at entry)
  (3) Hard rules:
      ALWAYS exclude response[-1] (RE-OHLC-002).
      ALWAYS stagger 1.1s between pair calls (RE-RL-002).
      NEVER use asyncio.gather() for concurrent OHLC calls.
      Use only committed candles. Never halt on failure.
      ★ ADX convergence at 128+ candles. We have 719.
        Batch computation on full history (RE-FPD-006).
  (4) Triggers: 00:00 UTC daily asyncio.Task
  (5) Logs: every regime classification, all indicator
      values, all rate limit hits, all stale fallbacks,
      all computation errors, ADX convergence status on
      first computation.

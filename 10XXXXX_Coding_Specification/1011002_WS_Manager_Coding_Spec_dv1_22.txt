WS MANAGER CODING SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document specifies the complete, unambiguous
implementation requirements for the WS Manager component
of TothBot V2. It is the direct input to code.

The WS Manager is TothBot's sole interface to all Kraken
WebSocket v2 connections. It is the central event processor
for the entire system. All Kraken push events flow through
it. All outbound orders originate from it.

This document supersedes and retires all prior WD versions
(dv1_0 through dv1_11). No TBD sections remain.

3. FIVE CODING-READINESS QUESTIONS
============================================================

(1) WHAT DOES WS MANAGER DO?

    Maintains all Kraken WS v2 connections (public and
    private). Receives all Kraken push events (ohlc, ticker,
    executions, balances, instrument, status). Dispatches
    inbound messages to correct handlers via O(1) dispatch
    table (AR-015). Manages per-symbol state: pair status
    cache, indicator state (ATR, RSI, EMA9, EMA21, VolMA20),
    HTF cache (EMA20, EMA50 — seeded from REST only, no WS
    ohlc(60) subscription per HR-WM-021), warm-up state
    machine (WARM_UP → READY), 24h liquidity cache
    (liquidity_24h — populated from REST Ticker at startup
    and refreshed periodically per WM-LIQ-001 through
    WM-LIQ-010). Fires pipeline trigger on each
    5-minute candle close. Fires Exit Controller on ticker bbo
    events for open positions, daily regime check (00:00 UTC),
    and 5m candle close for max hold count. Executes all WS
    outbound messages (add_order, batch_add, cancel_order,
    amend_order, batch_cancel). Manages token acquisition
    (startup and every reconnect). Manages startup indicator
    warm-up via _warm_up_all_pairs() — triggered from
    _subscribe_ohlc_channels() after ohlc(5) subscription
    sent (WM-WARMUP-001). Tracks portfolio_baseline_USD
    (set once at startup Step 6, never reset). Updates
    spot_usd_balance from balances channel. Computes
    drawdown_pct from mark-to-market. Enforces SESSION_PAUSE
    and FULL_HALT drawdown circuit breakers. Maintains
    Pending Order Registry (cl_ord_id → estimated_USD_cost).
    Detects entry partial fills (GTD expiry/cancel with
    cum_qty > 0) and dispatches batch_add protection.
    Handles TP partial fills by amending emergSL qty (not
    cancel+resubmit). Dispatches CIATS Trade Outcome Bus
    on each full position close. Manages application-level
    JSON ping (30s). Detects zombie connections (90s no real
    data). Detects sequence gaps (executions and balances).
    Manages mid-session reconnect as a separate code path.
    Maintains Selection Controller state (exit_cooldown_log,
    consecutive_loss_count) across reconnects. Manages
    ticker event_trigger subscription per pair position state.
    Alerts on unexpected order amendments (amended exec_type).
    Logs all events to Logger (non-blocking async queue).
    Prohibits cancel_all_orders_after under all circumstances.

(2) WHAT ARE ITS INTERFACES?

    TO SIGNAL PIPELINE (0511002):
      Fires pipeline on each 5m candle close.
      Passes closed candle data, pre-computation cache,
      Parameter Store snapshot.

    TO EXECUTION ENGINE (0511003):
      Receives sizing output from Gate 8.
      Dispatches add_order on entry.

    TO EXIT CONTROLLER (0511004):
      Fires on ticker bbo (drawdown check, open positions).
      Fires on ohlc(60) close (HTF check L1a-001).
      Fires on ohlc(5m) close (max hold count L1a-003).
      Fires on 00:00 UTC (daily regime check L1a-002).
      Fires on executions fill events (L1b, L2).
      Dispatches cancel_order and batch_cancel on EC signal.

    TO POSITION MIRROR (0511005):
      WS Manager is the SOLE WRITER to Position Mirror.
      Updates on: entry dispatch (cl_ord_id recorded
      immediately at dispatch, no async gap), fill,
      partial fill, position close, reconciliation.

    TO LOGGER (0511006):
      All events, state transitions, alerts, and data
      records passed to Logger via non-blocking async queue.

    TO CIATS PARAMETER STORE:
      Reads frozen snapshot at pipeline start.
      WS Manager NEVER writes to Parameter Store directly.

    TO CIATS TRADE OUTCOME BUS:
      Fires on every full position close (TP_FILL, L1a/b,
      L2, or entry protection cancel).
      Fires ONCE per full close — aggregates partial fills.

    TO REST (Kraken):
      GetWebSocketsToken: startup and every reconnect.
      GetOHLCData: startup warm-up per pair (AR-044).
      GetOHLCData (1440): daily regime Engine seed.
      GetOpenOrders: executions gap recovery fallback.
      GetAccountBalance: balances gap recovery fallback.
      Status API: startup proactive maintenance check
        (AR-038).

(3) WHAT ARE ITS HARD RULES?

    See Section 16 for the complete consolidated hard rules
    list (HR-WM-001 through HR-WM-020 + all WM-* rules).
    Absolute prohibitions:
      - DMS (cancel_all_orders_after): NEVER CALL.
      - Startup code reuse for reconnect: NEVER.
      - pipeline eval during reconnect: PROHIBITED.
      - Decimal(float_value): PROHIBITED.
      - EMA alpha=2/15 for RSI: PROHIBITED.
      - response[-1] in any indicator calculation: PROHIBITED.
      - stp_type with hyphens in WS v2: PROHIBITED.

(4) WHAT TRIGGERS IT AND WHAT DOES IT TRIGGER?

    TRIGGERS WS MANAGER:
      Kraken ohlc(5m) close event    → Pipeline trigger
      Kraken ticker bbo event        → Drawdown check (EC)
      Kraken executions event        → Dispatch table handler
      Kraken balances event          → Balance update, seq check
      Kraken instrument event        → Status cache update
      Kraken status event            → Engine state update
      30-second timer                → JSON ping, both connections
      90-second inactivity           → Zombie detection trigger
      00:00 UTC                      → Daily regime refresh
      System startup                 → Full startup sequence
      WS disconnect                  → Reconnect sequence

    TRIGGERS WS MANAGER FIRES:
      Signal Pipeline                → on each 5m candle close
      Exit Controller                → on bbo, 00:00, fills
      Execution Engine               → on Gate 8 output
      Logger                         → on all events (async queue)
      CIATS Trade Outcome Bus        → on full position close
      Operator alert (alert@tothbot.com) → on CRITICAL events

4.1 Connection Inventory (AR-029)
------------------------------------------------------------

  PUBLIC WS v2 (wss://ws.kraken.com/v2):
    Subscriptions:
      instrument  — per-pair specs + status cache (startup)
      status      — global engine state + connection_id
      ohlc(5)     — 5-minute candle events (SYSTEM CLOCK)
                    NOTE: subscribed AFTER instrument snapshot
                    builds monitored_universe (WM-OHLC-SUB-001)
      ohlc(60)    — NOT subscribed via WS. Kraken WS v2 rejects
                    a second ohlc interval per symbol (OI-NEW-001):
                    "Already subscribed to one ohlc interval on
                    this symbol." 1H HTF cache sourced from REST
                    only via seed_indicators_from_rest() at startup
                    and after reconnect gap > 15 min.
      ticker      — price data (per-pair, event_trigger mode
                    managed per position state — Section 12)

  PRIVATE WS v2 (wss://ws-auth.kraken.com/v2):
    Inbound subscriptions:
      executions  — fills, expirations, rejections, status
      balances    — real-time settlement
    Outbound methods:
      add_order, amend_order, batch_add,
      cancel_order, batch_cancel

  Two API key pairs required (HR-WM-001, AR-037):
    DATA key:   public WS subscriptions, REST market data
    TRADE key:  private WS, REST auth, GetWebSocketsToken
    Both keys IP-whitelisted to 87.99.141.44.
    Update IP whitelist on any VPS migration (HR-WM-020).

4.2 Connection Parameters — All Four Connections
------------------------------------------------------------

  REQUIRED import (AR-060):
    from websockets.asyncio.client import connect

  DEPRECATED — DO NOT USE:
    import websockets; websockets.connect()  ← NEVER USE

WM-CONN-001  max_queue=None REQUIRED (AR-058).
             Default max_queue=16 causes message drops on
             burst events (startup snapshots, 50+ pair
             ticker bursts, post-reconnect snapshots).
             Set max_queue=None (unlimited) on ALL connections.

WM-CONN-002  Connection template (ALL FOUR CONNECTIONS):

             from websockets.asyncio.client import connect

             conn = await connect(
                 uri,
                 max_size=10 * 1024 * 1024,  # 10MB (AR-029)
                 open_timeout=10,             # 10s (AR-029)
                 max_queue=None,              # Unlimited (AR-058)
                 ping_interval=None,          # Disabled (AR-059)
             )

WM-CONN-003  Applies to all four connections:
             (a) public WS  wss://ws.kraken.com/v2
             (b) private WS wss://ws-auth.kraken.com/v2
             (c) public WS reconnect path
             (d) private WS reconnect path
             All four use identical connection parameters.

WM-CONN-004  ping_interval=None — disable library ping (AR-059).
             Application-level JSON ping is the SOLE keepalive.
             Library TCP PING frames disabled. Running both
             creates dual keepalive, library pong is invisible
             to application code and has no zombie detection
             value. Single authoritative mechanism only.

WM-CONN-005  Application-level JSON ping (A-7):
             Every 30 seconds on EACH active connection:
               {"method": "ping", "req_id": <ping_req_id>}
             Expected response within 10 seconds:
               {"method": "pong", "req_id": <ping_req_id>}
             No pong in 10s: log PING_TIMEOUT, reconnect
             immediately. This is the SOLE keepalive.

WM-CONN-006  Zombie vs Ping are two independent health checks:
             PING (A-7): Application JSON ping every 30s.
               No pong within 10s = dead TCP connection.
             ZOMBIE (A-8): Track last_real_data_time.
               > 90s without real data = zombie connection.
               Reconnect even if ping/pong is passing
               (zombie delivers pong but no market data).
             Both must be active. Neither is redundant.

WM-CONN-007  Use websockets.asyncio.client.connect (AR-060).
             Legacy websockets.connect() deprecated in v14+.
             Using deprecated API = ticking time bomb for a
             24/7 trading system.

4.4 Token Management and REST Private-Call Signing
------------------------------------------------------------

WM-TOKEN-001  WS auth token valid 900 seconds (15 minutes).
              Acquire fresh token at startup (Step 1) and
              on EVERY reconnect via REST GetWebSocketsToken.
              Call MUST be signed per WM-REST-SIGN-001.

WM-TOKEN-002  Use TRADE API key (not DATA key) for token
              acquisition. Token grants private WS access.

WM-TOKEN-003  Token stored as instance variable. Never
              persisted to disk. Regenerate on every
              reconnect — do not reuse expired tokens.

WM-REST-SIGN-001  Every private Kraken REST call made by
                  WS Manager MUST carry both the API-Key
                  header and the API-Sign header. Attaching
                  only API-Key (without API-Sign) is a
                  defect and MUST fail code review. Kraken
                  rejects every such request with
                  EAPI:Invalid key. Authoritative contract:
                  0411002 Kraken_REST_API_Specification
                  dv1_1 REST-AUTH-001 and REST-AUTH-003.
                  Private endpoints currently called by
                  WS Manager under this rule:
                    /0/private/GetWebSocketsToken
                      (WM-TOKEN-001)
                    /0/private/OpenOrders
                      (executions gap fallback, AR-035)
                    /0/private/Balance
                      (balances gap fallback, AR-035)
                  Any private endpoint added in future
                  versions MUST go through the same
                  signing path.

WM-REST-SIGN-002  The signature MUST be computed per the
                  exact formula mandated by 0411002
                  REST-AUTH-001:
                    message   = URI_path +
                                SHA256(nonce +
                                       POST_data_string)
                    signature = HMAC-SHA512(
                                  message,
                                  base64_decode(api_secret))
                    API-Sign  = base64_encode(signature)
                  URI_path is the path segment only
                  (e.g. "/0/private/GetWebSocketsToken"),
                  not the full URL. POST_data_string is
                  the urlencoded body (e.g.
                  "nonce=1700000000000"). nonce is a
                  millisecond epoch string, monotonically
                  increasing per the constraint in
                  REST-AUTH-007.
                  Implementation MUST live in a single
                  private helper on WSManager:
                    _sign_rest_request(
                      url_path: str,
                      data: dict,
                      api_secret: str,
                    ) -> tuple[str, str]
                  returning (post_data_string,
                  signature_b64). The helper is the ONLY
                  place in the code base where Kraken
                  REST signing is implemented. Call sites
                  invoke the helper; they do not inline
                  the algorithm.

WM-REST-SIGN-003  The body transmitted to Kraken MUST be
                  the exact post_data_string returned by
                  _sign_rest_request — not the source
                  dict. Any drift between the signed
                  body and the transmitted body (e.g.
                  re-urlencoding the dict a second time,
                  re-ordering keys, re-typing nonce)
                  breaks the signature and Kraken returns
                  EAPI:Invalid key. Call-site pattern:
                    data = {"nonce": str(int(
                             time.time() * 1000))}
                    post_data, signature = \
                        self._sign_rest_request(
                            url_path, data, trade_secret)
                    resp = await session.post(
                        f"{REST_BASE_URL}{url_path}",
                        headers={
                            "API-Key": trade_key,
                            "API-Sign": signature,
                            "Content-Type":
                              "application/x-www-form-urlencoded",
                        },
                        data=post_data,
                    )
                  All three call sites MUST follow this
                  pattern verbatim. Deviation is a defect.

4.5 Startup Sequence Reference
------------------------------------------------------------

WM-STARTUP-001  The complete TothBot startup sequence is
                specified in 1011014 Startup_Sequence_Coding_Spec
                dv1_3. WS Manager executes that sequence at
                launch. Key points for WS Manager coding:

                All WS connections use websockets.asyncio.client
                import connect (SS-STARTUP-006, SS-STARTUP-013,
                SS-RECON-006 in 1011014 dv1_4).

                max_queue=None and ping_interval=None on all
                connections (1011014 dv1_4, AR-058/059).

                portfolio_baseline_USD set ONCE at Step 6
                (snap_orders reconcile complete). NEVER updated
                during operation. NEVER reset on reconnect.

                systemd sd_notify READY=1 issued after startup
                sequence completes (SS-STARTUP-026 in 1011014).

WM-RUN-001  run() exception handling MUST extract sub-exceptions
            from ExceptionGroup (Python 3.11+ asyncio.TaskGroup
            raises ExceptionGroup on task failure — str(exc)
            only shows the outer wrapper message, permanently
            losing the actual root cause).

            Required implementation in the except block of run():

              import traceback

              tb_str = traceback.format_exc()
              sub_msgs: list[str] = []
              if isinstance(exc, ExceptionGroup):
                  for i, sub in enumerate(exc.exceptions):
                      sub_tb = "".join(
                          traceback.format_tb(sub.__traceback__)
                      )
                      sub_msgs.append(
                          f"[{i}] {type(sub).__name__}: {sub} "
                          f"| tb: {sub_tb}"
                      )
              log WS_MGR_FATAL (CRITICAL) with fields:
                error:          str(exc)
                traceback:      tb_str[-2000:]
                sub_exceptions: sub_msgs or None

            This is the ONLY correct way to surface the actual
            TaskGroup crash cause. DEFECT-WM-CRASH-001 was caused
            by the absence of this extraction.

5. INBOUND MESSAGE DISPATCH
============================================================

------------------------------------------------------------
5.1 O(1) Dispatch Table — Channel Level (AR-015)
------------------------------------------------------------

All inbound WS messages routed via O(1) dispatch table
keyed on channel. Unknown message types logged as
UNKNOWN_MESSAGE_TYPE (WARN) — NEVER silently dropped.

  DISPATCH TABLE (channel → handler):
    "ohlc"        → handle_ohlc(msg)
    "ticker"      → handle_ticker(msg)
    "instrument"  → handle_instrument(msg)
    "status"      → handle_status(msg)
    "executions"  → handle_executions(msg)
    "balances"    → handle_balances(msg)
    "pong"        → handle_pong(msg)
    DEFAULT       → log UNKNOWN_MESSAGE_TYPE (WARN)

------------------------------------------------------------
5.2 Channel Handlers
------------------------------------------------------------

handle_ohlc(msg):
  - Update last_real_data_time for this connection.
  - Apply candle-close detection (Section 8).
  - If ohlc(5m) and candle closed: fire pipeline.
  - If ohlc(60) and candle closed: fire Exit Controller
    HTF check and update htf_ema_20, htf_ema_50.

handle_ticker(msg):
  - Update last_real_data_time for this connection.
  - Extract bid = Decimal(str(msg["data"][0]["bid"])).
  - Update drawdown calculation (Section 11).
  - Fire Exit Controller MAE check for open positions.

handle_instrument(msg):
  - Update last_real_data_time for this connection.
  - Update pair_status cache per symbol.
  - On startup snapshot: populate monitored_universe
    (Section 9.1). Build price_increment, qty_min,
    cost_min, qty_increment per pair (AR-028).
  - On startup snapshot: after monitored_universe is
    built, schedule _subscribe_ohlc_channels() via
    asyncio.create_task() (WM-OHLC-SUB-001).
    ohlc(5) subscribed with explicit symbol list =
    monitored_universe. NOTE: ohlc(60) NOT subscribed
    via WS (OI-NEW-001 — Kraken one-interval-per-symbol
    constraint). This is the ONLY correct time to
    subscribe ohlc — Kraken WS v2 rejects ohlc
    subscription without a symbol list.
  - _subscribe_ohlc_channels() triggers REST warm-up
    immediately after subscription via
    asyncio.create_task(_warm_up_all_pairs())
    (WM-WARMUP-001).

handle_status(msg):
  - Update last_real_data_time for this connection.
  - Extract and log connection_id (WM-STATUS-001).
  - Update system and api_version from status data.

handle_executions(msg):
  - Update last_real_data_time (private connection).
  - Check sequence gap (Section 7.4).
  - Update rate counter from msg (A-1, AR-030).
  - Dispatch to exec_type handler (Section 5.3).

handle_balances(msg):
  - Update last_real_data_time (private connection).
  - Check sequence gap (Section 7.3).
  - Extract spot USD balance (Section 10).

handle_pong(msg):
  - Record pong receipt (cancel ping timeout timer).
  - DO NOT reset last_real_data_time.
  - Log PONG_RECEIVED.

------------------------------------------------------------
5.3 exec_type Dispatch Table — All 10 Values (AR-023)
------------------------------------------------------------

ALL 10 exec_type values MUST be handled explicitly.
No silent drops. Unknown exec_type logged as WARNING.

  executions dispatch (exec_type → handler):
    "pending_new"    → handle_pending_new
    "new"            → handle_new
    "trade"          → handle_trade
    "filled"         → handle_filled
    "iceberg_refill" → handle_iceberg_refill
    "canceled"       → handle_canceled
    "expired"        → handle_expired
    "amended"        → handle_amended
    "restated"       → handle_restated
    "status"         → handle_exec_status
    DEFAULT          → log UNKNOWN_EXEC_TYPE (WARN)

Note: Use reason field (NOT cancel_reason — deprecated,
AR-022) in canceled and expired event parsing.

handle_pending_new(event):
  Order accepted by matching engine. Register in
  req_id_registry. No Position Mirror update.

handle_new(event):
  Order live on book. Confirm via log. No Mirror update.

handle_trade(event):
  Partial fill event.
  Extract: cum_qty=Decimal(str(event["cum_qty"])),
           avg_price=Decimal(str(event["avg_price"])),
           last_qty=Decimal(str(event["last_qty"])),
           last_price=Decimal(str(event["last_price"])).
  Identify order type:
    - If order_id matches a TP order_id in Position Mirror
      → Section 5.4 (TP partial fill).
    - If order_id matches an entry order → Update Position
      Mirror cum_qty and avg_price.
  Log FILL_EVENT with all four values (WM-EXE-014).

handle_filled(event):
  Full fill.
  If entry order filled: Execution Engine dispatches
    batch_add (TP limit + emergSL stop) per 0511003.
  If TP order filled: L1b logic. Exit Controller cancels
    emergSL (0511004). Fire CIATS Trade Outcome Bus.

handle_iceberg_refill(event):
  Log only. No Position Mirror update. No action.

handle_canceled(event):
  Clear cl_ord_id from Pending Order Registry.
  If entry order AND cum_qty > 0: Section 5.5 (entry
    partial fill protection, CASE B).
  If entry order AND cum_qty == 0: Section 5.5 (CASE C).
  If exit order canceled: cancel timeout fallback — check
    req_id_registry for ACK state.

handle_expired(event):
  Same handling as handle_canceled.
  Entry AND cum_qty > 0: Section 5.5 (CASE A).
  Entry AND cum_qty == 0: Section 5.5 (CASE C).

handle_amended(event):
  TothBot V2 NEVER sends amend_order for its own orders
  during normal operation (except emergSL qty adjustment
  which uses amend_order — that is NOT processed as an
  inbound amended event).
  Any inbound amended event is UNEXPECTED (AR-057).
  See Section 5.6 for handler implementation.

handle_restated(event):
  Engine maintenance amend. NOT a fill or cancel.
  DO NOT update Position Mirror.
  If resting order affected: elevated alert (AR-024).
  Log EXEC_RESTATED.

handle_exec_status(event):
  Order status snapshot. Parse trigger update data
  (stop trigger price, state). Log. No trade action.
  Used to confirm emergSL placement on Kraken
  (WM-EXE-013).

------------------------------------------------------------
5.4 TP Partial Fill Handling (AR-066)
------------------------------------------------------------

WM-EC-004  TP partial fill occurs when exec_type=trade
           for a TP order (identified by matching order_id
           against TP order_ids across all Position Mirror
           entries).

WM-EC-005  Identification on trade exec_type:
           1. Check order_id against tp_order_id in
              Position Mirror for all open positions.
           2. If TP match found → PARTIAL_TP_FILL path.
           3. If entry match → entry partial update path.

WM-EC-006  Partial TP fill sequence:

           def handle_partial_tp_fill(event, symbol):
               cum_qty    = Decimal(str(event["cum_qty"]))
               avg_exit   = Decimal(str(event["avg_price"]))
               pos        = position_mirror[symbol]
               orig_qty   = pos["qty"]
               remaining  = orig_qty - cum_qty
               emergsl_id = pos["emergsl_order_id"]
               p_incr     = pair_cache[symbol]["price_increment"]
               q_incr     = pair_cache[symbol]["qty_increment"]
               qty_min    = pair_cache[symbol]["qty_min"]
               cost_min   = pair_cache[symbol]["cost_min"]
               bid        = latest_bid[symbol]

               # Update Position Mirror
               position_mirror[symbol]["qty"] = remaining

               # Quantize remaining qty
               remaining_r = remaining.quantize(q_incr,
                                 ROUND_DOWN)

               # Check minimum size
               if (remaining_r < qty_min or
                   remaining_r * bid < cost_min):
                   # Cannot protect — exit remainder
                   cancel_order(emergsl_id)
                   dispatch_market_sell(symbol, remaining_r)
                   del position_mirror[symbol]
                   logger.log("TP_PARTIAL_FILL_BELOW_MIN_EXIT",
                       symbol=symbol, remaining=remaining_r)
                   return

               # Amend emergSL qty (NOT cancel+resubmit)
               amend_order(
                   order_id=emergsl_id,
                   order_qty=remaining_r,
                   token=ws_token
               )
               logger.log("TP_PARTIAL_FILL",
                   symbol=symbol,
                   filled_qty=cum_qty,
                   remaining_qty=remaining_r,
                   avg_exit_price=avg_exit,
                   emergsl_amended_to=remaining_r)

WM-EC-007  WHY amend_order, NOT cancel+resubmit:
           cancel_order (emergSL <5s): +8 rate counter
           add_order (new emergSL): +1 rate counter
           Total cancel+resubmit: +9 rate counter units

           amend_order (resting >300s): +1+1 = +2 rate units
           Saves 7 rate counter units per TP partial fill.
           Also preserves queue position on Kraken book —
           important during high-volatility events when
           rate limits may already be under pressure.

WM-EC-008  Full TP fill (exec_type=filled for TP):
           Existing L1b logic unchanged. Cancel emergSL,
           clear Position Mirror, fire CIATS Trade Outcome
           Bus. No qty amendment needed.

           Fire CIATS Trade Outcome Bus ONCE per full
           position close — aggregate all partial fill data.
           NOT on each individual partial fill.

  rsi_14_avg_loss:     Decimal  — Wilder SMMA loss state
  ema_9:               Decimal  — standard EMA, alpha=0.2
  ema_21:              Decimal  — standard EMA, alpha=2/22
  volume_ma_20:        Decimal  — rolling 20-candle SMA
  last_interval_begin: str      — candle close detection
  last_complete_candle: OHLCCandle  — closed candle data

SEED FORMULAS (from GetOHLCData response[:-1]):

  ATR(14):
    Seed:        SMA of first 14 True Ranges.
                   TR = max(high-low, |high-prev_close|,
                            |low-prev_close|)
    Incremental: ATR = (prev_ATR * 13 + current_TR) / 14
    O(1) per update (AR-016).

  RSI(14) — Wilder's SMMA (AR-076):
    Seed:
      avg_gain = sum(gains[:14]) / 14
      avg_loss = sum(losses[:14]) / 14
    Incremental:
      avg_gain = (prev_avg_gain * 13 + gain) / 14
      avg_loss = (prev_avg_loss * 13 + loss) / 14
      RS = avg_gain / avg_loss
      RSI = 100 - (100 / (1 + RS))
    !! DO NOT use EMA alpha=2/15 for RSI (HR-WM-018) !!
    Wilder's SMMA alpha = 1/14. Standard EMA alpha=2/15
    is WRONG for RSI and MUST NOT be used.

  EMA(9):
    Seed: SMA of first 9 closes.
    Incremental: alpha = 2/10 = 0.2
      EMA = alpha * close + (1 - alpha) * prev_EMA

  EMA(21):
    Seed: SMA of first 21 closes.
    Incremental: alpha = 2/22
      EMA = alpha * close + (1 - alpha) * prev_EMA

  Vol MA(20):
    Seed: SMA of first 20 volumes.
    Incremental: rolling SMA (sum last 20 / 20).

WARM-UP STATE MACHINE (AR-068):
  warm_up_state: dict[str, str]  {"WARM_UP" | "READY"}
  Pair transitions WARM_UP → READY only when ALL FIVE
  indicators are seeded. (ATR, RSI, EMA9, EMA21, VolMA20.)
  WARM_UP pairs SKIPPED at pipeline pre-check.
  READY pairs begin trading immediately — system does NOT
  wait for all pairs to reach READY.

WM-LIQ-011  _rest_build_pair_maps() method:

14. DECIMAL ROUNDING (AR-047)
============================================================

WM-ROUND-001  All numeric values from Kraken (WS or REST):
              ALWAYS convert via Decimal(str(value)).
              NEVER Decimal(float_value).
              Decimal(float) inherits float binary precision
              error. Exchange orders with precision errors
              are rejected = failed trade = loss.

              Applies to: ticker bid/ask, executions
              avg_price, order_qty, cum_qty, last_qty,
              last_price, instrument price_increment,
              qty_increment, qty_min, cost_min, balances.

WM-ROUND-002  Entry limit_price rounding:
              from decimal import Decimal, ROUND_DOWN
              D_incr = Decimal(str(price_increment))
              limit_price = raw_price.quantize(
                  D_incr, rounding=ROUND_DOWN)
              Conservative: lower limit → more likely
              post_only fill.

WM-ROUND-003  order_qty rounding:
              D_incr = Decimal(str(qty_increment))
              order_qty = raw_qty.quantize(
                  D_incr, rounding=ROUND_DOWN)
              ROUND_DOWN for quantities — never overshoot.

WM-ROUND-004  TP limit_price rounding:
              tp_price = raw_tp.quantize(
                  D_incr, rounding=ROUND_UP)
              ROUND_UP for TP — higher TP preserves net R:R.

WM-ROUND-005  emergSL trigger price rounding:
              sl_price = raw_sl.quantize(
                  D_incr, rounding=ROUND_DOWN)
              ROUND_DOWN for stop — wider stop = more
              protective.

WM-ROUND-006  Cost validation before every order dispatch:
              if (order_qty < qty_min or
                  order_qty * price < cost_min):
                  SKIP — do not dispatch.
                  Log INSUFFICIENT_QTY with both check values.

WM-ROUND-007  Use ROUND_DOWN and ROUND_UP (not ROUND_FLOOR
              and ROUND_CEILING). For positive prices these
              are equivalent, but ROUND_DOWN/UP avoids
              incorrect behavior if negative prices ever
              appear unexpectedly.

                  (same as startup Steps 7a-7b).

WM-RECONNECT-015  exit_cooldown_log and consecutive_loss_count:
                  PRESERVED across reconnect (WM-SC-003).
                  NEVER discarded.

WM-RECONNECT-016  Transient WS disconnect errors
                    (ConnectionClosedError,
                     ConnectionClosedOK,
                     ConnectionResetError)
                  raised by the WS iterator (async for in
                  _recv_loop_public / _recv_loop_private) or by
                  ws.send() in _send_public / _send_private MUST be
                  caught LOCALLY at the point of raise. Each catch MUST:
                    (a) log RECONNECT_TRIGGERED (component=WS_MGR,
                        level=HIGH) with "source" and "error_type"
                        context fields,
                    (b) invoke _initiate_reconnect() — awaited in recv
                        loops; scheduled via asyncio.create_task() in
                        send helpers so the send caller is not blocked,
                    (c) NOT propagate the exception to the _main_loop
                        TaskGroup.
                  Receive loops resume iteration on the new connection
                  object after reconnect completes (self._ws_public and
                  self._ws_private are reassigned inside
                  _execute_reconnect_sequence). Send helpers swallow the
                  failed send — the send is lost but the process does
                  NOT terminate. This rule is the primary fix for
                  DEFECT-WM-RECONNECT-001.

                  A clean (non-exception) exit of the async-for in
                  either recv loop is ALSO treated as a disconnect
                  (reconnect triggered, loop resumes). This covers
                  websockets-library edge cases where the server closes
                  the connection without raising.

WM-RECONNECT-017  _initiate_reconnect() retry schedule:
                    attempts: MAX_RECONNECT_ATTEMPTS   = 10
                    base:     RECONNECT_BACKOFF_BASE_SEC = 1.0 s
                    cap:      RECONNECT_BACKOFF_CAP_SEC  = 30.0 s
                    factor:   RECONNECT_BACKOFF_FACTOR   = 2.0
                  Matches WM-RECONNECT-002 (10 attempts, cap 30s).
                  Worst-case wall time across all attempts:
                    1 + 2 + 4 + 8 + 16 + 30 + 30 + 30 + 30 + 30 = 181s
                  (upper bound on sleep — actual attempt latency adds).
                  FATAL_RECONNECT_FAILURE MUST be raised ONLY after all
                  N attempts have been exhausted. Each failed attempt
                  logs RECONNECT_ATTEMPT_FAILED (level=WARN, non-fatal).
                  Each successful reconnect logs RECONNECT_COMPLETE
                  (level=INFO) with "attempts" count. All four numbers
                  are module-level constants declared at the top of
                  ws_manager.py — no magic numbers (DC-4).

WM-RECONNECT-018  The _main_loop() TaskGroup MUST receive only truly
                  fatal conditions. The three transient types named in
                  WM-RECONNECT-016 MUST be fully handled at loop level.
                  If the TaskGroup ever observes any of the three
                  transient types as a sub-exception, that is a
                  WM-RECONNECT-016 defect (a loop-level catch is
                  missing or broken).

                  Implementation gate:
                    self._reconnect_done_event: asyncio.Event
                  Cleared by _initiate_reconnect on entry; set in its
                  finally block on every exit path (success, fatal, or
                  re-entry). Concurrent disconnect detection by both
                  recv loops collapses to a single reconnect cycle:
                  whichever loop reaches _initiate_reconnect first
                  drives the retry schedule; the other awaits the
                  event and returns without starting a second cycle.

                  Terminal flag:
                    self._fatal_reconnect_failure: bool
                  Set by _initiate_reconnect immediately before raising
                  the final RuntimeError. Prevents siblings that awaken
                  from the event wait from starting a fresh retry cycle
                  while TaskGroup teardown is in flight. Recv loops and
                  send helpers check this flag and short-circuit when
                  set.

WM-RECONNECT-019  Paper-mode reconnect gating (OI-028 /
                  FIX-WM-RECONNECT-019, dv1_21).

                  When self.paper_mode is True,
                  _execute_reconnect_sequence MUST skip every
                  private-side step:
                    - Step 1: _rest_get_ws_token()            SKIP
                    - Step 2b: _ws_connect(PRIVATE_WS_URI)    SKIP
                    - Step 3b: _subscribe_private()           SKIP
                    - Step 4: _rest_get_open_orders() +
                              _detect_gap_closed_positions     SKIP
                    - Step 5: GAP_CLOSED_POSITION logging      SKIP
                    - Step 6: _reconcile_pending_orders()      SKIP
                    - Step 7: executions_last_seq /
                              balances_last_seq resets         SKIP

                  Paper-mode reconnect executes ONLY the
                  public-side subset:
                    - Step 2a: _ws_connect(PUBLIC_WS_URI)
                    - Step 3a: _subscribe_public()
                    - Step 8:  resume ticker subscriptions for
                               every symbol in monitored_universe
                    - Step 10: if gap_sec >
                               RECONNECT_STALE_CACHE_SEC,
                               seed_indicators_from_rest() for
                               every symbol

                  This mirrors the paper-mode branch of
                  _startup_connect_and_subscribe (FIX-WM-PT-001,
                  dv1_14). Rationale: private Kraken API key is
                  not exercised anywhere in paper mode — order
                  dispatch is suppressed, balance is static,
                  executions channel is unused. Calling
                  _rest_get_ws_token() in paper mode requires a
                  valid private key for signature generation
                  and exchanges the key with Kraken; in the
                  current deployment that key is rejected by
                  Kraken (EAPI:Invalid key — tracked as OI-041).
                  Every paper-mode reconnect therefore failed at
                  Step 1, consumed a retry attempt, and after
                  MAX_RECONNECT_ATTEMPTS consecutive identical
                  failures reached the FATAL_RECONNECT_FAILURE
                  exit path → systemd restart.

                  Preserved invariants:
                    - HR-WM-013 portfolio_baseline_USD NEVER
                      reset on reconnect (paper balance too).
                    - HR-WM-011 system_state PRESERVED.
                    - WM-SC-003 exit_cooldown_log and
                      consecutive_loss_count PRESERVED.

                  Live mode reconnect (self.paper_mode == False)
                  is unchanged — full Steps 1-10 still apply
                  per WM-RECONNECT-003 through WM-RECONNECT-014.

                  Test coverage (1021001):
                    - paper-mode reconnect completes with no
                      private-WS calls and no REST auth calls
                    - live-mode reconnect unchanged
                    - gap > RECONNECT_STALE_CACHE_SEC in paper
                      mode triggers indicator re-seed

16. TICKER EVENT_TRIGGER MANAGEMENT (AR-034)
============================================================

  Pairs WITH open positions:
    Subscribe ticker with event_trigger:bbo.
    bbo fires on every bid/ask change.
    bid updates drive MAE detection and drawdown MTM.
    More frequent than trades trigger — necessary for
    adverse price detection on open longs.

  Pairs WITHOUT open positions:
    Subscribe ticker with event_trigger:trades.
    Conserves WS bandwidth. Trade events sufficient
    for price monitoring on no-position pairs.

  WS Manager updates ticker subscription mode:
    On position open: switch symbol to event_trigger:bbo.
    On position close: switch symbol to event_trigger:trades.
  Subscription update is sent immediately on position
  state change — no deferred mode switch.

WS MANAGER CODING SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document specifies the complete, unambiguous
implementation requirements for the WS Manager component
of TothBot V2. It is the direct input to code.

The WS Manager is TothBot's sole interface to all Kraken
WebSocket v2 connections. It is the central event processor
for the entire system. All Kraken push events flow through
it. All outbound orders originate from it.

This document supersedes and retires all prior WD versions
(dv1_0 through dv1_11). No TBD sections remain.

3. FIVE CODING-READINESS QUESTIONS
============================================================

(1) WHAT DOES WS MANAGER DO?

    Maintains all Kraken WS v2 connections (public and
    private). Receives all Kraken push events (ohlc, ticker,
    executions, balances, instrument, status). Dispatches
    inbound messages to correct handlers via O(1) dispatch
    table (AR-015). Manages per-symbol state: pair status
    cache, indicator state (ATR, RSI, EMA9, EMA21, VolMA20),
    HTF cache (EMA20, EMA50 — seeded from REST only, no WS
    ohlc(60) subscription per HR-WM-021), warm-up state
    machine (WARM_UP → READY), 24h liquidity cache
    (liquidity_24h — populated from REST Ticker at startup
    and refreshed periodically per WM-LIQ-001 through
    WM-LIQ-010). Fires pipeline trigger on each
    5-minute candle close. Fires Exit Controller on ticker bbo
    events for open positions, daily regime check (00:00 UTC),
    and 5m candle close for max hold count. Executes all WS
    outbound messages (add_order, batch_add, cancel_order,
    amend_order, batch_cancel). Manages token acquisition
    (startup and every reconnect). Manages startup indicator
    warm-up via _warm_up_all_pairs() — triggered from
    _subscribe_ohlc_channels() after ohlc(5) subscription
    sent (WM-WARMUP-001). Tracks portfolio_baseline_USD
    (set once at startup Step 6, never reset). Updates
    spot_usd_balance from balances channel. Computes
    drawdown_pct from mark-to-market. Enforces SESSION_PAUSE
    and FULL_HALT drawdown circuit breakers. Maintains
    Pending Order Registry (cl_ord_id → estimated_USD_cost).
    Detects entry partial fills (GTD expiry/cancel with
    cum_qty > 0) and dispatches batch_add protection.
    Handles TP partial fills by amending emergSL qty (not
    cancel+resubmit). Dispatches CIATS Trade Outcome Bus
    on each full position close. Manages application-level
    JSON ping (30s). Detects zombie connections (90s no real
    data). Detects sequence gaps (executions and balances).
    Manages mid-session reconnect as a separate code path.
    Maintains Selection Controller state (exit_cooldown_log,
    consecutive_loss_count) across reconnects. Manages
    ticker event_trigger subscription per pair position state.
    Alerts on unexpected order amendments (amended exec_type).
    Logs all events to Logger (non-blocking async queue).
    Prohibits cancel_all_orders_after under all circumstances.

(2) WHAT ARE ITS INTERFACES?

    TO SIGNAL PIPELINE (0511002):
      Fires pipeline on each 5m candle close.
      Passes closed candle data, pre-computation cache,
      Parameter Store snapshot.

    TO EXECUTION ENGINE (0511003):
      Receives sizing output from Gate 8.
      Dispatches add_order on entry.

    TO EXIT CONTROLLER (0511004):
      Fires on ticker bbo (drawdown check, open positions).
      Fires on ohlc(60) close (HTF check L1a-001).
      Fires on ohlc(5m) close (max hold count L1a-003).
      Fires on 00:00 UTC (daily regime check L1a-002).
      Fires on executions fill events (L1b, L2).
      Dispatches cancel_order and batch_cancel on EC signal.

    TO POSITION MIRROR (0511005):
      WS Manager is the SOLE WRITER to Position Mirror.
      Updates on: entry dispatch (cl_ord_id recorded
      immediately at dispatch, no async gap), fill,
      partial fill, position close, reconciliation.

    TO LOGGER (0511006):
      All events, state transitions, alerts, and data
      records passed to Logger via non-blocking async queue.

    TO CIATS PARAMETER STORE:
      Reads frozen snapshot at pipeline start.
      WS Manager NEVER writes to Parameter Store directly.

    TO CIATS TRADE OUTCOME BUS:
      Fires on every full position close (TP_FILL, L1a/b,
      L2, or entry protection cancel).
      Fires ONCE per full close — aggregates partial fills.

    TO REST (Kraken):
      GetWebSocketsToken: startup and every reconnect.
      GetOHLCData: startup warm-up per pair (AR-044).
      GetOHLCData (1440): daily regime Engine seed.
      GetOpenOrders: executions gap recovery fallback.
      GetAccountBalance: balances gap recovery fallback.
      Status API: startup proactive maintenance check
        (AR-038).

(3) WHAT ARE ITS HARD RULES?

    See Section 16 for the complete consolidated hard rules
    list (HR-WM-001 through HR-WM-020 + all WM-* rules).
    Absolute prohibitions:
      - DMS (cancel_all_orders_after): NEVER CALL.
      - Startup code reuse for reconnect: NEVER.
      - pipeline eval during reconnect: PROHIBITED.
      - Decimal(float_value): PROHIBITED.
      - EMA alpha=2/15 for RSI: PROHIBITED.
      - response[-1] in any indicator calculation: PROHIBITED.
      - stp_type with hyphens in WS v2: PROHIBITED.

(4) WHAT TRIGGERS IT AND WHAT DOES IT TRIGGER?

    TRIGGERS WS MANAGER:
      Kraken ohlc(5m) close event    → Pipeline trigger
      Kraken ticker bbo event        → Drawdown check (EC)
      Kraken executions event        → Dispatch table handler
      Kraken balances event          → Balance update, seq check
      Kraken instrument event        → Status cache update
      Kraken status event            → Engine state update
      30-second timer                → JSON ping, both connections
      90-second inactivity           → Zombie detection trigger
      00:00 UTC                      → Daily regime refresh
      System startup                 → Full startup sequence
      WS disconnect                  → Reconnect sequence

    TRIGGERS WS MANAGER FIRES:
      Signal Pipeline                → on each 5m candle close
      Exit Controller                → on bbo, 00:00, fills
      Execution Engine               → on Gate 8 output
      Logger                         → on all events (async queue)
      CIATS Trade Outcome Bus        → on full position close
      Operator alert (alert@tothbot.com) → on CRITICAL events

(5) WHAT DOES IT LOG?

    All log entries include: timestamp (UTC), component=WS_MGR,
    symbol (where applicable), connection_id, level.

    STARTUP:        WS_TOKEN_ACQUIRED, WS_CONNECTED (with
                    connection_id), INSTRUMENT_SNAPSHOT_COMPLETE,
                    SUBSCRIPTION_ACK (warnings if any),
                    MAXRATECOUNT_SET, WARM_UP_STARTED,

                    KRAKEN_MAINTENANCE_SCHEDULED,

    CONNECTION:     PING_SENT, PONG_RECEIVED, PING_TIMEOUT,
                    ZOMBIE_CONNECTION_DETECTED,
                    RECONNECT_INITIATED, RECONNECT_COMPLETE,
                    RECONNECT_TRIGGERED, SEND_DISCONNECT,
                    RECONNECT_ATTEMPT_FAILED,
                    FATAL_RECONNECT_FAILURE,
                    CONNECTION_ID_LOGGED
    SEQUENCE GAPS:  EXECUTIONS_SEQUENCE_GAP,

    CANDLE EVENTS:  CANDLE_CLOSE (symbol, interval, OHLC)
    EXEC DISPATCH:  EXEC_TRADE (cum_qty, avg_price, last_qty,

                    UNEXPECTED_ORDER_AMENDED (CRITICAL),

4. WS CONNECTION ARCHITECTURE
============================================================

------------------------------------------------------------
4.1 Connection Inventory (AR-029)
------------------------------------------------------------

  PUBLIC WS v2 (wss://ws.kraken.com/v2):
    Connection model: N_conns shards (PATH 2 per
                      0511001 dv1_4 §15A ADR / §3.1.1).
                      Each shard is an independent
                      WebSocket connection. Connection-
                      wide channels (instrument, status)
                      are subscribed ONCE on shard 0;
                      per-pair channels (ohlc, ticker)
                      are subscribed on the assigned
                      shard for each pair.

    Subscriptions on shard 0 ONLY:
      instrument  — per-pair specs + status cache (startup)
      status      — global engine state + connection_id

    Subscriptions per shard (each shard subscribes its
    own assigned symbol partition):
      ohlc(5)     — 5-minute candle events (SYSTEM CLOCK)
                    NOTE: subscribed AFTER instrument snapshot
                    builds tradeable_universe (WM-OHLC-SUB-001)
      ohlc(60)    — NOT subscribed via WS. Kraken WS v2 rejects
                    a second ohlc interval per symbol (OI-NEW-001):
                    "Already subscribed to one ohlc interval on
                    this symbol." 1H HTF cache sourced from REST
                    only via seed_indicators_from_rest() at startup
                    and after reconnect gap > 15 min.
      ticker      — price data (per-pair, event_trigger mode
                    managed per position state — Section 12)

  PRIVATE WS v2 (wss://ws-auth.kraken.com/v2):
    Connection model: SINGLE connection. Private feed is
                      account-scoped, not symbol-sharded.
    Inbound subscriptions:
      executions  — fills, expirations, rejections, status
      balances    — real-time settlement
    Outbound methods:
      add_order, amend_order, batch_add,
      cancel_order, batch_cancel

  Total connection count at runtime:
    Live mode:   N_conns (public shards) + 1 (private)
    Paper mode:  N_conns (public shards), no private

  N_conns formula:
    N_conns = ceil(universe_size / SYMBOLS_PER_CONN_SAFE)
    SYMBOLS_PER_CONN_SAFE = 500 (CIATS-owned starting
                                 value; never hardcoded)

  Two API key pairs required (HR-WM-001, AR-037):
    DATA key:   public WS subscriptions, REST market data
    TRADE key:  private WS, REST auth, GetWebSocketsToken
    Both keys IP-whitelisted to 87.99.141.44.
    Update IP whitelist on any VPS migration (HR-WM-020).

4.2 Connection Parameters — All Connections (Public Shards
    + Private + Reconnect Paths)
------------------------------------------------------------

  REQUIRED import (AR-060):
    from websockets.asyncio.client import connect

  DEPRECATED — DO NOT USE:
    import websockets; websockets.connect()  ← NEVER USE

WM-CONN-001  max_queue=None REQUIRED (AR-058).
             Default max_queue=16 causes message drops on
             burst events (startup snapshots, 50+ pair
             ticker bursts, post-reconnect snapshots).
             Set max_queue=None (unlimited) on ALL connections.

WM-CONN-002  Connection template (ALL FOUR CONNECTIONS):

             from websockets.asyncio.client import connect

             conn = await connect(
                 uri,
                 max_size=10 * 1024 * 1024,  # 10MB (AR-029)
                 open_timeout=10,             # 10s (AR-029)
                 max_queue=None,              # Unlimited (AR-058)
                 ping_interval=None,          # Disabled (AR-059)
             )

WM-CONN-003  Applies to all connections at runtime:
             (a) public WS shards 0..N_conns-1
                 (each at wss://ws.kraken.com/v2)
             (b) private WS (wss://ws-auth.kraken.com/v2)
             (c) public WS shard reconnect paths
                 (per-shard reconnect)
             (d) private WS reconnect path
             All connections use identical connection
             parameters. The shard count N_conns is
             determined at runtime per §4.6 sharding
             contract; there is no hardcoded
             connection count.

WM-CONN-004  ping_interval=None — disable library ping (AR-059).
             Application-level JSON ping is the SOLE keepalive.
             Library TCP PING frames disabled. Running both
             creates dual keepalive, library pong is invisible
             to application code and has no zombie detection
             value. Single authoritative mechanism only.

WM-CONN-005  Application-level JSON ping (A-7):
             Every 30 seconds on EACH active connection
             (every public shard runs its own 30-second
             ping; private runs its own 30-second ping):
               {"method": "ping", "req_id": <ping_req_id>}
             Expected response within 10 seconds:
               {"method": "pong", "req_id": <ping_req_id>}
             No pong in 10s on a given connection: log
             PING_TIMEOUT (level=ERROR, with shard_index
             or "private"), reconnect that connection
             ONLY (per §4.6 per-shard reconnect
             semantics; PRIVATE reconnect per §11
             of 0511001 dv1_4). This is the SOLE
             keepalive.

WM-CONN-006  Zombie vs Ping are two independent health checks:
             PING (A-7): Application JSON ping every 30s.
               No pong within 10s = dead TCP connection.
             ZOMBIE (A-8): Track last_real_data_time.
               > 90s without real data = zombie connection.
               Reconnect even if ping/pong is passing
               (zombie delivers pong but no market data).
             Both must be active. Neither is redundant.

WM-CONN-007  Use websockets.asyncio.client.connect (AR-060).
             Legacy websockets.connect() deprecated in v14+.
             Using deprecated API = ticking time bomb for a
             24/7 trading system.

4.4 Token Management and REST Private-Call Signing
------------------------------------------------------------

WM-TOKEN-001  WS auth token valid 900 seconds (15 minutes).
              Acquire fresh token at startup (Step 1) and
              on EVERY reconnect via REST GetWebSocketsToken.
              Call MUST be signed per WM-REST-SIGN-001.

WM-TOKEN-002  Use TRADE API key (not DATA key) for token
              acquisition. Token grants private WS access.

WM-TOKEN-003  Token stored as instance variable. Never
              persisted to disk. Regenerate on every
              reconnect — do not reuse expired tokens.

WM-REST-SIGN-001  Every private Kraken REST call made by
                  WS Manager MUST carry both the API-Key
                  header and the API-Sign header. Attaching
                  only API-Key (without API-Sign) is a
                  defect and MUST fail code review. Kraken
                  rejects every such request with
                  EAPI:Invalid key. Authoritative contract:
                  0411002 Kraken_REST_API_Specification
                  dv1_1 REST-AUTH-001 and REST-AUTH-003.
                  Private endpoints currently called by
                  WS Manager under this rule:
                    /0/private/GetWebSocketsToken
                      (WM-TOKEN-001)
                    /0/private/OpenOrders
                      (executions gap fallback, AR-035)
                    /0/private/Balance
                      (balances gap fallback, AR-035)
                  Any private endpoint added in future
                  versions MUST go through the same
                  signing path.

WM-REST-SIGN-002  The signature MUST be computed per the
                  exact formula mandated by 0411002
                  REST-AUTH-001:
                    message   = URI_path +
                                SHA256(nonce +
                                       POST_data_string)
                    signature = HMAC-SHA512(
                                  message,
                                  base64_decode(api_secret))
                    API-Sign  = base64_encode(signature)
                  URI_path is the path segment only
                  (e.g. "/0/private/GetWebSocketsToken"),
                  not the full URL. POST_data_string is
                  the urlencoded body (e.g.
                  "nonce=1700000000000"). nonce is a
                  millisecond epoch string, monotonically
                  increasing per the constraint in
                  REST-AUTH-007.
                  Implementation MUST live in a single
                  private helper on WSManager:
                    _sign_rest_request(
                      url_path: str,
                      data: dict,
                      api_secret: str,
                    ) -> tuple[str, str]
                  returning (post_data_string,
                  signature_b64). The helper is the ONLY
                  place in the code base where Kraken
                  REST signing is implemented. Call sites
                  invoke the helper; they do not inline
                  the algorithm.

WM-REST-SIGN-003  The body transmitted to Kraken MUST be
                  the exact post_data_string returned by
                  _sign_rest_request — not the source
                  dict. Any drift between the signed
                  body and the transmitted body (e.g.
                  re-urlencoding the dict a second time,
                  re-ordering keys, re-typing nonce)
                  breaks the signature and Kraken returns
                  EAPI:Invalid key. Call-site pattern:
                    data = {"nonce": str(int(
                             time.time() * 1000))}
                    post_data, signature = \
                        self._sign_rest_request(
                            url_path, data, trade_secret)
                    resp = await session.post(
                        f"{REST_BASE_URL}{url_path}",
                        headers={
                            "API-Key": trade_key,
                            "API-Sign": signature,
                            "Content-Type":
                              "application/x-www-form-urlencoded",
                        },
                        data=post_data,
                    )
                  All three call sites MUST follow this
                  pattern verbatim. Deviation is a defect.

4.5 Startup Sequence Reference
------------------------------------------------------------

WM-STARTUP-001  The complete TothBot startup sequence is
                specified in 1011014 Startup_Sequence_Coding_Spec
                dv1_3. WS Manager executes that sequence at
                launch. Key points for WS Manager coding:

                All WS connections use websockets.asyncio.client
                import connect (SS-STARTUP-006, SS-STARTUP-013,
                SS-RECON-006 in 1011014 dv1_4).

                max_queue=None and ping_interval=None on all
                connections (1011014 dv1_4, AR-058/059).

                portfolio_baseline_USD set ONCE at Step 6
                (snap_orders reconcile complete). NEVER updated
                during operation. NEVER reset on reconnect.

                systemd sd_notify READY=1 issued after startup
                sequence completes (SS-STARTUP-026 in 1011014).

WM-RUN-001  run() exception handling MUST extract sub-exceptions
            from ExceptionGroup (Python 3.11+ asyncio.TaskGroup
            raises ExceptionGroup on task failure — str(exc)
            only shows the outer wrapper message, permanently
            losing the actual root cause).

            Required implementation in the except block of run():

              import traceback

              tb_str = traceback.format_exc()
              sub_msgs: list[str] = []
              if isinstance(exc, ExceptionGroup):
                  for i, sub in enumerate(exc.exceptions):
                      sub_tb = "".join(
                          traceback.format_tb(sub.__traceback__)
                      )
                      sub_msgs.append(
                          f"[{i}] {type(sub).__name__}: {sub} "
                          f"| tb: {sub_tb}"
                      )
              log WS_MGR_FATAL (CRITICAL) with fields:
                error:          str(exc)
                traceback:      tb_str[-2000:]
                sub_exceptions: sub_msgs or None

            This is the ONLY correct way to surface the actual
            TaskGroup crash cause. DEFECT-WM-CRASH-001 was caused
            by the absence of this extraction.

------------------------------------------------------------
4.6 Connection Sharding (PATH 2 Implementation Contract)
------------------------------------------------------------

  This section is the implementation contract for the
  PATH 2 multi-connection batched-subscribe architecture
  established in 0511001 dv1_4 §15A ADR. All ws_manager.py
  code touching public WS connections MUST satisfy this
  contract.

WM-SHARD-001  N_CONNS COMPUTATION.
              N_conns is computed at startup AFTER the
              final tradeable_universe is finalized
              (after REST Ticker liquidity filter
              applied per 0511001 dv1_4 §4.2 Step 4).
              Formula:

                N_conns = ceil(universe_size /
                               SYMBOLS_PER_CONN_SAFE)

              SYMBOLS_PER_CONN_SAFE is read from CIATS
              parameter store at startup; default
              starting value is 500. NEVER hardcoded
              in code. NEVER inferred from any other
              parameter. Guard:

                assert SYMBOLS_PER_CONN_SAFE > 0
                assert universe_size > 0
                N_conns = math.ceil(universe_size /
                                    SYMBOLS_PER_CONN_SAFE)

WM-SHARD-002  SHARD ASSIGNMENT.
              Symbol-to-shard assignment uses
              alternating-index across the SORTED
              tradeable_universe:

                sorted_universe = sorted(
                    tradeable_universe,
                    key=lambda p: p.kraken_id
                )
                pair_to_shard_index = {
                    pair: i % N_conns
                    for i, pair in enumerate(sorted_universe)
                }

              Sort key MUST be deterministic
              (kraken_id is canonical). Random or
              hash-based assignment is PROHIBITED —
              determinism enables reproducible
              debugging across restarts.

WM-SHARD-003  SHARD DATA STRUCTURE.
              Each shard is represented by a WSShard
              object with at minimum these fields:

                class WSShard:
                    shard_index: int
                    connection: websockets connection
                    connection_id: int  # from status ack
                    symbols: List[Pair]  # owned symbols
                    last_real_data_time: float
                    last_pong_time: float
                    pair_states: Dict[Pair, PairState]
                    # PairState enum:
                    #   INITIAL, SUBSCRIBED,
                    #   DATA_PENDING, DATA_READY

              The WSManager holds:

                shards: List[WSShard]   # length N_conns
                pair_to_shard_index: Dict[Pair, int]
                private_connection: WSConnection or None
                                    # None in paper mode

WM-SHARD-004  PARALLEL CONNECT.
              Public shards are connected in parallel
              via asyncio.gather. Reference pattern:

                conn_coros = [
                    self._connect_shard(i)
                    for i in range(N_conns)
                ]
                self.shards = await asyncio.gather(
                    *conn_coros,
                    return_exceptions=False
                )

              If ANY shard connect raises, the gather
              propagates the exception. Startup fails
              fast. Partial-shard startup is PROHIBITED
              (a degraded universe at startup is an
              AR-070 silent-narrowing pattern).

WM-SHARD-005  PER-SHARD SUBSCRIBE ROUTING.
              For per-pair channels (ohlc, ticker),
              each subscribe is dispatched to the
              pair's assigned shard:

                async def subscribe_pair(pair, channel):
                    shard_idx = self.pair_to_shard_index[pair]
                    shard = self.shards[shard_idx]
                    await shard.send_subscribe(
                        channel=channel,
                        symbols=[pair.wsname]
                    )

              For connection-wide channels (instrument,
              status), subscribe ALWAYS goes to shard 0.

WM-SHARD-006  PER-SHARD INBOUND DISPATCH.
              Each shard owns its own inbound message
              loop. The dispatch entry point is keyed
              on (shard_index, channel) at the
              connection layer; channel-level dispatch
              (per §5.1) is unchanged once the message
              is routed to the appropriate handler.
              Reference pattern:

                async def shard_inbound_loop(shard):
                    async for raw_msg in shard.connection:
                        msg = json.loads(raw_msg)
                        msg["_shard_index"] = shard.shard_index
                        await self._dispatch(msg)

              The _shard_index annotation enables
              per-shard health tracking and per-pair
              state updates without changing the
              underlying dispatch semantics.

WM-SHARD-007  PER-SHARD HEALTH MONITORING.
              Zombie detection (A-8), application JSON
              ping (A-7), and rate counter monitoring
              (AR-030) all run per-shard. Each shard
              has independent timers and independent
              fault detection. Loss of one shard does
              not trigger reconnect of other shards.

WM-SHARD-008  PER-SHARD RECONNECT.
              Reconnect is per-shard. Reference
              pattern:

                async def reconnect_shard(shard_index):
                    old_shard = self.shards[shard_index]
                    self.shards[shard_index] = await (
                        self._connect_shard(shard_index)
                    )
                    # Re-subscribe SAME symbol partition
                    # (NO re-shard; pair_to_shard_index
                    # preserved across per-shard
                    # reconnect)
                    await self._resubscribe_shard_symbols(
                        shard_index
                    )
                    # Reset pair states for shard's pairs
                    for pair in old_shard.symbols:
                        self.shards[shard_index].pair_states[pair] = (
                            PairState.SUBSCRIBED
                        )

              Per-shard reconnect MUST NOT touch
              other shards' pair_states or connections.

WM-SHARD-009  PIPELINE-DURING-RECONNECT GUARD.
              The pipeline trigger is gated on
              all-shards-healthy. Pseudocode:

                def _all_connections_healthy(self):
                    for shard in self.shards:
                        if shard.state != HEALTHY:
                            return False
                    if (not self.paper_mode and
                        self.private_connection.state
                            != HEALTHY):
                        return False

4.7 Subscribe Pacing — Outbound Token Bucket
------------------------------------------------------------

  PURPOSE. Enforce a deterministic upper bound on
  outbound subscribe message rate from this VPS to
  Kraken. The bound applies across ALL connections
  (every public WS shard plus the private WS
  connection in live mode). It defends against
  Kraken's IP-level rate limit (Cloudflare layer)
  under any sequence of startup, per-shard
  reconnect, full-restart, and universe-
  re-evaluation events. This is the design-level
  fix for OI-060 WS_SUBSCRIBE_RATE_LIMIT_STORM
  per TB00143 STREAM 4 FP/DP analysis. PATH 2
  sharding alone does NOT bound IP-level subscribe
  rate; the token bucket does.

  ARCHITECTURAL POSITION. Token bucket sits between
  the per-shard subscribe routing layer
  (WM-SHARD-005) and the WebSocket send call. Every
  outbound subscribe — startup batch, reconnect
  batch, universe-re-evaluation batch, ad-hoc per-
  pair — passes through the bucket. There is no
  bypass path. The bucket is process-singleton:
  one bucket instance shared by every shard and
  the private connection.

WM-PACE-001  PROCESS-SINGLETON TOKEN BUCKET.
             ws_manager.py instantiates exactly one
             token bucket at process startup. All
             shards and the private connection share
             this bucket instance. Per-shard private
             buckets are PROHIBITED — they would
             violate the IP-level bound the bucket
             exists to enforce.

WM-PACE-002  BUCKET CAPACITY AND REFILL RATE.
             Starting values (CIATS-owned per
             TB00000 §9.16):

               SUBSCRIBE_RATE_PER_SEC      = 10
               SUBSCRIBE_BURST_CAPACITY    = 20

             Refill: SUBSCRIBE_RATE_PER_SEC tokens
             per second up to SUBSCRIBE_BURST_
             CAPACITY ceiling. Subscribe consumes
             one token. Bucket empty: subscribe
             call blocks (await) until at least one
             token is available.

             RATIONALE FOR STARTING VALUES.
             At SUBSCRIBE_RATE_PER_SEC=10 the full
             D-03 universe of 748 pairs subscribed
             across 2 channels (1496 subscribes
             total) takes ~150 seconds (2.5 min)
             at steady-state pacing, plus the
             initial 20-token burst (consumes 2s of
             effective rate-limit headroom). The
             observed Kraken Cloudflare bound that
             killed dv1_22 is approximately 150
             subscribes per 10 minutes
             (~0.25/sec). 10/sec aggregate exceeds
             this if Kraken's bound were stable at
             that level — but TB00141+TB00142 long
             Phase D ran 1496 startup subscribes
             across 2 shards in approximately 5-10
             seconds (effective ~150-300/sec
             aggregate) with zero rate-limit
             errors. The dv1_22 storm crossed
             the bound; the Phase D storm did not.
             The actual Kraken bound is therefore
             above the Phase D peak rate but below
             the dv1_22 peak rate. SUBSCRIBE_RATE_
             PER_SEC=10 is well below the
             empirically-confirmed-clean Phase D
             peak. CIATS revises post-deploy
             observation per HR-WM-032.

WM-PACE-003  BUCKET ACQUISITION SEMANTICS.
             Reference pattern:

               class SubscribeTokenBucket:
                   def __init__(self, rate, burst):
                       self.rate = rate
                       self.capacity = burst
                       self.tokens = burst
                       self.last_refill = time.monotonic()
                       self.lock = asyncio.Lock()

                   async def acquire(self):
                       async with self.lock:
                           now = time.monotonic()
                           elapsed = now - self.last_refill
                           self.tokens = min(
                               self.capacity,
                               self.tokens + elapsed * self.rate
                           )
                           self.last_refill = now
                           if self.tokens < 1:
                               wait = (1 - self.tokens) / self.rate
                               await asyncio.sleep(wait)
                               self.tokens = 0
                           else:
                               self.tokens -= 1

             Lock ensures correctness under
             concurrent shard subscribe coroutines.
             time.monotonic() prevents wall-clock
             skew anomalies.

WM-PACE-004  ALL OUTBOUND SUBSCRIBES PASS THROUGH
             THE BUCKET. Every send_subscribe()
             call awaits bucket.acquire() before
             writing to the WebSocket. This applies
             to:

               - Startup subscribe batch (per shard,
                 all channels, all pairs).
               - Per-shard reconnect re-subscribe
                 batch (WM-SHARD-008).
               - Universe Re-evaluation new-pair
                 subscribes (future, when procedure
                 exists).
               - Ad-hoc per-pair subscribes (none
                 currently planned but reserved).
               - Private connection authenticated
                 channels at startup and reconnect.

             There is NO bypass. There is NO
             "high-priority" lane.

WM-PACE-005  BUCKET STATE LOGGING.
             Bucket emits a structured log entry on:

               - Token consumption when wait
                 occurred (event = SUBSCRIBE_PACE_
                 WAIT, level = DEBUG, fields:
                 wait_ms, tokens_remaining,
                 channel, symbol).
               - Cumulative subscribes per startup
                 / per reconnect (event =
                 SUBSCRIBE_PACE_BATCH_COMPLETE,
                 level = INFO, fields:
                 batch_kind ["startup",
                 "reconnect", "univ_reeval"],
                 shard_index, total_subscribes,
                 elapsed_s, mean_rate).

             These logs are CIATS sole data source
             per 0511006. CIATS uses them to
             empirically validate WM-PACE-002
             starting values and revise toward
             optimal margin.

WM-PACE-006  CIATS PARAMETER OWNERSHIP.
             SUBSCRIBE_RATE_PER_SEC and
             SUBSCRIBE_BURST_CAPACITY are CIATS-
             owned parameters per TB00000 §9.16.
             They are starting values, not sacred.
             CIATS revises post-200-trade-floor
             based on SUBSCRIBE_PACE_BATCH_COMPLETE
             logs and observed Kraken rate-limit
             error frequency (target: zero rate-
             limit errors over a 30-day window
             with margin per DC-PREFLIGHT-006 Q3).

             Any change to these values is subject
             to RR-SCOPE-009 four-question origin
             investigation per HR-WM-031.

WM-PACE-007  STARTUP BATCH ORDERING.
             Per-shard startup subscribe batch
             order:

               (a) instrument channel (shard 0
                   only) — 1 subscribe.
               (b) status channel (shard 0 only) —
                   1 subscribe.
               (c) ohlc(5) channel — for each pair
                   on this shard, one subscribe.
               (d) ticker channel — for each pair
                   on this shard, one subscribe.

             All four steps share the same token
             bucket. Multiple shards run their
             batches concurrently via
             asyncio.gather but every subscribe
             from every shard contends for the
             same bucket tokens. Concurrency does
             not bypass the bound.

WM-PACE-008  PRE-DEPLOY DC-PREFLIGHT-006 LINKAGE.
             Any code change to WM-PACE-002 values
             (SUBSCRIBE_RATE_PER_SEC,
             SUBSCRIBE_BURST_CAPACITY) or to the
             pacing architecture itself triggers
             DC-PREFLIGHT-006 per 0311002 v1_8
             §8.2.5. Q1 traffic profile MUST
             enumerate the new bounds. Q3 margin
             MUST be recomputed against the most
             recently observed Kraken rate-limit
             behavior cited in Q4. Q5 rollback
             plan MUST address bucket-induced
             startup latency anomalies (subscribe
             completion exceeding sd_notify
             READY=1 watchdog window per VD-WD-001).

WM-PACE-009  STARTUP LATENCY BUDGET.
             SUBSCRIBE_RATE_PER_SEC=10 and 1496
             startup subscribes across 2 shards
             implies ~150 seconds for full
             startup subscribe completion (after
             the initial 20-token burst). This
             must complete before sd_notify
             READY=1 is sent (per VD-WD-001).
             VD-WD-001 / VD-SYS-002 unit-file
             watchdog is 120 seconds steady-state
             but startup is bounded only by sd_
             notify timing. ws_manager.py dv1_25
             startup sequence ordering:

               (1) Connect all shards in parallel.
               (2) Issue all subscribes through
                   token bucket (concurrent across
                   shards; aggregate-rate-bounded).
               (3) Await all subscribe acks.
               (4) Issue sd_notify READY=1 ONLY
                   after all subscribes acked.

             Watchdog-during-startup must allow
             this completion window. If startup
             subscribe time exceeds 5 minutes,
             FP/DP review of WM-PACE-002 starting
             values is required before next
             deploy.

WM-PACE-010  EMERGENCY OVERRIDE PROHIBITED.
             There is NO operator command, NO
             configuration flag, NO environment
             variable, NO CIATS directive that
             bypasses the token bucket within a
             single ws_manager.py process
             lifetime. The bucket is unconditional.

             Bucket parameters change ONLY via
             code change (CIATS-driven) which
             passes RR-SCOPE-009 + DC-PREFLIGHT-006
             gates and ships in a new ws_manager.py
             dv version per project document
             control. Runtime tuning is not
             permitted because runtime tuning
             cannot satisfy DC-PREFLIGHT-006
             pre-deploy analysis.

WM-EC-006  Partial TP fill sequence:

           def handle_partial_tp_fill(event, symbol):
               cum_qty    = Decimal(str(event["cum_qty"]))
               avg_exit   = Decimal(str(event["avg_price"]))
               pos        = position_mirror[symbol]
               orig_qty   = pos["qty"]
               remaining  = orig_qty - cum_qty
               emergsl_id = pos["emergsl_order_id"]
               p_incr     = pair_cache[symbol]["price_increment"]
               q_incr     = pair_cache[symbol]["qty_increment"]
               qty_min    = pair_cache[symbol]["qty_min"]
               cost_min   = pair_cache[symbol]["cost_min"]
               bid        = latest_bid[symbol]

               # Update Position Mirror
               position_mirror[symbol]["qty"] = remaining

               # Quantize remaining qty
               remaining_r = remaining.quantize(q_incr,
                                 ROUND_DOWN)

               # Check minimum size
               if (remaining_r < qty_min or
                   remaining_r * bid < cost_min):
                   # Cannot protect — exit remainder
                   cancel_order(emergsl_id)
                   dispatch_market_sell(symbol, remaining_r)
                   del position_mirror[symbol]
                   logger.log("TP_PARTIAL_FILL_BELOW_MIN_EXIT",
                       symbol=symbol, remaining=remaining_r)
                   return

               # Amend emergSL qty (NOT cancel+resubmit)
               amend_order(
                   order_id=emergsl_id,
                   order_qty=remaining_r,
                   token=ws_token
               )
               logger.log("TP_PARTIAL_FILL",
                   symbol=symbol,
                   filled_qty=cum_qty,
                   remaining_qty=remaining_r,
                   avg_exit_price=avg_exit,
                   emergsl_amended_to=remaining_r)

WM-EC-007  WHY amend_order, NOT cancel+resubmit:
           cancel_order (emergSL <5s): +8 rate counter
           add_order (new emergSL): +1 rate counter
           Total cancel+resubmit: +9 rate counter units

           amend_order (resting >300s): +1+1 = +2 rate units
           Saves 7 rate counter units per TP partial fill.
           Also preserves queue position on Kraken book —
           important during high-volatility events when
           rate limits may already be under pressure.

WM-EC-008  Full TP fill (exec_type=filled for TP):

           clear Position Mirror, fire CIATS Trade Outcome
           Bus. No qty amendment needed.

           Fire CIATS Trade Outcome Bus ONCE per full
           position close — aggregate all partial fill data.
           NOT on each individual partial fill.

8. OHLC CANDLE CLOSE DETECTION (AR-045)
============================================================

WM-OHLC-001  OHLC channel fires on every trade event within
             a candle period — NOT only on candle close.
             Detection is MANDATORY.

WM-OHLC-002  Detection algorithm (per symbol S):

             On each ohlc(5m) message for symbol S:
               if msg.interval_begin == last_interval_begin[S]:
                 # In-progress candle update
                 Update last_complete_candle[S] = msg data.
                 DO NOT fire pipeline.
               else:
                 # NEW interval — previous candle is CLOSED
                 closed_candle = last_complete_candle[S]
                 Fire pipeline with closed_candle.
                 last_complete_candle[S] = msg data.
                 last_interval_begin[S] = msg.interval_begin.
                 Log CANDLE_CLOSE (symbol, interval, OHLC).

             Same logic for ohlc(60) using separate
             last_interval_begin_60[S] dict.

             The timestamp field is DEPRECATED. MUST NOT
             be used for candle boundary detection.

WM-OHLC-004  Maintain SEPARATE dicts for 5m and 60m:
               last_interval_begin:    dict[str, str] (5m)
               last_interval_begin_60: dict[str, str] (60m)
             These MUST NOT be combined.

WM-OHLC-005  OHLC stall: If no trades occur after an
             interval border, no OHLC message is sent until
             next trade. Pipeline simply does not fire for
             stalled pairs. Not an error condition. Stall
             handling at system clock level addressed in
             0511002 Signal_Pipeline_Specification.

WM-OHLC-006  GetOHLCData response[-1] ALWAYS excluded from
             indicator calculations (AR-017, AR-027).
             Use only response[:-1].
             Initialize last_interval_begin from

9.2 Indicator State — 5-Minute (AR-016, AR-076, AR-068)
------------------------------------------------------------

Per monitored pair in monitored_universe:

  atr_14:              Decimal  — running incremental value
  prev_tr:             Decimal  — previous True Range
  rsi_14_avg_gain:     Decimal  — Wilder SMMA gain state
  rsi_14_avg_loss:     Decimal  — Wilder SMMA loss state
  ema_9:               Decimal  — standard EMA, alpha=0.2
  ema_21:              Decimal  — standard EMA, alpha=2/22
  volume_ma_20:        Decimal  — rolling 20-candle SMA
  last_interval_begin: str      — candle close detection
  last_complete_candle: OHLCCandle  — closed candle data

SEED FORMULAS (from GetOHLCData response[:-1]):

  ATR(14):
    Seed:        SMA of first 14 True Ranges.
                   TR = max(high-low, |high-prev_close|,
                            |low-prev_close|)
    Incremental: ATR = (prev_ATR * 13 + current_TR) / 14
    O(1) per update (AR-016).

  RSI(14) — Wilder's SMMA (AR-076):
    Seed:
      avg_gain = sum(gains[:14]) / 14
      avg_loss = sum(losses[:14]) / 14
    Incremental:
      avg_gain = (prev_avg_gain * 13 + gain) / 14
      avg_loss = (prev_avg_loss * 13 + loss) / 14
      RS = avg_gain / avg_loss
      RSI = 100 - (100 / (1 + RS))
    !! DO NOT use EMA alpha=2/15 for RSI (HR-WM-018) !!
    Wilder's SMMA alpha = 1/14. Standard EMA alpha=2/15
    is WRONG for RSI and MUST NOT be used.

  EMA(9):
    Seed: SMA of first 9 closes.
    Incremental: alpha = 2/10 = 0.2
      EMA = alpha * close + (1 - alpha) * prev_EMA

  EMA(21):
    Seed: SMA of first 21 closes.
    Incremental: alpha = 2/22
      EMA = alpha * close + (1 - alpha) * prev_EMA

  Vol MA(20):
    Seed: SMA of first 20 volumes.
    Incremental: rolling SMA (sum last 20 / 20).

WARM-UP STATE MACHINE (AR-068):
  warm_up_state: dict[str, str]  {"WARM_UP" | "READY"}
  Pair transitions WARM_UP → READY only when ALL FIVE
  indicators are seeded. (ATR, RSI, EMA9, EMA21, VolMA20.)
  WARM_UP pairs SKIPPED at pipeline pre-check.
  READY pairs begin trading immediately — system does NOT
  wait for all pairs to reach READY.

14. DECIMAL ROUNDING (AR-047)
============================================================

WM-ROUND-001  All numeric values from Kraken (WS or REST):
              ALWAYS convert via Decimal(str(value)).
              NEVER Decimal(float_value).
              Decimal(float) inherits float binary precision
              error. Exchange orders with precision errors
              are rejected = failed trade = loss.

              Applies to: ticker bid/ask, executions
              avg_price, order_qty, cum_qty, last_qty,
              last_price, instrument price_increment,
              qty_increment, qty_min, cost_min, balances.

WM-ROUND-002  Entry limit_price rounding:
              from decimal import Decimal, ROUND_DOWN
              D_incr = Decimal(str(price_increment))
              limit_price = raw_price.quantize(
                  D_incr, rounding=ROUND_DOWN)
              Conservative: lower limit → more likely
              post_only fill.

WM-ROUND-003  order_qty rounding:
              D_incr = Decimal(str(qty_increment))
              order_qty = raw_qty.quantize(
                  D_incr, rounding=ROUND_DOWN)
              ROUND_DOWN for quantities — never overshoot.

WM-ROUND-004  TP limit_price rounding:
              tp_price = raw_tp.quantize(
                  D_incr, rounding=ROUND_UP)
              ROUND_UP for TP — higher TP preserves net R:R.

WM-ROUND-005  emergSL trigger price rounding:
              sl_price = raw_sl.quantize(
                  D_incr, rounding=ROUND_DOWN)
              ROUND_DOWN for stop — wider stop = more
              protective.

WM-ROUND-006  Cost validation before every order dispatch:
              if (order_qty < qty_min or
                  order_qty * price < cost_min):
                  SKIP — do not dispatch.
                  Log INSUFFICIENT_QTY with both check values.

WM-ROUND-007  Use ROUND_DOWN and ROUND_UP (not ROUND_FLOOR
              and ROUND_CEILING). For positive prices these
              are equivalent, but ROUND_DOWN/UP avoids
              incorrect behavior if negative prices ever
              appear unexpectedly.

WM-RECONNECT-016  Transient WS disconnect errors
                    (ConnectionClosedError,
                     ConnectionClosedOK,
                     ConnectionResetError)

                    (b) invoke _initiate_reconnect() — awaited in recv

                    (c) NOT propagate the exception to the _main_loop

                  object after reconnect completes (self._ws_public and
                  self._ws_private are reassigned inside
                  _execute_reconnect_sequence). Send helpers swallow the
                  failed send — the send is lost but the process does
                  NOT terminate. This rule is the primary fix for
                  DEFECT-WM-RECONNECT-001.

                  A clean (non-exception) exit of the async-for in
                  either recv loop is ALSO treated as a disconnect
                  (reconnect triggered, loop resumes). This covers
                  websockets-library edge cases where the server closes
                  the connection without raising.

WM-RECONNECT-017  _initiate_reconnect() retry schedule:
                    attempts: MAX_RECONNECT_ATTEMPTS   = 10
                    base:     RECONNECT_BACKOFF_BASE_SEC = 1.0 s
                    cap:      RECONNECT_BACKOFF_CAP_SEC  = 30.0 s
                    factor:   RECONNECT_BACKOFF_FACTOR   = 2.0
                  Matches WM-RECONNECT-002 (10 attempts, cap 30s).
                  Worst-case wall time across all attempts:
                    1 + 2 + 4 + 8 + 16 + 30 + 30 + 30 + 30 + 30 = 181s
                  (upper bound on sleep — actual attempt latency adds).
                  FATAL_RECONNECT_FAILURE MUST be raised ONLY after all
                  N attempts have been exhausted. Each failed attempt
                  logs RECONNECT_ATTEMPT_FAILED (level=WARN, non-fatal).
                  Each successful reconnect logs RECONNECT_COMPLETE
                  (level=INFO) with "attempts" count. All four numbers
                  are module-level constants declared at the top of
                  ws_manager.py — no magic numbers (DC-4).

WM-RECONNECT-018  The _main_loop() TaskGroup MUST receive only truly
                  fatal conditions. The three transient types named in
                  WM-RECONNECT-016 MUST be fully handled at loop level.
                  If the TaskGroup ever observes any of the three
                  transient types as a sub-exception, that is a
                  WM-RECONNECT-016 defect (a loop-level catch is
                  missing or broken).

                  Implementation gate:
                    self._reconnect_done_event: asyncio.Event
                  Cleared by _initiate_reconnect on entry; set in its
                  finally block on every exit path (success, fatal, or
                  re-entry). Concurrent disconnect detection by both
                  recv loops collapses to a single reconnect cycle:
                  whichever loop reaches _initiate_reconnect first
                  drives the retry schedule; the other awaits the
                  event and returns without starting a second cycle.

                  Terminal flag:
                    self._fatal_reconnect_failure: bool
                  Set by _initiate_reconnect immediately before raising
                  the final RuntimeError. Prevents siblings that awaken
                  from the event wait from starting a fresh retry cycle
                  while TaskGroup teardown is in flight. Recv loops and
                  send helpers check this flag and short-circuit when
                  set.

                  private-side step:
                    - Step 1: _rest_get_ws_token()            SKIP
                    - Step 2b: _ws_connect(PRIVATE_WS_URI)    SKIP
                    - Step 3b: _subscribe_private()           SKIP
                    - Step 4: _rest_get_open_orders() +
                              _detect_gap_closed_positions     SKIP
                    - Step 5: GAP_CLOSED_POSITION logging      SKIP
                    - Step 6: _reconcile_pending_orders()      SKIP
                    - Step 7: executions_last_seq /
                              balances_last_seq resets         SKIP

                  Paper-mode reconnect executes ONLY the
                  public-side subset:
                    - Step 2a: _ws_connect(PUBLIC_WS_URI)
                    - Step 3a: _subscribe_public()
                    - Step 8:  resume ticker subscriptions for
                               every symbol in monitored_universe
                    - Step 10: if gap_sec >
                               RECONNECT_STALE_CACHE_SEC,
                               seed_indicators_from_rest() for
                               every symbol

                  This mirrors the paper-mode branch of
                  _startup_connect_and_subscribe (FIX-WM-PT-001,
                  dv1_14). Rationale: private Kraken API key is
                  not exercised anywhere in paper mode — order
                  dispatch is suppressed, balance is static,
                  executions channel is unused. Calling
                  _rest_get_ws_token() in paper mode requires a
                  valid private key for signature generation
                  and exchanges the key with Kraken; in the
                  current deployment that key is rejected by
                  Kraken (EAPI:Invalid key — tracked as OI-041).
                  Every paper-mode reconnect therefore failed at
                  Step 1, consumed a retry attempt, and after
                  MAX_RECONNECT_ATTEMPTS consecutive identical
                  failures reached the FATAL_RECONNECT_FAILURE
                  exit path → systemd restart.

                  Preserved invariants:
                    - HR-WM-013 portfolio_baseline_USD NEVER
                      reset on reconnect (paper balance too).
                    - HR-WM-011 system_state PRESERVED.
                    - WM-SC-003 exit_cooldown_log and
                      consecutive_loss_count PRESERVED.

                  Live mode reconnect (self.paper_mode == False)
                  is unchanged — full Steps 1-10 still apply
                  per WM-RECONNECT-003 through WM-RECONNECT-014.

                  Test coverage (1021001):
                    - paper-mode reconnect completes with no
                      private-WS calls and no REST auth calls
                    - live-mode reconnect unchanged
                    - gap > RECONNECT_STALE_CACHE_SEC in paper
                      mode triggers indicator re-seed

16. TICKER EVENT_TRIGGER MANAGEMENT (AR-034)
============================================================

  Pairs WITH open positions:
    Subscribe ticker with event_trigger:bbo.
    bbo fires on every bid/ask change.
    bid updates drive MAE detection and drawdown MTM.
    More frequent than trades trigger — necessary for
    adverse price detection on open longs.

  Pairs WITHOUT open positions:
    Subscribe ticker with event_trigger:trades.
    Conserves WS bandwidth. Trade events sufficient
    for price monitoring on no-position pairs.

  WS Manager updates ticker subscription mode:
    On position open: switch symbol to event_trigger:bbo.
    On position close: switch symbol to event_trigger:trades.
  Subscription update is sent immediately on position
  state change — no deferred mode switch.

16A. PAPER MODE OPERATIONS (NEW dv1_26)
============================================================

This section is the implementation contract for the
paper-mode synthetic ledger and paper exit routing
mandated by 0511001 dv1_5 §13.7 + §13.8 + HR-WM-032 +
HR-WM-033. All rules in §16A apply ONLY when
self.paper_mode is True. Live mode is unaffected.

------------------------------------------------------------
16A.1 Paper Synthetic Ledger
------------------------------------------------------------

Paper mode has no Kraken balances channel by HR-WM-022
(paper does NOT connect private WS). Without the balances
channel, spot_usd_balance cannot be updated by exchange-
pushed events. Paper mode therefore maintains a SYNTHETIC
LEDGER that is updated locally on every simulated fill
using the same arithmetic Kraken applies in live.

WM-PAPER-LEDGER-001  INITIALIZATION.

           At startup Step 9b (paper mode branch in
           _startup):
             self.spot_usd_balance = Decimal(str(
                 self._cfg.get("paper_starting_balance",
                               PAPER_STARTING_BALANCE_DEFAULT)))
             self.portfolio_baseline_USD = self.spot_usd_balance

           PAPER_STARTING_BALANCE_DEFAULT = Decimal("1000")
           per D-05 LOCKED.

           portfolio_baseline_USD is NEVER updated after
           startup (HR-WM-011 unchanged in paper mode).

           Log emission:
             PAPER_BALANCE_SET (level=INFO,
               balance=spot_usd_balance,
               baseline=portfolio_baseline_USD,
               source="paper_starting_balance")

WM-PAPER-LEDGER-002  ENTRY-FILL DEBIT.

           In _simulate_entry_fill(cl_ord_id, symbol,
           price, qty), AFTER position_mirror is
           populated and BEFORE invoking the Execution
           Engine entry callback:

             entry_cost = qty * price
             entry_fee  = entry_cost * FEE_MAKER_PCT
             self.spot_usd_balance -= (entry_cost +
                                       entry_fee)

           PositionRecord MUST capture fees_entry_usd =
           entry_fee for downstream exit P/L computation
           (consumed by Exit Controller's _close_position
           per WM-PAPER-EXIT-001..003).

           PositionRecord schema extension (dv1_26):
             fees_entry_usd: Decimal  (paper + live;
                                       set on entry fill;
                                       read by EC on exit)

           Log emission per WM-PAPER-LEDGER-004.

           Rationale: paper entry uses limit order at
           limit price. Limit-order fills incur maker
           fee per Kraken fee schedule (FEE_MAKER_PCT =
           Decimal("0.0016") per 0411003).

WM-PAPER-LEDGER-003  EXIT-FILL CREDIT.

           Triggered by paper exit paths per
           WM-PAPER-EXIT-001..004. The exit path computes
           exit_price and fees_exit, applies the ledger
           credit:

             exit_proceeds = qty * exit_price
             self.spot_usd_balance += (exit_proceeds -
                                       fees_exit)

           Fee schedule by exit type:

             TP fill (limit order, maker):
               fees_exit = exit_proceeds * FEE_MAKER_PCT

             emergSL trigger / Layer 2 MAE breach /
             Layer 1 signal exit / time expiry /
             regime exit (market sell, taker):
               fees_exit = exit_proceeds * FEE_TAKER_PCT

           FEE_MAKER_PCT = Decimal("0.0016")
           FEE_TAKER_PCT = Decimal("0.0026")

           Order of operations:
             (1) Compute exit_price + fees_exit (in
                 ws_manager.py paper-exit code path).
             (2) Apply ledger credit per this rule.
             (3) Pass exit_price + fees_exit to Exit
                 Controller's _close_position(...) per
                 WM-PAPER-EXIT-001..004.
             (4) Exit Controller emits TRADE_CLOSE log
                 record with full P/L payload.
             (5) Exit Controller clears position_mirror,
                 releases semaphore, updates Selection
                 Controller state.

           Ledger update MUST occur BEFORE
           _close_position() so that any downstream
           drawdown computation triggered during
           position close reads a consistent ledger
           state.

WM-PAPER-LEDGER-004  PAPER_LEDGER_UPDATED LOG EMISSION.

           Every ledger mutation (initialization,
           entry-fill debit, exit-fill credit) emits a
           structured log record:

             event:        PAPER_LEDGER_UPDATED
             level:        INFO
             component:    WS_MGR
             event_type:   "INIT" | "ENTRY_FILL" |
                           "EXIT_FILL"
             symbol:       trading pair (or "" for INIT)
             delta_usd:    Decimal — net change to
                           spot_usd_balance (negative
                           for debit, positive for
                           credit)
             fee_usd:      Decimal — fee component of
                           the transaction
             new_balance:  Decimal — spot_usd_balance
                           AFTER the mutation
             exit_reason:  str — exit_reason for
                           EXIT_FILL events; "" for
                           INIT and ENTRY_FILL

           CIATS log-file polling reads
           PAPER_LEDGER_UPDATED records to verify
           paper-mode capital evolution matches
           live-mode balances-channel evolution
           wherever physically possible.

16A.2 Paper Exit Routing Through Exit Controller
------------------------------------------------------------

All paper-mode exit paths MUST route through Exit
Controller's _close_position() close sequence. The
dv1_25 parallel _fire_ciats_outcome path is RETIRED.
Per HR-WM-033 and 1011005 dv1_3 §EC-PAPER.

WM-PAPER-EXIT-001  TP FILL DETECTION ROUTING.

           In _maybe_paper_fill(symbol, bid, ask) when
           ask >= pos.tp_price:

             # 1. Compute exit_price + fees.
             exit_price = pos.tp_price
             qty        = pos.qty
             exit_proceeds = qty * exit_price
             fees_exit  = exit_proceeds * FEE_MAKER_PCT

             # 2. Apply HR-WM-032 ledger update.
             self.spot_usd_balance += (exit_proceeds -
                                       fees_exit)
             self._log("PAPER_LEDGER_UPDATED", ...)

             # 3. Log paper-fill detection event.
             self._log("PAPER_TP_FILL_DETECTED", ...)

             # 4. Route to Exit Controller.
             #    Exit Controller emits TRADE_CLOSE,
             #    clears position_mirror, releases
             #    semaphore, updates SC state.
             await self._exit_controller_fn(
                 event="paper_close",
                 symbol=symbol,
                 exit_price=exit_price,
                 exit_reason="TP_FILL",
                 fees_exit=fees_exit,
             )

             # 5. Switch ticker mode to trades.
             await self._update_ticker_event_trigger(
                 symbol, "trades")

           ws_manager.py MUST NOT directly pop the
           position from position_mirror. Position
           Mirror clearing is Exit Controller's
           responsibility (per HR-EC-009 cascade).

           ws_manager.py MUST NOT call the retired
           _fire_ciats_outcome. CIATS data flow goes
           through Exit Controller's TRADE_CLOSE log
           emission (EC-TOB-002 in 1011005).

WM-PAPER-EXIT-002  EMERG_SL TRIGGER ROUTING.

           In _maybe_paper_fill(symbol, bid, ask) when
           bid <= pos.emergsl_price:

             # 1. Compute exit_price + fees.
             exit_price = bid    # market sell at bid
             qty        = pos.qty
             exit_proceeds = qty * exit_price
             fees_exit  = exit_proceeds * FEE_TAKER_PCT

             # 2. Apply HR-WM-032 ledger update.
             self.spot_usd_balance += (exit_proceeds -
                                       fees_exit)
             self._log("PAPER_LEDGER_UPDATED", ...)

             # 3. Log paper-fill detection event.
             self._log("PAPER_EMERG_SL_TRIGGERED", ...)

             # 4. Route to Exit Controller.
             await self._exit_controller_fn(
                 event="paper_close",
                 symbol=symbol,
                 exit_price=exit_price,
                 exit_reason="EMERGENCY_SL",
                 fees_exit=fees_exit,
             )

             # 5. Switch ticker mode to trades.
             await self._update_ticker_event_trigger(
                 symbol, "trades")

           Same restrictions as WM-PAPER-EXIT-001:
           NO direct position_mirror pop, NO call to
           retired _fire_ciats_outcome.

WM-PAPER-EXIT-003  LAYER 2 MAE BREACH (EC-DRIVEN).

           Layer 2 MAE exits are Exit Controller's
           own logic (1011005 §7 EC-L2-001..004). In
           live mode EC dispatches a market_sell via
           ws_manager.dispatch_market_sell(). In paper
           mode the same EC code path executes; the
           paper-mode dispatch_market_sell synthesizes
           a fill locally per WM-PAPER-EXIT-004.

           No new code path required at the WS
           Manager layer beyond WM-PAPER-EXIT-004.

WM-PAPER-EXIT-004  dispatch_market_sell PAPER MODE
                   BEHAVIOR.

           The dv1_25 paper branch of
           dispatch_market_sell() directly pops the
           position from position_mirror and returns.
           This is RETIRED in dv1_26. New behavior:

             async def dispatch_market_sell(
                 self, symbol, qty,
             ) -> tuple[Decimal, Decimal]:
                 """
                 Returns (exit_price, fees_exit) for
                 paper mode so Exit Controller can
                 receive the realized values for
                 _close_position. Live-mode return is
                 also (exit_price, fees_exit) computed
                 from the actual fill — uniform return
                 contract per HR-WM-033 / 1011005
                 dv1_3 EC-MS-001.
                 """
                 if self.paper_mode:
                     bid = self.latest_bid.get(
                         symbol, Decimal("0"))
                     if bid <= Decimal("0"):
                         self._log(
                             "PAPER_MARKET_SELL_NO_BID",
                             level="WARN",
                             symbol=symbol)
                         return (Decimal("0"),
                                 Decimal("0"))
                     exit_price = bid
                     exit_proceeds = qty * exit_price
                     fees_exit = exit_proceeds * \
                                 FEE_TAKER_PCT
                     # HR-WM-032 ledger update.
                     self.spot_usd_balance += (
                         exit_proceeds - fees_exit)
                     self._log(
                         "PAPER_LEDGER_UPDATED", ...)
                     self._log(
                         "PAPER_MARKET_SELL_SIMULATED",
                         level="INFO",
                         symbol=symbol, qty=qty,
                         exit_price=exit_price,
                         fees_exit=fees_exit)
                     return (exit_price, fees_exit)

                 # Live path unchanged from dv1_25.
                 # Live return value is computed by
                 # _market_sell_with_retry helper (in
                 # exit_controller.py) from the actual
                 # exec_type=trade event captured on
                 # the executions channel.
                 ...

           ws_manager.py paper-mode dispatch_market_sell
           MUST NOT directly pop position_mirror; Exit
           Controller's _close_position handles that
           after receiving the (exit_price, fees_exit)
           tuple.

WM-PAPER-EXIT-005  _fire_ciats_outcome RETIRED.

           The dv1_25 _fire_ciats_outcome method is
           RETIRED in dv1_26. All CIATS outcome data
           flows via Exit Controller's TRADE_CLOSE log
           emission per 1011005 EC-TOB-002.

           ws_manager.py:
             - DELETE the _fire_ciats_outcome method.
             - DELETE all call sites of
               _fire_ciats_outcome.
             - DELETE the constructor parameter
               ciats_outcome_bus_fn (no longer needed).
             - Selection Controller state updates
               (wm.exit_cooldown_log /
               wm.consecutive_loss_count) MUST be
               performed by Exit Controller per
               1011005 EC-CLOSE-005, NOT by ws_manager.

           This change is byte-impacting on the
           ws_manager.py constructor signature. Module
           wire-up in tothbot/__main__.py MUST be
           updated to remove the
           ciats_outcome_bus_fn argument. Closes
           FINDING-TB00147-08 final architectural seam.

HR-WM-010  cancel_all_orders_after: EXPLICITLY PROHIBITED

HR-WM-011  portfolio_baseline_USD: set once at startup

HR-WM-012  Pipeline evaluations PROHIBITED during reconnect.

HR-WM-013  GetOHLCData response[-1]: ALWAYS excluded from

HR-WM-014  deadline parameter required on ALL add_order

HR-WM-015  emergSL stop orders MUST include explicit trigger

HR-WM-016  Mid-session reconnect is a separate code path
           from startup. Never use startup code for
           reconnect (AR-056).

HR-WM-017  All five SSS indicators (ATR, RSI, EMA9, EMA21,

           READY. WARM_UP pairs skipped at pipeline (AR-068).

HR-WM-018  RSI(14) uses Wilder's SMMA (alpha=1/14).
           Standard EMA (alpha=2/15) MUST NOT be used for
           RSI (AR-076).

HR-WM-019  Subscription ACK warnings[] parsed and logged
           on every subscribe call. maxratecount from
           executions ACK is operative rate ceiling
           (AR-030, AR-031).

HR-WM-020  Both DATA and TRADE keys IP-whitelisted. Update
           on any VPS migration (AR-037).

HR-WM-021  1H HTF cache (htf_ema_20, htf_ema_50) sourced
           from REST only. ohlc(60) WS subscription is
           PROHIBITED. Kraken WS v2 rejects a second ohlc
           interval per symbol (OI-NEW-001). HTF EMAs are
           seeded by seed_indicators_from_rest() at startup
           and after reconnect gap > 15 min. They do NOT
           receive incremental WS updates within a session.

HR-WM-022  liquidity_24h populated ONLY from REST Ticker
           (0411002 REST-TKR-001). The instrument channel
           provides NO volume data. Any code reading volume
           from the instrument channel is a defect.
           (DEFECT-SS-006 — corrected in dv1_15)

HR-WM-023  Every private Kraken REST call MUST be signed
           with both API-Key AND API-Sign headers per
           WM-REST-SIGN-001 / WM-REST-SIGN-002 /
           WM-REST-SIGN-003. Shipping only API-Key
           (without API-Sign) is a defect. Kraken rejects
           every unsigned private request with
           EAPI:Invalid key. Signing implementation MUST
           use the single _sign_rest_request helper on
           WSManager; inline signing at call sites is a
           defect. (DEFECT-WM-REST-SIGN-001 — corrected
           in dv1_23)

HR-WM-024  CONNECTION SHARDING (PATH 2). Public WS
           connections are sharded per §4.6.
           N_conns = ceil(universe_size /
           SYMBOLS_PER_CONN_SAFE).
           SYMBOLS_PER_CONN_SAFE is CIATS-owned (500
           starting). NEVER hardcoded. Single-
           connection architectures (PATH 1) are
           PROHIBITED for any universe approaching
           the 650-700 single-connection ceiling.
           (Cascaded from 0511001 dv1_4 HR-WM-028.)

HR-WM-025  SHARD INDEPENDENCE. Each public WS shard
           is an independent reconnect domain.
           Per-shard reconnect re-subscribes only the
           reconnecting shard's symbol partition;
           other shards are unaffected. (Cascaded
           from 0511001 dv1_4 HR-WM-029.)

HR-WM-026  SILENT-PAIR HANDLING. Pairs that ack
           subscribe but emit no data within T_silent
           (60s starting) are marked DATA_PENDING and
           skipped by Signal Pipeline. They remain in
           tradeable_universe and are never auto-
           removed. State machine per WM-SHARD-010 /
           WM-PS-007. (Cascaded from 0511001 dv1_4
           HR-WM-030.)

HR-WM-027  SUBSCRIBE-COUNT vs MAX-CONCURRENT
           DECOUPLING. The number of pairs subscribed
           on the WS layer is determined by the D-03
           universe filter. It is NOT bounded by
           max_concurrent (CIATS-owned position cap).
           Universe scope ≠ position count.
           (Cascaded from 0511001 dv1_4 HR-WM-031.)

HR-WM-028  AR-070 SILENT-NARROWING PROHIBITION.
           tradeable_universe MUST NOT be mutated
           outside the explicit Universe Re-evaluation
           procedure. DATA_PENDING does not remove a
           pair from the universe. Per-pair subscribe
           failure does not remove a pair from the
           universe. max_concurrent does not bound
           the universe. Any mutation outside Universe
           Re-evaluation is a session-halting AR-070
           defect (per WM-PS-008).

HR-WM-029  PIPELINE-DURING-RECONNECT GUARD
           (GENERALIZED). Pipeline trigger is gated
           on all-shards-healthy AND
           private-healthy (live mode) /
           all-shards-healthy (paper mode). If ANY
           connection is in reconnect state, candle
           events are discarded; pipeline does not
           run. Per WM-SHARD-009.

HR-WM-030  PRE-DEPLOY RATE-LIMIT GATE. Any code
           change to ws_manager.py touching
           connection count, subscribe rate, REST
           rate, channels, universe size, or
           reconnect cadence MUST satisfy 0311002
           v1_8 §8.2.5 DC-PREFLIGHT-006 five-question
           gate before VPS deploy. Q1-Q5 documented
           in the relevant session log, ADR, or NSI.
           Deploy without documented Q1-Q5 is a
           session-halting defect.

HR-WM-031  CONSTRAINT REMOVAL — RR-SCOPE-009. Any
           proposal to remove, relax, or bypass any
           hard rule in this section MUST satisfy
           TB00000 v2_17 §4.3.1 RR-SCOPE-009 four-
           question origin investigation before
           recommendation. The hard rules in this
           section are load-bearing-by-default. Bill
           explicit override is the sole bypass.

HR-WM-032  PAPER LEDGER UPDATE (NEW dv1_26 — cascaded
           from 0511001 dv1_5 HR-WM-032). In paper
           mode, spot_usd_balance is a synthetic
           ledger initialized at startup to
           paper_starting_balance and EVOLVED locally
           on every simulated fill per §16A.1
           (WM-PAPER-LEDGER-001..004). Entry fills
           debit the ledger by (entry_qty *
           entry_price * (1 + FEE_MAKER_PCT)). Exit
           fills credit the ledger by (exit_qty *
           exit_price - fees_exit) where fees_exit
           uses FEE_MAKER_PCT for limit-order TP
           fills and FEE_TAKER_PCT for market-sell
           exits. portfolio_baseline_USD is NEVER
           updated after startup (HR-WM-011
           unchanged). Every ledger mutation emits a
           PAPER_LEDGER_UPDATED log record with
           {event_type, symbol, delta_usd, fee_usd,
           new_balance, exit_reason}. Without this
           rule, paper-mode drawdown numerators are
           wrong and CIATS cannot reconstruct paper
           P/L. Closes FINDING-TB00147-06.

HR-WM-033  PAPER EXITS ROUTE THROUGH EXIT CONTROLLER
           (NEW dv1_26 — cascaded from 0511001 dv1_5
           HR-WM-033). All paper-mode exit paths (TP
           fill detected in _maybe_paper_fill,
           emergSL trigger in _maybe_paper_fill,
           Layer 1 signal exit, Layer 2 MAE breach,
           time expiry, regime exit) MUST route
           through Exit Controller's _close_position()
           per §16A.2 (WM-PAPER-EXIT-001..005).
           ws_manager.py applies the HR-WM-032 ledger
           update, then calls Exit Controller; Exit
           Controller emits the TRADE_CLOSE log
           record (per 1011005 dv1_3 EC-TOB-002 +
           EC-PAPER), clears Position Mirror,
           releases the semaphore, and updates
           Selection Controller state. The
           ws_manager._fire_ciats_outcome method is
           RETIRED in dv1_26. Without this rule,
           paper-mode CIATS data flow is non-parity
           with live (no TRADE_CLOSE records
           emitted), in direct violation of HR-WM-025
           and TB00000 v2_18 §4.4 PA-005. Closes
           FINDING-TB00147-08.

HR-WM-034  OUTBOUND SUBSCRIBE PACING — TOKEN BUCKET.
           (RENUMBERED dv1_26: was HR-WM-032 in
           dv1_25; renumbered to make room for
           cascaded HR-WM-032/033 from 0511001 dv1_5.
           Rule content unchanged.) Every outbound
           subscribe to Kraken MUST pass through the
           process-singleton token bucket per §4.7
           WM-PACE-001 through WM-PACE-010. There is
           NO bypass for any subscribe pathway:
           startup, per-shard reconnect, full-
           process-restart, universe re-evaluation,
           ad-hoc, or authenticated-channel are ALL
           bound by the same bucket. This is the
           design-level fix for OI-060 (rate-limit
           storm) per TB00143 STREAM 4 FP/DP
           analysis. Architecture alone (PATH 2
           sharding) does NOT bound IP-level
           subscribe rate against back-to-back-
           restart scenarios; only the bucket does.
           Any code path that emits a Kraken WS
           subscribe outside the bucket is a
           session-halting defect.

============================================================
1. PURPOSE
============================================================

This document specifies:
  Section 1 — The complete startup sequence for TothBot V2.
  Section 2 — The mid-session WS reconnect sequence.

Both sequences govern when TothBot may begin or resume
pipeline evaluations after a connectivity event.

TothBot cannot begin trading until all indicators are
seeded, all channels subscribed, all open positions
reconciled, and all pairs reach READY state.

TothBot cannot resume trading after a mid-session WS
disconnect until Position Mirror is reconciled, caches
verified, and channels re-subscribed.

No pipeline evaluations are permitted during either
sequence.

4. PAIR STATES
============================================================

Every monitored pair exists in one of these states:

  WARM_UP   ATR or EMA cache not yet seeded. No entries
            permitted. Gates 4 and 8 block. Pair exits
            WARM_UP after seed + first candle-close event.

  READY     All caches seeded. Pair eligible for pipeline
            evaluation. Gates 4 and 8 can operate.

  BLOCKED   Pair excluded by instrument status check.
            reduce_only / work_in_progress / delisted /
            limit_only / cancel_only / maintenance.

  WARM_UP is the initial state for ALL pairs on startup.
  Transition to READY is defined in Section 7.

6. SECTION 1 — STARTUP SEQUENCE (10 STEPS)
============================================================

Steps execute in this order. No step is skipped.
Each step must complete successfully before proceeding
to the next (unless explicitly noted as non-blocking).

------------------------------------------------------------
STEP 1 — Kraken Status API Check (AR-038)
------------------------------------------------------------

SS-STARTUP-001  Query:
  GET https://status.kraken.com/api/v2/
      scheduled-maintenances/upcoming.json
  No authentication required.
  aiohttp ClientSession. ClientTimeout applies.

SS-STARTUP-002  If scheduled maintenance within 2 hours:
  Log: KRAKEN_MAINTENANCE_SCHEDULED
  Alert: alert@tothbot.com with maintenance details.
  Action: Non-blocking. Continue startup.
  Rationale: Bill can decide to delay start manually.

SS-STARTUP-003  If request fails (network error, timeout):
  Log: STATUS_API_UNAVAILABLE
  Action: Non-blocking. Continue startup.
  Rationale: Status API failure does not prevent trading.

------------------------------------------------------------
STEP 2 — Acquire WebSocket Token (AR-004)
------------------------------------------------------------

SS-STARTUP-004  Call GetWebSocketsToken (REST, TRADE key).
  Token valid 15 minutes from creation. AR-042 (no expiry
  while connection maintained).

SS-STARTUP-005  On failure: retry up to 3 times with 2s
  delay. If all fail: log FATAL_TOKEN_ACQUISITION_FAILED,
  halt startup. Cannot proceed without token.

------------------------------------------------------------
STEP 3 — Connect Public WS and Subscribe (AR-029)
------------------------------------------------------------

SS-STARTUP-006  Connect: wss://ws.kraken.com/v2
  websockets.connect() with max_size=10MB, open_timeout=10.

SS-STARTUP-007  Subscribe (single message, all channels):
  - instrument (snapshot=true)
  - status (snapshot=true)
  - ohlc (interval=5, snapshot=true, all monitored pairs)
  - ohlc (interval=60, snapshot=true, all monitored pairs)
  NOTE: Do NOT subscribe ticker yet. Ticker subscriptions
  are managed per-pair after Position Mirror is restored.

SS-STARTUP-008  Parse all subscription ACK warnings[].
  Log any non-empty warnings. AR-031.

SS-STARTUP-009  Start ping task (30s interval). AR-A7.
  Start zombie detection task (90s threshold). AR-042.
  Only real channel events reset zombie timer.

------------------------------------------------------------
STEP 4 — Process Instrument Snapshot (AR-020)
------------------------------------------------------------

SS-STARTUP-010  Wait for instrument snapshot message.
  Timeout: 10 seconds. On timeout: reconnect + retry.

SS-STARTUP-011  For each pair in snapshot:
  Populate per-pair instrument cache:
    price_increment (float → Decimal(str()))
    qty_increment   (float → Decimal(str()))
    qty_min         (float → Decimal(str()))
    cost_min        (float → Decimal(str()))
    status (str)
  Use price_increment (NOT deprecated tick_size). AR-028.
  Use qty_increment for Gate 8 rounding. AR-047.
  All values converted to Decimal(str()) immediately. AR-047.

SS-STARTUP-012  Set pair state:
  online / post_only → WARM_UP (eligible for seeding)
  All other statuses → BLOCKED

------------------------------------------------------------
STEP 5 — Connect Private WS and Subscribe (AR-003)
------------------------------------------------------------

SS-STARTUP-013  Connect: wss://ws-auth.kraken.com/v2
  websockets.connect() with max_size=10MB, open_timeout=10.

SS-STARTUP-014  Subscribe executions with:
    token: (acquired in Step 2)
    snap_orders: true
    snap_trades: true
    order_status: true  <- MANDATORY (AR-026 / AR-015)
    ratecounter: true   <- (AR-A1)
  Extract maxratecount from ACK. Use as operative threshold.
  AR-019 (IMP-11).

SS-STARTUP-015  Subscribe balances:
    token: (acquired in Step 2)
    snapshot: true
  Parse initial snapshot: use wallets[type=spot][id=main]
  only. AR-050. Set portfolio_baseline_USD = spot_usd_balance.

SS-STARTUP-016  Start ping task on private WS connection.
  Start zombie detection on private WS connection.

------------------------------------------------------------
STEP 6 — Reconcile Open Positions (AR-003)
------------------------------------------------------------

SS-STARTUP-017  Process snap_orders snapshot from
  executions channel. Identify all open orders.

SS-STARTUP-018  Restore Position Mirror from snapshot:
  For each open position found:
    symbol, entry_fill_price (avg_price), qty,
    TP order_id, emergSL order_id, cl_ord_id
  If a position has a TP but no emergSL (or vice versa):
    Log INCOMPLETE_PROTECTION and alert operator.
    Do NOT attempt to re-place missing orders automatically
    without operator confirmation. Position state is
    ambiguous.

SS-STARTUP-019  On reconciliation gap (executions seq gap):
  Fall back to REST GetOpenOrders. AR-021.
  GetAccountBalance for balance check.

------------------------------------------------------------
STEP 7 — Restore Ticker for Open Positions (AR-034)
------------------------------------------------------------

SS-STARTUP-020  For each pair with open position in
  Position Mirror:
  Subscribe ticker with event_trigger:bbo.
  This activates real-time MAE monitoring (bid price).

SS-STARTUP-021  For all other monitored pairs:
  Subscribe ticker with event_trigger:trades.
  This provides data for Gate 2 (24h volume) and
  pre-computation cache updates.

------------------------------------------------------------
STEP 8 — REST Warm-Up: GetOHLCData (AR-044)
------------------------------------------------------------

SS-WARMUP-001  For all WARM_UP pairs, execute 3 GetOHLCData
  calls per pair. Use asyncio.gather() to parallelize
  ACROSS pairs. Stagger 1.1s WITHIN the same pair.

SS-WARMUP-002  Per pair — Call A: interval=5 (ATR seed)
  GetOHLCData(pair, interval=5)
  Use response[:-1] (exclude current uncommitted candle).
  Take last 14+ committed candles.
  All candle values: Decimal(str()) immediately on parse.
  ATR seed:
    prev_close = ohlc[-15].close
    TR_0 = max(high-low, |high-prev_close|, |low-prev_close|)
    ... compute TR for all 14 candles ...
    ATR_seed = sum(TR_list) / 14
  Incremental from here on per candle-close event.

SS-WARMUP-003  Per pair — Call B: interval=60 (EMA seed)
  GetOHLCData(pair, interval=60)
  1.1s AFTER Call A for the same pair.
  Use response[:-1]. Take last 100+ candles.
  All candle values: Decimal(str()) immediately on parse.
  EMA(20) seed:
    alpha_20 = 2/21
    EMA_20_seed = SMA of first 20 close values
    Compute forward through all 100+ candles
  EMA(50) seed:
    alpha_50 = 2/51
    EMA_50_seed = SMA of first 50 close values
    Compute forward through all 100+ candles
  Store current EMA(20) and EMA(50) in 1H HTF cache.

SS-WARMUP-004  Per pair — Call C: interval=1440 (Regime)
  GetOHLCData(pair, interval=1440)
  1.1s AFTER Call B for the same pair.
  Use response[:-1]. Compute ADX(14), EMA(20), EMA(50)
  on daily candles. Classify regime. Store in regime cache.
  (Full specification in 1011012 Regime_Engine_Coding_Spec)

SS-WARMUP-005  On rate limit error (HTTP 429) for any call:
  Exponential backoff: 2s, 4s, 8s. Max 3 retries.
  On all retries failed:
    ATR/EMA: pair remains in WARM_UP (will seed on candle
    close events instead — slower but acceptable).
    Regime: use stale regime if available, or
    NO_REGIME_AVAILABLE -> Gate 3 blocks all entries.
    Log WARMUP_REST_FAILED for affected pair.

SS-WARMUP-006  Stagger enforcement within same pair:
  asyncio.sleep(1.1) between Call A -> B -> C for pair X.
  Calls for pair Y can run concurrently with pair X.
  Do not issue all 3 calls for the same pair in parallel.

SS-WARMUP-007  OHLC interval_begin initialization (AR-045):
  After Call A for each pair:
    last_interval_begin[pair] = response[-2].interval_begin
    last_complete_candle[pair] = response[-2] data
    (response[-2] is last committed candle of interval=5)
  After Call B for each pair:
    last_interval_begin_60[pair] = response[-2].interval_begin
    last_complete_candle_60[pair] = response[-2] data
  From this point, WS OHLC messages are compared against
  these values to detect candle-close events.

SS-WARMUP-008  Pair transitions from WARM_UP -> READY
  when all three of the following are true:
  (a) ATR(14) seeded (from Call A or first 14 candle-close)
  (b) EMA(20) and EMA(50) seeded (from Call B or 50+
      candle-close events — may take hours without REST)
  (c) Current regime available (from Call C)
  Pairs that fail REST warm-up will be delayed. This is
  acceptable. The system does NOT wait indefinitely for
  all pairs — it begins trading READY pairs immediately.

------------------------------------------------------------
STEP 9 — At Least One READY Pair: Begin Pipeline
------------------------------------------------------------

SS-STARTUP-021  System enters OPERATIONAL state when
  at least one pair is in READY state.

SS-STARTUP-022  WARM_UP pairs continue seeding via
  WS candle events. They enter READY organically.

SS-STARTUP-023  BLOCKED pairs are re-evaluated on each
  instrument channel update event. If status changes
  to online or post_only: transition to WARM_UP,
  begin seeding process.

SS-STARTUP-024  Pipeline is per-symbol. READY pairs
  proceed through the full 8-gate pipeline.
  WARM_UP pairs are skipped at the pipeline level
  (per-pair status check, pre-Gate 1).

------------------------------------------------------------
STEP 10 — Continuous Operation
------------------------------------------------------------

SS-STARTUP-025  At 00:00 UTC: Regime Engine re-runs
  GetOHLCData(interval=1440) for all pairs. AR-036 stagger.
  This refreshes the daily regime classification.
  Startup Step 8 Call C provides the initial regime.
  00:00 UTC refresh provides daily updates.

SS-STARTUP-026  systemd watchdog: asyncio task sends
  sd_notify WATCHDOG=1 every 30 seconds. AR-025/AR-008.
  If event loop freezes, systemd restarts TothBot.
  On restart: full startup sequence from Step 1.

7. SECTION 1 — ERROR HANDLING MATRIX
============================================================

  FAILURE               ACTION
  ─────────────────────────────────────────────────────────
  Token failure         Retry 3x. FATAL halt if all fail.
  WS connect fail       Retry 5x instant. FATAL halt if all.
  Instrument timeout    Reconnect + resubscribe.
  snap_orders gap       Fall back to REST GetOpenOrders.
  GetOHLCData 429       Backoff 3x. Log. Pair stays WARM_UP.
  GetOHLCData fail      Log. Pair stays WARM_UP. Continue.
  Incomplete position   Log INCOMPLETE_PROTECTION. Alert Bill.
                        Do not auto-repair without operator.
  Status API fail       Log. Non-blocking. Continue.

============================================================
8. SECTION 1 — TIMING EXPECTATIONS
============================================================

Best case startup (50 pairs, all REST calls succeed):
  Steps 1-7:          ~5 seconds
  Step 8 (parallel):  ~3.3 seconds per pair (3 calls x 1.1s)
                      asyncio.gather across pairs -> ~3-5s
  Total startup:      ~8-10 seconds before first READY pair

Worst case (sequential, all calls):
  50 pairs x 3 calls x 1.1s = 165 seconds (~2.75 minutes)
  Unacceptable. Must use asyncio.gather() for parallelism.

Target: All pairs READY within 15 seconds of startup.

9. SECTION 2 — MID-SESSION WS RECONNECT SEQUENCE (AR-056)
============================================================

------------------------------------------------------------
9.1 PURPOSE AND DISTINCTION FROM STARTUP
------------------------------------------------------------

SS-RECON-001  ★ NEW dv1_1 (AR-056): Mid-session WS reconnect
              is DISTINCT from the startup sequence (Section 1).
              Different rules apply. Do not execute Section 1
              on a mid-session reconnect.

              TRIGGER: Private WS connection drops during live
              operation. WS Manager detects via asyncio
              exception or connection timeout.

              KEY DISTINCTIONS FROM STARTUP:
              (a) portfolio_baseline_USD: NEVER reset.
                  Reconnect in the middle of a session must
                  not reset the drawdown counter — that would
                  mask actual session losses.
              (b) ATR/EMA caches: PRESERVED unless stale
                  (gap > 15 minutes). Do NOT re-run full
                  warm-up unless caches are stale.
              (c) Positions may have closed during gap (TP
                  or emergSL fired while disconnected).
                  Must detect and fire CIATS Trade Outcome Bus.
              (d) Pending Order Registry: reconcile against
                  snap_orders (orders may have filled or
                  expired during gap).
              (e) system_state (halt/pause): PRESERVED.
                  A drawdown halt active before disconnect
                  remains active after reconnect.

SS-RECON-002  ★ INVARIANTS — Must be preserved across all
              mid-session reconnects. Non-negotiable.

                portfolio_baseline_USD    NEVER reset
                drawdown_pct              PRESERVED
                ATR cache per pair        PRESERVED (unless stale)
                EMA cache per pair        PRESERVED (unless stale)
                Position Mirror           Updated by reconciliation
                system_state (halt)       PRESERVED
                regime_cache              PRESERVED

------------------------------------------------------------
9.2 RECONNECT STEPS (11 STEPS)
------------------------------------------------------------

SS-RECON-003  ★ STEP R1: Close broken connection.
              Close WS connection cleanly (suppress errors).
              Cancel all pending asyncio tasks for this
              connection (ping task, zombie task, etc.).
              Reset per-connection sequence numbers.
              Log WS_DISCONNECT_DETECTED with timestamp.

SS-RECON-004  ★ STEP R2: Wait.
              Normal disconnect (transient):
                Retry instantly, up to 5 attempts.
              After 5 failures OR after confirmed maintenance:
                Wait 5 seconds between attempts.
              Per Kraken WS v2 intro guidance.

SS-RECON-005  ★ STEP R3: Fetch fresh WebSocket token.
              Call GetWebSocketsToken (REST, TRADE key).
              Token may have expired during the outage.
              Per WM-TOKEN-001: always fetch fresh on reconnect.
              Retry up to 3 times with 2s delay.
              If all fail: log FATAL_TOKEN_RECONNECT_FAILED.
              Systemd watchdog will restart TothBot.

SS-RECON-006  ★ STEP R4: Reconnect private WS.
              Connect: wss://ws-auth.kraken.com/v2
              websockets.connect():
                max_size=10MB
                open_timeout=10

SS-RECON-007  ★ STEP R5: Re-subscribe executions.
              {
                "method": "subscribe",
                "params": {
                  "channel": "executions",
                  "token": <fresh_token>,
                  "snap_orders": true,
                  "snap_trades": true,
                  "order_status": true,
                  "ratecounter": true
                }
              }
              Extract maxratecount from ACK (AR-019).
              Parse ACK warnings[] and log any warnings.

SS-RECON-008  ★ STEP R6: Position Mirror reconciliation.
              Compare pre-disconnect Position Mirror against
              snap_orders received from new subscription.

              For each symbol in Position Mirror but NOT
              found in snap_orders open orders:
                Position was closed during the gap.
                (TP filled or emergSL fired while disconnected)
                Find corresponding trade in snap_trades
                  (last 50 fills returned by snap_trades:true).
                Fire CIATS Trade Outcome Bus with trade data.
                Remove position from Position Mirror.
                Log POSITION_CLOSED_DURING_GAP.

              For each open order in snap_orders but NOT
              in Position Mirror (manual / error):
                Alert operator ONLY. Do not auto-trade.
                Log UNEXPECTED_ORDER_FOUND.

              Pending Order Registry reconciliation:
                For each cl_ord_id in pending_orders:
                  If now in snap_orders as "new" or
                  "pending_new": keep in registry (order
                  placed before disconnect, now confirmed live).
                  If NOT in snap_orders: clear from registry
                  (expired or never accepted during gap).
                  Log PENDING_ORDER_LOST for cleared entries.

SS-RECON-009  ★ STEP R7: Re-subscribe balances.
              {
                "method": "subscribe",
                "params": {
                  "channel": "balances",
                  "token": <fresh_token>,
                  "snapshot": true
                }
              }
              On snapshot receipt:
                Update spot_asset_balances from spot/main
                wallet only (AR-050). Do NOT reset
                portfolio_baseline_USD.
              Log BALANCES_RESYNCED.

SS-RECON-010  ★ STEP R8: Re-subscribe public channels.
              Re-subscribe: instrument, status, ohlc(5m),
              ohlc(60m). Update pair cache from new
              instrument snapshot (status, increments).
              If pair status changed during gap: update pair
              state accordingly (READY/BLOCKED).
              Log PUBLIC_CHANNELS_RESUBSCRIBED.

SS-RECON-011  ★ STEP R9: Restore ticker subscriptions.
              For each pair with open position in
              (updated) Position Mirror:
                Subscribe ticker with event_trigger:bbo.
              For all other monitored pairs:
                Subscribe ticker with event_trigger:trades.
              This restores real-time MAE monitoring.
              Log TICKER_RESTORED.

SS-RECON-012  ★ STEP R10: Cache staleness check.
              Record gap_duration = reconnect_time - disconnect_time.

              If gap_duration <= 15 minutes:
                ATR/EMA caches are valid. No re-warm required.
                Regime cache is valid (regime is daily).
                Skip REST warm-up. Log CACHE_VALID_NO_WARMUP.

              If gap_duration > 15 minutes:
                ATR/EMA caches may be stale.
                Re-run GetOHLCData(interval=5) for affected pairs.
                Re-run GetOHLCData(interval=60) for affected pairs.
                DO NOT re-run GetOHLCData(interval=1440) unless
                date has changed (regime is daily — not stale
                within same day).
                Use asyncio.gather() across pairs (not sequential).
                1.1s stagger within same pair. AR-036.
                Log CACHE_REWARM_STARTED.

SS-RECON-013  ★ STEP R11: Resume operations.
              Pairs with fresh caches: remain in READY state.
              Pairs with stale caches (rewarm in progress):
                Set to WARM_UP until rewarm completes.
              BLOCKED pairs: unchanged (no state change on reconnect).
              Log RECONNECT_COMPLETE with gap_duration.
              Resume pipeline at next candle-close event.
              Discard any candle-close events that fired
              during Steps R1-R11 (stale data risk).

------------------------------------------------------------
9.3 PIPELINE DURING RECONNECT
------------------------------------------------------------

SS-RECON-014  ★ While reconnect is in progress (Steps R1-R11),
              no pipeline evaluations are permitted.
              Any candle-close events queued during reconnect
              are DISCARDED after reconnect completes.
              Rationale: incomplete state during reconnect
              could produce incorrect signals. A missed
              evaluation is safer than a mis-fired entry.
              Log CANDLE_DISCARDED_DURING_RECONNECT for each.

------------------------------------------------------------
9.4 FATAL RECONNECT FAILURE
------------------------------------------------------------

SS-RECON-015  ★ If reconnect fails after 10 total attempts
              spanning 120 seconds:
              Log FATAL_RECONNECT_FAILED (CRITICAL severity).
              Alert operator at alert@tothbot.com.
              Stop retrying.
              systemd WatchdogSec=120 will detect that the
              asyncio watchdog ping has stopped and will
              restart TothBot automatically.
              On restart: full startup sequence (Section 1).
              Open positions remain protected by resting
              emergSL orders on Kraken matching engine
              throughout the restart window.

------------------------------------------------------------
9.5 RECONNECT INVARIANT VERIFICATION
------------------------------------------------------------

SS-RECON-016  ★ After RECONNECT_COMPLETE, verify:
              portfolio_baseline_USD unchanged (log value).
              drawdown_pct unchanged (log value).
              system_state (halt/pause/normal) unchanged.
              If any invariant is violated: log INVARIANT_BREACH,
              alert operator CRITICAL. Do not resume pipeline.

10. FIVE CODING-READINESS QUESTIONS
============================================================

  (1) What does this document specify?
      Section 1: The 10-step startup sequence TothBot MUST
      complete before any pipeline evaluation. Defines
      WARM_UP/READY/BLOCKED pair states.
      Section 2: The 11-step mid-session reconnect sequence
      TothBot MUST complete after any WS disconnect during
      live operation before resuming pipeline evaluations.

  (2) Interfaces:
      Section 1: startup interfaces to WS Manager, Position
      Mirror, Pending Order Registry, Regime Engine,
      ATR/EMA cache, ticker subscription manager.
      Section 2: reconnect interfaces to WS Manager, Position
      Mirror, Pending Order Registry, CIATS Trade Outcome Bus,
      ATR/EMA cache, ticker subscription manager.

  (3) Hard rules:
      Startup: No pipeline until at least one READY pair.
      Startup: portfolio_baseline_USD set ONCE from startup
        Step 6 balance snapshot. Never set again in Section 1.
      Reconnect: NEVER reset portfolio_baseline_USD.
      Reconnect: NEVER reset drawdown_pct.
      Reconnect: PRESERVE system_state across reconnect.
      Reconnect: DISCARD candle events fired during reconnect.
      Reconnect: DETECT positions closed during gap via
        Position Mirror vs snap_orders comparison.
      Reconnect: Fire CIATS Trade Outcome Bus for any gap-
        closed positions before resuming pipeline.
      Both: Sequence is executed step-by-step. No steps skipped.
      Both: DMS (cancel_all_orders_after) PROHIBITED. AR-055.

  (4) Triggers:
      Section 1: TothBot process start.
      Section 2: WS disconnect detected during live operation.

  (5) Logs:
      Section 1: STATUS_API_UNAVAILABLE, BALANCES_RESYNCED,
        INCOMPLETE_PROTECTION, WARMUP_REST_FAILED,
        FATAL_TOKEN_ACQUISITION_FAILED, KRAKEN_MAINTENANCE_SCHEDULED.
      Section 2: WS_DISCONNECT_DETECTED, POSITION_CLOSED_DURING_GAP,
        PENDING_ORDER_LOST, UNEXPECTED_ORDER_FOUND,
        CACHE_VALID_NO_WARMUP, CACHE_REWARM_STARTED,
        RECONNECT_COMPLETE, FATAL_RECONNECT_FAILED,
        CANDLE_DISCARDED_DURING_RECONNECT, INVARIANT_BREACH.

1. PURPOSE
============================================================

This document is the complete specification for the TothBot
V2 SSS (Simple Signal System) signal model. It defines
what the SSS signal IS, how every indicator is computed,
seeded, and updated, and what output the SSS produces.

This document is the sole authoritative specification for
SSS signal logic. It is a direct coding contract. Claude
must be able to implement the SSS from this document
without asking any questions.

3. SSS OVERVIEW
============================================================

SSS = Simple Signal System. It is the signal engine that
runs at Gate 5 of the 8-gate trading pipeline on every
5-minute OHLC candle close event, for every monitored
pair that has passed Gate 3 (Regime Pre-Filter) and
Gate 4 (1H HTF Confirmation).

SSS is a three-factor scoring model. All three factors
must be simultaneously true for SSS to PASS. Two-of-three
is a FAIL. Partial credit does not exist.

SSS evaluates the 5-minute timeframe only. Daily regime
and 1H HTF alignment are evaluated at Gates 3 and 4
respectively before SSS runs. SSS does not re-evaluate
regime or HTF — it evaluates only the 5-minute conditions.

This specification covers the long-side implementation of
the direction-symmetric SSS Signal Engine encoded
canonically in 0500000 dv1_80 AR-067 (three-factor momentum
scoring on 5-minute candles consumed by both Long_Module
and Short_Module via the D7 Dispatch Seam per the parallel-
module framework, TB00000 v2_50 §9.3). Short-side SSS
implementation is in 0811005 Short_Module Specification.
Per-module SSS parameter ownership is defined by the per-
module CIATS framework (TB00000 v2_50 §9.6) — Long_Module
CIATS owns rsi_long_low/rsi_long_high; Short_Module CIATS
owns rsi_short_low/rsi_short_high; both modules share
sss_ema_short/sss_ema_long/volume_sss_threshold per TB00000
v2_50 §9.17 Common SSS signal model subsection.

============================================================
4. SSS CONDITIONS — THREE REQUIRED
============================================================

------------------------------------------------------------
SSS-001  SC-SSS-1 — RSI(14) Long-Side Entry Gate
------------------------------------------------------------

  Condition:
    RSI(14) on 5-min > rsi_long_low (30)
    AND RSI(14) on 5-min < rsi_long_high (50)

  Interpretation:
    RSI > 30: the asset has lifted off oversold
    conditions. Selling pressure has eased relative to
    the prior down-move. This is the start of the
    recovery phase, not the confirmation of bullish
    momentum.

    RSI < 50: the asset has not yet entered confirmed
    bullish-momentum territory (RSI > 50). Entry above
    50 increases the probability of buying into already-
    extended price action and reduces residual upside.

    The window RSI(30-50) captures the long-side
    oversold-recovery zone — RSI lifting off oversold
    but not yet into momentum-confirmed bull territory.
    Direction-symmetric to the short-side 50-70 zone
    per TB00000 v2_50 §9.17 (rsi_short_low = 70,
    rsi_short_high = 50 — short-side oversold-short
    equivalent above the 50 mid-line).

  Parameters (CIATS-owned starting values per TB00000
  v2_50 §9.17 CIATS Parameter Registry):
    rsi_long_low:  30
    rsi_long_high: 50

  RESULT: PASS if 30 < RSI(14) < 50. FAIL otherwise.

------------------------------------------------------------
SSS-002  SC-SSS-2 — EMA Crossover Gate
------------------------------------------------------------

  Condition:
    EMA(9) on 5-min > EMA(21) on 5-min

  Interpretation:
    Short-term EMA above long-term EMA on the entry
    timeframe confirms that price momentum is upward
    within the confirmed higher-timeframe trend. This
    crossover state — not the crossover event itself —
    is the condition. The state must hold at candle close.

  Parameters (CIATS-owned starting values):
    sss_ema_short: 9
    sss_ema_long:  21

  RESULT: PASS if EMA(9) > EMA(21). FAIL otherwise.

------------------------------------------------------------
SSS-003  SC-SSS-3 — Volume Confirmation Gate
------------------------------------------------------------

  Condition:
    current_candle_volume > Volume_MA(20) x volume_sss_threshold

  Interpretation:
    Above-average volume confirms genuine participant
    interest in the current price move. A signal on low
    volume is a weak signal subject to reversal. Volume
    above the 20-candle average indicates institutional
    or broad retail participation.

  Parameters (CIATS-owned starting values):
    volume_sss_threshold: 1.0x

  RESULT: PASS if volume > Volume_MA(20). FAIL otherwise.

------------------------------------------------------------
SSS-004  SSS PASS Definition
------------------------------------------------------------

  SSS PASS = SC-SSS-1 AND SC-SSS-2 AND SC-SSS-3

  All three must be simultaneously true at candle close.
  If any one condition is false, SSS FAIL.
  SSS FAIL rejection code: SELECTION_REJECTED__SSS_SIGNAL_FAIL

5. INDICATOR SPECIFICATIONS
============================================================

Four indicators power the three SSS conditions.
All four are maintained per monitored symbol in the
per-symbol state dict (AR-075). All four are updated
incrementally on every 5-minute ohlc candle close.

------------------------------------------------------------
SSS-005  RSI(14) — Relative Strength Index
------------------------------------------------------------

CRITICAL: RSI(14) MUST use Wilder's Smoothed Moving
Average (SMMA), also known as RMA. DO NOT use standard
EMA (alpha=2/n+1) for RSI computation. Using standard
EMA produces 5-8% variance in RSI values and would
systematically mis-fire SC-SSS-1. (AR-076)

  Seeding (first 14 complete candles):
    gains = [max(0, close[i] - close[i-1]) for i in 1..14]
    losses = [max(0, close[i-1] - close[i]) for i in 1..14]
    avg_gain = sum(gains) / Decimal("14")
    avg_loss = sum(losses) / Decimal("14")

  Incremental update (each subsequent candle):
    current_gain = max(Decimal("0"), close - prev_close)
    current_loss = max(Decimal("0"), prev_close - close)
    avg_gain = (prev_avg_gain * Decimal("13") + current_gain)
               / Decimal("14")
    avg_loss = (prev_avg_loss * Decimal("13") + current_loss)
               / Decimal("14")
    RS = avg_gain / avg_loss
    RSI = Decimal("100") - (Decimal("100") / (Decimal("1") + RS))

  State stored per symbol:
    rsi_14_avg_gain: Decimal  (Wilder SMMA running state)
    rsi_14_avg_loss: Decimal  (Wilder SMMA running state)

  Division guard: if avg_loss == 0 and avg_gain > 0: RSI = 100
                  if avg_loss == 0 and avg_gain == 0: RSI = 50

  Evidence base: 10+ independent sources confirm Wilder's
  SMMA (α=1/n) as the correct RSI formula. A 14-period
  SMMA is equivalent to a 27-period standard EMA (not 15).
  (TradingView rma(), StockCharts.com, Supra Oracle docs,
  Wikipedia, LuxAlgo, AlphaRithms, Quantinsti,
  PineScriptMarket, Medium — TB00021 validation.)

------------------------------------------------------------
SSS-006  EMA(9) — Short-Term EMA
------------------------------------------------------------

  Period: 9
  Algorithm: Standard EMA
  Alpha: 2 / (9 + 1) = 2/10 = 0.2000

  Seeding (first 9 complete candles):
    ema_9 = sum(close[:9]) / Decimal("9")  (SMA seed)

  Incremental update (each subsequent candle):
    ema_9 = (close - prev_ema_9) * alpha + prev_ema_9
            where alpha = Decimal("2") / Decimal("10")

  State stored per symbol:
    ema_9: Decimal

------------------------------------------------------------
SSS-007  EMA(21) — Long-Term EMA
------------------------------------------------------------

  Period: 21
  Algorithm: Standard EMA
  Alpha: 2 / (21 + 1) = 2/22 ≈ 0.0909

  Seeding (first 21 complete candles):
    ema_21 = sum(close[:21]) / Decimal("21")  (SMA seed)

  Incremental update (each subsequent candle):
    ema_21 = (close - prev_ema_21) * alpha + prev_ema_21
             where alpha = Decimal("2") / Decimal("22")

  State stored per symbol:
    ema_21: Decimal

------------------------------------------------------------
SSS-008  Volume MA(20) — Volume Moving Average
------------------------------------------------------------

  Period: 20
  Algorithm: Simple Moving Average (rolling)

  Seeding (first 20 complete candles):
    volume_ma_20 = sum(volume[:20]) / Decimal("20")

  Incremental update (each subsequent candle):
    volume_ma_20 = ((prev_volume_ma_20 * Decimal("19"))
                    + current_volume) / Decimal("20")

  State stored per symbol:
    volume_ma_20: Decimal

  Note: this is a running SMA, not a true rolling window.
  CIATS may evaluate a true rolling window after 200 trades
  if the approximation proves material.

============================================================
6. SEEDING PROCEDURE (AR-068)
============================================================

------------------------------------------------------------
SSS-009  Data Source for Seeding
------------------------------------------------------------

All five per-pair indicators (ATR(14) — per AR-016,
plus RSI(14), EMA(9), EMA(21), Volume MA(20)) are seeded
from the SAME REST call already made per AR-044:

  GetOHLCData(pair=symbol, interval=5)

This call returns 700+ candles — adequate to seed all
five indicators from response[:-1] (last entry excluded).
No additional REST calls are required for SSS seeding.

------------------------------------------------------------
SSS-010  Seeding Sequence Per Symbol
------------------------------------------------------------

Using response[:-1] (committed candles only):

  Step 1: Seed ATR(14) (AR-016):
          First 14 True Ranges → SMA seed.
          Incremental Wilder SMMA thereafter.

  Step 2: Seed RSI(14):
          First 14 closes → avg_gain / avg_loss (SMA).
          Wilder SMMA incremental thereafter.
          Requires 14 candles minimum.

  Step 3: Seed EMA(9):
          First 9 closes → SMA seed.
          Standard EMA incremental thereafter.
          Requires 9 candles minimum.

  Step 4: Seed EMA(21):
          First 21 closes → SMA seed.
          Standard EMA incremental thereafter.
          Requires 21 candles minimum.

  Step 5: Seed Volume MA(20):
          First 20 volumes → SMA seed.
          Rolling SMA incremental thereafter.
          Requires 20 candles minimum.

Minimum candles required to seed all five: 21
(limited by EMA(21) seeding requirement).
GetOHLCData(interval=5) returns 700+ — well in excess.

------------------------------------------------------------
SSS-011  WARM_UP to READY Transition
------------------------------------------------------------

A pair transitions from WARM_UP to READY only when ALL
FIVE indicators are seeded and valid. ATR seeding alone
is insufficient for READY status.

  WARM_UP: pair is subscribing and seeding indicators.
           Pair is NOT eligible for trade evaluation.

  READY:   all five indicators seeded. Pair IS eligible
           for trade evaluation at next candle close.

Transition trigger: after seeding completes successfully
for all five indicators in the startup sequence.

------------------------------------------------------------
SSS-012  Incremental Updates After Seeding
------------------------------------------------------------

After seeding, all four SSS indicators are updated
incrementally on every ohlc(5) candle close event for the
pair. Each candle close produces one update cycle:

  1. Receive confirmed candle (not the live partial candle)
  2. Update ATR(14) → Wilder SMMA
  3. Update RSI(14) → Wilder SMMA (avg_gain, avg_loss)
  4. Update EMA(9) → standard EMA
  5. Update EMA(21) → standard EMA
  6. Update Volume MA(20) → rolling SMA
  7. Read current state from Parameter Store snapshot (I-4)
  8. Evaluate Gate 5 SSS if Gates 3 and 4 have passed

The update occurs before Gate 5 evaluation. The SSS
always operates on the freshest indicator values.

============================================================
7. SSS OUTPUT
============================================================

------------------------------------------------------------
SSS-013  signal_params Dict
------------------------------------------------------------

On every SSS evaluation (pass or fail), SSS produces a
signal_params dict. This dict is logged to the CIATS
Trade Outcome Bus (Stream 2) on every position close,
carrying the signal state at entry time.

  signal_params = {
      "rsi_14":         Decimal,    # RSI value at evaluation
      "ema_9":          Decimal,    # EMA(9) value
      "ema_21":         Decimal,    # EMA(21) value
      "volume_ratio":   Decimal,    # volume / volume_ma_20
      "sss_pass":       bool,       # True if all 3 passed
  }

signal_params is always populated, pass or fail.
A SSS FAIL still produces a signal_params dict (with
sss_pass=False) for CIATS analysis of what failed and why.

No SSS evaluation is silent. Every evaluation is logged.

7A. SIGNAL DECAY DETECTION (PENDING-ENTRY CANCEL TRIGGER)
============================================================

This section specifies the SIGNAL_DECAY detection condition
for a still-working long-side entry order. Per DEC-065 Q2
(RATIFIED; TB00153 v1_59 lines 7377-7386) SIGNAL_DECAY is
NOT an exit_reason value; it is re-homed as a PENDING-ENTRY-
ORDER CANCEL TRIGGER: if the entry signal (SSS) deteriorates
below threshold while the entry order is still working
(unfilled or partially filled), the unfilled / remaining qty
is canceled. This section authors the DETECTION half only
(SSS_Signal_Model). The cancel-DISPATCH mechanics (0511003
Execution_Engine) and the cancel-CONTROL decision ownership
(Selection Controller specification) are SEPARATE targets and
are NOT specified in this document (DEC-065 register framing
+ TB00447 SL v1_1 sec 3.0 Bill-ratified refinement).

OWNERSHIP BOUNDARY (Bill-ratified, TB00449 NSI sec 1.2 /
TB00447 SL v1_1 sec 3.0). A single working entry order is
owned by the Selection module (entry-side control) while
unfilled. On a PARTIAL fill the one order bisects into two
concurrently-owned objects: the filled qty becomes a real
position owned by the Exit Controller (AR-054 handles the
unprotected-stub case; 0500000 dv1_132 sec 4 line 5942), and
the unfilled remainder stays owned by the Selection module.
If SIGNAL_DECAY fires before the remainder fills, the cancel
of the unfilled remainder is a SELECTION-module action
(mod:Selection_Controller), NOT an Exit-module / AR-054
action. The boundary is the fill: filled -> Exit; unfilled ->
Selection. The still-working order's capital commitment is
tracked in the per-module Pending Order Registry (AR-053;
0500000 dv1_132 sec 4 line 5895).

------------------------------------------------------------
SSS-014  SC-SSS-DECAY-1 — Long-Side Signal Decay Detection
------------------------------------------------------------

  Applies ONLY while a long-side entry order for the pair is
  still working (unfilled, or partially filled with an open
  remainder). Re-evaluated on every committed 5-min candle
  close for that pair until the order is fully filled,
  canceled, or expired.

  Condition (SIGNAL_DECAY fires when either is true at
  committed candle close):
    RSI(14) on 5-min <= rsi_long_low   (RSI floor breach)
    OR EMA(9) on 5-min <= EMA(21) on 5-min  (EMA reversion)

  Interpretation:
    The two momentum-persistence conditions that authorized
    the entry are SC-SSS-1 (RSI lifted off the oversold floor)
    and SC-SSS-2 (EMA(9) > EMA(21) crossover state). These are
    persistence conditions: they must continue to hold for the
    entry thesis to remain valid while the order is working.
      - RSI(14) <= rsi_long_low: RSI has fallen back to or
        below the entry floor. The oversold-recovery thesis
        that authorized the entry is invalidated.
      - EMA(9) <= EMA(21): the 5-min momentum crossover state
        has reverted. The directional-momentum thesis is
        invalidated.
    Volume confirmation (SC-SSS-3) is an entry-instant
    participation gate, NOT a persistence condition, and is
    therefore NOT evaluated for decay (see HR-SSS-011). A
    single-candle volume dip does not invalidate an intact
    RSI + EMA momentum thesis; including it would cause
    premature cancels (opportunity loss).

  Loss-prevention rationale (TB00000 v2_60 sec 1.2 / sec 9.10
  prime directive — minimize loss):
    Cancelling the still-working qty on thesis invalidation
    removes the capital commitment (AR-053 registry) before an
    adverse fill on a signal that has already decayed,
    minimizing realized loss. The threshold deliberately uses
    the two directional-persistence conditions (not full
    three-factor SSS PASS) so that decay tracks the thesis,
    not transient volume.

  Parameters (reused from sec 9 — NO new parameters; CIATS-
  owned per-module per sec 9):
    rsi_long_low    (RSI floor; starting value 30)
    sss_ema_short   (short EMA period; 9)
    sss_ema_long    (long EMA period; 21)

  RESULT: signal_decay = (RSI(14) <= rsi_long_low)
                         OR (EMA(9) <= EMA(21)).
          signal_decay = True  -> hand verdict to Selection
            module to cancel the unfilled / remaining qty.
          signal_decay = False -> order continues working;
            re-evaluate at the next committed candle close.

------------------------------------------------------------
SSS-015  decay_params Dict + Cancel-Trigger Handoff
------------------------------------------------------------

On every decay evaluation (i.e., every committed 5-min candle
close while the order is still working), SSS produces a
decay_params dict, logged to the CIATS Trade Outcome Bus
consistent with the never-silent discipline (HR-SSS-007).

  decay_params = {
      "rsi_14":           Decimal,  # RSI at decay evaluation
      "ema_9":            Decimal,  # EMA(9) value
      "ema_21":           Decimal,  # EMA(21) value
      "rsi_floor_breach": bool,     # RSI(14) <= rsi_long_low
      "ema_revert":       bool,     # EMA(9) <= EMA(21)
      "signal_decay":     bool,     # floor_breach OR ema_revert
  }

HANDOFF (detection -> control boundary):
  signal_decay = True is emitted to the Selection module
  (mod:Selection_Controller), which owns the cancel of the
  unfilled / remaining qty (entry-side control). Any already-
  filled portion remains owned by the Exit Controller per
  AR-054. The control-decision logic (Selection Controller
  spec) and the cancel-dispatch mechanics (0511003
  Execution_Engine) are out of scope for this document and
  are sequenced separately (each gated by its own DD-011
  decision per TB00449 NSI sec 2.3).

  Event code (working-entry cancel trigger):
    SELECTION_CANCEL__SSS_SIGNAL_DECAY
  Parallel to the entry-time reject code
  SELECTION_REJECTED__SSS_SIGNAL_FAIL (SSS-004).

This section specifies the DETECTION condition and its output
only. No cancel is dispatched from within SSS.

SHORT-SIDE NOTE: this specification is the long-side
implementation. The direction-symmetric short-side
SIGNAL_DECAY variant (RSI >= rsi_short_low / EMA(9) >= EMA(21)
reversion) is defined in 0811005 Short_Module_Specification
per the parallel-module framework.

8. HARD RULES — SSS SIGNAL MODEL
============================================================

HR-SSS-001  SSS requires all three conditions
            simultaneously. Two-of-three is a fail.
            Partial credit is not permitted.

HR-SSS-002  RSI(14) MUST use Wilder's SMMA (α=1/14).
            Standard EMA (α=2/15) is PROHIBITED for RSI.
            EMA(9) and EMA(21) use standard EMA.
            Only RSI uses Wilder's SMMA. Do not conflate.

HR-SSS-003  All indicator arithmetic MUST use Python
            Decimal. float arithmetic is PROHIBITED for
            any RSI, EMA, or volume computation.
            Decimal.quantize() is the only rounding
            method permitted.

HR-SSS-004  Division by zero must be guarded. If avg_loss
            is zero and avg_gain > 0: RSI = 100.
            If both are zero: RSI = 50. This case should
            not arise from real market data but must be
            handled defensively.

HR-SSS-005  WARM_UP to READY requires all five indicators
            seeded. ATR alone is insufficient. The pair
            is not tradeable until all five are valid.

HR-SSS-006  SSS operates on committed candles only.
            The live partial candle (ohlc response[-1] or
            the current streaming snapshot) MUST NOT be
            evaluated. Wait for candle close confirmation.

HR-SSS-007  signal_params is always logged, pass or fail.
            CIATS requires both pass and fail data.
            Failing evaluations must not be suppressed.

HR-SSS-008  SSS parameters are read from the Parameter
            Store snapshot at pipeline evaluation time (I-4).
            SSS does not hold its own parameter copies.
            The snapshot is taken once per pipeline
            evaluation and is frozen for that evaluation.

HR-SSS-009  Seeding uses response[:-1] from GetOHLCData.
            The last entry is always the not-yet-committed
            current candle and MUST be excluded.

HR-SSS-010  No additional REST calls are made for SSS
            seeding. The GetOHLCData(interval=5) call
            already made per AR-044 provides the seeding
            data. Zero additional calls required.

HR-SSS-011  SIGNAL_DECAY is a PENDING-ENTRY CANCEL TRIGGER,
            NOT an exit_reason value (DEC-065 Q2). It applies
            ONLY to a still-working entry order (unfilled or
            open remainder) and is evaluated only on committed
            candle closes (HR-SSS-006). The cancel of the
            unfilled / remaining qty is a Selection-module
            action (mod:Selection_Controller); any already-
            filled portion is owned by the Exit Controller per
            AR-054. SIGNAL_DECAY MUST NOT be written to the
            exit_reason enum. Volume (SC-SSS-3) MUST NOT be
            used as a decay condition; decay uses only the RSI
            floor (SC-SSS-1) and EMA crossover (SC-SSS-2)
            persistence conditions per SSS-014.

9. CIATS PARAMETER REGISTRY — SSS PARAMETERS
============================================================

All SSS parameters are CIATS-owned starting values per
TB00000 v2_50 §9.17 CIATS Parameter Registry. All will be
evaluated and updated by CIATS after the 200-trade floor
is reached via PDCA, per-module (Long_Module CIATS
instance owns long-side parameter evolution; Short_Module
CIATS instance owns short-side parameter evolution; cross-
module data contamination prohibited per TB00000 v2_50
§9.6).

Long-side SSS parameters (this specification):

  rsi_long_low:           30    (RSI > threshold = lift
                                 off oversold)
  rsi_long_high:          50    (RSI < threshold = not yet
                                 momentum-confirmed bull)
  sss_ema_short:          9     (short EMA period, 5-min)
  sss_ema_long:           21    (long EMA period, 5-min)
  volume_sss_threshold:   1.0x  (volume multiplier on MA20)

Short-side SSS parameters (defined in 0811005
Short_Module_Specification §9; included here for cross-
reference only):

  rsi_short_low:          70    (RSI > threshold per
                                 0811005 §9 + TB00000
                                 v2_50 §9.17)
  rsi_short_high:         50    (RSI < threshold per
                                 0811005 §9 + TB00000
                                 v2_50 §9.17)

Starting-value rationale (long-side per AR-067 Path 2
long-side reconciliation ratified at TB00180 SL §5):
  Long-side RSI window 30-50 selected as direction-
  symmetric mirror of short-side RSI window 50-70.
  Short-side starts at 70/50 (oversold-short above the
  50 mid-line); long-side starts at 30/50 (oversold-
  recovery below the 50 mid-line). The 30/50 window
  captures the long-side oversold-recovery zone (RSI
  lifting off oversold but not yet momentum-confirmed
  bull). Both windows are starting hypotheses subject to
  per-module CIATS evaluation from paper-trading data
  per TB00000 v2_50 §6.8 + §9.16. Net 1:1.5 R:R minimum
  floor (TB00000 v2_50 §9.10 sacred constraint) governs
  all entry sizing regardless of RSI window selection.

10. WHAT DOES THIS COMPONENT DO?
============================================================

(Five coding-readiness questions per TB00000 Section 3.2)

  (1) What does SSS DO? (inputs → outputs)
      Inputs: 5-min candle close price, volume, and
      per-symbol state (rsi_14_avg_gain, rsi_14_avg_loss,
      ema_9, ema_21, volume_ma_20). Parameter Store snapshot
      (rsi_long_low, rsi_long_high, volume_sss_threshold).
      Outputs: sss_pass (bool), signal_params dict.

  (2) What are its interfaces to other components?
      Reads from: per-symbol state dict (WS Manager), ohlc(5)
      stream (WS Manager), Parameter Store snapshot (I-4).
      Writes to: signal_params dict consumed by Signal
      Pipeline Gate 5, logged to Trade Outcome Bus by Logger.

  (3) What are its hard rules?
      HR-SSS-001 through HR-SSS-010 above.

  (4) What triggers it and what does it trigger?
      Triggered by: Gate 4 pass (1H HTF confirmed) within
      the 5-minute pipeline evaluation cycle.
      Triggers: Gate 5 pass → Selection Controller (Gate 6).
                Gate 5 fail → rejection logged, pipeline ends
                for this pair this candle.

  (5) What does it log?
      signal_params dict on every evaluation (pass or fail).
      Logged to Trade Outcome Bus via Logger. Never silent.
      Rejection code on fail: SELECTION_REJECTED__SSS_SIGNAL_FAIL.

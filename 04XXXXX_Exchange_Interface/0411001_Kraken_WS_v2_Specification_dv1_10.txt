3.44 amended EXEC_TYPE HANDLING [NEW dv1_9 AR-057]
------------------------------------------------------------

WS-AMEND-001  ★ NEW dv1_9 CRITICAL (AR-057):
              The complete exec_type list from Kraken
              executions channel WS v2 is:
                pending_new, new, trade, filled,
                iceberg_refill, canceled, expired,
                amended, restated, status
              That is 10 exec_types total.

              The amended exec_type was NOT in the prior
              dispatch table (WM-DISP-023 dv1_9). This
              gap is now closed.

WS-AMEND-002  ★ WHAT amended MEANS:
              "There is a user-initiated amend on the order,
              i.e. limit price change." (Kraken API docs)

              This is DISTINCT from restated:
                amended: user-initiated via amend_order
                restated: engine-initiated (maintenance)

WS-AMEND-003  ★ TOTHBOT V1 BEHAVIOR:
              TothBot V1 does NOT use amend_order for any
              of its own orders. All TothBot orders are
              set-and-forget (entry GTD, TP resting limit,
              emergSL resting stop). TothBot does not
              amend any of them in V1.

              Therefore, any amended exec_type event is:
              (a) Operator manual amend via Kraken web UI
                  (should never happen in production)
              (b) A future bug in TothBot code

              HANDLING:
                if exec_type == "amended":
                    log(UNEXPECTED_ORDER_AMENDED,
                        order_id=msg["order_id"],
                        cl_ord_id=msg.get("cl_ord_id"),
                        new_limit_price=msg.get("limit_price"),
                        new_qty=msg.get("order_qty"),
                        level=CRITICAL)
                    alert(PRIORITY_HIGH,
                        "Unexpected order amendment detected")
                    # If the amended order is a TP or emergSL:
                    # The sacred R:R may have been violated.
                    # Do NOT auto-correct. Alert operator.
                    # Bill must review and decide.

DECISION RATIONALE (WS-AMEND-001 through WS-AMEND-003):
  TB00019 Search 1-2 confirmed from Kraken API docs that
  amended is a valid exec_type that must be in the dispatch
  table per AR-023 ("all 10 exec_type values handled
  explicitly"). TothBot V1 never sends amend_order, so
  any amended event is unexpected. CRITICAL alert protects
  the sacred R:R — if a TP or emergSL was manually amended,
  the trade may no longer satisfy 1:1.5 net R:R.

3.45 EXECUTIONS last_qty AND last_price FIELDS [NEW dv1_9]
------------------------------------------------------------

WS-EXE-020  ★ NEW dv1_9 (AR-061): Kraken added last_qty
            and last_price fields to executions channel
            exec_type=trade events:
              last_qty: quantity executed in THIS specific
                fill (float → Decimal(str()) on receipt)
              last_price: price of THIS specific fill
                (float → Decimal(str()) on receipt)

WS-EXE-021  ★ DISTINCTION FROM CUMULATIVE FIELDS:
            The existing cumulative fields:
              cum_qty: total quantity filled so far (all
                fills up to and including this one)
              avg_price: average price across all fills
            are for Position Mirror and sizing.

            The new fill-level fields:
              last_qty: just this fill's quantity
              last_price: just this fill's price
            are for fill-level logging and analytics.

WS-EXE-022  ★ USAGE:
            On exec_type=trade (partial fill event):
              filled_this_event = Decimal(str(msg["last_qty"]))
              price_this_fill   = Decimal(str(msg["last_price"]))
              cumulative_filled = Decimal(str(msg["cum_qty"]))
              average_price     = Decimal(str(msg["avg_price"]))

            Log both last_qty and last_price for entry fill
            analytics. Feed to CIATS Trade Outcome Bus
            entry fill quality stream (planned — CIATS
            can track slippage on post_only fills by
            comparing last_price to expected entry price).

            Position Mirror and Gate 8 sizing continue
            to use avg_price (authoritative for R:R).

DECISION RATIONALE (WS-EXE-020 through WS-EXE-022):
  TB00019 Search 1 confirmed last_qty and last_price were
  added to the Kraken WS v2 executions channel. Capturing
  fill-level data enables CIATS to analyze entry execution
  quality over time (e.g., whether post_only fills are
  consistently at the requested price or worse). This is
  a free diagnostic at zero cost.

3.46 connection_id FROM STATUS CHANNEL [NEW dv1_9]
------------------------------------------------------------

WS-STAT-005  ★ NEW dv1_9 (AR-064): The Kraken status
             channel provides a connection_id field
             (uint64) on every WS connection. This is
             a unique Kraken-side identifier for the
             WS session.

             Status channel message format:
             {
               "channel": "status",
               "data": [{
                 "api_version": "v2",
                 "connection_id": 13834774380200032777,
                 "system": "online",
                 "version": "2.0.0"
               }],
               "type": "update"
             }

WS-STAT-006  ★ LOGGING REQUIREMENT:
             On every new WS connection, log connection_id
             from the first status channel message.
             Include connection_id in:
               - All connection establishment log entries
               - All reconnect log entries
               - All disconnect log entries
             Format: LOG_WS_CONNECTED(connection_id=...,
                       endpoint="public|private",
                       timestamp=...)

             Usefulness: When contacting Kraken support
             about connectivity issues, providing the
             connection_id enables faster diagnosis.

DECISION RATIONALE (WS-STAT-005 through WS-STAT-006):
  TB00019 Search 6 confirmed from Kraken status channel
  docs that connection_id is available. Zero cost to log.
  Improves debug and support capability.

3.47 TP ORDER PARTIAL FILL HANDLING [NEW dv1_9 AR-066]
------------------------------------------------------------

WS-TP-001  ★ NEW dv1_9 CRITICAL (AR-066):
           TP limit orders can receive partial fills.
           When exec_type=trade arrives for a TP order:
             remaining_qty = TP_order_qty - cum_qty
             The position is only partially closed.
           This requires:
           (a) Position Mirror qty update
           (b) emergSL qty amendment via amend_order

WS-TP-002  ★ WHEN PARTIAL TP FILL OCCURS:
           exec_type == "trade" AND
           order_id matches a known TP order_id in
           Position Mirror.

           Note: Normal post_only entries also fire
           exec_type=trade on partial fills. TothBot
           identifies TP-specific fills by checking
           whether the order_id is the TP order_id
           stored in Position Mirror for that symbol.

WS-TP-003  ★ PARTIAL TP FILL SEQUENCE:
           1. remaining_qty = tp_order_qty - cum_qty
           2. position_mirror[sym]["qty"] = remaining_qty
           3. amend_order the emergSL to remaining_qty:
                {
                  "method": "amend_order",
                  "params": {
                    "order_id": emergsl_order_id,
                    "order_qty": remaining_qty_rounded,
                    "token": token
                  }
                }
              Use Decimal rounding per AR-047.
           4. If remaining_qty < qty_min OR
              remaining_qty * bid < cost_min:
                cancel emergSL (cancel_order)
                market sell remaining_qty immediately
                Clear Position Mirror for symbol
                Log TP_PARTIAL_FILL_BELOW_MIN_EXIT
           5. Log TP_PARTIAL_FILL(symbol, filled=cum_qty,
                remaining=remaining_qty, avg_price=avg_price)

WS-TP-004  ★ WHY amend_order NOT cancel+resubmit:
           cancel_order on emergSL (<5s age): +8 rate
           add_order new emergSL: +1 rate
           Total cancel+resubmit: +9 rate counter

           amend_order on emergSL (resting, age >300s):
           +1 fixed + +1 (>300s bracket) = +2 rate counter
           Total amend: +2 rate counter

           amend_order saves 7 rate counter units per
           partial TP fill. More importantly: amend_order
           preserves queue position (resting emergSL
           keeps its place in the book).

WS-TP-005  ★ FULL TP FILL (exec_type=filled for TP):
           Existing L1b logic applies unchanged:
             cancel emergSL (cancel_order)
             clear Position Mirror for symbol
             record trade in CIATS Trade Outcome Bus
           No qty amendment needed for full fill.

DECISION RATIONALE (WS-TP-001 through WS-TP-005):
  TB00019 Search 2 confirmed from Kraken API docs that
  exec_type=trade fires on any partial fill including
  TP limit orders. Without handling this case, a partial
  TP fill leaves the emergSL at the original full qty —
  if the emergSL fires after a partial TP fill, Kraken
  would attempt to sell the ORIGINAL qty, which exceeds
  the REMAINING position. In spot trading, Kraken would
  either reject the sell (insufficient balance) or sell
  into a position the trader doesn't fully hold. This is
  a loss-exposure event. amend_order is used (not cancel+
  resubmit) to save rate counter and preserve book position.

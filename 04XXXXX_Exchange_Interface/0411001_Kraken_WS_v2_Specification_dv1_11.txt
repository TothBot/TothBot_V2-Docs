KRAKEN WS V2 SPECIFICATION
============================================================

Verified across 3 independent analysis passes (15 sources),
2 deep validation sessions (144+ sources), and 10 sequential
10-search FP/DP validation sessions (TB00006 through TB00019).
Total: 430+ unique sources. All rules in this document are
FP/DP validated unless explicitly noted as starting value.

============================================================
1. PURPOSE AND SCOPE
============================================================

This document is the complete, coding-ready specification
for the Kraken WebSocket v2 interface as used by TothBot V2.
It defines every channel, every message format, every
parameter, every behavioral rule, and every hard constraint
that governs the WS boundary between TothBot and Kraken.

This document is the authoritative wire contract for all
WebSocket communication. The WS Manager coding specification
(1011002) implements this contract. If this document and
1011002 conflict, this document governs.

This document does NOT cover:
  - Kraken REST API endpoints (see 0411002)
  - Fee structure and rate limits detail (see 0411003)
  - WS Manager implementation architecture (see 1011002)

3. CONNECTION ENDPOINTS
============================================================

------------------------------------------------------------
3.1 WebSocket Endpoints
------------------------------------------------------------

WS-EP-001  Public WS v2:
             wss://ws.kraken.com/v2
             Receive-only. No authentication required.
             Channels: instrument, status, ohlc, ticker.

WS-EP-002  Private WS v2:
             wss://ws-l3.kraken.com/v2
             Authenticated. Requires WebSocket token.
             Inbound:  executions, balances.
             Outbound: add_order, amend_order, batch_add,
                       cancel_order, batch_cancel, ping.

WS-EP-003  The old private WS endpoint wss://ws-auth.kraken.com/v2
           is DEPRECATED. The correct private endpoint is
           wss://ws-l3.kraken.com/v2. (PL-009 / GAP-06)

------------------------------------------------------------
3.2 Connection Parameters — All Connections
------------------------------------------------------------

WS-LIB-001  Python library: websockets (asyncio client).
            Import path: from websockets.asyncio.client
            import connect
            This is the correct import path for the
            asyncio-native client. Do NOT use the legacy
            websockets.connect() path.

WS-LIB-002  All WS connect() calls MUST set:
              max_size=10*1024*1024   (10MB)
              open_timeout=10         (10 seconds)
            Rationale: Kraken instrument channel snapshot
            for 500+ pairs can exceed the 1MB default,
            causing PayloadTooBig and silent disconnect.
            (GAP-E / A-18 / AR-029)

WS-LIB-003  All WS connect() calls MUST set:
              max_queue=None          (unlimited)
              ping_interval=None      (disable library ping)
            max_queue=None prevents burst event loss during
            startup snapshots and post-reconnect recovery.
            ping_interval=None disables the library TCP-level
            PING frames. TothBot uses application-level JSON
            ping exclusively (see Section 7.1).
            (AR-058, AR-059)

WS-LIB-004  Complete connect() call template (all four
            connections — public, private, and their
            reconnects):

              conn = await connect(
                  uri,
                  max_size=10 * 1024 * 1024,
                  open_timeout=10,
                  max_queue=None,
                  ping_interval=None,
              )

------------------------------------------------------------
3.3 Authentication
------------------------------------------------------------

WS-AUTH-001  Private WS v2 requires a WebSocket token
             obtained from the REST GetWebSocketsToken
             endpoint before connecting.

WS-AUTH-002  Kraken Spot REST authentication model:
             HMAC-SHA512 of (URI path + SHA256(nonce +
             POST data)) using base64-decoded API secret.
             The October 1, 2025 authentication breaking
             change applied to Kraken FUTURES REST ONLY.
             Kraken Spot REST authentication is UNCHANGED.
             (A-14 / PL-014 RESOLVED)

WS-AUTH-003  WebSocket token is valid for approximately
             15 minutes. A fresh token MUST be acquired
             on every reconnect. The token is passed in
             the subscription message, not in the connect()
             call. (WM-TOKEN-001)

WS-AUTH-004  Two separate API key pairs are required:
               DATA key:  public market data access
               TRADE key: private order management access
             Both keys MUST be IP-whitelisted to the VPS
             IP (87.99.141.44). Update on any VPS migration.
             (AR-037)

------------------------------------------------------------
3.4 Subscription ACK Warning Handling
------------------------------------------------------------

WS-ACK-001  Every subscribe call returns an ACK message
            that may include a warnings[] array.

WS-ACK-002  TothBot MUST parse warnings[] on every
            subscribe ACK. Any non-empty warnings[] MUST
            be logged immediately. Known deprecation
            warnings (timestamp, tick_size) are expected
            and logged at INFO level. Unknown warnings
            are logged at WARN level and alerted.
            (AR-031)

============================================================
4. PUBLIC WS v2 — CHANNELS
============================================================

------------------------------------------------------------
4.1 instrument Channel
------------------------------------------------------------

WS-INST-001  Subscribe at startup with snapshot:true.
             The instrument channel delivers the complete
             per-pair asset specification snapshot on
             subscription, followed by delta updates.

WS-INST-002  From each pair's instrument snapshot or
             update, extract and cache:
               price_increment  (Decimal)
               qty_increment    (Decimal)
               qty_min          (Decimal)
               cost_min         (Decimal)
               status           (string)
             All float values converted to Decimal(str())
             immediately on parse. No float arithmetic
             permitted on financial values.

WS-INST-003  price_increment replaces deprecated tick_size.
             The subscription ACK warns: "tick_size is
             deprecated, use price_increment". Always use
             price_increment. Never reference tick_size.
             (GAP-C / A-17 / AR-028)

WS-INST-004  qty_min and cost_min are MANDATORY Gate 8
             validation inputs. Every add_order MUST verify:
               order_qty >= qty_min
               order_qty * limit_price >= cost_min
             Violation causes immediate Kraken order rejection.
             (GAP-D / A-17 / AR-028)

WS-INST-005  qty_increment is the rounding base for all
             order quantity calculations. All qty values
             MUST be rounded DOWN to the nearest
             qty_increment multiple before order submission.
             Use Decimal quantize with ROUND_DOWN.
             (AR-047)

WS-INST-006  The instrument channel is the sole source for
             the per-pair status cache. WS Manager maintains
             this cache and updates it on every instrument
             channel delta event.

WS-INST-007  Instrument channel subscription example:
               {
                 "method": "subscribe",
                 "params": {
                   "channel": "instrument",
                   "snapshot": true
                 }
               }

WS-INST-008  Complete pair status list (all 8 states):
               online          — normal trading
               post_only       — post-only entries only
               limit_only      — IOC/GTC limit, no market
               reduce_only     — reduce positions only
               cancel_only     — cancel only, no new orders
               work_in_progress — transitioning (unstable)
               maintenance     — engine maintenance
               delisted        — pair removed

WS-INST-009  NO-ENTRY statuses — block all new entry orders:
               cancel_only, work_in_progress, delisted,
               limit_only, reduce_only, maintenance
             Only online and post_only pairs are eligible
             for new entry. (AR-039)

WS-INST-010  post_only pair with no open position:
             TothBot limit+post_only entries are valid on
             post_only pairs. Entry proceeds normally.
             (A-2 — Kraken post_only engine state context)

WS-INST-011  post_only pair with open position:
             Pair entered post_only state while position
             is open. Existing resting TP and emergSL
             remain active on the matching engine.
             WS Manager triggers Exit Controller pair
             status adaptation (WS-EXIT-003).

------------------------------------------------------------
4.2 status Channel
------------------------------------------------------------

WS-STAT-001  Subscribe at startup with snapshot:true.
             The status channel delivers the Kraken global
             engine state and system status.

WS-STAT-002  Four global engine states:
               online       — All orders. Normal operation.
               post_only    — limit+post_only entries valid.
               cancel_only  — No new orders. Cancel only.
               maintenance  — No orders or cancels.
             TothBot reacts immediately on state change.

WS-STAT-003  Status channel subscription example:
               {
                 "method": "subscribe",
                 "params": {
                   "channel": "status",
                   "snapshot": true
                 }
               }

WS-STAT-004  Scheduled maintenance detection:
             At startup, TothBot calls the Kraken Status
             REST API (0411002 Section 5) in addition to
             status channel subscription. The status channel
             provides real-time state. The REST endpoint
             provides advance warning of scheduled
             maintenance. (AR-038)

WS-STAT-005  connection_id field: The status channel
             message includes a connection_id field
             identifying this specific WS connection.

WS-STAT-006  MANDATORY: Log connection_id on every new WS
             connection establishment. Log format:
               WS_CONNECTED(uri=..., connection_id=...)
             connection_id enables Kraken support diagnosis
             when investigating connectivity issues.
             (AR-064)

------------------------------------------------------------
4.3 ohlc Channel
------------------------------------------------------------

WS-OHLC-001  Two ohlc subscriptions maintained:
               interval=5    — 5-minute candles (SYSTEM CLOCK)
               interval=60   — 1-hour candles (HTF Gate 4)
             Both subscribed at startup for all monitored
             pairs. (A-16 FLAG 1)

WS-OHLC-002  interval_begin is the canonical candle start
             time field. The timestamp field is DEPRECATED.
             The subscription ACK warns: "timestamp is
             deprecated, use interval_begin". Parse only
             interval_begin. Never reference timestamp.
             (GAP-B / A-16 / AR-027)

WS-OHLC-003  interval_begin format: RFC3339 nanosecond
             string. Parse to datetime with timezone.

WS-OHLC-004  Candle-close detection rule:
             A new candle has closed when a new ohlc(5m)
             event arrives with a DIFFERENT interval_begin
             than the previous event. The previous
             interval_begin's candle is now committed.
             (WS-OHLC-001 carry forward)

WS-OHLC-005  On candle-close: the PREVIOUS candle's OHLC
             data (the one just committed) is used for
             all signal computations. The new candle
             (current interval_begin) is in progress and
             NOT used for any calculation.

WS-OHLC-006  ohlc subscription example (5-minute):
               {
                 "method": "subscribe",
                 "params": {
                   "channel": "ohlc",
                   "interval": 5,
                   "snapshot": true,
                   "symbol": ["BTC/USD", "ETH/USD", ...]
                 }
               }

------------------------------------------------------------
4.4 ticker Channel
------------------------------------------------------------

WS-TKR-001  Ticker provides real-time price data.
            ticker is NOT subscribed at startup.
            Ticker subscriptions are managed per-pair
            based on Position Mirror state. (AR-034)

WS-TKR-002  event_trigger modes:
               bbo    — pairs WITH open positions
               trades — pairs WITHOUT open positions
            bbo provides faster adverse price detection.
            For longs, bid price = realizable exit price.
            event_trigger:trades provides sufficient data
            for Gate 2 (24h volume) on non-position pairs.

WS-TKR-003  WS Manager switches event_trigger per pair
            when position state changes:
              Position opened → switch to bbo
              Position closed → switch to trades

WS-TKR-004  Ticker subscription example (with open pos):
               {
                 "method": "subscribe",
                 "params": {
                   "channel": "ticker",
                   "symbol": ["BTC/USD"],
                   "event_trigger": "bbo",
                   "snapshot": true
                 }
               }

============================================================
5. PRIVATE WS v2 — INBOUND CHANNELS
============================================================

------------------------------------------------------------
5.1 executions Channel
------------------------------------------------------------

WS-EXE-001  executions subscription MANDATORY parameters:
               token:        (WebSocket auth token)
               snap_orders:  true
               snap_trades:  true
               order_status: true    ← MANDATORY (see below)
               ratecounter:  true

WS-OSTA-001  order_status:true is MANDATORY. Without this
             flag, Kraken only delivers exec_types:
               new, filled, canceled, expired
             The exec_types amended and restated are
             SILENTLY DROPPED. (GAP-A / A-15 / AR-026)

WS-OSTA-002  Consequence of omitting order_status:true:
             (a) The restated exec_type on resting
                 crash-protection orders (emergSL, TP)
                 never arrives — Layer 3 crash protection
                 monitoring is completely non-functional.
             (b) The dispatch table handles 10 exec_types
                 but only receives 4.
             This is a CRITICAL architectural failure mode.

WS-OSTA-003  order_status:true MUST be present on EVERY
             executions subscription, including reconnects.
             It is NOT optional or configurable.

WS-EXE-002  snap_orders:true and snap_trades:true are the
            current parameters. The legacy parameters
            snapshot and snapshot_trades are DEPRECATED.
            Never use snapshot or snapshot_trades.
            (GAP-09)

WS-EXE-003  ratecounter:true provides real-time rate
            counter per pair at zero additional connection
            cost. The rate counter value from executions
            is the operative monitoring signal for CIATS
            EWMA Monitor. (A-1)

WS-EXE-004  executions subscription example:
               {
                 "method": "subscribe",
                 "params": {
                   "channel": "executions",
                   "token": token,
                   "snap_orders": true,
                   "snap_trades": true,
                   "order_status": true,
                   "ratecounter": true
                 }
               }

WS-EXE-005  maxratecount from executions ACK:
            The subscription ACK returns maxratecount —
            the ACTUAL operative rate counter ceiling for
            this user tier. TothBot MUST extract this
            value and use it as the rate counter threshold.
            Do NOT hardcode 125. (A-19 / IMP-11 / AR-030)

WS-EXE-006  req_id: All outbound WS messages MUST carry
            req_id (client-specified integer). WS Manager
            maintains a pending-request registry keyed by
            req_id. All responses are matched to requests.
            (A-2)

WS-EXE-007  cl_ord_id: All add_order and batch_add MUST
            carry cl_ord_id (max 18 characters). TothBot
            assigns cl_ord_id at dispatch time BEFORE
            Kraken response. Position Mirror records
            cl_ord_id immediately at dispatch — no async
            gap between dispatch and recording. (A-2)

WS-EXE-008  time_in and time_out: All WS v2 responses
            include these fields to nanosecond precision.
            Logger records both. CIATS EWMA Monitor adds
            ws_roundtrip_latency_ms as a monitoring signal.
            (A-3)

WS-EXE-009  Complete exec_type dispatch table (all 10):
               pending_new   — order accepted by engine
               new           — order confirmed active
               trade         — partial fill event
               filled        — order fully filled
               iceberg_refill — iceberg order refill
               canceled      — order canceled
               expired       — GTD order expired
               amended       — user-initiated price change
               restated      — engine-initiated maintenance
               status        — status-only update
            ALL 10 must be handled explicitly. Unknown
            exec_types are logged at WARN, never silently
            dropped. (AR-023)

WS-EXE-010  reason field: Use reason for cancellation
            context. cancel_reason is DEPRECATED and
            returns None silently. Never reference
            cancel_reason. (AR-022)

------------------------------------------------------------
5.1.1 exec_type: trade — Partial Fill Events
------------------------------------------------------------

WS-EXE-011  exec_type=trade fires on every partial fill
            (entry order or TP order). It does NOT mean
            the order is fully filled.

WS-EXE-012  Fill fields on exec_type=trade:
              cum_qty    — total qty filled across all fills
              avg_price  — average fill price (authoritative)
              last_qty   — qty filled in THIS fill only
              last_price — price of THIS fill only
            cum_qty and avg_price are used by Position
            Mirror and R:R calculations. last_qty and
            last_price are used for fill-level analytics.
            (AR-061 / WS-EXE-020 through -022)

WS-EXE-013  On entry exec_type=trade:
              filled_this_event = Decimal(str(last_qty))
              price_this_fill   = Decimal(str(last_price))
              cumulative_filled = Decimal(str(cum_qty))
              average_price     = Decimal(str(avg_price))
            Log last_qty and last_price for CIATS entry
            fill quality stream (slippage monitoring on
            post_only fills vs. expected entry price).

------------------------------------------------------------
5.1.2 exec_type: amended — Unexpected Amendment
------------------------------------------------------------

WS-AMEND-001  The complete exec_type list includes amended.
              amended = user-initiated price change via
              amend_order (e.g., Kraken web UI manual amend).
              This is DISTINCT from restated (engine-
              initiated maintenance amend). (AR-057)

WS-AMEND-002  TothBot V1 does NOT use amend_order on any
              of its own orders. All TothBot orders are
              set-and-forget: entry GTD, TP resting limit,
              emergSL resting stop. TothBot does not amend
              any of them.

WS-AMEND-003  Therefore ANY amended exec_type event is:
                (a) Manual operator amend via Kraken web UI
                    (must never happen in production)
                (b) A future code bug

              MANDATORY handling on amended exec_type:
                log(UNEXPECTED_ORDER_AMENDED,
                    order_id=msg["order_id"],
                    cl_ord_id=msg.get("cl_ord_id"),
                    new_limit_price=msg.get("limit_price"),
                    new_qty=msg.get("order_qty"),
                    level=CRITICAL)
                alert(PRIORITY_HIGH,
                    "Unexpected order amendment detected")
              If the amended order is a TP or emergSL,
              the sacred 1:1.5 R:R may have been violated.
              Do NOT auto-correct. Alert operator. Bill
              must review and decide.

------------------------------------------------------------
5.1.3 exec_type: restated — Engine Maintenance Amend
------------------------------------------------------------

WS-EXE-014  restated = engine-initiated maintenance amend.
            Kraken modifies a resting order's internal
            representation during maintenance. NOT a fill.
            NOT a user action.

WS-EXE-015  restated MUST NOT trigger Position Mirror
            update. It is not a position-changing event.

WS-EXE-016  If restated arrives for a resting TP or
            emergSL order: log at WARN level and queue a
            reconciliation check on the next pipeline cycle.
            An engine amend on crash-protection orders
            must be visible and verified. (AR-024)

------------------------------------------------------------
5.1.4 exec_type: status — Rate Counter Update
------------------------------------------------------------

WS-EXE-017  exec_type=status carries the rate counter
            update for a pair. This is the real-time
            rate monitoring signal. Extract and update
            the rate counter per pair on every status
            event.

------------------------------------------------------------
5.1.5 Sequence Gap Detection
------------------------------------------------------------

WS-EXE-018  Every executions channel message carries a
            sequence integer. WS Manager tracks the
            last-seen sequence number per connection.

WS-EXE-019  On sequence gap (jump > 1):
              Alert immediately: EXECUTIONS_SEQUENCE_GAP
              Trigger REST GetOpenOrders reconciliation.
            Missed execution events cause Position Mirror
            desync — direct loss risk. (A-10 / AR-021)

------------------------------------------------------------
5.2 balances Channel
------------------------------------------------------------

WS-BAL-001  balances channel delivers real-time balance
            updates on every settlement event. Subscribe
            with snapshot:true at startup.

WS-BAL-002  MANDATORY: Use wallets[type=spot][id=main]
            ONLY. Filter out any non-spot, non-main wallet
            entries. Futures and staking balances must
            NEVER be included in TothBot portfolio
            calculations. (AR-050)

WS-BAL-003  Balances parsing:
              Snapshot: contains full wallet state at
                subscription time.
              Update: contains the changed balance
                entries only (delta, not full snapshot).
            Both must be handled. On update, merge delta
            into the cached spot/main balance.

WS-BAL-004  Every balances channel message carries a
            sequence integer. Track last-seen sequence.

WS-BAL-005  On balances sequence gap (jump > 1):
              Alert immediately: BALANCES_SEQUENCE_GAP
              Trigger REST GetAccountBalance reconciliation.
            Missed balance events cause incorrect available
            capital calculation — direct loss risk.
            (A-9 / AR-009)

WS-BAL-006  balances subscription example:
               {
                 "method": "subscribe",
                 "params": {
                   "channel": "balances",
                   "token": token,
                   "snapshot": true
                 }
               }

============================================================
6. PRIVATE WS v2 — OUTBOUND MESSAGES
============================================================

------------------------------------------------------------
6.1 Common Fields — All Outbound Messages
------------------------------------------------------------

WS-OUT-001  ALL outbound WS v2 messages MUST include:
              req_id: (integer, client-assigned, unique
                       per session)

WS-OUT-002  req_id must be tracked in the Pending Order
            Registry. All inbound responses are matched
            to their originating req_id.

------------------------------------------------------------
6.2 Self-Trade Prevention
------------------------------------------------------------

WS-STP-001  stp_type MUST be set on all add_order and
            batch_add messages. TothBot standard:
              stp_type: "cancel_newest"

WS-STP-002  CRITICAL FORMAT: WS v2 uses UNDERSCORE format.
              WS v2 correct:  cancel_newest
              REST (wrong for WS): cancel-newest
            These are different protocols with different
            formats. Using the hyphen format in WS v2
            causes order rejection or silent failure.
            (AR-032 / A-20 / GAP-B)

WS-STP-003  Never use cancel-newest, cancel-oldest, or
            cancel-both (hyphen format) in any WS v2
            message. The underscore format is mandatory:
            cancel_newest, cancel_oldest, cancel_both.

------------------------------------------------------------
6.3 deadline Parameter
------------------------------------------------------------

WS-DL-001  deadline MUST be set on all add_order and
           batch_add messages. Standard value:
             deadline = UTC_now + 5 seconds (ISO 8601)
           (AR-033 / A-21)

WS-DL-002  deadline range: 500ms to 60 seconds from
           current time. TothBot uses 5 seconds.

WS-DL-003  Kraken rejects any order whose deadline has
           passed by the time the message is processed.
           This prevents stale entry placement due to
           network delay or event loop pause.

WS-DL-004  deadline applies to batch_add. A delayed
           batch_add with stale TP/emergSL prices from
           fill-price slippage is prevented by deadline.

------------------------------------------------------------
6.4 add_order
------------------------------------------------------------

WS-ADD-001  add_order is used for entry limit orders only.
            Standard TothBot entry order template:
              {
                "method": "add_order",
                "params": {
                  "order_type": "limit",
                  "side": "buy",
                  "symbol": symbol,
                  "limit_price": price_str,
                  "order_qty": qty_str,
                  "post_only": true,
                  "time_in_force": "gtd",
                  "expire_time": expire_iso8601,
                  "cl_ord_id": cl_ord_id_str,
                  "stp_type": "cancel_newest",
                  "deadline": deadline_iso8601,
                  "token": token,
                  "req_id": req_id
                }
              }

WS-ADD-002  Entry GTD expire_time: 30 to 60 seconds from
            order submission time. Starting value: 30s.
            CIATS-owned parameter.

WS-ADD-003  limit_price = last closed candle close price
            quantized DOWN to price_increment.
            (OI-004 CLOSED / AR-069)

WS-ADD-004  order_qty MUST pass Gate 8 validation:
              qty >= qty_min
              qty * limit_price >= cost_min
            Quantities are rounded DOWN to qty_increment.

WS-ADD-005  post_only:true on all entry orders. TothBot
            is a maker-only entry strategy. Taker fills
            on entry violate the fee structure baseline.

------------------------------------------------------------
6.5 amend_order
------------------------------------------------------------

WS-AMD-001  amend_order is the SOLE amendment method.
            edit_order is DEPRECATED and PROHIBITED.
            edit_order costs 43% more than amend_order
            for orders resting < 5 seconds (+7 vs +4).
            (PL-005 / GAP-04)

WS-AMD-002  amend_order preserves queue position on the
            Kraken order book. cancel+resubmit does not.

WS-AMD-003  amend_order template (qty amendment):
              {
                "method": "amend_order",
                "params": {
                  "order_id": order_id_str,
                  "order_qty": new_qty_str,
                  "token": token,
                  "req_id": req_id
                }
              }

WS-AMD-004  amend_order rate cost:
              +1 fixed always
              +3 additional if order age < 5 seconds
              +2 additional if order age < 10 seconds
              +1 additional if order age < 15 seconds
            For resting orders (age > 300s): +2 total.

WS-AMD-005  Primary use of amend_order in TothBot V1:
            TP partial fill emergSL qty amendment
            (see Section 6.7 and WS-TP-003).
            TothBot V1 does NOT use amend_order for
            price changes on its own active orders.

------------------------------------------------------------
6.6 batch_add
------------------------------------------------------------

WS-BA-001   batch_add places TP limit order and emergSL
            stop order atomically on fill confirmation.
            Fired immediately on exec_type=filled for
            entry order. (OTO evaluated and rejected
            AR-008 — uses limit price not fill price,
            violates R:R.)

WS-BA-002   batch_add standard template on entry fill:
              {
                "method": "batch_add",
                "params": {
                  "orders": [
                    {
                      "order_type": "limit",
                      "side": "sell",
                      "symbol": symbol,
                      "limit_price": tp_price_str,
                      "order_qty": fill_qty_str,
                      "cl_ord_id": tp_cl_ord_id,
                      "stp_type": "cancel_newest",
                      "deadline": deadline_iso8601
                    },
                    {
                      "order_type": "stop-loss",
                      "side": "sell",
                      "symbol": symbol,
                      "limit_price": emerg_sl_price_str,
                      "order_qty": fill_qty_str,
                      "cl_ord_id": emerg_sl_cl_ord_id,
                      "triggers": {
                        "reference": "last",
                        "price": emerg_sl_trigger_str
                      },
                      "stp_type": "cancel_newest",
                      "deadline": deadline_iso8601
                    }
                  ],
                  "token": token,
                  "req_id": req_id
                }
              }

WS-BA-003   emergSL triggers.reference MUST be "last".
            "last" = last traded price. This is the
            correct reference for a momentum stop.
            Using "index" or "mark" is incorrect for
            spot trading. (WS-EMSL-001)

WS-BA-004   batch_add rate cost: +(n/2) rounded up.
            Two orders (TP + emergSL) = +1 rate cost.

WS-BA-005   deadline applies to batch_add. Use UTC_now
            + 5 seconds, same as add_order.

------------------------------------------------------------
6.7 TP Partial Fill — emergSL Amendment
------------------------------------------------------------

WS-TP-001   TP limit orders can receive partial fills.
            When exec_type=trade arrives for a TP order
            (identified by matching order_id to the TP
            order_id stored in Position Mirror):
              remaining_qty = tp_order_qty - cum_qty
            The position is only partially closed.

WS-TP-002   Identification: exec_type=trade is also fired
            for entry partial fills. Distinguish TP fills
            by checking whether order_id matches the TP
            order_id stored in Position Mirror for that
            symbol.

WS-TP-003   Partial TP fill sequence:
              1. remaining_qty = tp_order_qty - cum_qty
              2. position_mirror[sym]["qty"] = remaining_qty
              3. amend_order the emergSL to remaining_qty:
                   order_qty = remaining_qty (rounded per
                   AR-047 Decimal rounding)
              4. If remaining_qty < qty_min OR
                 remaining_qty * bid < cost_min:
                   cancel emergSL (cancel_order)
                   market sell remaining_qty immediately
                   Clear Position Mirror for symbol
                   Log TP_PARTIAL_FILL_BELOW_MIN_EXIT
              5. Log TP_PARTIAL_FILL(symbol,
                   filled=cum_qty, remaining=remaining_qty,
                   avg_price=avg_price)

WS-TP-004   WHY amend_order NOT cancel+resubmit:
              cancel_order (resting order, age > 300s): +1
              add_order new emergSL: +1
              Total cancel+resubmit: +2 rate counter
              (but loses queue position)

              amend_order (resting, age > 300s):
              +1 fixed + +1 (>300s bracket) = +2 rate counter
              AND preserves queue position.

              In practice the emergSL is a resting order.
              amend_order is preferred because it preserves
              book position. This is critical during high-
              volatility partial fills when rate limits may
              already be under pressure.

WS-TP-005   Full TP fill (exec_type=filled for TP):
            Existing L1b logic applies:
              cancel emergSL (cancel_order)
              clear Position Mirror for symbol
              record trade in CIATS Trade Outcome Bus
            No qty amendment needed for full fill.

------------------------------------------------------------
6.8 cancel_order
------------------------------------------------------------

WS-CAN-001  cancel_order sends a single cancel request and
            returns a stream of individual responses per
            order. Each response is matched by req_id.
            Use for Layer 2 MAE exit cancel sequence.
            (AR-041)

WS-CAN-002  cancel_order template:
              {
                "method": "cancel_order",
                "params": {
                  "order_id": [order_id_str],
                  "token": token,
                  "req_id": req_id
                }
              }

WS-CAN-003  NEVER use batch_cancel for MAE Layer 2 exit.
            MAE exit requires per-order ACK tracking for
            the cancel timeout fallback (I-6). Only
            cancel_order provides per-order responses.
            (WS-CAN-002 carry forward)

WS-CAN-004  cancel_order rate cost:
              +8 if order age < 5 seconds
              +6 if order age < 10 seconds
              +1 if order age < 300 seconds

------------------------------------------------------------
6.9 batch_cancel
------------------------------------------------------------

WS-CAN-005  batch_cancel cancels multiple orders in a
            single WS message. Returns a single count
            response (number of orders canceled).

WS-CAN-006  batch_cancel bypasses the rate counter maximum.
            Use for Full Halt scenario where all open entry
            orders must be canceled immediately regardless
            of rate counter state. (GAP-05)

WS-CAN-007  batch_cancel template:
              {
                "method": "batch_cancel",
                "params": {
                  "orders": [order_id_1, order_id_2, ...],
                  "token": token,
                  "req_id": req_id
                }
              }

WS-CAN-008  batch_cancel rate cost: cumulative sum of
            individual cancel costs per order in the batch.

WS-CAN-009  cancel_order vs batch_cancel — use cases:
              cancel_order:  MAE exit (per-order ACK needed)
              batch_cancel:  Full Halt (count sufficient,
                             rate bypass required)
            These are NOT interchangeable. (AR-041)

WS-DMS-001  cancel_all_orders_after (Dead Man's Switch)
            is PROHIBITED. It cancels ALL resting orders
            on WS disconnect, including TP and emergSL
            crash protection orders. This destroys Layer
            3 crash protection. If this method is ever
            called by TothBot code, it is a CRITICAL bug.
            Log CRITICAL + alert PRIORITY_HIGH. (AR-001)

7. CONNECTION MANAGEMENT
============================================================

------------------------------------------------------------
7.1 Keepalive — JSON Ping
------------------------------------------------------------

WS-PING-001  WS Manager MUST send application-level JSON
             ping on each active connection every 30
             seconds:
               {"method": "ping"}

WS-PING-002  Expected response:
               {"method": "pong"}
             No pong within 10 seconds = dead connection.
             Reconnect immediately. (A-7)

WS-PING-003  The ping interval (30 seconds) clears all
             known proxy and CDN idle timeouts:
               Kraken WS disconnect: ~60 seconds idle
               Cloudflare CDN idle: ~100 seconds
             30-second interval provides 2x safety margin.

WS-PING-004  Heartbeat ping events (pong responses) do
             NOT reset the zombie detection timer. Only
             real market data events reset it.

------------------------------------------------------------
7.2 Zombie Connection Detection
------------------------------------------------------------

WS-ZOM-001  A WS connection can appear alive (ping/pong
            passing) while delivering no real market data.
            This occurs when the upstream stops sending
            events without closing the TCP connection.

WS-ZOM-002  WS Manager MUST track last_real_data_time per
            connection using time.monotonic(). Any real
            market data event resets the timestamp. Pong
            responses and heartbeats do NOT reset it.

WS-ZOM-003  Zombie detection threshold: 90 seconds.
            If time.monotonic() - last_real_data_time
            > 90 seconds: zombie detected.
            Action: Log ZOMBIE_CONNECTION_DETECTED,
            alert operator, trigger reconnect. (A-8)

WS-ZOM-004  Real data events (reset zombie timer):
              instrument channel messages
              status channel messages
              ohlc channel messages
              ticker channel messages
              executions channel messages
              balances channel messages

WS-ZOM-005  Non-resetting events (do NOT reset timer):
              pong responses
              subscription ACK messages
              heartbeat-only messages

------------------------------------------------------------
7.3 Reconnection
------------------------------------------------------------

WS-REC-001  Two reconnect scenarios, distinct behaviors:

WS-REC-002  Scenario A — Random disconnect:
            Reconnect immediately. Up to 5 attempts with
            no artificial delay. After 5 failures, apply
            exponential backoff starting at 1 second.

WS-REC-003  Scenario B — After confirmed trading engine
            maintenance: minimum 5-second delay before
            reconnect attempt. (A-5)

WS-REC-004  On every reconnect:
              Acquire fresh WebSocket token (GetWebSocketsToken)
              Reconnect with full connection parameters
                (max_size, open_timeout, max_queue,
                 ping_interval — per WS-LIB-002 through -004)
              Re-subscribe all channels with same parameters
              Extract maxratecount from executions ACK
              Resume zombie detection and ping tasks
              Restore Position Mirror from snap_orders
              Restore per-pair ticker subscriptions

WS-REC-005  Subscription ACK warnings[] MUST be parsed
            and logged on reconnect subscriptions the
            same as initial subscriptions. (WS-ACK-002)

8. RATE LIMITS
============================================================

WS-RL-001   Rate limits are shared across REST, WebSocket,
            and FIX. There is no per-protocol budget.
            All rate costs count against one shared counter
            per pair. (Intermediate Tier C-2)

WS-RL-002   Rate counter parameters (Intermediate Tier):
              Threshold:   maxratecount from executions ACK
                           (do NOT hardcode 125 — AR-030)
              Decay rate:  2.34 per second
              Max orders:  80 open per pair

WS-RL-003   MANDATORY: Extract maxratecount from the
            executions subscription ACK on every connect
            and reconnect. Use this value as the operative
            rate counter ceiling for all monitoring.
            (A-19 / IMP-11 / AR-030)

WS-RL-004   Rate cost schedule (carried from 0400000
            Section 5 — reference only here):
              add_order:      +1
              amend_order:    +2 to +4 depending on age
              batch_add:      +(n/2) rounded up
              cancel_order:   +1 to +8 depending on age
              batch_cancel:   cumulative per order
              edit_order:     PROHIBITED

9. EXIT CONTROLLER — PAIR STATUS ADAPTATION
============================================================

WS-EXIT-001  When a pair's instrument status changes while
             TothBot holds an open position in that pair,
             the Exit Controller must adapt. Status changes
             received via instrument channel.

WS-EXIT-002  WS Manager monitors the instrument channel
             for status changes on all pairs with open
             positions. Status change event for an open
             position pair is routed immediately to the
             Exit Controller.

WS-EXIT-003  Exit strategy by new pair status:
               limit_only:
                 IOC limit sell at best_bid (NOT market
                 sell). Limit orders still valid.
               post_only:
                 Existing position manageable. TP and
                 emergSL resting orders remain active.
                 No new entries.
               cancel_only:
                 HOLD. No new orders possible. Existing
                 resting TP and emergSL provide only
                 protection. Log CRITICAL + alert operator.
               maintenance:
                 HOLD. Same as cancel_only response.
                 Log CRITICAL + alert operator.
               reduce_only:
                 Exit only. TP sell orders may remain
                 valid. emergSL sell remains valid.
                 No new entries permitted.
               work_in_progress:
                 HOLD. Treat as unstable state.
                 Monitor for resolution.
               delisted:
                 CRITICAL alert. Manual intervention
                 required. Attempt market sell if possible.
               (AR-039, AR-040)

WS-EXIT-004  IOC limit exit for limit_only pairs:
             Submit sell as IOC limit at best_bid price.
             This preserves maker pricing where possible
             while ensuring execution in limit_only mode.

WS-EXIT-005  HOLD procedure for cancel_only/maintenance:
             Do not attempt new orders. Existing resting
             TP and emergSL on the matching engine provide
             the only active protection. Log CRITICAL.
             Alert operator. Monitor status channel for
             state change back to online/post_only.
             This validates the resting emergSL architecture
             as correct design for pair-level disruption.

10. FIVE CODING-READINESS QUESTIONS
============================================================

(1) WHAT DOES THIS COMPONENT DO?
    Specifies the complete wire contract between TothBot
    and Kraken WebSocket v2. Defines every channel, message,
    parameter, and behavioral rule that governs all WS
    communication. Is the authoritative input to WS Manager
    (1011002) implementation.

(2) INTERFACES:
    Inputs consumed by WS Manager from Kraken WS:
      Public WS: instrument, status, ohlc(5m), ohlc(60),
                 ticker
      Private WS inbound: executions, balances
    Outputs sent by WS Manager to Kraken WS:
      add_order, amend_order, batch_add, cancel_order,
      batch_cancel, ping
    Kraken matching engine:
      Resting TP limit orders and emergSL stop orders
      placed via batch_add — survive independently of
      TothBot state

(3) HARD RULES:
    All HR-EI-001 through HR-EI-015 from 0400000 apply.
    Document-specific mandatory rules:
      WS-EP-003:    Private endpoint is ws-l3.kraken.com/v2
      WS-LIB-002:   max_size=10MB, open_timeout=10
      WS-LIB-003:   max_queue=None, ping_interval=None
      WS-OSTA-001:  order_status:true MANDATORY (silent
                    drop of amended/restated if omitted)
      WS-EXE-002:   snap_orders, snap_trades (NOT snapshot)
      WS-INST-003:  price_increment (NOT tick_size)
      WS-OHLC-002:  interval_begin (NOT timestamp)
      WS-STP-002:   stp_type underscore format (WS v2)
      WS-DL-001:    deadline on all add_order/batch_add
      WS-BA-003:    emergSL triggers.reference="last"
      WS-CAN-003:   NEVER batch_cancel for MAE exit
      WS-DMS-001:   cancel_all_orders_after PROHIBITED
      WS-AMEND-003: Any amended event = CRITICAL alert
      WS-ZOM-003:   Zombie threshold 90 seconds

(4) TRIGGERS AND TRIGGER CHAIN:
    Triggered by: WS Manager at startup and on every
    inbound Kraken WS event.
    Triggers: ohlc(5m) candle-close → signal pipeline;
    executions fills → batch_add (TP+emergSL), Position
    Mirror update, CIATS Trade Outcome Bus; executions
    expires → Position Mirror cleanup; balances events
    → portfolio balance update; instrument events →
    pair status cache update, Exit Controller if open
    position; status events → engine state update;
    sequence gaps → REST reconciliation triggers.

(5) WHAT DOES IT LOG?
    Every new WS connection (uri + connection_id)
    All subscription ACK warnings[]
    All sequence gaps (executions and balances)
    All zombie detections
    All reconnect events (scenario A vs B)
    All instrument channel status changes for open pairs
    All emergSL events (placement, amendment, cancellation)
    All TP partial fill events (filled qty, remaining qty)
    All amended exec_type events (CRITICAL level)
    All restated exec_type events for resting orders (WARN)
    All cancel_order submissions and ACKs (req_id tracked)
    All batch_cancel executions (Full Halt)
    Any DMS call detection (CRITICAL — prohibited)
    Rate counter readings (per pair, per event)
    Latency: time_in, time_out from all WS responses
    Fill analytics: last_qty, last_price on all trade events
    HOLD alerts for cancel_only/maintenance pair states

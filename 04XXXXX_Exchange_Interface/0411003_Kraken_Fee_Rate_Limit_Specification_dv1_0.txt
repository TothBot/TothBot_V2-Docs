KRAKEN FEE RATE LIMIT SPECIFICATION
============================================================

All content derived from FP/DP validated sources (430+
unique sources across 10 validation sessions, TB00006
through TB00019). All values are CIATS-owned starting
values unless explicitly marked HARDCODED or CONFIRMED.

============================================================
1. PURPOSE AND SCOPE
============================================================

This document specifies the complete Kraken fee structure,
API rate limit rules, API key configuration requirements,
and CIATS monitoring hooks for fee and rate actuals as
used by TothBot V2.

This document does NOT cover:
  - WS v2 message formats and channels (see 0411001)
  - REST endpoint specifications (see 0411002)
  - Position sizing logic (see 0611001)
  - CIATS statistical engine (see 0211001)

3. FEE STRUCTURE
============================================================

------------------------------------------------------------
3.1 Kraken Fee Tier — Confirmed
------------------------------------------------------------

FEE-TIER-001  TothBot V2 operates on Kraken Pro
              Intermediate tier (C-2). Confirmed.
              (AR-013)

FEE-TIER-002  Kraken Pro uses a maker/taker fee model.
              Fee tier is determined by 30-day trading
              volume in USD.

------------------------------------------------------------
3.2 Fee Baseline — Starting Values
------------------------------------------------------------

FEE-BASE-001  Fee baseline (Intermediate tier, starting):
                Maker fee: 0.16%
                Taker fee: 0.26%
              These are CIATS-monitored starting values.
              CIATS compares actual fees from the Logger
              trade records against this baseline and
              detects tier changes automatically.
              (AR-012)

FEE-BASE-002  Round-trip fee baseline:
                Entry (maker) + TP exit (maker) = 0.32%
                Entry (maker) + emergSL exit (taker) = 0.42%
              The 0.42% figure (worst case) is used in
              Kelly formula net P/L calculations to ensure
              conservative position sizing. (AR-065)

FEE-BASE-003  TothBot entry order classification:
                Entry add_order: post_only = TRUE
                → Entry fills are ALWAYS maker fills
                → Entry fee = 0.16% (maker)

FEE-BASE-004  TothBot exit order classification:
                TP limit order (resting): maker fill
                → TP exit fee = 0.16% (maker)
                emergSL stop order: taker fill
                → emergSL exit fee = 0.26% (taker)

FEE-BASE-005  Fee impact on net R:R:
              At 1:1.5 gross R:R with round-trip fees:
                Gross R:R target: 1.50x
                Entry fee: -0.16% of position
                TP exit fee: -0.16% of (position × 1.5)
                Net R:R ≈ 1.46x after fees on TP exit
                Net R:R ≈ 1.42x after fees on emergSL exit
              Kelly formula MUST use net P/L (fees
              included), not gross price change. (AR-065)

FEE-BASE-006  Fee tier advancement:
              As 30-day volume grows, Kraken may advance
              TothBot to a lower fee tier. CIATS fee
              monitoring detects this automatically via
              the actual fee fields in Logger trade records.
              When detected: CIATS updates the fee baseline
              parameter and recalculates affected metrics.

------------------------------------------------------------
3.3 Fee Calculation
------------------------------------------------------------

FEE-CALC-001  Fee amount per trade (entry):
                fee_entry = fill_qty * avg_price * 0.0016
              All values in Decimal. All arithmetic in
              Decimal. No float fee calculations.

FEE-CALC-002  Fee amount per trade (TP exit):
                fee_tp = fill_qty * tp_price * 0.0016

FEE-CALC-003  Fee amount per trade (emergSL exit):
                fee_emsl = fill_qty * sl_price * 0.0026

FEE-CALC-004  Net P/L per closed trade (TP exit):
                net_pnl = (tp_price - entry_price) * qty
                          - fee_entry - fee_tp

FEE-CALC-005  Net P/L per closed trade (emergSL exit):
                net_pnl = (sl_fill_price - entry_price) * qty
                          - fee_entry - fee_emsl
              Note: sl_fill_price is the actual execution
              price from the emergSL stop order fill, not
              the stop trigger price.

FEE-CALC-006  The Logger records actual fees from Kraken
              execution events (the fee field in executions
              channel trade events). These actual fees are
              the authoritative inputs to all CIATS
              calculations. Calculated fees (FEE-CALC-001
              through -005) are used only for pre-trade
              R:R estimation and Gate 8 validation.

4. API RATE LIMITS
============================================================

------------------------------------------------------------
4.1 Rate Limit Architecture
------------------------------------------------------------

RL-ARCH-001   Rate limits are shared across REST,
              WebSocket v2, and FIX API. There is no
              per-protocol rate budget. All calls across
              all protocols count against one shared
              counter per currency pair.
              (0400000 Section 5)

RL-ARCH-002   Rate limit tier: Intermediate (C-2).
              Confirmed for TothBot V2. (AR-013)

RL-ARCH-003   Rate counter parameters (Intermediate tier):
                Threshold:  maxratecount (from executions ACK)
                Decay rate: 2.34 units per second
                Max open orders per pair: 80

RL-ARCH-004   MANDATORY: Use maxratecount from the
              executions channel subscription ACK as
              the operative rate counter ceiling. Do NOT
              hardcode 125. The ACK value reflects the
              actual tier ceiling and updates automatically
              on tier changes. (AR-030 / A-19 / IMP-11)

RL-ARCH-005   Decay formula (per pair, per second):
                rate_counter -= 2.34
                rate_counter = max(0, rate_counter)
              Counter decays continuously regardless of
              order activity. A counter at 125 returns
              to zero in approximately 53 seconds of
              inactivity.

------------------------------------------------------------
4.2 Rate Cost Schedule — Complete
------------------------------------------------------------

RL-COST-001   add_order (limit entry):
                Fixed cost: +1
                No age-dependent surcharge.

RL-COST-002   amend_order (PRIMARY amendment method):
                Base cost: +1 (always)
                Age < 5 seconds:  +3 additional = +4 total
                Age < 10 seconds: +2 additional = +3 total
                Age < 15 seconds: +1 additional = +2 total
                Age >= 15 seconds: +0 additional = +1 total
              amend_order is 43% cheaper than edit_order
              for orders resting < 5 seconds (+4 vs +7).
              amend_order also preserves queue position.

RL-COST-003   edit_order: DEPRECATED. PROHIBITED.
              Do NOT use. Cost reference only:
                Base cost: +1 (always)
                Age < 5 seconds:  +6 additional = +7 total
                Age < 10 seconds: +5 additional = +6 total
              Using edit_order is a defect. (AR-018)

RL-COST-004   batch_add (TP + emergSL placement):
                Cost: +(n/2) rounded up
                2 orders (TP + emergSL): +1 total
                This is the standard TothBot batch_add
                cost on every entry fill.

RL-COST-005   cancel_order:
                Age < 5 seconds:   +8
                Age < 10 seconds:  +6
                Age < 300 seconds: +1
                Age >= 300 seconds: +1
              Note: canceling a newly placed order is
              expensive (+8). Avoid canceling entry orders
              within 5 seconds of placement.

RL-COST-006   batch_cancel:
                Cost: cumulative sum of individual cancel
                costs for each order in the batch.
                No discount vs individual cancels, but
                bypasses rate counter maximum — critical
                for Full Halt execution under rate pressure.

RL-COST-007   Rate cost reference — typical TothBot cycle:
                New entry:           +1  (add_order)
                Batch TP+emergSL:    +1  (batch_add)
                Normal MAE cancel:   +1  (cancel resting)
                emergSL amend (TP partial): +2 (amend resting)
              Typical cycle cost per active position: 2-5
              units. At 20 concurrent positions: 40-100
              units per pipeline cycle. Decay at 2.34/s
              over 300 seconds between candles provides
              ~702 units of headroom per pair.

------------------------------------------------------------
4.3 Rate Limit Monitoring and Protection
------------------------------------------------------------

RL-MON-001    CIATS EWMA Monitor tracks rate_counter_by_pair
              as one of three monitoring signals. Source:
              executions channel with ratecounter:true.
              Real-time rate counter value arrives on every
              exec_type=status event per pair. (A-1)

RL-MON-002    Rate counter warning threshold:
              When rate_counter > (maxratecount × 0.80):
                Log RL_WARNING(pair, counter, threshold)
                Alert operator if sustained > 3 consecutive
                pipeline evaluations at > 80% threshold.
              This is a CIATS monitoring starting value.
              CIATS may adjust the 80% threshold based on
              observed rate pressure patterns.

RL-MON-003    Rate counter critical threshold:
              When rate_counter > (maxratecount × 0.95):
                Log RL_CRITICAL(pair, counter, threshold)
                Alert operator PRIORITY_HIGH immediately.
                Suppress new entry orders for this pair
                until counter decays below 80% threshold.

RL-MON-004    Cloudflare connection limit:
              Kraken WS connections pass through Cloudflare.
              Cloudflare rate limit: 150 reconnects per
              10-minute window per IP.
              WS Manager reconnect logic must not exceed
              this rate. Exponential backoff after 5 rapid
              reconnect attempts prevents Cloudflare block.

5. API KEY CONFIGURATION
============================================================

------------------------------------------------------------
5.1 Key Pair Requirements
------------------------------------------------------------

KEY-CFG-001   Two separate API key pairs are required:

              DATA key (market data access):
                Permissions needed:
                  Query Funds
                  Query Open Orders and Trades
                  Query Closed Orders and Trades
                Connects on: Public WS v2 (no auth)
                             REST public endpoints (no auth)
                Used by: DATA channel subscriptions

              TRADE key (order management access):
                Permissions needed:
                  Query Funds
                  Query Open Orders and Trades
                  Create and Modify Orders
                  Cancel and Close Orders
                Connects on: Private WS v2 (token auth)
                             REST private endpoints (HMAC)
                Used by: executions, balances, all order ops

KEY-CFG-002   MANDATORY: Both API keys MUST be IP-whitelisted
              to the VPS IP: 87.99.141.44.
              Configure separately for each key in Kraken
              API settings. Update both on any VPS migration
              or IP change. IP whitelisting prevents use of
              TothBot API keys even if compromised.
              (AR-037)

KEY-CFG-003   API keys are never stored in source code.
              Loaded from environment variables or encrypted
              configuration file at startup. The VPS is the
              only authorized execution environment for
              TothBot V2 (Pathway 2).

KEY-CFG-004   Nonce window: 10,000ms. All private REST calls
              must use a monotonically increasing nonce
              (Unix timestamp in milliseconds). VPS system
              clock must be NTP-synchronized to prevent
              nonce rejection. (REST-AUTH-004/005 in 0411002)

------------------------------------------------------------
5.2 Key Pair Separation Rationale
------------------------------------------------------------

KEY-CFG-005   DATA and TRADE keys are separated to enforce
              least-privilege. The DATA key cannot place
              or cancel orders even if compromised.
              The TRADE key is used only for private
              operations and is more tightly held.

KEY-CFG-006   Both keys use Kraken's IP whitelist as an
              independent security layer. An attacker with
              the key but without the VPS IP cannot use it.

6. CIATS MONITORING HOOKS
============================================================

------------------------------------------------------------
6.1 Fee Monitoring
------------------------------------------------------------

CIATS-FEE-001  Logger records actual fee values from
               Kraken execution events on every trade
               close. Fee fields from executions channel:
                 fee: string (actual fee charged this fill)
               Convert to Decimal(str(fee)) on receipt.

CIATS-FEE-002  CIATS fee monitoring signals (per trade):
                 actual_entry_fee_pct:
                   fee_entry / (qty * avg_entry_price)
                 actual_exit_fee_pct:
                   fee_exit / (qty * exit_price)
                 actual_roundtrip_fee_pct:
                   actual_entry_fee_pct + actual_exit_fee_pct

CIATS-FEE-003  Fee tier change detection:
               If EWMA of actual_entry_fee_pct diverges
               from baseline 0.0016 by > 0.0002 (sustained
               over 50 trades): log FEE_TIER_CHANGE_DETECTED,
               alert operator. CIATS updates fee_maker_pct
               and fee_taker_pct parameters via PDCA.

CIATS-FEE-004  Fee impact on net P/L:
               The CIATS Trade Outcome Bus records net P/L
               (actual fees deducted) on every position
               close. Kelly formula uses net P/L exclusively.
               See AR-065 and FEE-CALC-004 through -006.

------------------------------------------------------------
6.2 Rate Counter Monitoring
------------------------------------------------------------

CIATS-RL-001   CIATS EWMA Monitor includes rate_counter_by_pair
               as a monitoring signal. Source: executions
               channel ratecounter:true events.

CIATS-RL-002   EWMA of rate_counter_by_pair (λ=0.2) provides
               a smoothed trend of rate pressure per pair.
               Spikes indicate burst order activity.
               Sustained elevation indicates systematic
               over-use requiring strategy review.

CIATS-RL-003   CIATS does NOT autonomously adjust rate
               limit parameters. Rate limit rules are
               exchange-defined and not CIATS-owned.
               CIATS monitors and alerts only.

------------------------------------------------------------
6.3 Rejection Rate Monitoring
------------------------------------------------------------

CIATS-REJ-001  CIATS tracks rejection_rate_by_regime:
               the rate at which post_only entry limit
               orders are rejected (not filled) per regime.
               Source: executions channel exec_type=expired
               on GTD entry orders.

CIATS-REJ-002  rejection_rate_by_regime is EWMA Monitor
               Stream 1 signal F6. It informs whether
               the entry limit price strategy (last candle
               close, quantized DOWN) is effective in
               each regime. (CIATS Proposal Engine input)

CIATS-REJ-003  If rejection_rate_by_regime exceeds CIATS-
               defined thresholds (starting: 30% per regime
               bucket over 50 evaluations), CIATS generates
               a proposal to review entry pricing strategy
               for that regime.

7. FIVE CODING-READINESS QUESTIONS
============================================================

(1) WHAT DOES THIS COMPONENT DO?
    Specifies the complete Kraken fee structure, rate limit
    rules, API key configuration, and CIATS monitoring
    hooks. Is the authoritative reference for all fee
    and rate calculations in TothBot V2. Consumed by
    Position Sizing (0611001), CIATS (0211001), and the
    coding specifications that implement them.

(2) INTERFACES:
    Inputs to TothBot from this spec:
      Fee rates → Kelly formula (net P/L via Logger)
      Rate costs → WS Manager (rate counter budget)
      maxratecount → WS Manager (from executions ACK)
      Actual fees → Logger → CIATS Trade Outcome Bus
    Outputs from TothBot to Kraken:
      None (this document is read-only reference for
      TothBot components — no outbound messages defined)

(3) HARD RULES:
    FEE-BASE-003: Entry orders ALWAYS post_only = maker fee
    FEE-CALC-006: Actual fees from Logger are authoritative
    RL-ARCH-001:  Rate limits shared across REST/WS/FIX
    RL-ARCH-004:  Use maxratecount from ACK — never hardcode
    RL-COST-003:  edit_order PROHIBITED
    KEY-CFG-002:  Both keys IP-whitelisted to VPS
    KEY-CFG-003:  API keys never in source code
    CIATS-FEE-004: Kelly uses net P/L (fees included)

(4) TRIGGERS AND TRIGGER CHAIN:
    Fee monitoring: triggered on every trade close event
      recorded by Logger. Feeds CIATS Trade Outcome Bus.
    Rate counter monitoring: triggered on every
      exec_type=status event from executions channel.
      Feeds CIATS EWMA Monitor.
    Rejection monitoring: triggered on every
      exec_type=expired for GTD entry orders.
      Feeds CIATS EWMA Monitor signal F6.
    Fee tier change: triggered by EWMA divergence from
      baseline, sustained over 50 trades.

(5) WHAT DOES IT LOG?
    Actual fee per fill (entry and exit, all trades)
    Actual fee percentage per fill
    Round-trip fee per closed position
    Fee tier change detection events
    Rate counter readings per pair (from executions)
    Rate limit warning events (>80% threshold)
    Rate limit critical events (>95% threshold)
    GTD entry order expiry events (rejection rate input)
    API key configuration validation at startup

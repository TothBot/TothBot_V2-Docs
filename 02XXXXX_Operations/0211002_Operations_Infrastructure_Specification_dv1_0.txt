OPERATIONS INFRASTRUCTURE SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document defines the complete operational infrastructure
requirements for TothBot V2. It specifies the VPS
environment, process management, network requirements,
API key security, alerting, log management, and all
standing operational constraints.

Infrastructure reliability is not optional. A crashed
and unmonitored TothBot V2 with open positions is a
direct loss event. Every infrastructure requirement in
this document exists to prevent that outcome.

This document is the parent specification for AA=10
coding specification 1011013 VPS_Deployment_Coding_Spec.

4. PROCESS MANAGEMENT
============================================================

------------------------------------------------------------
IN-PM-001  TOTHBOT MUST RUN AS A SYSTEMD SERVICE
------------------------------------------------------------

TothBot V2 must be managed by systemd. Manual process
management is prohibited in production. systemd provides:
  - Automatic restart on crash (Restart=on-failure)
  - Automatic start on VPS reboot (WantedBy=multi-user.target)
  - Watchdog monitoring of event loop health
  - Structured startup/shutdown lifecycle
  - Integration with system journal logging

------------------------------------------------------------
IN-PM-002  SYSTEMD SERVICE REQUIREMENTS
------------------------------------------------------------

Required systemd unit configuration:

  [Unit]
  Description=TothBot V2 Trading System
  After=network-online.target
  Wants=network-online.target

  [Service]
  Type=notify
  User=root
  WorkingDirectory=/root/TothBot_V2-Code
  EnvironmentFile=/root/.tothbot.env
  ExecStart=/usr/bin/python3 -m tothbot
  Restart=on-failure
  RestartSec=5
  WatchdogSec=120
  LimitNOFILE=65535

  [Install]
  WantedBy=multi-user.target

Requirements explained:
  After=network-online.target: TothBot does not start
    until the network is confirmed available. Prevents
    startup failures caused by boot-time race conditions.
  Type=notify: TothBot signals systemd when it is
    actually ready (READY=1 via sd_notify). systemd
    does not mark the service as started until TothBot
    confirms readiness after full startup validation.
  EnvironmentFile: API keys and secrets are loaded from
    /root/.tothbot.env — never hardcoded in source code.
  Restart=on-failure with RestartSec=5: automatic restart
    on crash after 5-second delay. Prevents restart storm.
  WatchdogSec=120: systemd restarts TothBot if no watchdog
    ping is received within 120 seconds. Detects frozen
    event loops that do not crash outright.
  LimitNOFILE=65535: prevents EMFILE errors under high
    WebSocket subscription load across many monitored pairs.

------------------------------------------------------------
IN-PM-003  SYSTEMD WATCHDOG REQUIREMENT
------------------------------------------------------------

TothBot V2 must implement an internal watchdog loop that
sends a systemd watchdog ping every 30 seconds. This is
separate from and in addition to the systemd WatchdogSec
timer.

The watchdog loop runs as a persistent asyncio Task.
If the event loop hangs, the watchdog Task stops sending
pings. systemd detects the absence of pings after 120
seconds and restarts TothBot.

The 30-second ping interval with a 120-second watchdog
timeout provides 4 missed pings before restart — enough
tolerance for brief event loop delays without triggering
spurious restarts.

------------------------------------------------------------
IN-PM-004  STARTUP NOTIFICATION REQUIREMENT
------------------------------------------------------------

TothBot V2 must send sd_notify READY=1 after all startup
validation steps complete successfully. Specifically,
READY=1 is sent only after:
  - Both WebSocket connections established
  - Position Mirror reconciled (snap_orders or REST)
  - Parameter Store loaded
  - CIATS initialized
  - All startup gates passed

systemd holds the service in activating state until
READY=1 is received. This prevents dependent services
from starting before TothBot is actually ready.

5. NETWORK REQUIREMENTS
============================================================

------------------------------------------------------------
IN-NET-001  OUTBOUND CONNECTIVITY REQUIREMENTS
------------------------------------------------------------

TothBot V2 requires persistent outbound connectivity to:

  Kraken Public WS v2:
    wss://ws.kraken.com/v2
    Port 443 (WSS). Persistent connection. 24/7.

  Kraken Private WS v2:
    wss://ws-auth.kraken.com/v2
    Port 443 (WSS). Persistent connection. 24/7.

  Kraken REST API:
    https://api.kraken.com
    Port 443 (HTTPS). Periodic calls. Not persistent.

  Kraken Status API:
    https://status.kraken.com/api/v2/scheduled-maintenances.json
    Port 443 (HTTPS). Called at startup only.

  Email alerts (SMTP):
    alert@tothbot.com outbound. SMTP port as configured.

------------------------------------------------------------
IN-NET-002  CONNECTION FAILURE BEHAVIOR
------------------------------------------------------------

WebSocket disconnection is a normal operational event
that must be handled gracefully per the reconnection
specification in 0511001 WS_Manager_Specification.

TothBot V2 must never halt on a transient WS disconnection.
It must reconnect automatically per the reconnection
procedure. Emergency SL orders on the Kraken matching
engine provide crash protection during any disconnection
period.

------------------------------------------------------------
IN-NET-003  CLOUDFLARE RECONNECT CONSTRAINT
------------------------------------------------------------

Kraken WS endpoints are served through Cloudflare.
Cloudflare enforces connection limits per IP. Rapid
reconnection cycling can trigger rate limiting.
Reconnection backoff must be implemented per 0511001.
Minimum reconnect delay: 5 seconds. Maximum: per
backoff schedule in 0511001.

6. API KEY SECURITY
============================================================

------------------------------------------------------------
IN-KEY-001  TWO API KEY PAIRS REQUIRED
------------------------------------------------------------

TothBot V2 requires exactly two Kraken API key pairs:
  DATA key:  market data access only. No order permissions.
  TRADE key: order submission and account access.

The two-key architecture limits blast radius: a compromise
of the DATA key cannot submit orders.

------------------------------------------------------------
IN-KEY-002  IP WHITELISTING — MANDATORY
------------------------------------------------------------

Both the DATA key and the TRADE key MUST be IP-whitelisted
to the VPS IP address in the Kraken account settings.
This is not optional. A non-whitelisted TRADE key is a
security exposure — any party with the key string can
submit orders.

IP whitelist must be updated BEFORE any VPS migration.
Executing a VPS migration without updating the whitelist
will immediately lock TothBot out of all private API calls
with open positions potentially unmonitored.

Sequence for VPS migration:
  1. Provision new VPS, obtain new IP.
  2. Update Kraken API key whitelist to new IP.
  3. Verify connectivity from new VPS.
  4. Migrate TothBot to new VPS.
  5. Decommission old VPS.

------------------------------------------------------------
IN-KEY-003  ENVIRONMENT FILE STORAGE
------------------------------------------------------------

API keys, secrets, and all credentials are stored in
/root/.tothbot.env on the VPS. This file is:
  - Loaded by systemd via EnvironmentFile directive.
  - Never committed to any Git repository.
  - Never logged in any log file.
  - Never transmitted in any alert message.
  - Readable only by root (chmod 600).

API keys are never hardcoded in source code. Any source
file containing an API key literal is a critical defect.

------------------------------------------------------------
IN-KEY-004  NONCE WINDOW
------------------------------------------------------------

Kraken API nonce window: 10,000ms (10 seconds).
Both DATA and TRADE key nonce windows must be set to
10,000ms in Kraken account settings. This accommodates
clock drift and retry delays without nonce collisions.

7. ALERTING
============================================================

------------------------------------------------------------
IN-ALT-001  ALERT DESTINATION
------------------------------------------------------------

All TothBot V2 operational alerts are sent to:
  alert@tothbot.com

No other alert destination is used. CIATS does not send
alerts directly — all alerts flow through the Logger
per 0511006 Section 7.

------------------------------------------------------------
IN-ALT-002  ALERT LEVELS
------------------------------------------------------------

Alert severity levels (per 0511006):
  INFO:     Informational. No action required.
            Example: startup complete, daily regime update.
  WARNING:  Degraded condition. Monitor.
            Example: WS reconnection, CUSUM signal.
  CRITICAL: Immediate operator attention required.
            Example: negative Kelly, full halt drawdown,
            Logger queue full, VPS resource exhaustion.

CRITICAL alerts require operator acknowledgment.
TothBot V2 does not auto-resolve CRITICAL alerts.

------------------------------------------------------------
IN-ALT-003  KRAKEN STATUS API CHECK AT STARTUP
------------------------------------------------------------

TothBot V2 must query the Kraken Status API at every
startup to check for scheduled maintenance windows:
  https://status.kraken.com/api/v2/scheduled-maintenances.json

If a scheduled maintenance is within 2 hours of startup:
  Log at CRITICAL level. Send alert to alert@tothbot.com.
  Continue startup — this check is informational only.
  It does not block startup.

Rationale: Forewarned maintenance allows Bill to decide
whether to proceed with live trading or stand down until
the maintenance window passes.

============================================================
8. LOG MANAGEMENT
============================================================

------------------------------------------------------------
IN-LOG-001  LOG RETENTION REQUIREMENTS
------------------------------------------------------------

TothBot V2 generates two log streams:
  System journal: managed by systemd/journald.
  TothBot log files: managed by the Logger (0511006).

TothBot log file retention:
  Minimum retention: 90 days of trading logs.
  Rotation: daily. Compressed after rotation.
  Location: /root/TothBot_V2-Code/logs/ (or as configured)

CIATS data retention:
  Trade Outcome Bus records: retained indefinitely.
  These are the zero-cost historical library. They must
  never be deleted — they are the foundation of all
  regime-segmented optimization after 600 trades.
  Stored in: /root/TothBot_V2-Code/data/ (or as configured)

------------------------------------------------------------
IN-LOG-002  LOGROTATE REQUIREMENT
------------------------------------------------------------

logrotate must be configured and active before the first
live trading run. Required configuration:

  /root/TothBot_V2-Code/logs/*.log {
      daily
      rotate 90
      compress
      delaycompress
      missingok
      notifempty
      copytruncate
  }

copytruncate: allows log rotation without restarting
TothBot — rotation is performed on the active file
without interrupting the Logger's file handle.

------------------------------------------------------------
IN-LOG-003  LOGGER QUEUE ALERT REQUIREMENT
------------------------------------------------------------

The Logger maintains an async bounded queue (maxsize=10,000
per 0511006). If the queue fills, an immediate CRITICAL
alert must be sent to alert@tothbot.com. The Logger must
never silently drop events. A full queue indicates either
a disk I/O problem or an unexpectedly high event rate —
both require immediate operator attention.

9. STANDING OPERATIONAL CONSTRAINTS
============================================================

------------------------------------------------------------
IN-OC-001  24/7/365 OPERATION
------------------------------------------------------------

TothBot V2 operates 24/7/365. Kraken Spot trades
continuously. There are no scheduled maintenance windows,
no planned downtime windows, and no trading hours. Any
planned maintenance or upgrade requires:
  (a) Waiting for all positions to close, OR
  (b) Manual position management by Bill before stopping
      TothBot.
  (c) Confirming emergency SL orders are active on the
      Kraken matching engine before stopping TothBot.

------------------------------------------------------------
IN-OC-002  TOTHBOT RESTART IS AN OPERATIONAL EVENT
------------------------------------------------------------

Every TothBot restart — whether from crash, manual stop,
or watchdog timeout — must be logged as an operational
event with timestamp and cause. Restarts are not routine
maintenance — they are incidents requiring review.

Frequent restarts (more than 3 per 24-hour period) are
a CRITICAL operational alert condition.

------------------------------------------------------------
IN-OC-003  VPS RESOURCE MONITORING
------------------------------------------------------------

The following VPS resource thresholds are CRITICAL alert
conditions:
  RAM utilization:  > 80% of 4GB = > 3.2GB
  CPU utilization:  > 80% sustained over 5 minutes
  Disk utilization: > 80% of 40GB = > 32GB
  Network:          any sustained packet loss > 1%

These thresholds are CIATS-owned starting values. CIATS
monitors ws_roundtrip_latency_ms (Stream 1 Signal 3) as
a proxy for network health. Direct VPS resource monitoring
is a future infrastructure enhancement (not in V1 scope).

------------------------------------------------------------
IN-OC-004  NO LIVE TRADING WITHOUT EMERGENCY SL ACTIVE
------------------------------------------------------------

TothBot V2 must never hold an open position without an
active emergency SL order on the Kraken matching engine.
The emergency SL is crash protection — it fires only if
TothBot fails to manage the exit. It must be present at
all times for all open positions.

Verification: confirmed at startup via snap_orders
reconciliation (AR-003). Any position without a
corresponding emergency SL order is a CRITICAL defect
requiring immediate remediation.

10. HARD RULES
============================================================

  HR-IN-001  TothBot V2 runs as a systemd service.
             Manual process management is prohibited
             in production.

  HR-IN-002  Both API keys MUST be IP-whitelisted to the
             VPS IP. Non-whitelisted TRADE key is a
             critical security exposure.

  HR-IN-003  API keys are stored in EnvironmentFile only.
             Never in source code. Never in logs.

  HR-IN-004  IP whitelist MUST be updated BEFORE any
             VPS migration. Sequence: update whitelist,
             verify, migrate.

  HR-IN-005  logrotate MUST be configured and active
             before the first live trading run.

  HR-IN-006  CIATS Trade Outcome Bus records are retained
             indefinitely. They must never be deleted.

  HR-IN-007  TothBot must never hold an open position
             without an active emergency SL order on
             the Kraken matching engine.

  HR-IN-008  A full Logger queue is a CRITICAL alert.
             Events must never be silently dropped.

  HR-IN-009  Frequent restarts (>3 per 24h) are a
             CRITICAL alert condition requiring
             immediate investigation.

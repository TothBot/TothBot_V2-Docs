============================================================
LOGGER SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document is the system-level specification for the
Logger component of TothBot V2. It defines what the Logger
does, its interfaces, its hard rules, what triggers it, and
what it logs (i.e., what data CIATS depends on). It is the
authoritative parent document for 1011007 Logger_Coding_Spec.

The Logger is the sole data interface between TothBot and
CIATS. Everything CIATS knows about TothBot's operation,
it knows from the Logger. The Logger must never block the
trading hot path. Every logged event is a potential CIATS
data point.

From dv1_1: the Logger operates a TWO-STREAM RECORD
ARCHITECTURE on disk. The diagnostic stream (finite-
retention rotating file) and the permanent stream
(append-only, no-rotation, annual-segmented trade record
file) are distinct components with distinct retention
contracts and distinct governing concerns (diagnostics /
CIATS live read vs. compliance, tax, audit). See
Section 3.3.

============================================================
2. COMPONENT SUMMARY
============================================================

What it does:
  Receives log entries from all TothBot components via an
  in-memory bounded queue. Writes entries asynchronously
  to disk via a background thread. Dispatches to two
  persistent disk sinks (Section 3.3). Provides real-time
  data stream to CIATS (two streams: EWMA Monitor and
  Trade Outcome Bus). Never blocks the trading hot path.
  Provides operator alert routing for CRITICAL and HIGH
  level events, with positive-delivery confirmation events.

Primary inputs:
  Log call from any TothBot component (WS Manager, Signal
  Pipeline, Execution Engine, Exit Controller, Position
  Mirror, Regime Engine)

Primary outputs:
  (1) Diagnostic disk log file (structured — CIATS-readable,
      finite retention via rotation). Receives ALL events.
  (2) Permanent trade record file (structured — append-only,
      annual-segmented, no rotation). Receives TRADE_CLOSE
      events only. Authoritative long-term source for
      CIATS's 200-trade statistical floor, IRS Form 8949 /
      26 CFR 1.6001-1 tax records, and audit trail.
  (3) Operator alerts for CRITICAL and HIGH events (email)
      plus positive-delivery confirmation events
      (ALERT_SENT) and failure events (ALERT_SMTP_FAILED)
      emitted back through the Logger itself.

============================================================
3. IMPLEMENTATION ARCHITECTURE (AR-014, AR-063)
============================================================

3.1 Queue Implementation

  CORRECT implementation (AR-063):
    import queue
    import logging.handlers

    log_queue = queue.Queue(maxsize=10000)
    queue_handler = logging.handlers.QueueHandler(log_queue)
    log_listener = logging.handlers.QueueListener(
        log_queue, file_handler, alert_handler,
        trade_record_handler)
    log_listener.start()

  NOT asyncio.Queue:
    QueueListener runs in a separate non-asyncio thread
    and is not compatible with asyncio.Queue. An asyncio
    coroutine writer would compete with the event loop
    for scheduling. stdlib queue.Queue is correct.

  queue.Queue(maxsize=10000):
    10,000 entries bounded queue (AR-014, FP/DP validated).
    Derivation: 20 positions x 10 events/candle x 50-candle
    buffer = 10,000 entries = 50-candle burst absorption.
    (Source: 0500000 dv1_18 Section 6, I-5.)

  QueueHandler: Non-blocking. Called on the asyncio event
    loop — puts entry into queue and returns immediately.
  QueueListener: Runs in its own background thread. Reads
    from queue and dispatches to ALL attached handlers
    (diagnostic file handler, alert handler, permanent
    trade record handler). Never blocks the asyncio event
    loop. Per-handler exception isolation via
    logging.Handler.handleError ensures that a failure
    in one handler does not prevent the others from
    processing the same record.

3.2 On Queue Full

  If log_queue.Full exception raised on put():
    Write directly to sys.stderr: "LOG QUEUE FULL — entry
    dropped: {timestamp} {event_type} {symbol}"
    Alert operator HIGH immediately.
    Skip the queued entry — NEVER block the caller.
    NEVER raise an exception back to the trading hot path.

3.3 Two-Stream Record Architecture (dv1_1)

  The Logger produces TWO persistent disk streams with
  distinct and independent retention contracts. Both
  streams are written from the single QueueListener
  background thread. Neither blocks the hot path.

  STREAM 1 — DIAGNOSTIC (tothbot.log)
    Handler:     RotatingFileHandler
    Location:    /home/tothbot/logs/tothbot.log
    Contents:    ALL log events from all components
    Format:      NDJSON (one JSON object per line)
    Retention:   Rotating — 90 files x 50 MB (AA=10 spec
                 1011007 LG-FILE-002). Finite.
    Consumers:   CIATS real-time tail (live read),
                 operator forensics, on-VPS grep/jq.
    Rationale:   High-volume diagnostic stream. Must not
                 grow unbounded. CIATS monitors live.

  STREAM 2 — PERMANENT TRADE RECORD (trades_<YYYY>.jsonl)
    Handler:     TothBotTradeRecordHandler
    Location:    /home/tothbot/records/trades_<YYYY>.jsonl
                 where <YYYY> is the current UTC calendar
                 year at time of write.
    Contents:    TRADE_CLOSE events ONLY. All other event
                 types are a no-op for this handler.
    Format:      JSONL — identical per-record payload to
                 Stream 1 (same pre-serialized JSON line,
                 plus "\\n"). No divergent serialization.
    Retention:   PERMANENT. Append-only. No rotation.
                 No size cap. No truncation. 0o644
                 permissions hard-pinned on create.
                 fsync after each write.
    Consumers:   Tax preparation (IRS Form 8949,
                 Schedule D, 26 CFR 1.6001-1 — 3-year
                 minimum; longer in audit-extension),
                 CIATS 200-trade statistical corpus
                 (future — currently served by Stream 1
                 tail; OI-024 parking lot in 1010000
                 dv1_11 Section 4.10), forensic audit of
                 any historical trade, operator
                 dashboards.
    Rationale:   The CIATS 200-trade statistical floor,
                 tax compliance, and audit trail require
                 a trade record horizon longer than the
                 diagnostic stream's bounded retention
                 can guarantee (TB00107 observed ~6 days
                 of tothbot.log retention on the live
                 VPS — orders of magnitude short of the
                 3-year tax minimum and structurally
                 insufficient for the 200-trade CIATS
                 corpus at realistic paper-trading
                 throughput).

  Contract between the two streams:
    (a) TRADE_CLOSE payload is BYTE-FOR-BYTE IDENTICAL on
        both streams (enforced by 1011007 dv1_4
        LG-TOB-003). The permanent stream is not a
        derived transform — it is the same record,
        written twice.
    (b) Diagnostic-stream TRADE_CLOSE within current
        retention window is an operational fallback if
        the permanent-stream write fails
        (TRADE_RECORD_WRITE_FAILED HIGH alert fires;
        operator can recover from tothbot.log until
        root cause is resolved).
    (c) The streams are INDEPENDENT from a failure-domain
        perspective: QueueListener dispatches each record
        to each handler with per-handler handleError
        isolation. A failing permanent-stream write does
        not prevent the diagnostic write, and vice versa.

3.4 Shutdown

  log_listener.stop() on TothBot shutdown.
  stop() drains remaining queue entries and joins the
  background thread. No log entries lost on clean shutdown.
  Queued TRADE_CLOSE records are dispatched to BOTH
  Stream 1 and Stream 2 handlers during drain.

============================================================
4. LOG ENTRY FORMAT
============================================================

4.1 Minimum required fields on every entry:

  timestamp_utc:  ISO 8601 string (UTC, nanosecond if available,
                  millisecond minimum)
  event_type:     str (see Section 5 — event type registry)
  level:          str (DEBUG | INFO | WARN | ERROR | CRITICAL)
  component:      str (WS_MGR | SIGNAL_PIPELINE |
                       EXEC_ENG | EXIT_CTRL | POS_MIRROR |
                       REGIME_ENG | LOGGER | CIATS)

4.2 Additional fields per event type:

  symbol:         str (where applicable)
  connection_id:  uint64 (all WS connection events, AR-064)
  req_id:         int (all outbound WS message events)
  cl_ord_id:      str (all order events)
  order_id:       str (all fill/cancel events)
  All numeric values: Decimal (stored as string in log)

4.3 Log file format:

  Structured (newline-delimited JSON recommended).
  Each line: one JSON object with all fields.
  CIATS reads log file for all statistical computation.
  File format governs CIATS data access.
  Rotation policy for STREAM 1 (diagnostic): defined in
  1011007 AA=10 coding spec.
  Rotation policy for STREAM 2 (permanent trade record):
  NONE. Explicit architectural contract — see 3.3.

6. CIATS DATA STREAMS
============================================================

6.1 Stream 1 — EWMA Monitor

  CIATS reads these fields for the EWMA Monitor:
  (288 candle evals/day, valid at 50 evals, lambda=0.2)

  Signal 1: rejection_rate_by_regime (F6)
    Source: GATE_5_RESULT events + regime from GATE_3_RESULT
    Fields needed: symbol, rejection_code, regime,
                   vol_regime, timestamp_utc

  Signal 2: rate_counter_by_pair (A-1)
    Source: RATE_COUNTER_UPDATE events
    Fields needed: symbol, value, maxratecount, timestamp_utc

  Signal 3: ws_roundtrip_latency_ms (A-3)
    Source: PONG_RECEIVED event — latency_ms field
    Fields needed: connection_id, latency_ms, timestamp_utc
    WS v2 responses include time_in and time_out to
    nanosecond precision. Logger MUST capture both fields
    where present (A-3).

  All three are MONITORING SIGNALS ONLY. The EWMA Monitor
  never drives parameter changes. It is a fast warning
  stream. Valid at 50 candle evals (~4 hours).

6.2 Stream 2 — Trade Outcome Bus

  CIATS reads these fields for statistical analysis.
  Fires ONCE on each complete position close.
  Source: POSITION_CLOSED or MARKET_SELL_FILLED events
  combined with entry data.

  Record type: TRADE_CLOSE (see 1011007 dv1_4 Section 7
  for the complete mandatory-field contract).

  From dv1_1: TRADE_CLOSE records are written to BOTH
  the diagnostic log (Stream 1 in Section 3.3) AND the
  permanent trade record file (Stream 2 in Section 3.3).
  The Trade Outcome Bus is therefore backed by a
  permanent on-disk source regardless of diagnostic-log
  rotation.

  Feed: Statistical Engine → Proposal Engine (at 200 trades)
        Regime Library (at 600 trades, 100+ per bucket)
        Half-Kelly computation (at 200+ trades)

7. ALERT ROUTING
============================================================

  Level CRITICAL:
    Events: PING_TIMEOUT, ZOMBIE_CONNECTION_DETECTED,
    FATAL_RECONNECT_FAILURE, EXECUTIONS_SEQUENCE_GAP,
    UNEXPECTED_ORDER_AMENDED, CANCEL_TIMEOUT_HOLD,
    MAE_HOLD_AMBIGUOUS, FULL_HALT_TRIGGERED,
    PAIR_CANCEL_ONLY_HOLD, PAIR_MAINTENANCE_HOLD,
    EMERGENCY_SL_FIRED, any unhandled exception
    Routing: alerts@tothbot.com (immediate email alert).
             (OI-019 dv1_3 code / dv1_3 spec — plural:
             real Proton mailbox. Singular does not
             exist — catch-all reservation.)

  Level HIGH:
    Events: BALANCES_SEQUENCE_GAP, SESSION_PAUSE_TRIGGERED,
            BATCH_CANCEL_SENT, LOG_QUEUE_FULL,
            UNEXPECTED_OPEN_ORDER,
            TRADE_RECORD_WRITE_FAILED (dv1_1),
            ALERT_SMTP_FAILED (dv1_1 — ALERT-EXEMPT;
            written to Stream 1 but does NOT trigger
            SMTP alert; anti-recursion per 1011007
            dv1_4 LG-ALERT-005)
    Routing: alerts@tothbot.com.

  Level WARN:
    Events: UNKNOWN_EXEC_TYPE, UNKNOWN_MESSAGE_TYPE,
            RATE_COUNTER_WARNING, REGIME_STALE_WARNING
    Routing: log file only (no email)

  All CRITICAL and HIGH: also written to stderr as fallback
  in case Logger queue is unavailable.

  Positive-delivery confirmation (dv1_1): after SMTP
  sendmail returns without exception, an ALERT_SENT (INFO)
  event is emitted via the standard Logger path. This
  provides operator observability of successful alert
  delivery — closing the gap observed during TB00107
  investigation where bounces were visible externally
  but no structured positive or negative signal existed
  in tothbot.log.

============================================================
8. INTERFACES
============================================================

8.1 From all TothBot components
  All components call Logger. Logger is the universal
  output sink. Non-blocking from caller perspective.

8.2 To disk (two streams — see 3.3)
  QueueListener background thread writes to BOTH:
    STREAM 1: RotatingFileHandler → tothbot.log
              (diagnostic, finite retention, all events)
    STREAM 2: TothBotTradeRecordHandler →
              trades_<YYYY>.jsonl (permanent, append-only,
              TRADE_CLOSE only, annual-segmented)
  Neither involves the asyncio event loop.

8.3 To CIATS
  CIATS reads from log files directly. Logger does not
  push to CIATS. CIATS is fully asynchronous and reads
  only from Logger output. CIATS never blocks TothBot.

  Current CIATS implementation tails STREAM 1
  (tothbot.log). Migration to STREAM 2 (trades_<YYYY>.jsonl)
  for the 200-trade statistical corpus is in the parking
  lot as OI-024 (see 1010000 dv1_11 Section 4.10) —
  once trade throughput surfaces the corpus-truncation
  risk that STREAM 1's finite retention creates.

8.4 To operator
  CRITICAL and HIGH events: email to alerts@tothbot.com.
  Routing implementation in AA=10 coding spec. Positive-
  delivery confirmation via ALERT_SENT (INFO) events
  (dv1_1). Failure observability via ALERT_SMTP_FAILED
  (HIGH, ALERT-EXEMPT) events (dv1_1).

============================================================
9. HARD RULES
============================================================

HR-LG-001  Logger NEVER blocks the trading hot path under
           any condition (AR-014). Queue full → drop entry
           → alert → continue. NEVER block caller. This
           applies to BOTH disk streams (Section 3.3).
           Stream 2 writes occur in the QueueListener
           background thread, not on the hot path;
           per-write fsync on Stream 2 does not violate
           HR-LG-001.

HR-LG-002  MUST use queue.Queue (stdlib), NOT asyncio.Queue.
           QueueListener runs in its own non-asyncio thread
           (AR-063). asyncio.Queue is incompatible with
           QueueListener thread model.

HR-LG-003  maxsize=10,000 (AR-014). Derived from FP/DP:
           20 positions x 10 events/candle x 50-candle buffer.
           Queue size is CIATS-owned starting value.

HR-LG-004  log_listener.stop() called on clean shutdown.
           Drains and joins background thread. No log loss,
           on EITHER stream.

HR-LG-005  Trade Outcome Bus: ALL fields in Section 6.2 are
           mandatory on every position close event. No
           optional fields. Missing fields break CIATS
           statistical computation. TRADE_CLOSE payload is
           byte-for-byte identical on STREAM 1 and
           STREAM 2 — enforced by 1011007 dv1_4 LG-TOB-003.

HR-LG-006  Trade Outcome Bus fires ONCE per complete position
           close. Not on each partial fill (AR-066).

HR-LG-007  EWMA Monitor Signal 3 (ws_roundtrip_latency_ms):
           time_in and time_out fields from WS v2 responses
           captured on Logger where present (A-3).

HR-LG-008  connection_id (AR-064) logged on every WS
           connection event and included in all reconnect,
           disconnect, and gap log entries.

HR-LG-009  All numeric values stored as string representation
           of Decimal in log. No float storage.

HR-LG-010  Log file format must be structured (JSON preferred)
           and machine-readable. CIATS reads it directly.
           Human-readable format secondary to CIATS readability.

HR-LG-011  Queue full event: write to stderr AND alert HIGH.
           The trade that was dropped must be recoverable
           from other sources if possible. Alert is the signal
           that queue sizing needs to be reviewed.

HR-LG-012  STREAM 2 (dv1_1) permanent trade record file:
             (a) Append-only. Never truncate. Never rotate.
             (b) Annual segmentation at /home/tothbot/records/
                 trades_<YYYY>.jsonl — UTC calendar year
                 at time of write.
             (c) File permissions 0o644 hard-pinned via the
                 mode argument to os.open with O_CREAT,
                 independent of runtime umask. Deming 6.1
                 — build quality in.
             (d) fsync after every write. Compliance-grade
                 records must survive VPS power loss /
                 kernel panic. Cost is negligible because
                 TRADE_CLOSE frequency is low and fsync
                 runs in the QueueListener thread.
             (e) Write failure emits TRADE_RECORD_WRITE_FAILED
                 (HIGH) via the standard Logger path. Does
                 not raise. Does not block STREAM 1 write.

10. WHAT TRIGGERS IT
============================================================

  Any TothBot component log() call:
    WS Manager (highest volume — every event)
    Signal Pipeline (every gate evaluation)
    Execution Engine (order dispatch and fills)
    Exit Controller (exit sequences)
    Position Mirror (state changes)
    Regime Engine (daily computation)

============================================================
11. WHAT IT LOGS
============================================================

  The Logger logs everything. It is the audit trail of the
  entire system. Every event from every component passes
  through it. The full event type registry is in Section 5.

  Volume estimate:
    288 candle evals/day x 20 pairs = 5,760 pipeline evals
    Each eval: ~8-15 log entries = ~60,000 entries/day
    Plus: WS events, fills, pings, heartbeats
    Total: ~80,000-120,000 entries/day (estimate)
    Queue absorption: 10,000 entries = ~10-minute burst buffer

  STREAM 2 (dv1_1) volume is negligible by comparison:
  one TRADE_CLOSE event per closed position. At target
  paper-trade throughput of ~20-50 trades/day, STREAM 2
  grows at ~500-800 bytes per event = ~10-40 KB/day.
  Annual file size at that throughput: ~4-15 MB.
  Well under any practical filesystem concern.

============================================================
EXECUTION ENGINE SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document is the system-level specification for the
Execution Engine component of TothBot V2. It defines what
the Execution Engine does, its interfaces, its hard rules,
what triggers it, and what it logs. It is the authoritative
parent document for 1011004 Execution_Engine_Coding_Spec.

The Execution Engine owns all order dispatch to Kraken
for position entry and TP/emergSL placement. It receives
the sizing output from Gate 8 of the Signal Pipeline and
translates it into precisely-constructed WS v2 messages.

In paper trading mode, the Execution Engine code path is
byte-identical to live mode (PA-005). Mode is read once at
WSManager.__init__ and enforced at the WSManager dispatch
seam (0500000 dv1_24 §12.3). The Execution Engine is
mode-blind by architectural intent; it never reads
paper_trading_mode and never branches on mode. Per
TB00000 v2_20 §4.4 PA-001..010 PAPER-AS-MASTER
PRINCIPLE.

============================================================
2. COMPONENT SUMMARY
============================================================

What it does:
  Receives Gate 8 sizing output. Assigns cl_ord_id to the
  entry order. Constructs and sends add_order (entry) via
  the WSManager dispatch seam. On execution fill confirmation,
  constructs and sends batch_add (TP limit + emergSL stop-
  market atomic) via the WSManager dispatch seam. Updates
  Position Mirror at dispatch. Populates Pending Order
  Registry. Handles entry rejection and expiry. Transfers
  rate counter cost to CIATS monitor. Behavior is byte-
  identical between paper and live modes per §5A
  EE-PAPER-001.

Primary inputs:
  Gate 8 output dict from Signal Pipeline (0511002):
    {symbol, entry_limit_price, entry_qty,
     tp_price, sl_trigger_price, entry_timeout_sec,
     regime_context, signal_params}
  executions channel fill/expiry events (live) OR
  _simulate_entry_fill callback (paper) — mode-opaque
  to the Execution Engine per §5A EE-PAPER-004.

Primary outputs:
  WS v2 add_order message (entry) handed to WSManager
    seam — paper gates and simulates; live transmits.
  WS v2 batch_add message (TP + emergSL, on fill) handed
    to WSManager seam — paper gates and simulates; live
    transmits.
  Position Mirror update (0511005)
  Pending Order Registry update (via WS Manager)
  Logger calls (0511006)

============================================================
3. PHASE 1 — ENTRY ORDER DISPATCH
============================================================

3.1 cl_ord_id Assignment

  Assigned at dispatch before Kraken response.
  Format: up to 18 characters. Must be unique per order.
  Suggested format: symbol prefix + timestamp in ms.
  Example: "BTCUSD1712230000001"
  cl_ord_id is recorded in Position Mirror immediately at
  dispatch — no async gap (A-2). Pending Order Registry
  populated at same time.

3.2 req_id Assignment

  Each outbound message carries req_id (unique integer).
  WS Manager req_id_registry tracks: {method, timestamp,
  symbol} keyed by req_id. Used for cancel timeout
  fallback (I-6) and response correlation.

3.3 add_order Construction (AR-006)

  All fields required. No optional fields omitted.

  {
    "method": "add_order",
    "params": {
      "order_type": "limit",
      "side":       "buy",
      "symbol":     <symbol>,
      "limit_price": <entry_limit_price>,
      "order_qty":  <entry_qty_quantized>,
      "post_only":  true,
      "time_in_force": "gtd",
      "expire_time":   <ISO 8601 UTC now + entry_timeout_sec>,
      "cl_ord_id":  <assigned cl_ord_id>,
      "stp_type":   "cancel_newest",
      "deadline":   <ISO 8601 UTC now + 5s>
    },
    "req_id": <assigned req_id>
  }

  Field notes:
    time_in_force = "gtd" (Good Til Date) — self-expiring.
    entry_timeout_sec: 30-60s (CIATS-owned starting range).
    stp_type: "cancel_newest" WITH UNDERSCORE (AR-032).
              REST API uses "cancel-newest" (hyphen).
              WS v2 ALWAYS uses underscore. Never confuse.
    deadline: UTC now + 5 seconds ISO 8601 string (AR-033).
    post_only: true — guarantees maker fill or rejection.
               No fill on spread crossing — NEVER taker.

  Construction is byte-identical between paper and live
  modes. The dispatch boundary is the WSManager seam per
  §5A EE-PAPER-002 and 0500000 dv1_24 §12.3.

3.4 Pending Order Registry Population (AR-053)

  On add_order dispatch:
    estimated_cost = entry_qty * entry_limit_price *
                     (1 + maker_fee_rate)
    pending_orders[entry_cl_ord_id] = estimated_cost
  Gate 7 available_USD uses this registry to prevent
  capital overcommitment when multiple pairs fire
  simultaneously. Identical behavior in paper and live.

3.5 Entry Rate Counter Cost

  add_order fixed cost: +1 rate counter unit.
  Rate counter monitored via executions channel (A-1)
  in live mode. In paper mode, rate counter is not
  Kraken-pushed (no private WS connection per HR-EE-014);
  CIATS rate-counter telemetry is mode-agnostic and uses
  the +1 unit attribution at dispatch.
  If rate counter near ceiling (approaching maxratecount
  from subscription ACK): log RATE_COUNTER_WARNING.

============================================================
4. ENTRY ORDER OUTCOMES
============================================================

4.1 exec_type = filled (full fill at entry)

  Trigger Phase 2 (TP + emergSL placement).
  Extract: qty = Decimal(str(cum_qty)),
           entry_fill_price = Decimal(str(avg_price)).
  Clear pending_orders[entry_cl_ord_id].
  Log ENTRY_FILLED.

  Live source: executions channel exec_type=filled.
  Paper source: _simulate_entry_fill callback per
                §5A EE-PAPER-004 (fill price = entry
                limit price, fill qty = full qty).
  EE handles both sources via the same callback path —
  EE does not branch on source.

4.2 exec_type = trade (partial fill while open)

  Order is still active — partially filled.
  Update Pending Order Registry: hold entry (do NOT clear).
  No TP/emergSL dispatch yet. Wait for filled or expiry.
  Log ENTRY_PARTIAL_TRADE (cum_qty, avg_price).

4.3 exec_type = expired (GTD window elapsed)

  If cum_qty == 0: no fill. Clear registry. Log
    ENTRY_EXPIRED_NO_FILL. No position opened.
  If cum_qty > 0: partial fill exists. No TP/emergSL.
    CRITICAL: unprotected position. Partial fill
    protection triggered per AR-054 (handled by
    WS Manager dispatch — see 0511001 Section 8.2).
    Log ENTRY_EXPIRED_PARTIAL_FILL.

4.4 exec_type = canceled

  Same handling as expired (AR-054 applies).
  Log ENTRY_CANCELED_PARTIAL_FILL or ENTRY_CANCELED_NO_FILL.

4.5 exec_type = new (order accepted on book)

  No action. Log ENTRY_ACCEPTED_ON_BOOK.

4.6 post_only rejection (exec_type = canceled, reason = post_only)

  Order hit spread — post_only prevented taker fill.
  Clear pending_orders. Log ENTRY_POST_ONLY_REJECTED.
  CIATS EWMA Monitor: rejection_rate_by_regime increments
  (signal 1 — Finding 6 of dv1_10).

============================================================
5. PHASE 2 — TP + EMERGENCY SL PLACEMENT (batch_add)
============================================================

5.1 batch_add Construction (AR-007, AR-046, AR-032, AR-033)

  Dispatched atomically on confirmed full entry fill.
  Two legs: TP limit order + emergSL stop-market order.

  {
    "method": "batch_add",
    "params": [
      {
        "order_type":  "limit",
        "side":        "sell",
        "symbol":      <symbol>,
        "limit_price": <tp_price>,
        "order_qty":   <entry_fill_qty>,
        "post_only":   true,
        "cl_ord_id":   <tp_cl_ord_id>,
        "stp_type":    "cancel_newest",
        "deadline":    <ISO 8601 UTC now + 5s>
      },
      {
        "order_type":  "stop-loss",
        "side":        "sell",
        "symbol":      <symbol>,
        "order_qty":   <entry_fill_qty>,
        "cl_ord_id":   <emg_sl_cl_ord_id>,
        "stp_type":    "cancel_newest",
        "deadline":    <ISO 8601 UTC now + 5s>,
        "triggers":    {
          "reference":  "last",
          "price":      <sl_trigger_price>,
          "price_type": "static"
        }
      }
    ],
    "req_id": <assigned req_id>
  }

  Field notes:
    TP order: post_only=true → resting limit on book.
    emergSL: stop-market. Fires on match with trigger price.
    triggers.reference = "last" (AR-046). MANDATORY.
      Uses Kraken internal last-traded price — always
      available. reference="index" uses external feeds
      that may be unavailable during crash scenarios.
      NEVER rely on API defaults for crash protection.
    stp_type: "cancel_newest" (underscore, WS v2, AR-032).
    deadline: UTC now + 5s on BOTH legs (AR-033).
    batch_add rate cost: +(n/2) = +(2/2) = +1 unit.

  Construction is byte-identical between paper and live
  modes. Dispatch boundary is the WSManager seam.

5.2 Position Mirror Update (0511005)

  Position Mirror updated with actual fill data:
    symbol (key), entry_fill_price (avg_price),
    qty (cum_qty), tp_order_id, tp_cl_ord_id,
    emergSL_order_id, emergSL_cl_ord_id.
  All recorded immediately at batch_add dispatch —
  no async gap (A-2). This is the record-at-dispatch
  rule: TothBot knows the orders exist before Kraken
  confirms them.

  In paper mode, tp_order_id and emergSL_order_id carry
  the prefix "PAPER_TP_" / "PAPER_SL_" per 0511001 dv1_5
  §13.2. In live mode, IDs are the Kraken-assigned values
  from the batch_add ACK. Both populate Position Mirror
  via the same pm.update_resting_orders() pathway per
  §5A EE-PAPER-003.

5.3 BoundedSemaphore Acquisition (AR-043)

  Execution Engine acquires asyncio.BoundedSemaphore
  before entry dispatch. Released by Exit Controller
  on position close. On CIATS max_concurrent update:
  recreate semaphore, re-acquire for all open positions.
  BoundedSemaphore raises ValueError on over-release
  (bug detection). Identical behavior in paper and live.

============================================================
5A. PAPER MODE EXECUTION BEHAVIOR (EE-PAPER) — NEW dv1_1
============================================================

This section specifies how the Execution Engine behaves
in paper mode. Per TB00000 v2_20 §4.4 PA-001..010
PAPER-AS-MASTER and 0500000 dv1_24 §12 Paper-Mode
Dispatch Boundary Architecture, paper trading is the
empirically-validated master configuration; live trading
is built to MIMIC paper. Outside the four PA-004
divergence points (private WS connection; order dispatch;
capital ledger; Position Mirror sourcing), paper and live
operation MUST be byte-identical (PA-005).

The Execution Engine sits ABOVE the WSManager dispatch
seam per 0500000 dv1_24 §12.3. EE does NOT participate in
mode selection. EE does NOT inspect mode state. EE
constructs Kraken WS v2 messages identically in both
modes and hands them to WSManager seam methods, which
gatekeep the paper-vs-live behavioral divergence.

------------------------------------------------------------
5A.1 Architectural Principle
------------------------------------------------------------

EE-PAPER-001  PAPER-LIVE BYTE-IDENTICAL EE PATH.

           The Execution Engine code path is byte-
           identical between paper and live modes. Every
           cl_ord_id assignment, every req_id assignment,
           every add_order construction, every batch_add
           construction, every pending_orders update,
           every Position Mirror update, every rate
           counter attribution, every log emission, and
           every BoundedSemaphore acquire/release in the
           Execution Engine MUST execute identically
           regardless of mode. Mode-conditional branching
           in the Execution Engine is PROHIBITED per
           HR-EE-013.

           The ONLY physical divergence between paper
           and live, viewed from the Execution Engine,
           is the SOURCE of the entry-fill confirmation
           (per EE-PAPER-004) and the underlying transport
           of the constructed WS v2 message (per
           EE-PAPER-002). Both divergences are absorbed
           by the WSManager seam per 0500000 dv1_24 §12.3
           and are invisible to the Execution Engine.

           Per 0500000 dv1_24 §12.2: "Execution Engine
           does NOT read [paper_trading_mode] directly.
           Calls WSManager order methods. Per HR-EE-013,
           EE has NO mode-conditional branching."

EE-PAPER-002  ENTRY DISPATCH MODE-OPACITY.

           The Execution Engine calls WSManager.add_order()
           to dispatch entry orders. The seam method is
           mode-opaque to the caller per 0500000 dv1_24
           §12.3 CALLER CONTRACT:

             PAPER MODE (self.paper_mode == True):
               WSManager gates at entry, logs
               PAPER_ORDER_SIMULATED, schedules
               _simulate_entry_fill via
               asyncio.create_task, and returns WITHOUT
               calling _send_private().

             LIVE MODE (self.paper_mode == False):
               WSManager constructs the Kraken WS v2
               message per AR-006 and calls
               _send_private() to transmit.

           The Execution Engine receives identical
           post-conditions in both cases:
             - cl_ord_id is registered with WSManager for
               callback.
             - Pending Order Registry is populated.
             - ENTRY_DISPATCHED log record is emitted by
               EE (mode-agnostic event).
             - The entry fill callback path is invoked
               on completion (asyncio.create_task in
               paper; executions channel in live;
               EE-PAPER-004 governs).

           The Execution Engine MUST NOT inspect the
           return value to determine mode. The
           Execution Engine MUST NOT hold a reference to
           ws_manager._ws_private. The Execution Engine
           MUST NOT construct a Kraken order JSON
           message and pass it to any send method other
           than the WSManager seam (HR-EE-014).

EE-PAPER-003  BATCH_ADD POSITION MIRROR PARITY.

           The Execution Engine calls WSManager.batch_add()
           on confirmed full entry fill to dispatch the
           atomic TP + emergSL pair. The seam method is
           mode-opaque per EE-PAPER-002.

             PAPER MODE: WSManager populates Position
             Mirror with synthetic order IDs prefixed
             "PAPER_TP_" / "PAPER_SL_" per 0511001 dv1_5
             §13.2 and logs PAPER_BATCH_ADD_SIMULATED.
             No outbound Kraken transmission.

             LIVE MODE: WSManager constructs the batch_add
             message per AR-007 and calls _send_private().
             Kraken-assigned order IDs populate Position
             Mirror on batch_add ACK.

           The Execution Engine receives identical
           post-conditions in both cases:
             - Position Mirror entry has tp_order_id,
               tp_cl_ord_id, emergSL_order_id,
               emergSL_cl_ord_id populated via the same
               pm.update_resting_orders() pathway.
             - TP_EMGSL_DISPATCHED log record is emitted
               by EE (mode-agnostic event).
             - The position is now under multi-layer
               exit governance per the Exit Controller.

           Position Mirror updates on batch_add are
           ATOMIC at dispatch (record-at-dispatch rule,
           A-2). This atomicity is preserved in both
           modes — the WSManager seam is responsible for
           ordering ledger and Mirror updates correctly
           (per 0511001 dv1_5 §13.2 and 1011002 dv1_26
           §16A).

EE-PAPER-004  ENTRY FILL CALLBACK MODE-OPACITY.

           The Execution Engine receives entry fill
           confirmations via a single mode-agnostic
           callback path. The originating event differs
           by mode; the callback signature and downstream
           handling are byte-identical:

             LIVE MODE: executions channel exec_type=filled
               event arrives via private WS. WSManager
               routes it to the EE entry fill handler with
               (symbol, cum_qty, avg_price, fees, cl_ord_id).

             PAPER MODE: WSManager._simulate_entry_fill
               (an asyncio.create_task scheduled from
               WSManager.add_order in paper mode) invokes
               the same EE entry fill handler with
               (symbol, qty=full_qty, price=entry_limit_price,
               fees=0_or_synthesized, cl_ord_id). Per
               1011002 dv1_26 WM-PAPER-LEDGER-002, the
               WSManager applies the synthetic ledger
               entry-fill debit BEFORE invoking the EE
               callback so that downstream EE Phase 2
               batch_add construction sees a consistent
               capital state.

           The Execution Engine MUST NOT branch on the
           originating source of the fill. The handler
           reads (symbol, cum_qty, avg_price) from the
           callback arguments and proceeds to Phase 2
           batch_add dispatch (§5).

           Per 0500000 dv1_24 §12.3 CALLER CONTRACT:
           "On entry order add_order: a cl_ord_id is
           registered for callback. In paper, a simulated
           fill arrives via asyncio.create_task. In live,
           an executions message arrives via the private
           WS. Both result in the same ENTRY_FILLED log
           record and the same Phase 2 batch_add
           invocation."

EE-PAPER-005  fees_entry_usd CAPTURE PARITY.

           Per 1011002 dv1_26 WM-PAPER-LEDGER-002, the
           PositionRecord captures fees_entry_usd at
           entry-fill time so that Exit Controller's
           _close_position can compute net P/L on close
           (per 0511004 dv1_3 §6A EC-PAPER-004 and 1011005
           dv1_3 EC-PAPER-CODE-003(a)). This field is
           populated in BOTH modes:

             PAPER MODE: WSManager._simulate_entry_fill
             populates fees_entry_usd from
             (entry_qty * entry_price * FEE_MAKER_PCT)
             per WM-PAPER-LEDGER-002.

             LIVE MODE: The EE-driven entry fill handler
             populates fees_entry_usd from the
             executions channel exec_type=filled event's
             fees field (Kraken-reported maker fee).

           The Execution Engine handler MUST populate
           fees_entry_usd in the PositionRecord on every
           entry fill in both modes. Failure to do so in
           live mode is a defect that breaks PA-005
           byte-identical CIATS data flow. Per 1011005
           dv1_3 EC-PAPER-CODE-003(a), Exit Controller
           does NOT recompute entry fees — they are
           consumed from PositionRecord on exit.

------------------------------------------------------------
5A.2 What This Section Does NOT Change
------------------------------------------------------------

  - Phase 1 entry order dispatch (§3) is unchanged. EE
    constructs add_order identically in both modes.
  - Entry order outcomes (§4) are unchanged. The
    callback signature is mode-opaque per EE-PAPER-004.
  - Phase 2 batch_add construction (§5) is unchanged.
    EE constructs batch_add identically in both modes.
  - Rate counter summary (§6) is unchanged. EE
    attributes +1 unit to add_order, +1 unit to
    batch_add in both modes; CIATS rate-counter
    telemetry consumes the attribution.
  - Hard rules HR-EE-001 through HR-EE-012 are
    unchanged.
  - Live-mode behavior is unchanged.
  - Log emissions §10 are unchanged. EE emits
    ENTRY_DISPATCHED, ENTRY_ACCEPTED, ENTRY_FILLED, etc.
    These are mode-agnostic events. PAPER_* events
    (PAPER_ORDER_SIMULATED, PAPER_BATCH_ADD_SIMULATED,
    PAPER_LEDGER_UPDATED, etc.) are emitted by WSManager
    at the dispatch seam per 0500000 dv1_24 §12.6 — NOT
    by the Execution Engine.

============================================================
6. RATE COUNTER SUMMARY (per action type)
============================================================

  add_order (entry):          +1 fixed
  batch_add (TP + emergSL):   +1 fixed (n/2 = 1)
  cancel_order (< 300s old):  +1 per cancel
  cancel_order (< 10s old):   +6 per cancel
  cancel_order (< 5s old):    +8 per cancel
  amend_order (< 5s old):     +1 fixed + 3 = +4 total
  amend_order (< 10s old):    +1 fixed + 2 = +3 total
  amend_order (< 15s old):    +1 fixed + 1 = +2 total
  amend_order (>= 15s old):   +1 fixed
  Rate counter ceiling: maxratecount from subscription ACK.
  Decay: 2.34 units/second.

  Rate counter attribution is mode-agnostic per
  EE-PAPER-001. CIATS rate-counter-by-pair telemetry
  consumes the attribution identically in both modes.

============================================================
7. INTERFACES
============================================================

7.1 From Signal Pipeline (0511002)
  Receives Gate 8 output dict.
  Triggered on full 8-gate pipeline pass.

7.2 From WS Manager (0511001)
  Receives executions fill events routed from dispatch
  table (live mode) OR _simulate_entry_fill callbacks
  (paper mode), via the same EE entry fill handler
  signature per §5A EE-PAPER-004. Execution Engine
  handlers called by WS Manager.

7.3 To WS Manager (0511001)
  Returns constructed WS v2 messages for dispatch via
  the WSManager dispatch seam (add_order, batch_add,
  cancel_order, amend_order, batch_cancel,
  dispatch_market_sell). The seam is the SOLE
  gatekeeper of paper-vs-live behavioral divergence
  per 0500000 dv1_24 §12.3 and HR-EE-014.

7.4 To Position Mirror (0511005)
  Updates Position Mirror on batch_add dispatch.
  WS Manager is the physical writer — Execution Engine
  provides data. fees_entry_usd is captured on entry
  fill per §5A EE-PAPER-005.

7.5 To Logger (0511006)
  All dispatch events, fill confirmations, rejections,
  and rate counter data logged (non-blocking). EE log
  records are mode-agnostic per §5A.2 and 0500000 dv1_24
  §12.6.

7.6 To CIATS EWMA Monitor
  rejection_rate_by_regime updated on post_only rejection.
  rate_counter_by_pair updated on each order action.
  CIATS data flow is mode-agnostic per PA-005.

============================================================
8. HARD RULES
============================================================

HR-EE-001  post_only=true on ALL entry add_order. No entry
           may be placed as a taker order.

HR-EE-002  stp_type="cancel_newest" (underscore) on ALL WS
           v2 add_order and batch_add (AR-032). REST uses
           hyphen. Never confuse the two.

HR-EE-003  deadline = UTC now + 5 seconds (ISO 8601) on ALL
           add_order and batch_add (AR-033).

HR-EE-004  triggers.reference = "last" on ALL emergSL
           stop orders in batch_add (AR-046). MANDATORY.
           Never use reference="index". Never omit.

HR-EE-005  TP and emergSL placed via batch_add atomic on
           fill. OTO conditional orders: REJECTED (AR-008).
           OTO uses limit price not fill price — violates
           sacred R:R.

HR-EE-006  cl_ord_id assigned at dispatch BEFORE Kraken
           response. Position Mirror cl_ord_id recorded
           at same moment — no async gap (A-2).

HR-EE-007  Pending Order Registry populated on every
           add_order dispatch. Cleared on filled, expired,
           or canceled (with cum_qty == 0) (AR-053).

HR-EE-008  All Decimal values: Decimal(str()) conversion
           on all WS message numeric fields (AR-047).

HR-EE-009  net_gain = net_loss * 1.5 is HARDCODED in Phase 1
           Gate 8 sizing. Not a parameter. Not CIATS-owned.

HR-EE-010  entry_qty_quantized >= qty_min AND
           entry_qty * price >= cost_min MUST be validated
           before dispatch. Failure: log, skip pair (AR-028).

HR-EE-011  amend_order is the primary order amendment method.
           edit_order is DEPRECATED and MUST NOT be used
           (AR-018).

HR-EE-012  Execution Engine does NOT send cancel_all_orders
           _after under any circumstance (AR-055).

HR-EE-013  PAPER-LIVE BEHAVIORAL PARITY (NEW dv1_1).
           Execution Engine has NO mode-conditional
           branching. Paper and live execute byte-
           identical EE code paths in every method,
           every loop, every callback, every log
           emission, every Position Mirror update, and
           every BoundedSemaphore acquire/release. The
           paper-vs-live behavioral divergence is
           absorbed by the WSManager dispatch seam per
           0500000 dv1_24 §12.3 and is invisible to the
           Execution Engine. Per TB00000 v2_20 §4.4
           PA-005 byte-identical paper-live outside
           PA-004 four divergence points. Closes parent-
           spec layer of TB00148 cluster 1 audit
           findings 09, 29, 30 (paper-mode dispatch
           seam undefined). Cascaded to 1011004 dv1_0
           HR-EE-013 (existing rule; binding update from
           D-06 / PT-MODE-005 / HR-PT-008 to v2_20 §4.4
           + 0500000 dv1_24 §12 is OUT OF SCOPE for
           this amendment per RR-SCOPE-002).

HR-EE-014  NO DIRECT PRIVATE-WS ACCESS (NEW dv1_1).
           Execution Engine MUST NOT:
             (a) Hold a reference to
                 ws_manager._ws_private.
             (b) Construct a Kraken order JSON message
                 and transmit it via any path other
                 than a WSManager seam method
                 (add_order, batch_add, cancel_order,
                 amend_order, batch_cancel,
                 dispatch_market_sell).
             (c) Bypass the WSManager seam by calling
                 private helpers (e.g., _send_private)
                 on WSManager.
           ALL Execution Engine outbound order
           operations MUST pass through the seam. Per
           0500000 dv1_24 §12.3 NO DIRECT PRIVATE-WS
           ACCESS BY ANY OTHER MODULE. Violation is a
           session-halting defect under PA-001 (paper
           is master) and HR-WM-023 (paper-mode
           dispatch isolation).

HR-EE-015  MODE-OPAQUE CALLER CONTRACT (NEW dv1_1).
           Execution Engine treats every WSManager seam
           method as mode-opaque. EE MUST NOT:
             (a) Read paper_trading_mode anywhere in EE
                 code.
             (b) Read ws_manager.paper_mode anywhere in
                 EE code.
             (c) Inspect the return value or post-
                 conditions of a seam method to infer
                 the mode.
             (d) Branch on mode to alter dispatch
                 behavior, log emission, Position
                 Mirror handling, or callback handling.
           Post-conditions of each seam method are
           identical in both modes per 0500000 dv1_24
           §12.3 CALLER CONTRACT. Per 0500000 dv1_24
           §12.2 WHO READS IT: "Execution Engine: Does
           NOT read directly. Calls WSManager order
           methods. Per HR-EE-013, EE has NO mode-
           conditional branching."

1. System Identity and Mission

1.1 What TothBot Is

TothBot is an automated cryptocurrency spot trading system on Kraken exchange. It runs
24/7/365 on a Hetzner VPS, processes 5-minute OHLC candle close events as its system
clock, and executes direction-symmetric LONG and SHORT trades via the parallel Long_Module / Short_Module framework (long on Kraken spot, short on Kraken margin per ar:AR-009) using a momentum-based signal engine.

TothBot is not an external system connected to Kraken — it IS Kraken's event processor.
Every action is a response to a Kraken push event. No timers. No polling. Idle and silent
until Kraken speaks.

1.2 The One Organism Principle

Three functional zones, one organism:
Kraken: generates events, executes orders, holds resting off-book emergency SL
stop orders on matching engine
TothBot: processes Kraken events, executes trading strategy, manages positions
CIATS: learns from event records, continuously improves processing rules

PRIMARY MISSION: Maximize profit. Minimize loss. With an emphasis on minimizing loss.
Loss prevention takes priority over profit generation. Everything else is secondary.

2.4 WS Operational Requirements (A-1 through A-10)

A-1 Rate counter monitoring via executions channel:
executions subscription accepts ratecounter:true. Real-time rate counter per pair
included at zero additional connection cost. CIATS EWMA Monitor adds
rate_counter_by_pair as third monitoring signal.

A-2 req_id and cl_ord_id on all outbound WS messages:
All outbound messages carry req_id (client-specified integer). All add_order and
batch_add additionally carry cl_ord_id (up to 18 characters). TothBot assigns
cl_ord_id at dispatch time before Kraken response. Position Mirror records cl_ord_id
immediately at dispatch — no async gap. WS Manager maintains pending-request registry. cl_ord_id and req_id MUST each be unique per outstanding order - they are the correlation keys used to bind acknowledgements and fills to the originating order, so a collision misattributes a fill. The uniqueness-achieving construction scheme (e.g. symbol prefix + millisecond timestamp) is an implementation choice, not architecture.

A-3 Round-trip latency monitoring and WS reconciliation:
All WS v2 responses include time_in and time_out to nanosecond precision. Logger
records these fields. CIATS EWMA Monitor adds ws_roundtrip_latency_ms. executions
channel supports snap_orders:true on subscription — preferred over REST GetOpenOrders
for restart reconciliation.

A-4 stp_type:cancel_newest on all WS v2 add_order and batch_add calls:
All add_order and batch_add include stp_type:cancel_newest [WS v2 underscore format].
REST API uses cancel-newest [hyphen] — different protocols, different formats (A-20).
Self Trade Prevention prevents TothBot from inadvertently filling against its own
resting orders.

A-5 Reconnect behavior distinction:
(1) Random drop: reconnect instantly, up to a handful of attempts.
(2) After confirmed trading engine maintenance: minimum 5-second delay.
Both implemented as separate paths in WS Manager.

A-6 OTO conditional orders — REJECTED:
OTO uses limit price not actual fill price — violates sacred R:R. Creates Position
Mirror race condition. batch_add on fill confirmed correct. See AR-008.

A-7 WS Ping / Keepalive Strategy:
Kraken WS server disconnects after ~60 seconds of inactivity. Cloudflare idle
timeout ~100 seconds. WS Manager MUST send {"method":"ping"} on each active
connection every 30 seconds. Expects {"method":"pong"} within 10 seconds. No pong
within 10 seconds = dead connection. Reconnect immediately. Application-level ping,
distinct from TCP keepalive.

A-8 Zombie Connection Detection:
A WS connection can appear alive (ping/pong passing) while delivering no real market
data. WS Manager MUST track last_real_data_time per connection using time.monotonic().
Only actual market data events reset this timestamp — heartbeat messages alone do NOT.
If elapsed > 90 seconds: log ZOMBIE_CONNECTION_DETECTED, alert operator, reconnect.

A-9 Balances Channel Sequence Gap Detection:
Every balances channel message carries a sequence integer. WS Manager MUST track
last-seen sequence. Any gap (skip > 1) indicates a missed ledger event. On gap:
alert immediately, trigger REST GetAccountBalance reconciliation. Missed balance
events cause incorrect available capital calculation — direct loss risk.

A-10 Executions Channel Sequence Gap Detection:
Every executions channel message carries a sequence integer. WS Manager MUST track
last-seen sequence independently of balances. Any gap (skip > 1) indicates missed
order/fill events. On gap: alert immediately, trigger REST GetOpenOrders reconciliation
to restore Position Mirror accuracy. Missed execution events mean TothBot does not know
a position is open or closed — direct loss risk. Higher severity than A-9 (balances):
a missed fill leaves Position Mirror in stale state; the next pipeline evaluation
operates on incorrect position data. Sequence tracking resets on each new subscription
(reconnect). Do not gap-detect across sessions.

A-11 Executions Channel: cancel_reason Deprecated — Use reason Field:
The cancel_reason field in executions channel events is DEPRECATED since WS v2.0.0
(December 2023). All code parsing cancellation events MUST read msg["reason"], not
msg["cancel_reason"]. cancel_reason returns None on all modern messages. Silent
reason loss corrupts CIATS EWMA rejection_rate_by_regime monitoring accuracy.

A-12 Executions Channel: Complete exec_type Enum Handling Required:
WS Manager MUST handle all exec_type values: pending_new, new, trade, filled,
iceberg_refill, canceled, expired, amended, restated, status. Using a partial
dispatch table causes unknown exec_type events to silently fall through. Use
handle_exec_unknown for unrecognized values — log full payload, never silently ignore.
TothBot primary events: trade (trigger batch_add), filled, expired (log entry-order expiry — IOC unfilled remainder),
canceled (log with reason). amended and restated: log only, no Position Mirror change.

A-13 Executions Channel: restated exec_type Must Not Trigger Position Change:
restated fires when Kraken's matching engine amends an order for maintenance purposes.
It is NOT a fill, NOT a cancel, NOT a user action. On restated: (1) log with reason
field, (2) alert operator (informational), (3) do NOT update Position Mirror, (4) if
the restated order is the resting emergSL, escalate to HIGH severity alert and
queue a reconciliation check on the next pipeline cycle. The restated event on a
resting crash-protection order indicates Kraken modified our stop — must be visible.

A-14 Spot REST Authentication: Confirmed Unchanged — PL-014 RESOLVED:
The October 1, 2025 authentication breaking change applied to Futures REST ONLY.
Kraken Spot REST authentication is UNCHANGED: HMAC-SHA512 of (URI path + SHA256
(nonce + POST data)) using base64-decoded secret. No code changes required.
PL-014 is fully resolved. No Bill verification action required.

A-15 Executions Channel: order_status:true MANDATORY — GAP-A CRITICAL FIX:
Without order_status:true in the executions subscription, the channel only delivers:
new, filled, canceled, expired. The exec_types amended and restated are SILENTLY DROPPED.
This means: (1) A-13 restated protection for crash-protection orders is completely non-
functional without this flag — the restated event never arrives. (2) A-12 dispatch table
handles 10 exec_types but receives only 4. The subscription is already specified correctly
(WS-EXE-001) but this architectural consequence must be explicitly documented.

A-16 OHLC Channel: interval_begin Replaces Deprecated timestamp — GAP-B:
The Kraken WS v2 OHLC channel deprecated the timestamp field. Subscription ACK warns:
"timestamp is deprecated, use interval_begin". TothBot MUST parse interval_begin
(RFC3339 nanosecond string) as the candle start time, not timestamp.

A-17 Instrument Channel: price_increment / qty_min / cost_min — GAP-C/D:
(GAP-C) The instrument channel deprecated tick_size. Use price_increment exclusively.
Subscription ACK warns: "tick_size is deprecated, use price_increment".
(GAP-D) The instrument channel provides qty_min (minimum order quantity) and cost_min
(minimum order cost = price × qty). Gate 8 Position Sizer MUST validate both before
submitting any add_order. Violation causes immediate order rejection.

A-18 WebSocket Library max_size = 10MB — GAP-E:
Python websockets library default max_size = 1MB. The Kraken instrument channel
snapshot for 500+ pairs can exceed 1MB, causing PayloadTooBig and silent disconnect.
All WS connect() calls MUST set max_size=10*1024*1024 (10MB) and open_timeout=10.

A-19 maxratecount from Executions ACK is Operative Rate Threshold — IMP-11:
The executions subscription ACK returns maxratecount — the actual operative rate
counter ceiling for this user tier. TothBot MUST extract and use maxratecount as the
operative threshold for all rate counter monitoring, not the hardcoded value 125.
If tier changes, maxratecount automatically updates on next reconnect.

A-20 stp_type Format CORRECTION — WS v2 Uses Underscore, Not Hyphen:
Official Kraken WS v2 documentation and batch_add examples use underscore format:
cancel_newest, cancel_oldest, cancel_both
REST API uses hyphen format: cancel-newest, cancel-oldest, cancel-both.
These are DIFFERENT protocols with DIFFERENT formats. All WS v2 outbound messages
(add_order, batch_add) MUST use the underscore format. Using the hyphen format in
WS v2 will cause order rejection or silent failure (ar:AR-032).

A-21 deadline Parameter on All WS v2 Order Submissions:
Both add_order and batch_add support a deadline parameter: an ISO 8601 UTC
timestamp string. The engine rejects any order arriving after this time.
Valid range: 500ms to 60 seconds from current time. Default: 5 seconds.
TothBot standard: deadline = current UTC time + 5 seconds.
Provides protection against stale order placement due to network delay or
event loop pauses. Without deadline, a delayed add_order could place an entry
at a price that has already moved adversely.
CRITICAL: deadline also applies to batch_add. A delayed batch_add with incorrect
emergSL prices due to fill price slippage is prevented by deadline enforcement.
Generate: deadline = (datetime.utcnow() + timedelta(seconds=5)).strftime(
'%Y-%m-%dT%H:%M:%S.%f')[:-3] + 'Z'

A-22 aiohttp ClientSession Timeout and Connector Configuration:
All REST calls use a single shared aiohttp.ClientSession with explicit timeout and
connector configuration. Without explicit timeout, REST calls can hang indefinitely
if Kraken REST servers become unresponsive. This blocks the asyncio event loop
for aiohttp operations and starves other tasks.
Required configuration:
timeout = aiohttp.ClientTimeout(total=10, connect=5, sock_read=8)
connector = aiohttp.TCPConnector(limit=10, limit_per_host=5, force_close=False)
session = aiohttp.ClientSession(timeout=timeout, connector=connector)
total=10: maximum 10 seconds for complete request (connect + send + read).
connect=5: maximum 5 seconds to establish TCP connection.
sock_read=8: maximum 8 seconds waiting for server response after sending.
force_close=False: enables HTTP keepalive — connection reused across calls.
Assign to 1011001 BP-HTTP-001 through -004.

A-23 Ticker event_trigger per Position State:
The ticker channel event_trigger parameter controls when updates are published.
event_trigger:bbo — fires on every change to best bid or ask price.
event_trigger:trades — fires only when a trade occurs (matching engine event).
For pairs WITH open positions: use event_trigger:bbo.
Rationale: For long positions, the bid price is the realizable exit price.
bbo fires immediately when the bid drops, giving the Exit Controller maximum
reaction time to detect MAE threshold breach. trades-only can miss bid drops
that occur without a matching trade.
For pairs WITHOUT open positions: use event_trigger:trades.
Rationale: Reduces unnecessary event volume. Signal pipeline uses last price
not bid, so trades trigger is sufficient for scoring.
WS Manager adjusts per-pair event_trigger when Position Mirror changes state.
Implementation: re-subscribe ticker for that pair with updated event_trigger.

A-24 Regime Engine GetOHLCData Rate Limit Staggering:
REST public GetOHLCData is rate-limited by IP address + currency pair at 1/second.
Calling it for all monitored pairs simultaneously at 00:00 UTC triggers rate limits.
All GetOHLCData calls in the Regime Engine MUST be staggered with asyncio.sleep(1.1)
between each pair to stay below the rate limit ceiling.
Example for 50 pairs: 50 × 1.1s = 55s total. Completes well before first 5m candle
of the new day (~05:00 UTC for the first significant candle after the daily open).
On rate limit error (HTTP 429): exponential backoff, log REGIME_OHLC_RATE_LIMITED,
retry up to 3 times. If all fail: use stale regime (per RE-SCH-004).

2.5 Data Architecture: Pre-Computation Cache (I-2)

HOT PATH RULE: The 5-minute pipeline hot path reads cached values ONLY. No computation
occurs during pipeline evaluation. All indicators maintained as incremental running
calculations updated on each event trigger.

IMP-06 aiohttp Mandatory for All REST Calls:
All Kraken REST calls MUST use aiohttp (async HTTP). Never use the requests library
inside asyncio — it blocks the event loop during the entire call duration. Create one
aiohttp.ClientSession at TothBot startup, reuse for all REST calls, close at shutdown.

IMP-07 asyncio TaskManager Pattern — Mandatory for 24/7 Operation:
All asyncio.create_task() calls MUST store a strong reference AND register a done
callback via task.add_done_callback(task_set.discard). Failure to do so causes memory
leaks in long-running processes: the task set grows indefinitely until OOM. All task
creation routed through a central create_task() helper function. Long-running tasks
(ping, zombie, watchdog) stored as named instance variables, cancelled and awaited
explicitly during reconnect cleanup.

IMP-08 systemd Watchdog Integration — Frozen Process Detection:
TothBot MUST run as a systemd service with WatchdogSec=120 and Type=notify. A
separate asyncio.Task pings systemd sd_notify every 30 seconds via WATCHDOG=1
message. If the event loop hangs (frozen process), the watchdog stops, systemd
detects no ping within 120s, and restarts TothBot. Without this, a frozen-but-alive
TothBot with open positions is undetected indefinitely.
Assign to 0211002 IN-PM-003 + 0211002 IN-PM-004 + D7 systemd-tier visual cluster.

IMP-16 aiohttp ClientSession Timeout — Required for REST Reliability:
All REST calls via aiohttp MUST use explicit timeout and connector configuration.
Without explicit timeout, a degraded Kraken REST server causes asyncio tasks to
hang indefinitely, blocking reconnect/gap recovery sequences.
ClientTimeout(total=10, connect=5, sock_read=8) applied at session creation.
See A-22 for full specification.

IMP-17 aiohttp TCPConnector for Connection Reuse:
TCPConnector(limit=10, limit_per_host=5, force_close=False) enables HTTP keepalive.
Without this, aiohttp closes the TCP connection after every REST call and re-opens
it on the next call. For GetWebSocketsToken (called every reconnect) and
GetOpenOrders (called on gap detection), connection reuse materially reduces latency.
See A-22 for full specification.

IMP-18 Ticker event_trigger:bbo for Open Position MAE Detection:
Pairs with open positions MUST use event_trigger:bbo on ticker subscription.
bbo fires immediately on any best bid/ask price change — not just on trades.
For long positions, bid = realizable exit price. bbo maximizes Layer 2 exit
detection speed. Pairs without open positions use event_trigger:trades.
See A-23 for full specification.

pairs to stay within public REST rate limits. Without stagger, simultaneous calls

3. TothBot Trading Pipeline

The pipeline fires on every 5-minute OHLC candle close event. Synchronous and event-driven.
8 gates.

NOTE — OHLC fires on trade events, not wall clock: If no trades occur after an interval
border, no message sent until next trade. Liquidity Gate ($500k/day) reduces this risk.
Same stall behavior applies to ohlc(60). TothBot must handle stalled system clock.

3.1 Gate Summary 

  PRE-STEP: Parameter Store Snapshot Frozen (I-4)
    CIATS params captured as read-only snapshot at pipeline start. Consistent throughout
    full eval. CIATS writes applied only at inter-trade boundaries.

  PRE-STEP: Pre-Computation Cache Read (I-2)
    Hot path reads: regime cache | 1H EMA cache (ohlc-60) | ATR(14) running value |
    24h liquidity | per-pair status. Zero computation on hot path.

  Per-pair Instrument Status Check
    Skip pairs in reduce_only, work_in_progress, delisted, limit_only,
    cancel_only, or maintenance state.
    Only online pairs proceed into pipeline.
    Prevents wasted rate counter.

  Gate 1: State Machine
    Kraken engine = maintenance or cancel_only: WAIT

  Gate 2: Liquidity Gate ★
    24h volume < $500k USD: SKIP → LIQUIDITY_REJECTED

  Gate 3: Regime Pre-Filter (I-1)
    TRENDING_NEG (any vol) or NON_DIR+ELEVATED: STOP → REGIME_BLOCKED
    Eliminates SSS computation on all no-trade regimes.

  Gate 4: 1H HTF Confirmation ★
    1H EMA(20) <= EMA(50) for TRENDING_POS entries: SKIP → HTF_GATE_REJECTED
    Cache read from the 1H feed DERIVED by folding the ohlc(5m) stream (TB00768 Opt 5:
    Kraken WS v2 refuses a 2nd ohlc interval per symbol per connection).

  SSS Signal Engine
    Scores 5-min candle. Only reached if Gate 3 pre-filter passed.

  Gate 5: Selection Controller
    Signal fails any of 4 quality gates: SKIP → SELECTION_REJECTED

  Gate 6: Regime Gate / Sizer ★
    NON_DIR+NORMAL: 50% position size. All NO ENTRY cases blocked by Gate 3.

  Gate 7: Risk Guard
    Drawdown halt / concentration / exposure. Pass or HALT.
    ★ Ticker-driven continuous drawdown monitoring between candle closes (I-7)

  Gate 8: Position Sizer ★
    MAE = ATR(14) x 1.5x (incremental), emergSL = ATR(14) x 3.0x. A1 floor: admit iff
    expected_reward / net_loss >= 1.5, where expected_reward = CIATS run-to-reversal
    estimate.

  AR-076 ★: RSI(14) uses Wilder's SMMA — NOT standard EMA. Specification correction
                    to AR-068 which stated "EMA-smoothed" — that phrase is ambiguous and points
                    to the wrong algorithm. The correct RSI(14) incremental formula is
                    Wilder's Smoothed Moving Average (SMMA, also called RMA), with α=1/14.
                    This is distinct from standard EMA which uses α=2/(n+1)=2/15.
                    The two produce materially different RSI values (~5-8% variance).
                    A coder reading "EMA-smoothed" would likely implement α=2/15, producing
                    non-standard RSI that does not match any trading platform and would
                    systematically mis-fire the SSS SC-SSS-1 gate (RSI 50-70 condition).

                    CORRECT RSI(14) INCREMENTAL FORMULA (Wilder's SMMA):
                      Seed (first 14 candles):
                        avg_gain = sum(gains[:14]) / Decimal("14")
                        avg_loss = sum(losses[:14]) / Decimal("14")
                      Incremental (each subsequent candle):
                        avg_gain = (prev_avg_gain * Decimal("13") + current_gain) / Decimal("14")
                        avg_loss = (prev_avg_loss * Decimal("13") + current_loss) / Decimal("14")
                      RS  = avg_gain / avg_loss
                      RSI = Decimal("100") - (Decimal("100") / (Decimal("1") + RS))

                    For contrast — standard EMA (WRONG for RSI):
                      alpha = 2/(n+1) = 2/15 ≈ 0.1333  ← DO NOT USE FOR RSI
                      avg_gain = prev_avg_gain * (1 - alpha) + current_gain * alpha

                    STANDARD EMA IS CORRECT for EMA(9) and EMA(21) in SSS Gate 2:
                      EMA(9):  alpha = 2/10 = 0.2000  ← standard EMA, correct
                      EMA(21): alpha = 2/22 = 0.0909  ← standard EMA, correct
                    Only RSI uses Wilder's SMMA. EMA(9) and EMA(21) use standard EMA.
                    Do not conflate the two algorithms.

                    STATE STORED (unchanged from AR-075 — formula clarified only):
                      rsi_14_avg_gain: Decimal  (Wilder SMMA running state)
                      rsi_14_avg_loss: Decimal  (Wilder SMMA running state)

                    EVIDENCE BASE: 10+ independent sources across validation search
                    (TradingView rma(), StockCharts.com, Supra Oracle docs, Wikipedia,
                    LuxAlgo, AlphaRithms, Quantinsti, PineScriptMarket, Medium) all confirm
                    Wilder's SMMA (α=1/n) as the correct RSI formula. A 14-period SMMA is
                    equivalent to a 27-period standard EMA (2×14-1=27), not a 15-period EMA.

12.1 PA-004 Permitted Divergence Points (Paper vs Live)

  DIVERGENCE POINT (1) — PRIVATE WEBSOCKET CONNECTION.

    LIVE:  Connects to Kraken private WS for order dispatch,
           executions reception, balances reception, snap_orders
           reconciliation, ratecounter monitoring, and ping/zombie

    Why:   Paper places no real orders. An authenticated session

           connection that exists for no operational purpose.
    Bind:  HR-WM-022; PT-MODE-003.

  DIVERGENCE POINT (2) — ORDER DISPATCH.
    PAPER: Simulates orders locally inside WSManager. No outbound
           order traffic of ANY kind transmitted to Kraken. Order
           methods (add_order, batch_add, cancel_order, amend_order,
           batch_cancel, dispatch_market_sell) gate at entry and
           return after logging a simulation event.
    LIVE:  Transmits orders to Kraken via private WS using
           _send_private().
    Why:   Paper trading by definition does not move real money.
           The dispatch boundary is the SOLE point at which paper
           mode protects operator capital from being placed at
           risk. Any code path that bypasses this gate violates
           PA-001..010 and is a session-halting defect.
    Bind:  HR-WM-023; PT-MODE-005.

  DIVERGENCE POINT (3) — CAPITAL LEDGER.
    PAPER: Synthetic spot_usd_balance starting at

           simulated-fill P&L applied locally using the SAME fee
           schedule (FEE_MAKER_PCT, FEE_TAKER_PCT) Kraken applies

    Why:   No real capital moves in paper. A synthetic ledger is

12.2 paper_trading_mode Flag — Definition and Lifecycle 

  paper_trading_mode is a single bool configuration parameter that
  selects mode at process start. It is NOT a runtime toggle.
  Switching modes requires a full TothBot process restart.

  CANONICAL VALUE.
    paper_trading_mode = True    -> paper-mode session
    paper_trading_mode = False   -> live-mode session
    Default if absent            -> False (live)

  LIFECYCLE.
    Authoring:  Bill manually sets the flag in the EnvironmentFile
                /root/.tothbot.env BEFORE invoking systemctl start.
    Read:       startup_sequence loads the config dict at
                process boot. paper_trading_mode is extracted and
                passed to WSManager.__init__ as the first
                consumer.
    Storage:    WSManager stores the value as self.paper_mode
                (HR-WM-021). Read once at __init__. NEVER mutated
                during operation. NEVER cached anywhere else.
    Logging:    First message emitted by Logger after startup is
                PAPER_TRADING_MODE_ON or PAPER_TRADING_MODE_OFF.
                Every subsequent log record carries the implicit
                mode-tag of the running process. CIATS Trade
                Outcome Bus records carry paper_trade: bool field
                derived from this mode.
    Termination: Mode persists for the lifetime of the process.
                 Process restart re-reads the config.

  WHY THIS DESIGN. A runtime-toggleable mode flag would create
  a category of defects in which simulated-fill state could
  contaminate live state or vice versa. Architectural risk
  asymmetry resolves to start-time-immutable: any operational
  inconvenience of restarting to switch modes is overwhelmed by
  the catastrophic risk of cross-contamination.

  WHO READS IT.
    WSManager:           Reads at __init__ via constructor argument
                         injected by startup_sequence. Stores as
                         self.paper_mode.
    Execution Engine:    Does NOT read directly. Calls WSManager
                         order methods. Per HR-EE-013, EE has NO
                         mode-conditional branching. Mode is
                         enforced at the WSManager dispatch
                         boundary (12.3).
    Long Module:         Does NOT read directly. Same architectural
                         pattern as EE.
    Exit Controller:     Does NOT read directly. Same architectural
                         pattern. EC's _close_position() close
                         sequence is mode-agnostic; WSManager
                         simulates or transmits the underlying
                         orders per the dispatch gate.
    All other modules:   Do NOT read paper_trading_mode. Mode is
                         not their concern.

  THIS IS A FIRST-PRINCIPLES SIMPLIFICATION. The flag is read
  ONCE, at one location (WSManager.__init__), by ONE module. Every
  other component is mode-blind by architectural intent. This
  eliminates entire defect classes (stale flag reads, divergent
  flag interpretations, mid-session mode flips) by construction.

12.3 The Dispatch Seam — WSManager as Sole Gatekeeper 

  The dispatch seam is the set of WSManager method entry points
  through which ALL outbound order operations MUST pass. WSManager
  is the SOLE gatekeeper. No other module may construct a Kraken
  order message and transmit it directly. No other module may
  call _send_private() on the private WS.

  GATED METHODS (the seam).
    WSManager.add_order()           Phase 1 entry order dispatch.
    WSManager.batch_add()           Phase 2 emergSL single-leg
                                    placement on entry fill.
    WSManager.cancel_order()        Individual cancel for MAE exit.
    WSManager.amend_order()         Sole order-modification method
                                    (ar:AR-018).
    WSManager.batch_cancel()        Full Halt multi-order cancel.
    WSManager.dispatch_market_sell() Market sell for Layer 1a
                                    regime-reversal / Layer 2 MAE exit.

  GATE BEHAVIOR.

    PAPER MODE (self.paper_mode == True):
      Each method gates at entry, logs PAPER_<METHOD>_SIMULATED,
      schedules any required simulation task (e.g.,
      _simulate_entry_fill via asyncio.create_task), updates the
      synthetic ledger or Position Mirror per the appropriate
      paper-mode rule (HR-WM-032 / HR-WM-033), and returns
      WITHOUT calling _send_private(). Per HR-WM-023, calling
      _send_private() in paper mode is a session-halting defect.

    LIVE MODE (self.paper_mode == False):
      Each method constructs the Kraken WS v2 message per the
      relevant AR rule (AR-006 add_order, AR-007 batch_add (emergSL single leg),
      AR-008 emergSL, AR-018 amend_order primary, AR-019
      batch_cancel, AR-032 stp_type underscore, AR-033 deadline,
      AR-046 emergSL trigger, AR-047 Decimal rounding) and calls
      _send_private() to transmit. Returns after dispatch.

  CALLER CONTRACT.

    Every caller of any seam method MUST treat the method as
    mode-opaque. Callers do not know whether the method simulated
    or transmitted. Callers receive identical post-conditions in
    both modes:
      - On entry order add_order: a cl_ord_id is registered for
        callback. In paper, a simulated fill arrives via
        asyncio.create_task. In live, an executions message
        arrives via the private WS. Both result in the same
        ENTRY_FILLED log record and the same Phase 2 batch_add
        invocation.
      - On batch_add: the emergSL price and order ID are
        recorded in PositionMirror via WSManager helpers. In
        paper, IDs carry the prefix "PAPER_SL_". In live, IDs are the
        Kraken-assigned values from the ACK. Both populate
        PositionMirror via the same
        pm.update_resting_orders() pathway.
      - On cancel / amend / batch_cancel / dispatch_market_sell:
        the post-condition is WSManager state mutation (Position
        Mirror, synthetic ledger, ticker event_trigger mode);
        the underlying transmission is invisible to the caller.

  NO DIRECT PRIVATE-WS ACCESS BY ANY OTHER MODULE.

    Execution Engine, Long Module, Exit Controller, Selection
    Controller, Risk Engine, Regime Engine, and all other modules
    MUST NOT:
      (a) Hold a reference to ws_manager._ws_private.
      (b) Construct a Kraken order JSON message and pass it to
          any send method.
      (c) Bypass the seam by calling private helpers on WSManager.

    ANY violation of (a)-(c) is a session-halting defect under
    PA-001 (paper is master) and HR-WM-023 (paper-mode dispatch
    isolation).

12.4 Synthetic Capital Ledger — Single-Owner Architecture 

  In paper mode the spot_usd_balance is a synthetic value
  maintained ENTIRELY inside WSManager. It is NEVER mutated by
  any other module. This single-owner pattern eliminates the
  distributed-write defect class (Position Mirror multi-writer
  ambiguity).

  OWNERSHIP. WSManager is the SOLE writer of spot_usd_balance in
  paper mode. WSManager is the SOLE writer in live mode also (it
  ingests balances channel events from Kraken and applies them).
  This is a paper-live parity property, not a paper-only rule.

  INITIALIZATION (paper mode only).
    spot_usd_balance = paper_starting_balance     # $5,000/module per D-05 (long $5,000 / short $5,000)
    portfolio_baseline_USD = spot_usd_balance     # captured ONCE
                                                  # at startup (HR-WM-011)
    Logger emits PAPER_LEDGER_UPDATED (event_type=INIT).

  ENTRY-FILL DEBIT (paper mode).
    On simulated entry fill at WSManager._simulate_entry_fill (FEE_TAKER_PCT: the marketable-IOC entry fills at taker):
      entry_proceeds = qty * entry_fill_price
      fees_entry = entry_proceeds * FEE_TAKER_PCT
      spot_usd_balance -= (entry_proceeds + fees_entry)
      pos.fees_entry_usd = fees_entry  # required for net P&L on close
      Logger emits PAPER_LEDGER_UPDATED (event_type=ENTRY_FILL).

  EXIT-FILL CREDIT (paper mode).
    On simulated market-sell exit (FEE_TAKER_PCT): all exits close
    at taker (L1a regime-reversal run-to-reversal, L2 MAE, L3
    emergSL; PAIR_LIMIT_ONLY IOC at best_bid):
      exit_proceeds = qty * exit_price
      fees_exit = exit_proceeds * FEE_TAKER_PCT
      spot_usd_balance += (exit_proceeds - fees_exit)
      Logger emits PAPER_LEDGER_UPDATED (event_type=EXIT_FILL).
      Control then yields to Exit Controller per 12.5.

  FEE PARITY. Paper uses identical FEE_MAKER_PCT and FEE_TAKER_PCT
  values to live. Live transitions to actual Kraken fee schedule
  per AR-012 baseline. Paper synthetic ledger arithmetic mirrors
  this exactly (PA-005).

  WHY SINGLE-OWNER. Position Mirror writes from multiple modules
  create a class of races and inconsistencies that no amount of
  locking can fully eliminate. The architectural fix is
  single-writer-by-design: only the module that owns the
  authoritative state may mutate it. WSManager owns
  spot_usd_balance. WSManager owns Position Mirror writes. Other
  modules READ via WSManager helper methods (HR-PM-009
  read-only-via-helpers pattern); they do NOT WRITE.

12.5 Paper Exit Routing Through Exit Controller 

  All paper-mode exit paths route through Exit Controller's
  _close_position() close sequence. This is the
  cornerstone of paper-live CIATS data-flow parity (PA-005).

  EXIT FLOW (paper, all exit reasons identical pattern):
    1. WSManager detects exit condition (L1a regime-reversal --
       HTF_REGIME_REVERSAL or DAILY_REGIME_DOWNGRADE, L2 MAE breach,
       L3 emergSL price breach, or PAIR_LIMIT_ONLY).
    2. WSManager applies HR-WM-032 ledger credit.
    3. WSManager logs PAPER_<EXIT_TYPE>_DETECTED.
    4. WSManager calls
         exit_controller.on_paper_close(symbol, exit_price,
                                        exit_reason, fees_exit, wm)
    5. Exit Controller calls _close_position(...).
    6. Exit Controller emits TRADE_CLOSE log record with full
       P/L payload (entry_price, exit_price, qty, fees_entry_usd,
       fees_exit, net_pnl_usd, mae_pct_reached, vol_regime).
    7. Exit Controller clears Position Mirror.
    8. Exit Controller updates Selection Controller state (loss
       paths increment consecutive_loss_count[symbol] and set
       exit_cooldown_log[symbol]; win paths reset
       consecutive_loss_count[symbol] to 0; AR-073).
    9. Exit Controller releases BoundedSemaphore.
   10. WSManager._update_ticker_event_trigger switches symbol to
       trades-mode (no open position).

  LIVE FLOW (every step identical except origin of step 1):
    Step 1 origin: Kraken executions channel exec_type=filled or
    exec_type=triggered for emergSL.
    Steps 2-10 IDENTICAL to paper flow except no synthetic ledger
    application (real Kraken balances channel applies the credit).

  CIATS PARITY. CIATS log-file polling reads TRADE_CLOSE records
  identically in both modes. The TRADE_CLOSE schema is mode-
  agnostic. CIATS Half-Kelly (CIATS-KE-002), Mann-Whitney U,
  EWMA, CUSUM, Spearman, and Sharpe ratio operate on a unified
  trade corpus. The 200-trade hard floor for statistical inference
  (TB00000 sec 5) accumulates equally in paper and live modes.

  Bind: HR-WM-033; EC-PAPER; WM-PAPER-EXIT-001..005; PT-MODE-006.

12.7 Architectural Diagram — Dispatch Boundary 

  The dispatch boundary at architectural level. All upstream callers
  pass through WSManager seam methods. WSManager applies the
  paper_mode gate. Outbound traffic to Kraken occurs ONLY in live
  mode. All other system flows (public WS, OHLC, indicators,
  pipeline, regime, CIATS data flow) are byte-identical between
  modes per PA-005.

  KEY ARCHITECTURAL OBSERVATIONS.
    (1) The mode gate exists at EXACTLY one place (the WSManager
        seam). Upstream callers are mode-blind.
    (2) The simulation path and the Kraken transmission path
        REJOIN at Exit Controller. From there forward (Exit
        Controller -> Logger -> CIATS) the flow is byte-identical.
    (3) Every synthetic state mutation is owned by exactly one
        module (WSManager). No multi-writer races exist by design.
    (4) Paper-mode telemetry is observable (PAPER_* events) so
        Bill and CIATS can verify boundary integrity continuously.
    (5) The PAPER_DISPATCH_BLOCKED defensive event is the canary
        that confirms NO code path slipped past the gate.

12.10 Hard Rule Registry — Execution Engine Paper-Mode Parity 

  This subsection is the prose-side companion to the diagram-
  side encoding of the triadic HR-EE-013/014/015 paper-as-master
  parity family in D7 (Paper-Mode Dispatch Boundary) root
  governs list. The diagram-side encoding establishes canonical
  authority; this prose registry is the derived prose
  restatement per the cross-document authority hierarchy.

  HR-EE-013  PAPER-LIVE BEHAVIORAL PARITY.
             Execution Engine has NO mode-conditional branching.
             Paper and live execute byte-identical EE code paths
             in every method, every loop, every callback, every
             log emission, every Position Mirror update, and
             every BoundedSemaphore acquire/release. The paper-
             vs-live behavioral divergence is absorbed by the
             WSManager dispatch seam per §12.3
             and is invisible to the Execution Engine. Per
             TB00000 sec 4.3 PA-005 byte-identical paper-live
             outside PA-004 four divergence points.

  HR-EE-014  NO DIRECT PRIVATE-WS ACCESS.
             Execution Engine MUST NOT:
               (a) Hold a reference to ws_manager._ws_private.
               (b) Construct a Kraken order JSON message and
                   transmit it via any path other than a
                   WSManager seam method (add_order, batch_add,
                   cancel_order, amend_order, batch_cancel,
                   dispatch_market_sell).
               (c) Bypass the WSManager seam by calling private
                   helpers (e.g., _send_private) on WSManager.
             ALL Execution Engine outbound order operations
             MUST pass through the seam. Per §12.3 NO DIRECT PRIVATE-WS ACCESS BY ANY OTHER
             MODULE. Violation is a session-halting defect
             under PA-001 (paper is master) and HR-WM-023
             (paper-mode dispatch isolation).

  HR-EE-015  MODE-OPAQUE CALLER CONTRACT.
             Execution Engine treats every WSManager seam
             method as mode-opaque. EE MUST NOT:
               (a) Read paper_trading_mode anywhere in EE
                   code.
               (b) Read ws_manager.paper_mode anywhere in EE
                   code.
               (c) Inspect the return value or post-conditions
                   of a seam method to infer the mode.
               (d) Branch on mode to alter dispatch behavior,
                   log emission, Position Mirror handling, or
                   callback handling.
             Post-conditions of each seam method are identical
             in both modes per §12.3 CALLER
             CONTRACT. Per §12.2 WHO READS IT:
             "Execution Engine: Does NOT read directly. Calls
             WSManager order methods. Per HR-EE-013, EE has NO
             mode-conditional branching."

  TRIADIC FAMILY ARCHITECTURAL ROLE.

  HR-EE-013 establishes behavioral parity (paper and live
  execute byte-identical code). HR-EE-014 establishes the
  parity-required surface (no direct private-WS access — all
  outbound order operations pass through the seam). HR-EE-015
  establishes the caller-contract discipline (mode-opaque —
  EE never reads paper_trading_mode or branches on mode).

  Encoding one rule without the others creates a governance gap.
  The three rules together establish that the dispatch boundary
  is the SOLE point at which paper and live diverge and that
  the Execution Engine above the boundary is fully mode-blind.
  Per TB00000 sec 4.3 PA-001..010 paper-as-master absolute
  standing rule, this triadic encoding is the architectural
  basis for paper-trading data validity for live operation.

  Kraken (§2 Matching Engine): the layer:L3 emergency-SL RESTS off-book on the
  matching engine and SURVIVES any TothBot failure — which is exactly why §2
  REJECTED cancel-on-disconnect / DMS (ar:AR-001): a DMS would DESTROY that resting
  crash protection.

  Bitnomial perps (LIMIT-ONLY): there is NO resting off-book stop to survive a
  crash — the layer:L2 and layer:L3 stops are CLIENT-SYNTHESIZED and enforced only
  while TothBot is alive, so a TothBot crash leaves a NAKED perps position. The
  mitigation INVERTS the Kraken logic: an exchange-side dead-man's-switch /
  kill-switch that FLATTENS on disconnect is PROTECTIVE here, not destructive,
  because it REPLACES the absent resting stop rather than destroying it. This is
  precisely why §13.1 confirm item 4 (REST cancel/modify + kill-switch) GATES live
  connectivity. The sacred 1:1.5 R:R floor is unaffected — it sets the synthesized
  limit exit prices either way.

13.3 Exit Synthesis under Limit-Only — DIRECT-BITNOMIAL FALLBACK ROUTE (demoted at TB00798; primary path = native Kraken stops + §13.7 isolated-margin)

DEMOTED TO FALLBACK (TB00798). On the PRIMARY §13.1 Kraken-Pro route the exit layers are NATIVE exchange orders — Stop-Loss / Take-Profit / Trailing-Stop — backstopped by §13.7 isolated-margin liquidation, so there is NO client-side exit synthesis; this machinery is DELETED from the primary build (a loss-minimization win). This section is PRESERVED — nothing erased — as the documented FALLBACK: the DIRECT-Bitnomial native protocol (BTP / FIX) exposes NO native stop or stop-market primitive, so under THAT route ONLY the §4 exit layers are SYNTHESIZED client-side from limit orders + the §13.2 mark-price watchdog. The §4 layer SEMANTICS are preserved exactly; only the ENFORCEMENT mechanism changes from a resting exchange order to a client-driven marketable limit. Everything below describes that fallback path. 

  SYNTHETIC EXIT MECHANISM (per §4 layer; mark-price watchdog on the §13.2 WS feed)

  layer:L1a regime-reversal exit (primary):
    fires on the 24h bearish-cross event (the mirror of the perps long entry
    trigger) — flatten via a MARKETABLE limit, event-driven, NOT a resting
    take-profit order.

  layer:L2 wide ATR stop (structural):
    NO native stop — the watchdog reads the WS mark each tick; when the mark
    crosses the synthetic L2 level it fires a MARKETABLE limit priced THROUGH the
    book by a bounded number of ticks to maximize fill probability.

  layer:L3 emergency-SL (outermost):
    the synthetic watchdog PLUS the exchange-side kill-switch / dead-man's-switch
    backstop (§13.2 CRASH-PROTECTION INVERSION) — the kill-switch covers the case
    where the watchdog itself is dead (a TothBot crash).

  HONEST CONSEQUENCE — synthetic-stop GAP RISK (stated, not papered over)

  A limit order cannot guarantee a fill at any price. If the mark GAPS past the
  synthetic L2/L3 level between ticks, or the marketable limit does not fill at the
  first price, the realized loss can EXCEED the planned 1R — a genuine degradation
  vs the Kraken matching-engine stop, which becomes a true MARKET order on trigger.

  Mitigations (design intent, refined at code time): tight mark polling; aggressive
  marketable-limit pricing (cross N ticks, N a proposed CIATS seed bounded by the
  §13.1 item-3 tick / lot); a bounded re-price CHASE up to a cap, then escalate to
  the kill-switch; and position sizing that accounts for the worse loss tail. The
  sacred 1:1.5 R:R floor is set at the PLANNED limit exit prices; the realized
  actual_rr (the existing contract:TRADE_CLOSE field) absorbs the bounded slippage
  and is the CIATS-monitored truth.

13.5 Funding / Margin Model — Bitnomial Perps (design intent; pre-spec, gated on the §13.1 confirm-first items)

The perps organism is a CFTC FCM account: margin and funding settle INSIDE the Bitnomial clearing account, with NO spot-wallet doorway. Unlike the §2 Kraken spot-margin short path (where a short borrows against a spot balance and pays the TB00000 sec 8 param:margin_borrow_fee), the perps side never touches a spot wallet — collateral, funding, and variation margin all live in the isolated FCM account (§13.1 ACCESS MODE). This slice documents the 8h funding model, the USDC margin model (§13.1 confirm item 2), and how the CIATS-owned fixed-notional sizing maps onto WHOLE contracts (§13.1 confirm item 3), with the LONG and SHORT sides documented to EQUAL DETAIL. No new namespace token or CIATS seed is minted here: the funding rate and the margin / tick / lot numbers are EXCHANGE-SET and gated by the confirm-first items, the 8h cadence is an engineering constant, and any proposed perps tunable is enumerated at the §13.6 parameter-siting slice. 

  FUNDING MODEL — 8h funding folded into Variation Margin (FCM; no spot doorway)

  Cadence:
    Bitnomial perps settle funding every 8h. The 8h cadence is an ENGINEERING
    CONSTANT (exchange-set), NOT a CIATS seed.

  Mechanism:
    Funding is folded into the Variation Margin accounting (the §13.2 funding-rates
    pull), NOT charged as a separate spot borrow. The funding RATE is EXCHANGE-SET
    (not a TothBot parameter); the realized funding cost folds into perps net P&L
    and into net_loss exactly as the spot-short param:margin_borrow_fee does
    (TB00000 sec 8), so the sacred 1:1.5 net (after-fee) R:R floor absorbs it
    AUTOMATICALLY and is NEVER lowered.

  Long vs Short — the natural sign difference (equal detail):
    LONG  pays funding when the funding rate is POSITIVE, RECEIVES it when negative.
    SHORT is the mirror — RECEIVES funding when the rate is positive, PAYS when
          negative.
    Same mechanism on both sides; only the SIGN of the funding flow differs by side
    and by funding regime. This REPLACES the spot-short per-4h margin rollover
    (param:margin_rollover_fee_pct): on perps BOTH sides settle 8h funding into
    Variation Margin, and NEITHER side pays a Kraken spot-margin rollover.

  MARGIN MODEL — USDC collateral, isolated operator-funded perps wallet

  Collateral:
    USDC as margin collateral (§13.1 confirm item 2 — pending Bitnomial
    confirmation; RLUSD + BTC/ETH/XRP are the confirmed first-class collateral,
    USDC is the open item).

  Wallet:
    Per TB00000 sec 7 parallel modules, the perps organism holds its OWN
    operator-funded margin wallet — what Bill can afford to lose on the perps side,
    the primary loss control — isolated from the spot Long/Short module wallets
    (§13.1 ACCESS MODE hot-path isolation). CIATS observes the USDC margin balance
    and sizes against it; it does NOT own the balance.

  Initial / maintenance margin:
    Per-contract initial + maintenance margin is EXCHANGE-SET and not publicly
    disclosed (§13.1 confirm item 3). Sizing reads the live per-contract margin so a
    position never exceeds the module wallet — the wallet balance is the SOLE sizing
    boundary (TB00000 sec 7), the same rule on both sides.

  CONTRACT SIZING — fixed notional onto WHOLE contracts (LONG and SHORT, equal detail)

  Target notional:
    The CIATS-owned fixed-notional sizing is UNCHANGED — per_trade_size_usd =
    max(50, 5 x max(costmin, ordermin x entry_limit_price)) (TB00000 sec 8). It sets
    a target DOLLAR notional per trade (~$50+ floor), NOT a risk-based 1R: the wide
    layer:L2 stop only sets the exit price, so the realized $ risk per trade varies
    with the stop width.

  Quantization onto contracts:
    Each Bitnomial perp contract is a fixed underlying multiplier x mark price = a
    per-contract notional. Contracts = floor(target_notional / per_contract_notional),
    snapped to the exchange lot increment (§13.1 confirm item 3). WHOLE contracts only
    — fractional perps do not exist, so the realized notional is the nearest whole-
    contract value at or below the target.

  Per-product floor raise (no new seed):
    If a SINGLE contract notional EXCEEDS the $50 target (a high-multiplier product),
    the fixed-notional floor is RAISED for that product to buy at least 1 whole
    contract — the existing per_trade_size_usd raise-per-product behaviour (TB00000
    sec 8), NOT a new seed. A product whose 1-contract notional is unaffordable for
    the perps wallet is EXCLUDED from the perps universe.

  Equal detail, both sides:
    The sizing MECHANISM is IDENTICAL for LONG and SHORT — both map the same
    fixed-notional target onto whole contracts against the same USDC margin wallet.
    The metric DIFFERENCE between sides lives in the §13.4 entry / stop / exit logic,
    NOT in funding, margin, or sizing.

13.7 Wallet / Isolation Model — Three Separately-Funded Pools (TB00798; Long Spot / Long Perp / Short Perp)

The perps organism is funded as THREE separately-funded, ring-fenced pools — Long Spot, Long Perp, and Short Perp — ratified by Bill at TB00798. This is the wallet-isolation realization of the §13.1 First-Principles property that venue isolation be a FUNDING boundary, not a direct-venue connection: separately-funded pools give the isolation the old direct-Bitnomial route was chosen to buy, while the §13.1 Kraken-Pro route keeps native server-side stops + isolated-margin liquidation. Each pool is its own TB00000 sec 7 module. The LONG and SHORT perp pools are documented here to EQUAL DETAIL. 

  THE THREE POOLS — separately funded, ring-fenced (TB00798 wallet model)

  Pool 1 — LONG SPOT (the live-in-paper spot organism):
    Its OWN full Kraken account. Kraken permits multiple full accounts and NAMES
    conflicting strategies / multiple bots / separating margin as legitimate uses.
    Physically isolated from the perps stack — a different account entirely.

  Pool 2 — LONG PERP, and Pool 3 — SHORT PERP:
    TWO LINKED DERIVATIVES SUBACCOUNTS under the perps stack. Derivatives subaccounts
    are open to ANY eligible client — UNLIKE spot subaccounts, which are institutional-
    only (this corrected an earlier wrong assumption that retail cannot hold
    subaccounts). Each has its OWN balance / margin / liquidation / API keys / rate
    limits, and one subaccount's liquidation CANNOT reach another's — a true
    ring-fence. The US Derivatives Client Agreement FORBIDS multiple UNLINKED
    derivatives accounts, so a SUBACCOUNT structure is the PRESCRIBED mechanism here,
    not a workaround.

  Isolation summary:
    Between SPOT and PERPS the isolation is PHYSICAL — separate full accounts.
    Between LONG-PERP and SHORT-PERP the isolation is SUBACCOUNT-ENFORCED — linked subs.
    Each pool = its own TB00000 sec 7 module: its own CIATS instance, its own
    operator-funded wallet, its own halts. Funded with only what Bill can afford to
    lose on THAT side — the primary loss control, per pool.

  ISOLATED-MARGIN LIQUIDATION — the crash-proof loss cap (§13.1 FP/DP primary path)

  Each perp pool runs in ISOLATED-margin mode, NOT cross: only the margin posted to a
  position is at risk, and the EXCHANGE liquidates the position when that isolated
  margin is exhausted. Sized at ~ the maximum intended loss, this liquidation IS the
  crash-proof loss cap — it is EXCHANGE-resident and fires whether or not TothBot is
  alive, which is exactly the First-Principles property §13.1 requires. It sits UNDER
  the native L2 / L3 stops (§13.1 ORDER MODEL): the native stops do the ordinary
  risk-managed exit at the 1:1.5-floor prices; isolated-margin liquidation catches the
  TAIL if a stop fails to fire or TothBot is dead. The sacred 1:1.5 R:R floor is
  unaffected and is NEVER lowered.

  CIATS RULE TO ADD — no same-instrument long+short collision (both sides, equal detail)

  Because Long Perp and Short Perp trade the SAME futures venue, a simultaneous LONG
  and SHORT on the SAME instrument (both in PBTCUC, say) would NET against each other
  inside ONE futures engine — defeating the ring-fence and wasting margin. New CIATS
  rule: NO same-instrument long+short open at once across the two perp pools. The rule
  is SYMMETRIC by construction — it binds the Long-Perp CIATS and the Short-Perp CIATS
  identically (equal detail). Different instruments on opposite sides are fine; only
  the SAME base_symbol is blocked from simultaneous long+short.

  FALLBACK — if US-perp retail subaccounts are NOT live (the one open Kraken item)

  The one genuinely non-public question (§13.1 confirm gate) is whether a retail
  derivatives SUBACCOUNT structure is wired into the US-Bitnomial perps stack. A Kraken
  support ticket settles it; Bill may ping Kraken. If the answer is NO:
    Both perp sides run in ONE Futures wallet under ISOLATED margin PER POSITION, with
    the Long / Short separation enforced by CIATS accounting — per-side ledgers, per-side
    wallet-fraction caps — instead of by a subaccount boundary. The isolated-margin loss
    cap and the no-same-instrument-collision rule are UNCHANGED in the fallback; only the
    ring-fence MECHANISM differs (subaccount boundary vs CIATS ledger). The three-pool
    model is the PRIMARY; this is the documented fallback, nothing erased.

  EQUAL DETAIL — Long Perp and Short Perp pools documented identically

  The two perp pools are STRUCTURALLY identical: each is a linked derivatives subaccount
  with its own balance / margin / isolated-liquidation / API keys / CIATS instance /
  operator-funded wallet / halts, funded with affordable-to-lose capital, bound by the
  same no-same-instrument-collision rule. They DIFFER only in the §13.4 direction metrics
  (long = breakout / wide-stop / reversal-exit; short = mean-reversion / filtered /
  trailing-or-target), NOT in wallet, margin, isolation, or loss-cap mechanics — which
  are documented here to EQUAL DETAIL on both sides.

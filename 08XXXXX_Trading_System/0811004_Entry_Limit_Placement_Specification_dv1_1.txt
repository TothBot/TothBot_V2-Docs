============================================================
ENTRY LIMIT PLACEMENT SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document is the complete specification for entry limit
price placement in TothBot V2. It defines how the
entry_limit_price is computed from the 5-minute candle
close price, how it is quantized to Kraken's
price_increment for BOTH long and short entries, and the
rationale for these rules. Direction-symmetric semantics
were added in dv1_1 per AR-069 amended dv1_42 in 0500000
to support Short_Module operation alongside Long_Module
under the parallel-module framework (TB00000 v2_29 §9.3).

The entry_limit_price computation is one of the last steps
before module dispatch. It runs after Gate 8 Position
Sizer authorization and before add_order construction —
identically for Long_Module and Short_Module dispatch
paths.

This document is the authoritative parent for entry limit
placement in AA=10 coding specifications.

4. WHAT ENTRY LIMIT PLACEMENT DOES
============================================================

Input:  candle_close (Decimal) from the triggering 5-minute
        ohlc(5m) close event.
        price_increment (Decimal) for this symbol from the
        instrument channel snapshot (per-symbol, per-pair).
        side (enum: long | short) from the dispatching
        module — selects the quantization direction.
Output: entry_limit_price (Decimal) — the limit_price field
        value submitted in the add_order message.

Computation (direction-symmetric per AR-069 amended dv1_42):
  Long  entry: entry_limit_price = candle_close quantized
               DOWN to the nearest price_increment.
  Short entry: entry_limit_price = candle_close quantized
               UP   to the nearest price_increment.

The candle_close basis is identical for both directions
(AR-069 unchanged). Only the rounding direction is side-
selected. This is the only direction-dependent behavior
in the entry-limit-price computation.

============================================================
5. ENTRY LIMIT PRICE RULE (AR-069 — direction-symmetric)
============================================================

ELP-001  entry_limit_price basis: candle_close price from
         the triggering ohlc(5m) close event. Same basis
         for both long and short entries — direction
         affects only the quantization rounding direction
         per ELP-002 (long) and ELP-010 (short). Per
         AR-069 (dv1_15; amended dv1_42 — M-2 short-
         direction) verbatim in 0500000 dv1_43.

ELP-002  Long-side quantization direction: ROUND_DOWN to
         nearest price_increment. PRESERVED VERBATIM from
         dv1_0.
           entry_limit_price = Decimal(str(candle_close)
             ).quantize(price_increment, rounding=ROUND_DOWN)

ELP-003  price_increment source: instrument channel snapshot.
         Stored in per-symbol instrument cache by WS Manager.
         Retrieved at pipeline start (pre-computation cache
         read, I-2). Never re-fetched mid-pipeline. Universal
         to both directions.

ELP-004  price_increment is Kraken's tick size for the pair.
         Varies by pair (e.g., BTC/USD: 0.1, SOL/USD: 0.01).
         Referred to as tick_size in some Kraken documentation.
         In instrument channel: field name is price_decimal_places
         or price_increment depending on API version.
         TothBot V2 uses the value as derived from 0411001
         Kraken_WS_v2_Specification Section on instrument
         channel (GAP-C). Universal to both directions.

ELP-005  Long-side ROUND_DOWN rationale (PRESERVED from dv1_0):
         Rounding DOWN ensures the entry limit is at or
         below the candle close. This avoids submitting a
         limit price that is slightly above the current
         market (which could cause an immediate taker fill,
         defeating post_only protection).
         ROUND_DOWN is the conservative direction for a
         buy limit order — it is less likely to cross the
         spread than ROUND_UP. Per AR-047 (conservative:
         lower limit → more likely post_only BUY fill below
         ask) per AR-069 verbatim in 0500000 dv1_43.

ELP-006  Candle close rationale (AR-069 — applies to both
         directions):
         The SSS signal is evaluated at candle close. The
         candle close price is the most recent confirmed
         price at signal evaluation time. Entering at or
         beyond the candle close — DOWN for long buys to
         stay below ask, UP for short sells to stay above
         bid — is consistent with the momentum signal:
         entry is sought at the same price level that
         triggered the signal.
         Alternative approaches considered and rejected
         (universal to both directions):
           - best_ask / best_bid: would change continuously,
             creating race condition between signal and order.
           - mid price: split between bid and ask, not a
             clean price level relative to the candle.
           - candle open: stale — from 5 minutes ago.
           - last trade price: same as close in practice
             but semantically less precise.
         Candle close is the correct, deterministic basis
         for both long and short.

============================================================
6. QUANTIZATION PRECISION
============================================================

ELP-007  All computations use Python Decimal module.
         candle_close from ohlc event: Decimal(str(close)).
         price_increment from instrument cache: Decimal
         (already stored as Decimal in cache).
         No float arithmetic in price computation.
         Universal to both directions.

ELP-008  The quantized price MUST be validated as positive
         and > 0 before dispatch. A zero or negative
         entry_limit_price is a system error. Log and abort.
         Universal to both directions.

ELP-009  Example computation (long-side, PRESERVED from dv1_0):
           candle_close    = Decimal("67234.7")
           price_increment = Decimal("0.1")
           entry_limit_price = Decimal("67234.7")
             .quantize(Decimal("0.1"), rounding=ROUND_DOWN)
           entry_limit_price = Decimal("67234.7")

           candle_close    = Decimal("67234.73")
           entry_limit_price = Decimal("67234.7")
           (Rounds DOWN from 67234.73 to 67234.7)

ELP-010  Short-side quantization direction (NEW dv1_1):
         ROUND_UP to nearest price_increment.
           entry_limit_price = Decimal(str(candle_close)
             ).quantize(price_increment, rounding=ROUND_UP)
         Direction-symmetric to ELP-002 (long-side
         ROUND_DOWN). Per AR-069 amended dv1_42 verbatim
         in 0500000 dv1_43:
           "Short entry: entry_limit_price = entry_limit_
            price_raw.quantize(price_increment, ROUND_UP)
            per AR-047 direction-symmetric (conservative:
            higher limit → more likely post_only SELL fill
            above bid)."

ELP-011  Short-side ROUND_UP rationale (NEW dv1_1):
         Rounding UP ensures the entry limit is at or
         above the candle close. This avoids submitting a
         sell limit price that is slightly below the
         current market (which could cause an immediate
         taker fill, defeating post_only protection on
         the SELL leg).
         ROUND_UP is the conservative direction for a
         sell limit order — it is less likely to cross
         the spread than ROUND_DOWN. Direction-symmetric
         to ELP-005. Per AR-047 direction-symmetric per
         AR-069 verbatim in 0500000 dv1_43.

ELP-012  Example computation (short-side, NEW dv1_1):
           candle_close    = Decimal("67234.7")
           price_increment = Decimal("0.1")
           entry_limit_price = Decimal("67234.7")
             .quantize(Decimal("0.1"), rounding=ROUND_UP)
           entry_limit_price = Decimal("67234.7")

           candle_close    = Decimal("67234.73")
           entry_limit_price = Decimal("67234.8")
           (Rounds UP from 67234.73 to 67234.8)

7. INTERFACES
============================================================

7.1 From WS Manager (ohlc event)
  Receives: candle_close as float from ohlc(5m) close event.
  Converts: Decimal(str(candle_close)) immediately.
  Universal to both directions.

7.2 From Instrument Cache (WS Manager)
  Receives: price_increment (Decimal) for this symbol.
  Retrieved: from pre-computation cache read at pipeline
  start (I-2). Already a Decimal in cache.
  Universal to both directions.

7.3 From Dispatching Module (side selector)
  Receives: side (enum: long | short) from the dispatching
  module (Long_Module or Short_Module). Selects which
  quantization direction applies per ELP-002 (long
  ROUND_DOWN) vs ELP-010 (short ROUND_UP). Required for
  every entry-limit-price computation under the parallel-
  module framework (TB00000 v2_29 §9.3).

7.4 To Long Module (0811001)
  Provides: entry_limit_price (Decimal) computed with
  ROUND_DOWN per ELP-002 for add_order construction
  (limit_price field).
  Also used: by SC-GATE-5 in Selection Controller for
  position size viability check (qty * entry_limit_price
  >= cost_min).

7.5 To Short Module (0811005)
  Provides: entry_limit_price (Decimal) computed with
  ROUND_UP per ELP-010 for add_order construction
  (limit_price field).
  Also used: by SC-GATE-5 Short variant in Selection
  Controller for position size viability check
  (qty * entry_limit_price >= cost_min for short
  notional sized against margin per Short_Module
  SM-012).

  0811005 SM-011 tactical-bridge cross-reference: the
  SM-011 inline ROUND_UP formula in 0811005 dv1_0 was a
  tactical bridge so 0811005 dv1_0 could be coding-ready
  before 0811004 native direction-symmetric support
  existed. With 0811004 dv1_1 native ELP-010 support,
  0811005 SM-011 may be retired in a subsequent
  0811005 dv increment to defer the entry-limit-price
  formula to 0811004 native rules. The 0811005 SM-011
  retirement amendment is forward-tracked; it is NOT
  part of the dv1_1 amendment scope per RR-SCOPE-001
  surgical-scope discipline.

7.6 To Logger (0511006)
  Logs: ENTRY_PRICE_COMPUTED event with side field added
  in dv1_1.

============================================================
8. HARD RULES
============================================================

HR-ELP-001  entry_limit_price MUST be derived from
            candle_close (ohlc close price) only, for
            BOTH long and short entries. Never from
            best_ask, best_bid, mid, or any other price
            source. Direction-symmetric per AR-069
            amended dv1_42.

HR-ELP-002  Quantization direction MUST be side-selected
            per AR-069 amended dv1_42:
              side=long  → ROUND_DOWN per ELP-002
              side=short → ROUND_UP   per ELP-010
            Never ROUND_HALF_UP. Never the wrong-direction
            rounding for the dispatching side. Cross-
            direction rounding (long with ROUND_UP, short
            with ROUND_DOWN) is a defect that defeats
            post_only protection.

HR-ELP-003  price_increment MUST come from the instrument
            channel snapshot for this specific symbol.
            Never hardcoded per-pair. Never assumed.
            price_increment varies by pair. Universal to
            both directions.

HR-ELP-004  All price values MUST use Decimal arithmetic.
            Decimal(str(float_value)) on all WS message
            numeric inputs. No float in price computation.
            Universal to both directions.

HR-ELP-005  entry_limit_price MUST be validated > 0 before
            dispatch. Zero or negative = system error.
            Log and abort dispatch for this pair.
            Universal to both directions.

HR-ELP-006  side field MUST be present on every entry-
            limit-price computation request. A computation
            request without a valid side enum (long |
            short) is a defect — dispatching modules MUST
            pass side. Per parallel-module framework
            (TB00000 v2_29 §9.3). NEW dv1_1.

9. CIATS PARAMETERS
============================================================

  entry_limit_basis: candle_close
    This is an architectural decision, not a numeric
    parameter. CIATS does not own the price basis.
    Changing the entry limit basis is an architectural
    change requiring document revision, not a CIATS
    parameter update. Universal to both directions.

  quantization_direction: side-selected per HR-ELP-002
    Architectural, not CIATS-owned. Long → ROUND_DOWN.
    Short → ROUND_UP. The rounding direction is a
    direction-symmetry consequence of the entry-limit
    post_only protection contract per AR-069 + AR-047
    direction-symmetric. CIATS cannot change rounding
    direction.

  No numeric CIATS parameters in this specification.
  entry_limit_price is fully determined by candle_close,
  price_increment, and side — all externally sourced.

11. FIVE CODING-READINESS QUESTIONS
============================================================

(1) What does Entry Limit Placement DO?
    Computes entry_limit_price = candle_close quantized
    to price_increment, with rounding direction selected
    by the side enum: ROUND_DOWN for long, ROUND_UP for
    short. Returns a single Decimal value used as the
    limit_price in add_order. Direction-symmetric per
    AR-069 amended dv1_42.

(2) What are its interfaces?
    FROM: WS Manager (candle_close from ohlc event),
    instrument cache (price_increment), dispatching
    module (side enum: long | short).
    TO: Long Module (entry_limit_price ROUND_DOWN for
    add_order), Short Module (entry_limit_price ROUND_UP
    for add_order), Selection Controller Gate 5 (for
    viability check, both sides), Logger.

(3) What are its hard rules?
    candle_close as basis only (both directions).
    Quantization direction side-selected per HR-ELP-002.
    price_increment from instrument snapshot, not
    hardcoded. Decimal arithmetic throughout. Validate
    > 0 before use. side enum required on every
    computation request (HR-ELP-006 NEW dv1_1).

(4) What triggers it and what does it trigger?
    Triggered by Gate 8 authorization (every pipeline
    evaluation that passes Gates 1-8, in either
    Long_Module or Short_Module dispatch path).
    Triggers: Long_Module add_order construction (for
    long) OR Short_Module add_order construction (for
    short).

(5) What does it log?
    ENTRY_PRICE_COMPUTED (every successful computation,
    with side field).
    ENTRY_PRICE_INVALID (CRITICAL, if zero or negative,
    with side field).
    ENTRY_PRICE_SIDE_MISSING (CRITICAL, if side enum is
    absent — NEW dv1_1).

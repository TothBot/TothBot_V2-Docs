============================================================
SELECTION CONTROLLER SPECIFICATION
============================================================

============================================================
1. PURPOSE
============================================================

This document is the complete trading-module specification
for the Selection Controller — Gate 5 of the TothBot V2
8-gate trading pipeline. It defines the 6 quality gates
applied to every SSS PASS signal, the in-memory state
structures that persist across evaluations, all reject
codes, hard rules, interfaces, and logging.

The Selection Controller converts a raw SSS signal into
a vetted dispatch authorization by applying quality,
position, cooldown, size, and streak filters.

This document is the authoritative parent for the
Selection Controller portion of AA=10 coding specifications.

4. WHAT THE SELECTION CONTROLLER DOES
============================================================

Gate 5 receives a SSS PASS signal (all three SSS conditions
true for a given symbol on the current 5-minute candle)
and applies 6 quality gates in strict sequence.

Input:  SSS PASS signal for symbol. Current candle data
        (close, open, ATR(14)). Position Mirror state.
        Cooldown state. Consecutive loss state.
        Entry_qty_quantized and entry_limit_price
        (computed by Gate 8 Position Sizer).
Output: PASS — authorized for entry dispatch.
        FAIL — rejected with specific reject code. Logged.

On FAIL: skip this pair, continue pipeline for remaining
pairs in this candle evaluation. Never halt pipeline.

============================================================
5. SIX QUALITY GATES
============================================================

Gates applied in strict sequence. First FAIL exits
immediately — remaining gates are not evaluated.

------------------------------------------------------------
5.1 SC-GATE-1: SSS Signal Pass
------------------------------------------------------------

SC-001  Condition: SSS PASS (all three SSS conditions true).
        This gate is the precondition for Selection
        Controller activation. The SC never runs without
        a valid SSS PASS.

SC-002  Reject code: SSS_SIGNAL_FAIL
        Action: skip pair. Log reject code.
        Note: In practice, SSS PASS is the activation
        trigger — SC-GATE-1 is a formal gate to make
        the dependency explicit. SSS FAIL means SC is
        not called for this pair this evaluation.

------------------------------------------------------------
5.2 SC-GATE-2: Momentum Candle Body
------------------------------------------------------------

SC-003  Condition:
          abs(candle_close - candle_open) > ATR(14) * sc_body_threshold
        sc_body_threshold: 0.3 starting value. CIATS-owned.

SC-004  Rationale: Momentum candle must show directional
        commitment. A doji or near-doji at SSS PASS
        indicates indecision. A candle body < 0.3x ATR
        is not a momentum entry. Entry on a doji increases
        false positive rate and reduces R:R expectancy.
        FP/DP: ATR-relative body filter removes entry on
        consolidation candles where SSS conditions happen
        to align without price commitment.

SC-005  Reject code: WEAK_CANDLE_BODY
        Action: skip pair. Log reject code.

------------------------------------------------------------
5.3 SC-GATE-3: No Existing Position
------------------------------------------------------------

SC-006  Condition: symbol NOT in position_mirror.
        Checked via O(1) dict key lookup.

SC-007  Rationale: No pyramiding. One position per pair.
        An existing position means the pair already has
        TP and emergSL resting. A second entry would
        create a conflicting position with no clean exit
        path and double emergSL exposure per pair. Gate 3
        enforces the one-position-per-pair constraint.

SC-008  Reject code: POSITION_ALREADY_OPEN
        Action: skip pair. Log reject code.

------------------------------------------------------------
5.4 SC-GATE-4: Cooldown Window
------------------------------------------------------------

SC-009  Condition:
          symbol NOT in exit_cooldown_log
          OR (current_monotonic - exit_cooldown_log[symbol])
             >= sc_cooldown_seconds
        sc_cooldown_seconds: 300 seconds starting value.
        CIATS-owned.
        current_monotonic: time.monotonic() (monotonic clock,
        never jumps backward on system time changes).

SC-010  Rationale: A pair that just exited (MAE breach,
        time expiry, regime downgrade) should not be
        immediately re-entered. The underlying condition
        that triggered exit is likely still present.
        A 300-second cooldown (one candle width) prevents
        re-entry during the adverse conditions that
        triggered the exit. CIATS adjusts based on
        re-entry win rate data.

SC-011  Reject code: PAIR_IN_COOLDOWN
        Action: skip pair. Log reject code with
        elapsed_seconds and remaining_seconds.

------------------------------------------------------------
5.5 SC-GATE-5: Position Size Viability
------------------------------------------------------------

SC-012  Condition:
          entry_qty_quantized >= qty_min
          AND entry_qty_quantized * entry_limit_price >= cost_min
        entry_qty_quantized: ROUND_DOWN quantized qty
        from Gate 8 Position Sizer.
        qty_min and cost_min: from instrument channel
        snapshot for this symbol.

SC-013  Rationale: Pre-validates that the computed position
        size meets Kraken's minimum order requirements
        before dispatch. Kraken rejects add_order if qty
        < qty_min or notional < cost_min. SC-GATE-5 catches
        this before consuming a rate counter unit on a
        guaranteed-reject order. This is loss prevention
        by avoiding execution overhead on unviable entries.

SC-014  Reject code: POSITION_TOO_SMALL
        Action: skip pair. Log reject code with computed
        qty, required qty_min, and cost_min.

------------------------------------------------------------
5.6 SC-GATE-6: Consecutive Loss Limit
------------------------------------------------------------

SC-015  Condition:
          consecutive_loss_count[symbol] < sc_consecutive_limit
        sc_consecutive_limit: 3 losses starting value.
        CIATS-owned.
        consecutive_loss_count[symbol]: defaults to 0 for
        symbols not yet in dict.

SC-016  Rationale: Three consecutive losses on a single pair
        indicates the pair is not responding to SSS signals
        as expected. The pair may have changed behavior,
        liquidity structure, or news-driven volatility.
        Blocking new entries surfaces the problem to CIATS
        and to the operator rather than letting losses
        accumulate. CIATS may reset the count via PDCA
        update or after investigating the pair's behavior.

SC-017  Reject code: CONSECUTIVE_LOSSES_EXCEEDED
        Action: skip pair. Log reject code with
        consecutive_loss_count[symbol].

SC-018  consecutive_loss_count resets on TP_FILL (win).
        Does NOT reset on TIME_EXPIRY (neutral — no loss).
        Resets on CIATS instruction (PDCA update).

============================================================
6. STATE MANAGEMENT (AR-073)
============================================================

The Selection Controller maintains two in-memory state
dicts via WS Manager. Both persist across reconnect.
Neither is ever discarded on WS reconnect (AR-056).

------------------------------------------------------------
6.1 exit_cooldown_log
------------------------------------------------------------

SC-019  Type: dict[str, float]
        Key: symbol (Kraken pair name)
        Value: time.monotonic() of most recent position exit

SC-020  Update rule: On ANY position close (all exit reasons,
        all layers): exit_cooldown_log[symbol] = time.monotonic()

SC-021  SC-GATE-4 reads this dict. Key absence = no cooldown.
        Key present = check elapsed vs sc_cooldown_seconds.

SC-022  PRESERVED across WS reconnect. In-memory dict is
        NOT reset on reconnect. Cooldown state is live
        operational state — loss of cooldown state creates
        a window of forbidden re-entries. Preserving it
        is correct (AR-073).

------------------------------------------------------------
6.2 consecutive_loss_count
------------------------------------------------------------

SC-023  Type: dict[str, int]
        Key: symbol (Kraken pair name)
        Value: number of consecutive losing exits without
               a winning exit

SC-024  Update rule on position close:
          If exit_reason is a loss exit:
            (MAE_THRESHOLD_BREACH, TIME_EXPIRY,
            HTF_REGIME_REVERSAL, DAILY_REGIME_DOWNGRADE,
            SIGNAL_DECAY, MOMENTUM_LOSS):
              consecutive_loss_count[symbol] += 1
          If exit_reason is TP_FILL (win):
              consecutive_loss_count[symbol] = 0
          If exit_reason is TP_PARTIAL_FILL_REMAINDER:
              consecutive_loss_count[symbol] = 0
          CIATS reset: consecutive_loss_count[symbol] = 0
            (via PDCA Parameter Store update)

SC-025  PRESERVED across WS reconnect. Same rationale as
        exit_cooldown_log — live operational state that
        must not be lost on reconnect (AR-073).

SC-026  Default on first access: consecutive_loss_count
        .get(symbol, 0). No key error on new pairs.

============================================================
7. GATE FAILURE BEHAVIOR
============================================================

SC-027  Any gate failure = SKIP this pair for this
        pipeline evaluation.

SC-028  Gate failure NEVER halts the pipeline. Other pairs
        in the same evaluation continue normally.

SC-029  Gate failure NEVER triggers a system halt or alert.
        Gate failures are expected operational behavior.

SC-030  All gate failures are logged with reject code.
        CIATS EWMA Monitor tracks rejection_rate_by_regime
        (A-1 signal 1 in 0500000). Patterns in rejection
        codes inform CIATS parameter evolution.

============================================================
8. INTERFACES
============================================================

8.1 From Signal Engine (0711001)
  Receives: SSS PASS signal for symbol.
  Receives: candle_close and candle_open (current 5m candle).

8.2 From Pre-computation Cache (via WS Manager)
  Receives: ATR(14) for symbol (read at pipeline start, I-2).
  Receives: qty_min, cost_min for symbol (instrument cache).

8.3 From Position Mirror (0511005)
  Reads: symbol presence check (O(1) dict lookup) for SC-GATE-3.

8.4 From Gate 8 Position Sizer
  Receives: entry_qty_quantized and entry_limit_price
  (required for SC-GATE-5 size viability check).
  Note: Gate 8 runs before SC-GATE-5 is evaluated.

8.5 To Pipeline
  Returns: PASS (authorized for Long Module dispatch)
           or FAIL with reject code (skip this pair).

8.6 To WS Manager (state dicts)
  Reads and writes: exit_cooldown_log and
  consecutive_loss_count. WS Manager is the in-memory
  state host. SC is the reader/writer via WS Manager API.

8.7 To Logger (0511006)
  All reject codes with supporting data.

============================================================
9. HARD RULES
============================================================

HR-SC-001  Gates MUST be applied in strict sequence 1-6.
           First FAIL exits immediately. Remaining gates
           are not evaluated for this pair this evaluation.

HR-SC-002  Gate failure MUST NEVER halt the pipeline.
           Always SKIP pair and continue for other pairs.

HR-SC-003  exit_cooldown_log and consecutive_loss_count
           MUST be preserved across WS reconnect. Never
           discard these dicts on any reconnect event.

HR-SC-004  consecutive_loss_count MUST reset to 0 on
           TP_FILL and TP_PARTIAL_FILL_REMAINDER only.
           It MUST increment on all loss exit reasons.
           TIME_EXPIRY counts as a loss for this purpose.

HR-SC-005  SC-GATE-5 MUST use entry_qty_quantized (already
           ROUND_DOWN quantized by Gate 8). Never use
           raw computed qty for minimum size validation.

HR-SC-006  Cooldown MUST use time.monotonic() exclusively.
           Never time.time() for cooldown interval.
           Monotonic clock never jumps backward on system
           time corrections.

HR-SC-007  All numeric CIATS parameters (sc_body_threshold,
           sc_cooldown_seconds, sc_consecutive_limit) are
           read from the frozen Parameter Store snapshot
           taken at pipeline start (I-4). Never re-read
           mid-evaluation.

============================================================
10. CIATS PARAMETERS
============================================================

  sc_body_threshold:    0.3 (ATR multiple for candle body gate)
  sc_cooldown_seconds:  300 (seconds post-exit before re-entry)
  sc_consecutive_limit: 3 (consecutive losses before block)

  All CIATS-owned starting values. All validated at 200+
  closed trades. Per-regime analysis at 600+ trades.
  sc_consecutive_limit: Mann-Whitney p<0.01 required before
  change (per 0611004 — this is a loss-prevention parameter).

============================================================
11. WHAT IT LOGS
============================================================

  GATE5_PASS                — symbol, all 6 gates passed
  SSS_SIGNAL_FAIL           — symbol (not called directly)
  WEAK_CANDLE_BODY          — symbol, body_size, threshold,
                              ATR(14), regime
  POSITION_ALREADY_OPEN     — symbol
  PAIR_IN_COOLDOWN          — symbol, elapsed_seconds,
                              remaining_seconds
  POSITION_TOO_SMALL        — symbol, computed_qty, qty_min,
                              computed_cost, cost_min
  CONSECUTIVE_LOSSES_EXCEEDED — symbol, count, limit

12. FIVE CODING-READINESS QUESTIONS
============================================================

(1) What does the Selection Controller DO?
    Applies 6 quality gates to every SSS PASS signal.
    Returns PASS for dispatch or FAIL with reject code.
    Manages two in-memory state dicts (cooldown and
    consecutive loss). All fails logged, never halt.

(2) What are its interfaces?
    FROM: Signal Engine (SSS PASS + candle data), pre-
    computation cache (ATR, minimums), Position Mirror
    (Gate 3 check), Gate 8 (quantized qty for Gate 5).
    TO: pipeline (PASS/FAIL), WS Manager (state dicts),
    Logger.

(3) What are its hard rules?
    Gates in strict sequence. Fail = skip, never halt.
    State dicts preserved across reconnect. Cooldown uses
    monotonic clock. CIATS params from frozen snapshot.

(4) What triggers it and what does it trigger?
    Triggered by SSS PASS signal from Signal Engine on
    every 5-minute candle evaluation.
    Triggers: Long Module dispatch on PASS. Logger on
    every PASS and FAIL.

(5) What does it log?
    GATE5_PASS, and one of six specific reject codes
    (WEAK_CANDLE_BODY, POSITION_ALREADY_OPEN,
    PAIR_IN_COOLDOWN, POSITION_TOO_SMALL,
    CONSECUTIVE_LOSSES_EXCEEDED) on FAIL.
